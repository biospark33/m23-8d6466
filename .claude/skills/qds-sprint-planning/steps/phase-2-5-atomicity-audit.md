# Phase 2.5 — Story Atomicity Audit

**Insertion point:** Runs AFTER Phase 2 (parallel story writing) and BEFORE
Phase 3 (wrap-up).

**Source:** [Epic RBAC-1 Skill Audit §4.1](../../../../_bmad-output/sprint-artifacts/sprint-62/epic-rbac-1-retro-skill-audit-2026-05-13.md)<br>
**Issue:** [#1435](https://github.com/biospark33/RFP-Agents/issues/1435)

**Why this phase exists.** Epic RBAC-1 stories averaged 660 lines/story
(range 474-804) with 26-40 DOD items each. RBAC-1.5 (13 SP, 32 DOD items,
804 lines) self-acknowledged it was "two implementation sessions, atomic
PR" — the skill recognised the over-sizing but had no enforcement step
to split. Result: PR #1394 took 15+ fix rounds versus ~5 for a
properly-atomic story.

---

## Inputs

- Every story file just generated by Phase 2:
  `_bmad-output/sprint-artifacts/sprint-{N}/stories/*.md`
- Sprint identifier `sprint-{N}` (resolved in Phase 0).
- Current date (UTC, ISO-8601).

## Outputs

- `_bmad-output/sprint-artifacts/sprint-{N}/atomicity-audit-{YYYY-MM-DD}.md`
  — one row per story with pass/fail per check, severity, and remediation
  suggestion.
- HALT before Phase 3 if any BLOCK-severity violation is unresolved.

---

## Validation checks (per story file)

For each `*.md` story file produced by Phase 2, apply ALL checks below.
Severity column: **BLOCK** halts Phase 3; **WARN** is advisory.

### 1. Normative content size

- **Limit:** ≤ 200 normative lines (excluding appendices and the Dev
  Agent Record block).
- **On violation (BLOCK above 250, WARN at 201-250):** surface the line
  count and recommend running `bmad-distillator`. ≤ 200 normative lines
  passes silently. Match the hard size cap that `bmad-create-story`
  (#1433) enforces; if both skills disagree the more restrictive limit
  wins.

### 2. Total file size

- **Limit:** ≤ 400 total lines.
- **On violation (WARN):** recommend extracting rationale / worked
  examples / cross-references to `<sprint>/CONTEXT.md` and replacing
  with a link from the story.

### 3. SP budget

- **Limit:** ≤ 8 SP per story.
- **On violation (BLOCK):** surface a "consider splitting into N+M
  sub-stories" recommendation with a suggested cut (e.g., Core / Tools
  pattern from SPL-007).

### 4. DOD checkbox count

- **Limit:** ≤ 10 high-signal items.
- **On violation (WARN):** flag the list of low-signal items.
  Specifically recommend removing project-wide CI invariants like
  `ruff clean`, `tests pass`, `mypy clean`, `lint clean`, `format check`
  — those are CI guarantees, not story-specific DOD.

### 5. Title `AND` connectors

- **Limit:** ≤ 1 `and` / `&` / `+` conjunction in the title (case-
  insensitive). Example: `subtree-and-delegation-primitives` suggests
  two concerns and likely needs a split.
- **On violation (WARN):** flag for split review.

### 6. Blocker markers

- **Limit:** 0 instances of `⛔`, `pending sign-off`, or `TBD on` in the
  story body.
- **On violation (BLOCK):** block ready-for-dev status. Require ADR
  resolution or explicit dependency-story link before the story moves
  past Phase 2.5.

### 7. Files-to-Modify section

- **Required:** `## Files to Modify` section MUST exist and list
  ≤ 10 unique file paths.
- **On violation:**
  - **BLOCK** if the section is absent.
  - **WARN** if the section lists >10 files (consider splitting).

### 8. Security-relevant detection

Trigger on ANY of these keyword classes in the story body, AC,
acceptance test text, or Files-to-Modify paths (case-insensitive):

- RLS / row-level security / policy
- migration / DDL / schema change / alembic
- auth / authentication / authorization / RBAC / capability / scope / permission
- encryption / secrets / KMS / vault / credential
- PII / personal data / GDPR / HIPAA
- payment / billing / financial / PCI
- tenant / multi-tenancy / cross-tenant
- upload / file handling / deserialization / parse

**Required when triggered:** `## Security Invariants` section MUST be
present with concrete, non-empty invariants. **`N/A` is NOT a valid
answer when keywords are triggered** — the trigger means at least one
security-relevant surface is touched, so the gate requires substantive
content (named invariants, threat-model notes, or explicit RLS / authz
clauses). Allowing `N/A — rationale` here would let any author opt out
of the BLOCK at will and defeat the gate (issue #1435).

Keep this keyword list in sync with `bmad-create-story` template
(#1433) and `bmad-check-implementation-readiness` (#1431). Any drift
between the three should be treated as a bug.

- **On violation (BLOCK):** flag the matched keywords and require the
  story author to add a substantive `## Security Invariants` section
  before Phase 3. A section whose body is `N/A`, empty, or pure
  rationale-without-invariants does NOT clear the BLOCK.

## Report format

Save the report at
`_bmad-output/sprint-artifacts/sprint-{N}/atomicity-audit-{YYYY-MM-DD}.md`
with this structure:

```markdown
# Atomicity Audit — sprint-{N} — {YYYY-MM-DD}

**Auditor:** qds-sprint-planning Phase 2.5
**Total stories audited:** N
**Pass:** P / **Warn:** W / **Block:** B

## Story-by-story findings

### {story-id} — {story-title}

| Check | Severity | Result | Notes |
|-------|----------|--------|-------|
| normative size (≤200) | BLOCK if >250 | {pass/warn/block} | {line count} |
| total size (≤400) | WARN | {pass/warn} | {line count} |
| SP budget (≤8) | BLOCK | {pass/block} | {N SP} |
| DOD count (≤10) | WARN | {pass/warn} | {N items} |
| title AND connectors | WARN | {pass/warn} | {N conjunctions} |
| blocker markers (=0) | BLOCK | {pass/block} | {matched strings} |
| Files-to-Modify section | BLOCK if absent | {pass/warn/block} | {N files} |
| Security Invariants | BLOCK if triggered+absent | {pass/block} | {matched keywords} |

## Summary

- BLOCK-severity violations: {list with story IDs}
- Recommendations: {distillator runs, splits, CONTEXT.md extracts}

## Override log (operator)

{populated only if operator overrode a BLOCK with rationale}
```

---

## HALT logic

After running all checks across all stories:

- If `BLOCK` count > 0 **and** no operator override is recorded in the
  report's "Override log" section → HALT the workflow. Do NOT enter
  Phase 3. Surface the report path to the user and require explicit
  override (with rationale) or remediation before resuming.
- If `WARN` count > 0 only → proceed to Phase 3 but include the audit
  report path in the Phase 3 wrap-up output for review.
- If all checks pass → proceed to Phase 3 silently (the report is still
  saved for traceability).

## Pseudocode

```python
def phase_2_5_atomicity_audit(sprint_id: str, story_files: list[Path]) -> bool:
    """Returns True iff Phase 3 may proceed (no unresolved BLOCKs)."""
    today = datetime.now(timezone.utc).strftime("%Y-%m-%d")
    report_path = (
        Path("_bmad-output/sprint-artifacts")
        / sprint_id
        / f"atomicity-audit-{today}.md"
    )
    findings = []
    for story in story_files:
        findings.append(audit_story(story))
    write_report(report_path, findings)
    blocks = [f for f in findings if f.severity == "BLOCK"]
    if blocks and not has_operator_override(report_path):
        return False  # HALT
    return True
```
