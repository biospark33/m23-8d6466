## User Story

As the factory operator,
I want a weekly schedule to wake the Maintenance manager bot, which assembles dep-bump/refactor briefs from deterministic hotspot signals and runs them through the fleet to an approvable pause,
so that maintenance work is continuously proposed and executed exactly as far as the same human approve gate every other run faces — and never one step further.

## Overview

The sweep is a deterministic pipeline with an E21 hat on: the platform's persisted scheduler wakes the Maintenance manager bot weekly (the bot is the **trigger and report carrier** — never the executor: B3 deny-lists `cli.exec`, so a Home bot cannot run factory scripts; the A1 host-composed precedent applies; the E21 schedule/Z2 wake drives ONLY the bot's trigger/report turn — Z2's observe allowlist stays `{status,result}`, read-only-closed, and no protocol step executes factory scripts); the sweep pass's own weekly firing is a documented **`deploy/vps/crontab.factory` entry — an A3-owned line in A6's file** (A1's documented-crontab-line precedent): a HOST-side **exiting pass** — `scripts/maintenance-sweep.ts`, run by the deploy user's host runner on the box via that entry — that (1) reads hotspots from A6's GitNexus graph (staleness-aware) and walks the audit chain over the recent window, (2) assembles at most `MAX_BRIEFS_PER_SWEEP` dep-bump/refactor briefs, (3) dispatches each brief as a fleet run (`--driver exedev`), and (4) reports, with the report leg delivered back through the bot's turn via a **durable handoff** — the pass and the wake fire independently (host cron vs the E21 schedule), so delivery cannot ride the pass's own process: the pass persists a delivery-targeted report record before exit (Technical Notes), and the wake delivers whichever record matches its correlation key, whenever the bot's turn actually happens. Every code-affecting run walks DF3.7's chain and parks at `awaiting-approval`. The 24/7 residency lives in the E21 bot; the factory side ships only bounded, exiting invocations.

**What this does NOT deliver.** No merge, no auto-approval, no second approval path (AC1's whole point). No Jev — brief selection and ordering are deterministic (A3's charter deps exclude J4; L9 triage as a brief-ranker is a v7 seam, not this story's). No denser cadence, no on-host daemon, no GitNexus refresh (A6's), no QA hunter-pack (A2's).

## E2E Slice

**Demonstrable behavior:** Given the persisted weekly schedule on the factory Home and the sweep's `deploy/vps/crontab.factory` entry, When the scheduler tick fires the bot wake (durable, recorded `initiatorPrincipal` = operator, E21 ADR run-2 D1 (DD-28.15)) and the crontab entry fires the pass, Then the wake reaches the Maintenance manager bot (trigger + report carrier — a Home bot cannot exec factory scripts, B3) and the authorized HOST-side runner (the deploy user on the box, via A3's crontab entry — the same runner A1's documented crontab line uses) executes `bun scripts/maintenance-sweep.ts`, which emits one `{ event: "sweep-plan", hotspots, briefs, graph_age_ms, graph_stale }` line, assembles ≤ `MAX_BRIEFS_PER_SWEEP` briefs, and per brief `fleet dispatch --driver exedev` reaches DF3.7's chain — ending with `extensions.approval.state = "awaiting-approval"`, `closedAt` set, bundle present, zero PRs merged, one `{ event: "sweep-complete", briefs_planned, briefs_dispatched, briefs_skipped, graph_stale, chain_refused }` line, exit 0.

## Acceptance Criteria

1. **(make-or-break — the sweep stops at the gate, and the gate is the one gate)** Given a sweep-produced run, When it settles, Then it reaches `awaiting-approval` through **DF3.7's `observeAndDriveChain`** (gate pre-registered before teardown closes the record, #383) and this story adds no second approval path: no approver-file write, no token handling, no auto-yes, no bypass verb. The unattended round's terminal state is **parked**, provably: `fleet status` shows `awaiting-approval` and `git log` shows zero merge commits from the sweep. *Negative controls, all MUST fail: a sweep that merges, opens-and-merges, or auto-approves its own PR — ADR-1 §3 says the gate stays scrypt-gated, allowlisted, token-on-stdin, human-only, and ADR-2 (PROPOSED, G1) is consumed by nothing here; an implementation that ships a scripted approver token or an unlabeled scripted approver — scripted approvers exist only labeled, SC2.7 precedent; and one that inlines its own harvest→teardown→reverify beside the chain — DF3.8's fence discipline applies, this story is a caller, never a second chain.*
2. **The weekly bot wake is durable, and durability comes from the persisted store; the sweep pass's own firing is the documented crontab entry.** Given a scheduler restart between schedule creation and fire, When the next tick runs, Then the bot wake fires from the persisted schedule row (`fork:src/lib/server/schedules/schedule-repository.ts` `loadSchedules`/`upsertSchedule` — fork-side, per Z2's substrate facts) via Z2's schedule→protocol path, driving the bot's trigger/report turn ONLY (the bot never executes the sweep — B3); the sweep pass's weekly firing rides the documented `deploy/vps/crontab.factory` entry (an A3-owned line in A6's file) — host cron is the pass's transport, the persisted schedule is the bot wake's; the persisted watch-job store (`fork:src/lib/server/runtime/watch-job-repository.ts`) is the sibling durable mechanism (post-merge triggers), not this wake's — and the turn carries a legitimate recorded `initiatorPrincipal` (the schedule owner = operator; INV-8 + E21 ADR run-2 D1 (DD-28.15) — a turn with `initiator_missing`/`initiator_mismatch`/`no_owner` is refused by S02b's machinery, never satisfied by a fallback). *Negative controls, all MUST fail: a wake delivered only via `enqueueSystemEvent` — an in-memory `hmrSingleton` Map capped at 20/session — evaporates on session restart and passes only the happy-path test; a wake whose turn forges or defaults an initiator principal; and a sweep pass with no owned transport — an implementation that expects the E21 wake or a Z2 protocol step to execute the script (Z2's observe allowlist is `{status,result}`; this story adds no 17th verb) MUST fail this one.*
3. **Hotspots are deterministic, staleness-aware, and never silently degraded.** <br />**(a)** (DD-28.21 — partial-consumer reading pending operator sign-off) The graph leg reads A6's freshness signal: last-completed-analyze age ≤ 8h → graph hotspots join the plan with `graph_age_ms` recorded. Age > 8h → the graph leg is **refused, counted `graph-stale`**, the plan proceeds on the audit chain alone, and the A6 alarm is named in the output — never a silent stale-graph traversal (NFR-OBS-5: "0 agent runs against a graph whose last completed analyze is >8h old"). <br />**(b)** While a GitNexus refresh is mid-run for the repo, the sweep does not read the graph (FR-MEM-6's refresh-vs-consumer clause), and the mechanism is A6's own lock, not a second one: the sweep takes a **non-blocking SHARED (`flock -s -n`) acquisition on the graph directory — the same flock A6's wrapper holds exclusive** — and holds it through BOTH the freshness check and the graph read; a failed acquisition (the refresh's exclusive lock is held) is the counted `refresh-in-progress` skip, retried next sweep. The lock target is A6's own: `flock` on `<graph-home>/.refresh.lock`, resolved through the same `QDS_GITNEXUS_HOME`-aware path the refresh uses. No marker file, no second lock vocabulary — one flock, two modes, is the whole contention contract. <br />**(c)** Audit-chain hotspots come from `walkAuditChain` + `chainVerdict` over the recent window (broken hops from `walkAuditChain`/`chainVerdict`; exit-6 outcomes from run records / `dispatch-log.jsonl`; fixloop escalations from record extensions) — read-only; `src/audit/link-store.ts` byte-identical. *Negative controls, all MUST fail: an implementation that consumes the graph without checking staleness, or folds `graph-stale` into a benign zero-hotspot outcome; one that reads a mid-refresh graph; and one that writes any audit hop.*
4. **The pass is bounded and exiting, and per-brief refusals never fail the pass.** ≤ `MAX_BRIEFS_PER_SWEEP` briefs per sweep; each dispatch honors existing admission (exit 5 fleet-busy/no-headroom, exit 3 setup-gate) as a **counted `briefs_skipped`/`chain_refused` outcome inside a pass that exits 0**; only a failure of the pass itself exits non-zero; no PID file, no loop flag, no resident factory-side process (INV-IBOX-16 doctrine — the bot is the only resident, and it is E21's). An empty sweep (zero hotspots) exits 0 with `briefs_planned: 0`. *Negative controls, all MUST fail: an implementation that lets one busy fleet abort the sweep, or exits non-zero on an empty sweep (a weekly cron that mails on every quiet tick is a cron the operator disables); and one that ships any always-on host supervision.*
5. **Bot spend and fleet spend are joinable per DD-20.** The sweep records, per brief, `workKey` (`w:` namespace), `runId`, and `botId`, so the factory cost-ledger (fleet runs) joins the zeropoint LLM-gateway ledger (bot turns); the join-key assertions live in `tests/maintenance/sweep-plan.test.ts`. Fleet spend stays under the existing per-run caps (DF2.3 ordering — consumed, not re-implemented). *Negative control: an implementation that mints a second spend ledger or drops the join keys — A5 consumes this join, and a row that cannot join is a row that lies.*

## Technical Notes

- **Deviation 1 (binding — the sweep-transport disposition).** ADR-1 §1's macro-process shape puts the protocol in the fork (`external_job` steps); A3 hosts the trigger factory-side instead — the sweep pass's weekly firing is the documented `deploy/vps/crontab.factory` entry and the bot wake rides E21's persisted schedule (Z2's schedule→protocol path drives ONLY the bot's trigger/report turn — its observe allowlist stays `{status,result}`, read-only-closed). Consequential work remains direct fleet runs through ADR-1 §3's CLI door (the 16-verb registry; no 17th verb). Dispositioned in the register as the **DD-28.26 sweep-transport disposition** — the DD-28.26 §8a sub-item (12), written by the register-owning agent; cited here, not authored here.
- **Deviation 2 (binding — the #380 disposition, mirroring A2's Deviation 1).** ADR-1's accepted gap: headless `workId` briefs do not book spend macro-side. A3's `w:`-keyed headless briefs are exactly that gap population, and **A3 does not close the gap and does not rely on it being closed:** brief spend is booked factory-side per runId (the cost-ledger + `run-cost` hop machinery every fleet run already has); the `w:` workKey rides the brief and the run record so DD-20's join (`workKey + runId + botId`) needs no schema change later. Macro-side per-workKey aggregation is DD-20/A5's surface.
- **The report handoff is durable, not in-band (the pass and the wake are independent processes).** The pass composes the report and persists ONE record before exit: `{sweepId, window, botTarget, report: {sweep-complete counters, per-brief lines}, deliveryState: "pending"}` at `.sandbox/maintenance/sweep-reports/<sweepId>.json` (the `.sandbox/` structured-store home, `dispatch-log.jsonl` precedent). The three load-bearing fields: **bot delivery target** = A1's config of record (factory Home + the Maintenance manager's `bot-` id, read from the manager config — never a bot name re-derived at pass time); **report payload** = the `sweep-complete` counters plus every brief's outcome line (the pass's own event vocabulary, digest-stable — no second one); **correlation key** = `sweepId`, the scheduled fire's window start, written by the pass and matched by the wake leg. Delivery rides the same counterpart fork seam as A1's digest (A1's stated-seam posture): the wake's fork-side leg reads the PENDING record whose `sweepId` matches its fire, renders it into the bot's report turn, then flips `deliveryState: "delivered"`. The pass NEVER waits on the bot (it exits 0 per AC4 regardless of delivery state — the report persist is the pass's last step) and the bot never polls factory scripts (B3). A record still `pending` past the NEXT scheduled wake is operator-visible residue — surfaced as a digest escalation mark on A1's surface — never silence. A report-persist failure fails the pass's report leg (recorded, non-silent) without unwinding the already-dispatched briefs.
- **Jev §8 guardrails verbatim (binding):** "`TYPESAFE_API_KEY` never hardcoded, never logged, never enters a box… No diff hunks or third-party bot prose shipped to the API in stage 1… Never edit: `AUDIT_HOPS`, `gate-runner.ts` verdict logic, `classifyRunExit`, `classifyDiffScope`, provider layer… No real API spend without explicit steve go in chat; mock mode is the default everywhere… Corpus records containing finding text stay in-repo under `_bmad-output/`." This story ships no Jev call at all — the binding is inherited via the fleet paths it reuses.
- **Guards/limits (named, not implied):** `MAX_BRIEFS_PER_SWEEP = 5` — derived from operator approval burden (five parked PRs/week is reviewable; fifty is a rubber stamp) and box headroom (one-box live tier); `GRAPH_STALENESS_BUDGET_MS = 8h` — NFR-OBS-5's threshold verbatim, not re-tuned; the sweep window is the trailing 7 days of chain activity (weekly cadence, no overlap with the previous sweep's window claim made or needed).
- **Region ownership on shared files:** `src/fleet/run-completion.ts`, `src/fleet/observe.ts`, `src/audit/**`, `src/fleet/verbs.ts`, `src/providers/**` are all **not modified**. The 16-verb registry is consumed as-is (`dispatch --driver exedev`; `fanout` is the wrong verb — it races candidates for one slot, and maintenance briefs are independent work items). No verb is added: a sweep is a script over existing verbs, not a seventeenth verb (skill-contract surface untouched). No image pin is owed: every touched path is host-side and outside the box COPY set (`oci/exedev/Dockerfile` copies `scripts/pipeline-run.ts`, `scripts/lib/`, `src/fleet/`, `src/lib/`, `src/phase-engine/`, `src/swarmclaw/` — nothing this story adds).
- **Ordering against A6:** the sweep reads the freshness signal before the graph leg and never triggers a refresh itself; refresh-triggering is A6's cron, contention handled by AC3(b).
- **Considered and rejected: letting the manager bot pick briefs itself.** The bot is an LLM; charter §6 forbids a bot gating code entry, and the standing rule demands a deterministic signal before any LLM investigates. The host-side pass orchestrates and the bot triggers and reports; the hotspot math is code. Revisit never — this is the story's identity, not a tuning choice.
