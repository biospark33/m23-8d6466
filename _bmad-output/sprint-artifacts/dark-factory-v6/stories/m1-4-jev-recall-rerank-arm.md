## User Story

As the operator taking the DD-22 checkpoint decision with the repeat recall measurement in hand, I want the same probe runs scored by Jev as a rerank arm — recorded, never applied — so that the checkpoint can see whether reranking the retrieved candidates WOULD have moved hit-rate@5, as a measurement, before anyone considers arming it.

## Overview

Two host-side scripts over M1.3's artifacts plus the merged judgment core: (1) `jev-arm-harvest.ts` — recalls each probe through M1.3's injectable recall surface, then asks Jev ONE relevance-score question per (probe, retrieved candidate) pair — the rerank pattern — recording one evidence row per pair alongside the deterministic recall order; (2) `jev-arm-report.ts` — a pure derivation from committed evidence: hit-rate@5 without rerank (recall order) vs with rerank (jevScore descending, ties break on recall order), rendered side by side. Every ask runs through `JudgmentClient.judge()` via the `src/judgment` barrel — mock default (`TYPESAFE_MOCK=1`, INV-J5), egress class `finding-text` (inside the code-pinned `ac-prose` stage-1 max), stage ceiling default (`DEFAULT_STAGE_CEILING_INPUT_TOKENS = 1_000_000`). **The arm never gates recall and never alters the brief shipped to any box while recording** — it receives recall results and writes only evidence; J2's arming gate (DD-21) is the only path by which a rerank ever reaches a shipped brief.

**What this does NOT deliver:** no brief-content change while recording (the arm cannot feed back — AC1 is make-or-break on this); no new gate (no threshold executes anything; the DD-22 bar is untouched); no in-box call (LOCKED #1 — nothing enters the box image or COPY set); no DD-22 swap machinery (M1.3 AC4's negative control stands — the Graphiti decision is the operator's at the dated checkpoint); no live spend without J1's double gate (`TYPESAFE_API_KEY` + `QDS_LIVE_PROBE_CONFIRMED=1`) PLUS explicit operator GO (INV-J5); no severity calibration (scores never become severity).

## Acceptance Criteria

1. **(make-or-break) Recording-only posture — the arm cannot reach a shipped brief.** Given the probe set and a recall run, When the harvest scores candidates, Then the brief shipped to any box and the recall results recorded by M1.3's runner are byte-identical with and without the arm: the harvest consumes recall results through the same injectable surface M1.3 already exposes, scores them, and writes only `_bmad-output/evidence/memory/` artifacts + corpus records + the seam's own provenance side-channel; no reranked recall query is ever issued to Hindsight, no `kg_context` brief is re-composed, no code path reads a `jevScore` for anything but reporting. *Negative controls: any implementation where a jevScore reorders a shipped brief or feeds a recall call (a second, reranked Hindsight query) MUST fail this AC; any write by the harvest into a `.sandbox` store or a M1.3-owned file MUST fail this AC.*
2. **One seam ask per (probe, candidate) pair — and the seam owns the policy.** Each pair produces exactly ONE `judge()` call through the `src/judgment` barrel with ONE `score` question; the envelope is strict-parsed by the seam or nothing is recorded (a failed/refused ask records an errored-pair count, never a fabricated score); evidence rows are unique on `(probeId, documentId)` and carry the seam-minted `requestId` as the correlation pointer into the provenance side-channel. *Negative controls: an ask bypassing `JudgmentClient.judge()` — a direct adapter/transport import or a hand-built request — MUST fail; a duplicate row for the same pair within one harvest MUST fail; a harvested score recorded from an ask the seam refused (no envelope) MUST fail.*
3. **Inherited policy, asserted behaviorally: egress, ceiling, mode.** The ask's `egressClass` is `finding-text` (closed list INV-J2; inside the code-pinned `ac-prose` stage-1 max) carrying only probe queries + candidate documents from `qds-` bank content; the stage ceiling is the default (`DEFAULT_STAGE_CEILING_INPUT_TOKENS`); `TYPESAFE_MOCK=1` is the default mode — the offline harvest runs keyless and never touches the network. *Negative controls: a harvest firing a live ask without `TYPESAFE_API_KEY` AND `QDS_LIVE_PROBE_CONFIRMED=1` MUST fail (INV-J5, before any request exists); an ask above the pinned stage-1 max class MUST be refused by the seam's choke; a second model literal anywhere in the arm's code MUST fail the contract grep (`TYPESAFE_MODEL` stays THE alarm); ask content containing anything outside `qds-` bank content — box-internal paths, credentials — MUST fail.*
4. **The arm report is re-derivable and separable.** `jev-arm-report.ts` computes reranked-vs-baseline hit-rate@5 ONLY from committed evidence JSONs — reranked order = jevScore descending, ties breaking on recall order; a rerank gain is rendered as the measured delta beside the baseline (JEV-4 honesty pattern: conditional wording, no causal claim, no verdict against the DD-22 bar). The `.md` renders purely from the report JSON. *Negative controls: a report path that re-judges or touches the network MUST fail; any metric computed inside the md renderer (making the JSON incomplete without it) MUST fail this AC; a report asserting "reranking improves recall" as fact (rather than the recorded conditional) MUST fail.*
5. **Digest-stable evidence rows; re-harvest is idempotent, never destructive.** Evidence rows exclude the envelope's volatile fields (`latency_ms`, `created_at`, `usage`) — those live in the seam's digest-stable provenance side-channel (INV-J3 pattern, untouched by this story); under the mock surface a re-harvest over the same probe set reproduces byte-identical aggregate rows (determinism); runs write timestamped files (M1.3's convention) and never overwrite or mutate an existing evidence file. *Negative controls: an evidence row carrying `latency_ms`, `created_at`, or `usage` MUST fail; a re-harvest that mutates a prior evidence file MUST fail; a non-deterministic mock-surface re-harvest (diverging aggregates) MUST fail.*

## Technical Notes

- **Why an arm and not a threshold:** the baseline missed the bar on hit-rate alone (0.565); the open question at the checkpoint is whether the MISS is the ranker's (right documents retrieved, wrong order — rerank fixes it) or the retriever's (right documents never retrieved — rerank cannot). The arm separates the two with the SAME probes and the SAME recall results: if reranked hit-rate@5 ≫ baseline, the deficit lives in ordering and J2's arming conversation has a measured floor; if not, the deficit is upstream of any reranker. Either way the DD-22 conversation gets a number it currently lacks — and the arm acquires it without touching the deterministic series it rides.
- **The ask shape is the rerank pattern, minimal:** state = `{query: <probe query>, candidate: <candidate document content>}`, one `score` question; criteria are relevance-to-query statements (writer-proposed, amendable at review like M1.3's DD-22 working bar) — never severity, never tier, never action guidance. Candidate content is the factory's own retained copy (the mint record / local corpus — the host retained every document it can be asked to score; no upstream fetch). Candidates scored = the retrieved top-k only (k = 5, the client's default limit — `MAX_ARM_CANDIDATES_PER_PROBE = 5`, exported, = k), so the 23-probe set is ≤ 115 asks per harvest.
- **Guards/limits (all named, all inherited or trivial):** `MAX_ARM_CANDIDATES_PER_PROBE = 5` (new, = k); `MIN_PROBE_SET_SIZE` and `MAX_PROBE_QUERY_CHARS` reused from `scripts/memory/probe-schema.ts` — nothing re-minted; concurrent harvests serialize via `acquireRunLock` on the arm evidence dir (`corpus-writer` precedent, lock id `jev-arm-writer`); probe selection and label integrity are M1.3's gate, invoked unmodified — the harvest refuses where probe-recall refuses, before any ask.
- **Ordering against M1.3:** strictly downstream and read-only — the harvest calls `runProbeRecall` (or consumes an injected recall surface in tests), it does not import into, fork, or modify any M1.3 file; if the arm's evidence contradicts the baseline hit-rate recomputed from the same rows, that is a bug to fix in the ARM (the baseline is deterministic and stays the deterministic series).
- **Considered and rejected: scoring inside `probe-recall.ts`.** It would couple M1.3's deterministic instrument to a live LLM leg — a mock-tier run would grow an API-shaped dependency and M1.3's evidence would change shape. The arm stays a separate consumer over the same injectable surface (fixes one-sided), the same seam discipline M1.3 itself applied to M1.2.
- **Considered and rejected: batching pairs into one ask per probe.** One ask per (probe, candidate) keeps per-pair provenance (requestId → envelope → corpus record) 1:1 and keeps every ask inside the stage ceiling trivially; batching would couple pair scores to a single refusal and break the per-pair corpus-record contract.
