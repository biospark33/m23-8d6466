## User Story

As the factory operator, I want the factory KG on a dedicated, digest-pinned Hindsight 0.10.0 container with its `qds-` banks provisioned and the full round trip verified on the pinned version, so that the verified 0.8.6 no-auth danger is retired — or honestly recorded — by live evidence on this instance, M1.2 and the M2 gateway have a real substrate, and P0.9 closes with evidence rather than waiver.

## Overview

The factory KG becomes a first-class substrate: Z4's compose fires the dedicated instance; this story proves the pin, provisions the `qds-` bank family, runs `verifyRoundTrip` live against 0.10.0, executes the retired-check on the no-auth danger, and lands the five re-homed P0.9 evidence legs (plus the P0.5 legs that ride the same operator-gated window). The story owns **no gateway**: D-2's "only front door = the M2 memory gateway" is the standing target, and until M2.1/M2.2 land, the only clients are host-side processes on the box over loopback — that interim containment is topology (loopback bind + firewall), stated here rather than hidden.

**What this does not deliver, stated before an AC implies otherwise.** No authz gateway (M2.1), no dispatch-time recall or harvest retain (M1.2), no in-box `kg_recall` (M2.2), no manager banks beyond the provisioner's existing `-dev-meta` (M3.1), and no factory exedev **image** re-pin — the hindsight pin and the `DEFAULT_IMAGE_REF` image pin are two different pins owned by two different rituals; this story owns only the former. Nothing here makes 8888/18889 reachable from outside the box, ever.

## Acceptance Criteria

1. **(make-or-break — dedicated, pinned, proven on the running container)** Given Z4's fired compose, When the stack is up, Then the hindsight service runs exactly the pin-file digest (`0.10.0@sha256:3edcb616…`), identity is verified from the container itself (version/health probe recorded in the hindsight-live leg JSON), and the factory resolves exactly one `HINDSIGHT_BASE_URL` pointing at the dedicated instance — Z4's host-side value `http://127.0.0.1:18890` (the compose split: containers address `hindsight-qds:8888` via `factory.env`, host legs read this env entry from `hindsight-qds.env`, G3; port 18889 is the platform tenant stack's map on a both-stacks box and is never resolved by a factory leg). **Shape check first:** before any downstream leg consumes the instance, the hindsight-live leg ALSO runs ONE retain+recall response-shape check against a disposable probe bank (created and finally-`deleteBank`'d inside the leg — never a roster bank), with the live retain/recall response shapes recorded in the leg JSON; those recorded shapes drive the response-schema conformance amendment (Technical Notes). Every leg driver reads the env by name — no host:port literal in driver code. *Negative control: an implementation that "re-pins" by editing a version string while the deployed image still resolves `:latest` — or any path that reaches the shared zeropoint tenant sidecar or a `solstice-*` bank — passes a file-diff check and MUST fail this one; the pin is proven by the running container, never by the diff.*
2. **(the round trip, live on 0.10.0)** Given the provisioned banks, When `verifyRoundTrip` runs against the dedicated instance, Then it returns `RoundTripOk` — retain → recall → reflect → consolidate → post-consolidation recall, five steps, `mode: "live"` (the client's mock short-circuit exists and MUST NOT be set on this leg) — with wall-clock `recallMs` and the server-side `serverRecall` both recorded, `slowQuery` flagged when `recallMs ≥ SLOW_QUERY_THRESHOLD_MS`. *Negative control: a leg driver that lets mock mode stand in for the live round trip produces schema-valid evidence for a network that was never touched and MUST fail.*
3. **(`qds-` provisioning, idempotent, zero partial banks by rollback)** Given the dedicated instance, When `provisionBanks` runs and then runs again, Then the roster (per-repo bank + `-dev-meta` + `qds-collective`; collision suffixes `-2..-11`, all-collide → `-32005`) is identical after both runs; every `createBank` remains the PUT upsert; and a FAILED sequence leaves zero partial banks **by compensation, not hope**: when a create partway through the roster fails, the driver deletes exactly the banks THIS attempt created (tracked in-attempt — the in-attempt created set = the `listBanks` diff taken immediately before and after the attempt, since the provisioner's failure envelope drops the partial roster, bank-provisioner.ts:463-467; never a bank from a prior run, never `qds-collective` unless this attempt created it) via the client's adds-only `deleteBank(bankId)` (`DELETE /v1/default/banks/{bank_id}` — exists server-side on 0.10.0; a 404 resolves as already-gone, idempotent like `createBank`'s PUT upsert), so the instance is left as-if-never-run and the idempotency-rerun leg starts clean. **The compensation-failure path is specified, not implied:** each delete's outcome is recorded per bank (`deleted` / `already-gone` / `failed`) in the leg JSON, and ANY compensation failure fails the leg (non-zero) with the residual bank roster listed in that JSON — a rollback that half-completes is a failed leg with named residue, never a clean exit claiming zero partial banks. The idempotency-rerun leg's coverage includes the rollback path — a fixture failure on a LATER create (e.g. bank 2 of 3) must show the earlier bank deleted, not merely assert the roster. *Negative controls, all MUST fail: an implementation that provisions into or reads any `solstice-*` bank; one that issues POST-based bank creation against the 0.10.0 surface; and a provision sequence whose mid-roster failure strands the banks it already created — "zero partial banks" claimed without a compensating delete is an unverified guarantee.*
4. **(the no-auth danger retired-check — measured, not assumed)** Given the deployed instance, When the retired-check runs, Then it records (a) an unauthenticated retain/recall — written to a disposable probe bank `qds-probe-<timestamp>` (explicit, `qds-`-prefixed per INV-MEM-1), deleted within the same leg via a finally-block `deleteBank` DELETE; a failed delete is recorded and fails the leg — never a roster bank, never a persistent new bank — and (b) an authenticated cross-bank attempt — authenticated meaning the instance's OWN configured credential from Z4's `hindsight-qds.env` (the dedicated instance's env file, runbook G3 pattern — never the tenant stack's `hindsight.env`; a wrong-key refusal is indistinguishable from a bank-scope refusal and would fake "danger retired" evidence), presented against a bank outside its scope, with the evidence JSON recording the auth-outcome class (known-key-out-of-scope vs unknown-key) separately — each with status and body-tail, into its own evidence JSON. The check does not presuppose its result: if 0.10.0 refuses both, the 0.8.6 danger (answered 200 with no auth header; `bank_id` per-call, no per-bank auth) is retired **on this instance by evidence**; if it still answers, the JSON records that and containment stays topological (loopback bind, firewall, gateway-when-it-lands) — stated, never silent. *Negative control: a story or implementation that declares the danger retired from the version bump alone — no live probe on the deployed instance — MUST fail.*
5. **(transport re-home of the P0.9 legs — annotate, never re-litigate)** Given Deviation 1, When the five legs execute, Then round-trip-via-bridge drives `resolveBankId(repoSlug)` semantics through the dedicated-instance REST client (`round-trip-verifier.ts`), negative-probes yields the non-existent-bank refusal (`HindsightHttpError` status 404, `src/hindsight/client.ts:79`) and the unavailable-instance refusal (502 / `fetch_failed` / 408 timeout — the client's own transport shapes) with **zero banks created** on either, hindsight-live and provision-and-import prove boot + import, and the closure plan carries an annotation block recording the re-home while its ACs stay byte-identical. Evidence lands in `_bmad-output/evidence/p0-9-closure/`. *Negative control: an implementation that edits a P0.9 AC — or one that re-creates the shared-platform `/invoke` transport to satisfy the plan's letter — MUST fail.*
6. **(firewall, per the runbook)** Given the deployed box, Then from outside, `curl -m 3 http://<box-ip>:18889/`, `:8888`, and `:18890` fail; only 22/80/443 are reachable; on-box loopback health answers at the env-carried `HINDSIGHT_BASE_URL` (`127.0.0.1:18890` — an on-box `18889` answer is the TENANT instance and fails AC1's negative control). **Disambiguation of record:** "runbook G5" = certbot issuance; the DF3.6b "G5 pairing" gate is a different register and is NOT a prerequisite of this story. *Negative control: a compose or firewall profile that publishes 18889/8888 — including "temporarily, for debugging" — MUST fail.*

Under D-2 the dedicated instance has no `/invoke` surface to call; the legs' **AC semantics** (round-trip order, negative refusals, idempotent provision) execute over the bank-scoped REST the factory client already speaks, and the plan gains an annotation block — its ACs stay untouched ("annotate the AC rather than re-litigate", the plan's own discipline). The re-homed leg writes the plan's evidence filename (`…-p0-9-round-trip-via-bridge.json`) so the plan's leg table keeps resolving; the annotation records the driver-name mapping (`scripts/p0-9/round-trip-dedicated.ts`). The annotation also fixes the refusal vocabulary, since the plan's own AC text speaks the MCP-era `-3200x` codes: on this REST transport the `-32001`-class (non-existent bank) resolves to `HindsightHttpError` 404 and the `-32002`-class (unavailable instance) to 502 / `fetch_failed` / 408 (`src/hindsight/client.ts:79`'s shapes) — `schemas.ts`'s `-3200x` **wire refusal** codes are superseded here, and the annotation says so rather than leaving both vocabularies live. Carve-out: the supersession covers the wire refusal classes only — the provisioner's internal all-collide envelope (`ERR_BANK_COLLISION`, `-32005`, `src/hindsight/schemas.ts:165`, emitted at bank-provisioner.ts:437/:461) remains authoritative for AC3's collision-exhaustion shape.
