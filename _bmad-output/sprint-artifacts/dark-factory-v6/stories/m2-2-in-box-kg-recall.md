## User Story

**As** the operator, **I want** every roster-granted worker in the box to hold exactly one read-only `kg_recall` tool backed by the M2 gateway under a per-run recall-only key, **so that** an agent can pull primed memory mid-run without ever holding a write credential, and recalled KG text is always sanitized, bounded, data-not-instructions.

## Overview

This story builds the in-box half of the memory lane: a pi extension registering one tool, `kg_recall`; the roster grant shape that makes it appear per-role; the per-run key delivery it consumes; and — because the extension is a NEW box file — the full image re-pin ritual, defined end-to-end here and **fired only on operator GO**. **What this does NOT deliver:** no write-back from the box (PARKED); no dispatch-time priming (M1.2's); no live round (M2.3); no gateway authz code (M2.1's — this story consumes it); the re-pin is not fired before the operator's explicit GO (zero agent spend until then, charter §6).

## E2E Slice

**Demonstrable behavior:** Given a roster role whose grant names the memory extension and a run dispatched with a per-run memory key, When the worker spawns in-box, Then the pi argv carries the `-e /opt/qds/pi-ext/kg-recall` pair, the tool surface contains exactly one memory tool (`kg_recall`), a recall call carries the runId-bound key and returns sanitized, char-budgeted content from a `qds-` bank (mock-mode gateway in CI), truncation carries an explicit marker, a gateway refusal surfaces as a tool-level error, and teardown revoke-verifies the key before box destroy. Given a role WITHOUT the grant, the same spawn shows no memory tool and no `-e` pair.

**Wiring closed:** On completion of this story, a granted worker can recall from the dedicated Hindsight banks through the M2 gateway using only code merged by this story plus M2.1 and M1.1 — extension → key (delivered per DD-16) → gateway → bank → sanitized output → revoke-verify at teardown. **No stub, no `TODO: wire later`.** The **live-round proof** is out of scope by construction (M2.3); the **ritual fire** is out of scope until operator GO.

**Dependency edges (predecessors):** **M2.1 is a *direct* edge** (the gateway and its key contract). **M1.1 is a *transitive* edge** through M2.1 (gateway fronts the dedicated instance) — not independently consumed here. The ops **re-pin ritual is an external prerequisite, not a story edge**: it is defined by this story but gated on the operator (charter §6 "ops stays operator-gated"). **Not an edge — M1.2:** dispatch-time priming is a different injection point (host-side brief appendix); M2.2 works with or without it.

## Acceptance Criteria

1. **(make-or-break — the roster grant)** Given roster role R with the `kg-recall` extension in its `harness_engineering` list (DF1.5 shape), When a worker for R spawns, Then `buildWorkerArgv` emits the `-e` pair, the extension registers exactly one tool named `kg_recall`, and — if R narrows `tools` — `kg_recall` is named there or pi silently drops it. Given role S without the extension entry, When a worker for S spawns, Then no memory tool appears in its surface. *Negative controls, both MUST fail this one: an implementation registering `kg_recall` for every run regardless of roster (an un-granted roster sees the tool); one registering any second, write-capable memory tool in-box (`kg_retain`, `kg_write`) — no write tool in-box, ever (F10/INV-7, DD-16).*
2. **(key consumption)** Given the per-run recall-only key delivered in-box (DD-16 set: one provider secret + one memory key, no more), When the extension calls the gateway, Then it authenticates with that key only — never the provider key, never a key from argv (D8) — against the gateway origin it was issued for, scoped to its bank allowlist; any gateway refusal surfaces as a tool-level error naming the gateway's reason token verbatim — bank outside the allowlist, including a bank bound to another run (`scope-bank`), expired TTL (`expired`), revoked (`revoked`) per M2.1's `memgate-refused` vocabulary — and, for the one battery-only class (a call with no auth header — reachable in-box only when delivery failed and the extension is keyless), the same passthrough under the register-flagged token `no-auth` (Deviation 2); the mock-tier suite feeds each refusal and asserts the tool-level error carries it, and the extension never retries a refused call against other credentials. *Negative control: an implementation falling back to the provider key or re-issuing recall through any non-gateway origin turns one scoped credential into a bearer for the whole store and MUST fail this one.*
3. **(sanitized, bounded, F10-treated output — with the threat stated honestly)** Given any recall result, When it reaches the worker turn, Then it passed the sanitization boundary THIS story owns — the extension treats recalled text as untrusted data (F10) and applies its sanitize pass (control-char strip + data-only framing: content enters the tool result as quoted data, never as harness instructions) — AND passed the extension's own ceiling `KG_RECALL_CHAR_CEILING` (8,000 chars): over-budget output truncates with the literal marker `[kg_recall:truncated]` — never silently. The gateway MAY sanitize too; nothing in-box depends on it (M2.1's spec registers no sanitizer — the Presidio lane was skipped factory-side — so the fence lives HERE, not in a phantom sibling contract). **What the sanitize pass is and is not:** it is prompt-injection HYGIENE (control-char and framing reduction), not an injection-proof boundary — sanitized text still reaches the model and can still steer it; the claim is therefore scoped, not absolute. The LOAD-BEARING fence is permission independence: **the worker's permissions, tool surface, credentials, and routes are wholly independent of recalled text** — nothing parsed from a recall result can grant a tool, un-grant a restriction, or alter what the run may touch (the roster grant and DD-16 credential set are fixed at dispatch, before any recall exists). The testable data-claim is exactly this: the extension never interprets recalled content as instructions and never places it in an instruction-bearing channel — it enters solely as quoted tool-result data. *Negative controls, all MUST fail this one: an implementation that delivers raw bank content without the sanitize pass, or truncates without a marker (satisfying "delivered" while shipping unbounded text); and one whose worker's effective permissions or tool surface can change based on recalled content — an injection that escalates privileges defeats every strip-and-frame measure and is the failure this AC exists to make impossible.*
4. **(key never survives the run)** Given a run ending in any terminal state, When the teardown chain runs, Then the memory key is revoked-and-verified-before-destroy mirroring `credentials.ts` ordering (:1622-1727), including revoke-verify **compensation** when delivery itself failed (a minted key never outlives a failed delivery). *Negative control: an implementation that skips revoke-verify because "box teardown already succeeded" lets a gateway credential outlive its box — a destroyed box does NOT revoke a gateway key — and MUST fail this one.*
5. **(the ritual, defined here, fired on GO)** Given the extension source enters the box COPY set, `deriveBuildId` (`scripts/build-exedev-image.ts:638`) moves by construction. The story ships: the ritual runbook (re-pin base → rebuild → re-sweep → publish via `publish-exedev-image.yml` → adopt the `DEFAULT_IMAGE_REF` + `DEFAULT_IMAGE_BUILD_ID` pair via `scripts/adopt-image-pin.ts`), CI expectations (verify-image-pin `verify` leg green after adopt; `base-drift` red BY DESIGN weekly upstream rebuild — not an incident; the current `ee802669…` MANIFEST_UNKNOWN real red retired by the new publish; exception register stays EMPTY), and the adoption + green-CI evidence artifact. FIRED only after operator GO; zero agent spend before. **The fire batches:** the ritual runs on a tree that already contains M1.2's COPY-set edits (`src/fleet/brief-schema.ts`, `scripts/pipeline-run.ts`), J3's adds-only `src/fleet/dispatch.ts` edit, J4's adds-only steering `compact` member (`src/phase-engine/steering.ts`), and A2's adds-only `workKey` field (`src/providers/run-record.ts`) — or is re-run after they land — so v6b pays ONE rebuild: the once-only ritual tree is **M1.2 + J3 + J4 + A2** (DD-28.26(4)), completed by this story's own Dockerfile COPY line, and the pin M2.3's round consumes carries the primed-dispatch code its AC1 leg needs. *Negative controls, both MUST fail this one: an implementation that adds the COPY line and treats verify-image-pin's current red as unrelated pre-existing breakage leaves T2 blocked behind an unowned ritual; and a ritual fired on a tree missing any ritual-tree member's COPY-set edits (M1.2's `kgContext` render, J4's steering `compact` member, A2's `workKey` field) pins an image without them, forcing a second paid rebuild before any T2 round.*
