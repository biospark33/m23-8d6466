# P2.11: Confirm Cron — 30-Day Auto-Rollback of Deployed Experiments

**Story Points:** 3

## Spec Reference

- QDS-MEM-003 §8.1–8.3 (A/B confirm-and-rollback); §4.1 CHECK (experiments status enum)
- QDS-MEM-003-IMPL §D.3 (D6 — self-optimization loop); state machine §B.2 (this research-context)

## User Story

As a QDS Meta-Optimizer,
I want every deployed A/B winner to be automatically confirmed or rolled back 30 days after deploy by comparing live post-deploy metrics against the snapshotted baseline,
so that no regression survives unattended and intervention outcomes feed `intervention_effectiveness` (G6 — the self-optimization loop closes without a human in the rollback path).

## Overview

This story wires the terminal transition of the A/B experiment state machine: a once-daily cron that scans `experiments` for rows still in status `deployed` (or orphaned `confirming` from a crashed prior tick) whose `confirm_until` (= `deployed_at + 30d`) has been reached, recomputes the experiment's `metric` over the post-deploy window, and compares it against the snapshotted `baseline_metrics_json` written by P2.10 (R8 shape). Each eligible experiment advances `deployed → confirming → confirmed | rolled_back` in ONE DB transaction (so `confirming` is never durably observable), and that SAME per-experiment transaction also closes the experiment's `experiment:<id>` lifecycle run by flipping `runs.status='completed'` — so the lifecycle events become decay-eligible for P2.12 retention (which excludes only `status='running'` runs), closing the permanent-retention-exemption hole. On regression the cron auto-reverts `deploy_ref` to the control variant (`experiments.variant_a_ref`, R9) — no human approval, by design. Every transition is emitted as an `event_type='outcome'` event (audit trail) using the shared state machine in `src/experiments/state-machine.ts` (R10 — no parallel transition logic), and the terminal verdict is `retain()`'d to qds-meta (`outcome:confirmed` | `outcome:rolled_back`) via the P2.8 bridge so the Meta-Optimizer can score `intervention_effectiveness`. The net-new `ConfirmCron` class plus a regression-comparison helper close this wiring with no stub or TODO; idempotency is per-experiment (status filter + per-experiment `documentId`), so retries never double-revert or double-`retain()`.

## E2E Slice

**Demonstrable behavior:** Seed two `deployed` experiments with `confirm_until` in the past — one whose post-deploy metric beats baseline, one that regresses below baseline by more than the regression threshold. Invoke `ConfirmCron.run(now)`. Assert: experiment #1 ends `confirmed` with `deploy_ref` unchanged; experiment #2 ends `rolled_back` with `deploy_ref` auto-reverted to its control variant (`variant_a_ref`); both have `decided_at` set; both emitted terminal `event_type='outcome'` transition events FK'd to their lifecycle run `experiment:<id>`; both produced a qds-meta `retain()` with the correct `outcome:` tag and per-experiment `documentId` `confirm-<experiment_id>`.

**Wiring closed:** On completion of this story, any deployed experiment past its `confirm_until` is automatically confirmed or rolled back on the next cron tick using only code merged by this story and predecessor P2.10. No stub, no `TODO: wire later`, and no sibling story is required to make this behavior real.

**Dependency edges (predecessors):** P2.9 (creates the `experiment:<id>` lifecycle run + owns `src/experiments/state-machine.ts`); P2.10 (writes `deploy_ref` + `baseline_metrics_json` + `confirm_until` + `variant_a_ref` control ref); P2.8 / P1.11 (the `retain()` path reused for the qds-meta finding).

> **Epic-level observability metric (NOT a per-tick AC):** fleet uptime — ≥95% of experiments that became `deployed` ≥35 days ago have reached `confirmed`/`rolled_back` within 35 days of `deployed_at` — is tracked as an epic observability metric (depends on cron schedule cadence + clock, outside one tick's control), not asserted by this story. This story's AC1 asserts only the per-tick binary property.

## Acceptance Criteria

> ≥3 scenarios, Given/When/Then. Exactly one tagged (make-or-break) and binary.

1. **(make-or-break)** Given a seeded `deployed` experiment with `confirm_until ≤ now`, When `ConfirmCron.run(now)` executes, Then in that single tick the row is left in status `confirmed` OR `rolled_back` (never still `deployed`, never stranded in `confirming`) with `decided_at` set — and this holds for **100% of eligible rows in the one tick** (count of eligible rows resolved to a terminal status ÷ count of eligible rows = 1.0).
2. Given a deployed experiment past `confirm_until` whose post-deploy `metric` regresses past `baseline_metrics_json` by more than the regression threshold — metric-aware direction with a SYMMETRIC multiplicative tolerance band: for `success_rate` (higher-is-better) the regression is post **below** `baseline_value × (1 − threshold)`; for `token_cost`/`duration`/`review_findings` (lower-is-better) the regression is post **above** `baseline_value × (1 + threshold)` — When the cron evaluates it, Then it transitions `deployed → confirming → rolled_back`, `deploy_ref` is reverted to the control variant (`experiments.variant_a_ref`, per P2.10 R9 — no prior-ref column exists), and the `rolled_back` `event_type='outcome'` event is written in the SAME DB transaction as the `deploy_ref` revert (the revert never commits without its audit event), `decided_at` is set — with no human approval step invoked.
3. Given a deployed experiment past `confirm_until` whose post-deploy `metric` meets or beats baseline, When the cron evaluates it, Then it transitions `deployed → confirming → confirmed`, `deploy_ref` is left unchanged, and a qds-meta finding is retained with tag `outcome:confirmed`.
4. Given an experiment still inside its 30-day window (`confirm_until` not reached), When the cron runs, Then the row is skipped and remains `deployed` (no premature confirm/rollback).
5. Given an experiment left in `confirming` by a crashed prior tick OR a duplicate same-tick invocation, When the cron's eligible scan runs, Then correctness rests on two mechanics: (a) the scan selects ONLY rows still in `deployed` or orphaned `confirming` — already-terminal (`confirmed`/`rolled_back`) rows are excluded, so a re-run applies no transition and re-reverts no `deploy_ref`; and (b) `retain()` uses the per-experiment `documentId` `confirm-<experiment_id>` with `updateMode:"replace"`, so a re-run issues no duplicate finding. (Orphaned `confirming` rows are resolved fail-safe → `rolled_back` + revert, per AC6.)
6. Given metric recomputation raises an error, post-deploy data is insufficient (post-window sample `post.n` below the configured `MIN_N`, mirroring P2.10), the baseline is malformed/missing, or the metric name is unrecognized (not in P2.9's `{success_rate,token_cost,duration,review_findings}` enum) for an eligible experiment, When the cron processes it, Then the experiment is treated fail-safe (regression assumed → `rolled_back` + `deploy_ref` reverted to `variant_a_ref`), the error is recorded on the transition event's `error` column (with structured context in `payload_json`), and the cron continues to the next experiment (never crashes or silently skips).
7. Given an experiment reaching a terminal verdict (`confirmed` OR `rolled_back`), When the cron commits that transition, Then in the SAME per-experiment DB transaction (status flip + `deploy_ref` write + `event_type='outcome'` audit event) the experiment's `experiment:<id>` lifecycle run is flipped to `runs.status='completed'`, making its lifecycle events decay-eligible for P2.12 retention (no permanently-`running` lifecycle run survives a terminal verdict).

## Technical Notes

- **Contracts/Schema:** No DDL changes — operates over P2.1's `experiments` table. Baseline input shape is the R8 P2.10 baseline shape by name (validated against P2.10 `baseline_metrics_json`): `{ metric, baseline_value, n, window_start_ms, window_end_ms, computed_at_ms }` — do not reinvent. `post = recomputePostDeployMetric(experiment)` returns the same shape over the `deployed_at → now` window using P2.1 recall aggregations (outcome rates / tokens / duration by `experiment_id`+`variant`); the `baseline_value` field is reused as the generic "measured value" for the post window too (and `post.n` carries the post-window sample size). `isRegression` gates on `post.n ≥ MIN_N` (mirror P2.10's `MIN_N`) before trusting the comparison — below `MIN_N` it fail-safes (does NOT confirm/rollback on noise; routes to fail-safe rollback per INV-CONFIRM1). `metric` strings MUST match P2.9's enum `{success_rate,token_cost,duration,review_findings}`; an unrecognized metric routes to fail-safe rollback, never crash/skip. Verdict: `isRegression(metric, baseline.baseline_value, post.baseline_value, threshold)` applies a SYMMETRIC multiplicative tolerance band — higher-is-better (`success_rate`) regresses iff `post < baseline × (1 − threshold)`; lower-is-better (`token_cost`/`duration`/`review_findings`) regresses iff `post > baseline × (1 + threshold)`. `threshold` is the configured regression tolerance (tunable via config, not hardcoded).
- **Integration points (each wired & exercised in this story):** P2.1 recall aggregation API (post-deploy metric recompute); shared `src/experiments/state-machine.ts` (R10 — REUSED for the `deployed → confirming → confirmed|rolled_back` confirm-entrypoint guards; the parallel transition logic in `experiment-store.ts` is dropped); `experiments` status writes (set `decided_at`, revert `deploy_ref` to `variant_a_ref`) + `runs` write (flip `experiment:<id>` lifecycle run to `status='completed'` in the same per-experiment transaction); per-transition event emit into `events` (`event_type='outcome'`, `experiment_id` set, `run_id="experiment:<id>"` lifecycle run created by P2.9); P2.8/P1.11 `retain()` to qds-meta (`skill:X, outcome:{confirmed|rolled_back}, quality_dim:intervention_effectiveness`); cron scheduler registration (`croner`, per §D.4) where `ConfirmCron.run` is scheduled once/day off-peak in `src/optimizer/scheduler.ts`.
- **Files / functions touched:** `src/optimizer/confirm-cron.ts` (`ConfirmCron` net-new — scan eligible incl. orphaned `confirming`, drive transitions per-experiment atomically); `src/optimizer/regression-compare.ts` (`recomputePostDeployMetric`, `isRegression` — metric-aware comparison); `src/optimizer/experiment-store.ts` (status/`deploy_ref`/`decided_at` writes + `experiment:<id>` lifecycle-run flip to `runs.status='completed'` + transition-event emit, all in one per-experiment transaction; transition validity delegated to the shared `state-machine.ts`); `src/experiments/state-machine.ts` (REUSE of P2.9 machine — confirm-entrypoint guards); `src/optimizer/retain-finding.ts` (qds-meta retain wrapper reusing P2.8 path); `src/optimizer/scheduler.ts` (croner registration of `ConfirmCron.run`).
- **Guards/limits:** idempotency is per-EXPERIMENT, not per-day — correctness = (a) the eligible scan selects only still-`deployed`/orphaned-`confirming` rows via the explicit SQL filter `WHERE status IN ('deployed', 'confirming') AND confirm_until <= :now` (the `status IN (...)` predicate excludes already-terminal `confirmed`/`rolled_back` rows, so a retry re-processes no terminal row), and (b) the per-experiment `documentId` `confirm-<experiment_id>` (R13, NO date) with `updateMode:"replace"`; an optional advisory single-instance run-marker (if kept) lives in a DEDICATED `confirm_cron_runs` table — NOT `schema_meta` — and is advisory only, never the correctness mechanism (R12). The whole `deployed → confirming → terminal` write (status + `deploy_ref` revert + event emit) is ONE DB transaction per experiment, so `confirming` is never durably observable; the orphan-`confirming` scan branch is the belt-and-suspenders recovery if a tick crashes mid-write. Regression threshold + observation window tunable via config (not hard-coded); fail-safe default on comparison error / unrecognized metric = rollback to `variant_a_ref` (never silent hold). `winner='none'` is NOT listed as a fail-safe condition here: P2.10's deploy guard (INV-EXP7) refuses deploy for `winner='none'` and finalizes it as a terminal no-op at `status='analyzed'`, so such a row structurally cannot enter the `status IN ('deployed','confirming')` candidate set — unreachable by construction.

## Security Invariants

> Concrete named invariants only — N/A NOT permitted when triggered.

- **INV-OM1:** No per-event LLM/HTTP. The cron's only network egress is the single per-experiment qds-meta `retain()` at terminal verdict; metric recompute and comparison are mechanical SQL/arithmetic (no LLM, no per-row HTTP).
- **INV-OM2:** Every transition event written to `events` carries a non-null `run_id` referencing a real `runs` row — lifecycle events use the experiment's lifecycle run `run_id="experiment:<id>"` (created by P2.9 at propose time, `dag_def_id="__experiment_lifecycle__"`), never NULL and never a silent drop — plus `experiment_id`; the audit trail is un-orphaned (R1).
- **INV-OM3:** The qds-meta finding payload is ≤64 KB and secret-pattern-masked before `retain()` — no raw metrics blob or deploy config leaks unbounded/unmasked into Hindsight.
- **INV-CONFIRM1 (fail-safe rollback):** A detected or assumed regression (including comparison error, insufficient data, malformed/missing baseline, or unrecognized metric name) ALWAYS resolves to `rolled_back` + `deploy_ref` revert to `variant_a_ref` — never a held `deployed` or silent `confirmed`. The safe default is revert, not hold.
- **INV-CONFIRM2 (per-experiment idempotency):** Idempotency is per-experiment, not per-day: the eligible scan excludes already-terminal (`confirmed`/`rolled_back`) rows and the per-experiment `documentId` `confirm-<experiment_id>` (`updateMode:"replace"`) means re-running applies no second transition, re-reverts no `deploy_ref`, and issues no duplicate `retain()`. Any run-marker row is advisory single-instance only (dedicated `confirm_cron_runs` table, NOT `schema_meta`), never the correctness mechanism (R12).
- **INV-CONFIRM3 (audit-before-commit rollback):** The `rolled_back` transition event is written in the SAME DB transaction as the `deploy_ref` revert — the revert never commits without its audit event, so there is no untraceable reversion (R13).
- **INV-CONFIRM4 (lifecycle run closed on terminal verdict):** On `confirmed` OR `rolled_back`, the `experiment:<id>` lifecycle run is flipped to `runs.status='completed'` in the SAME per-experiment transaction as the status flip + audit event — no terminal experiment leaves a permanently-`running` lifecycle run, so its events are decay-eligible for P2.12 retention (which exempts only `status='running'` runs) rather than permanently exempt.
- **INV-CONFIRM5 (post-window min-n fail-safe):** `isRegression` is trusted only when the post-window sample `post.n ≥ MIN_N` (mirror of P2.10's `MIN_N`); below that threshold the comparison is treated as noise and routed to fail-safe rollback (INV-CONFIRM1) — the cron never confirms or rolls back on a statistically insufficient post window.
