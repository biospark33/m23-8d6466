## User Story

As the Operator,
I want a single binary make-or-break gate that runs the §13 Phase-1 assertion list end-to-end on a sample repo,
so that "the Dev vertical slice works" is one machine-checkable pass/fail — a real PR produced, a reconstructable audit chain, spend within budget, a working Telegram approve/resume, and retained findings — and any red clause blocks promotion past Phase 1 (G1 accountability; G4 human-on-the-loop).

## Overview

It cuts across every Phase-1 layer (Paperclip control plane → Hermes Dev manager → Warren `qds-mkbrk` DAG → Pi team → pi-lens → Seeds → cost_events ledger → approvals → Hindsight) by running **one orchestrated gate harness** that executes the §13 Phase-1 flow on a sample repo and asserts the eight clauses as a single pass/fail. Each predecessor story (P1.1–P1.16) ships one Phase-1 capability; this story owns only the **aggregating gate harness + assertion runner** that proves they compose end-to-end with no missing wiring. **SP note: P1.17 writes the gate harness (`bin/qds-gate.ts`), which is new infrastructure code (not product feature code). 3SP covers harness + 8 clause assertions + e2e demo. The harness is a one-time tool, not a reusable product component.** **Per PRD §13 / R5: item 15 (the PR review-comment fix loop, our P1.18 + P1.19) is scope-included in Phase 1 but SEPARABLE from this make-or-break gate** — the gate passes on clauses 1–8 alone and does NOT require the comment loop to be closed (P1.18/P1.19 are a parallel branch, not predecessors of this gate).

## E2E Slice

**Demonstrable behavior:** The Operator runs `qds-gate phase-1 --repo ./sample-repo --json`. The harness drives the §13 Phase-1 flow (a `/qds` request → one parent Dev issue → Seeds decompose+mirror → `qds-mkbrk` run → pi-lens-gated implement node → real PR) and then evaluates clauses 1–8, emitting **one** JSON gate report `{ phase: "1", pass: boolean, clauses: [{ id, name, pass, evidenceRef }×8] }` on stdout and exit code `0` iff **all eight** clauses pass (non-zero with the failing clause id(s) otherwise). **Clauses MUST run sequentially in order 1–8.** Clause N+1 does not execute until clause N completes. This preserves causal dependencies (e.g., clause 3 must complete before clause 5 can audit its results). Parallel evaluation is explicitly forbidden.

**Wiring closed:** On completion of this story, `qds-gate phase-1 --repo ./sample-repo --json` produces a gate report whose `pass` is `true` and exit code `0` **iff every §13 Phase-1 clause (1–8) passes on the sample repo**, using only the runner/assertion code merged by this story over predecessor-merged capabilities. No stub, no `TODO: wire later`, and no sibling story is required to make this gate real — predecessors are dependency edges (listed below), not unfinished wiring inside this story. (Item 15 / P1.18–P1.19 is explicitly out of this gate's scope.)

**Dependency edges (predecessors):** P1.10 (executionPolicy Telegram approve/resume → satisfies clause 8; P1.10 absorbs the Hermes-Telegram gateway wiring formerly scoped to killed P0.8). P1.14 (per-run outcome record / FR-ACT-2 substrate → clause-6 predecessor: P1.14 writes the outcome record which P1.13's cost-summary endpoint reads for aggregation context. P1.14 is NOT the cost-sum owner — P1.13 owns the SUM. Dependency chain: P1.13 (cost aggregation) → P1.14 (outcome record reads P1.13 output) → P1.17 (gate asserts P1.13's cost-summary). Both P1.13 and P1.14 are clause-6 predecessors.). P1.16 (audit-chain reconstruction for one real PR → satisfies clause 5; and transitively P1.15 real PR → clause 4, P1.3 Seeds decompose+mirror → clause 2, P1.6–P1.7 DAG+implement+gate → clause 3, P1.11/P1.13 ledger+memory → clauses 6/7, P1.1/P1.2 manager+intake → clause 1). All Phase-1 capability stories must be done for this gate to pass; this story wires the assertion runner only.

## Acceptance Criteria

> The eight ACs below are the §13 Phase-1 clauses transcribed EXACTLY (quoted), each cross-referenced to the predecessor (P1.x) that satisfies it. AC-0 is the binary make-or-break.

0. **(make-or-break)** Given the sample repo and all Phase-1 predecessors merged, When `qds-gate phase-1 --repo ./sample-repo --json` runs, Then **all §13 Phase-1 assertions (clauses 1–8) pass end-to-end** — the gate report `pass` is `true` and exit code is `0`; **any red clause = make-or-break not met** (exit non-zero, `pass:false`, failing clause id reported). No clause may be skipped, defaulted-true, or marked N/A.

1. **(clause 1 — P1.2 intake / P1.1 Dev manager)** Given a Dev manager registered as a Paperclip agent, When the harness issues `/qds <request>`, Then *"Telegram `/qds <request>` creates exactly one parent Paperclip issue assigned to the Dev manager"* — Clause 1 assertion: `SELECT COUNT(*) FROM issues WHERE parentId IS NULL AND companyId = $QDS_COMPANY_ID` returns exactly 1. This is an unconditional end-state check regardless of how the parent was created (idempotent upsert via P1.2 or manual creation). Gate does not assert creation mechanism — only the final state. Clause 1 issue-creation uses `POST /companies/:companyId/issues` (companyId from PAPERCLIP_COMPANY_ID, per verified-correct element). The gate verifies the issue exists via `GET /issues?parentId=null&companyId=$QDS_COMPANY_ID`.

2. **(clause 2 — P1.3 Seeds decompose+mirror)** Given the parent issue, When the Dev manager decomposes, Then *"The Dev manager decomposes via Seeds and mirrors stories to child Paperclip issues, with dependencies held only in `.seeds/issues.jsonl` and assignment+cost only in Paperclip (no duplicated authority)"* — every child issue carries `originKind='seeds_story'`+`originId`, and no dependency edge or cost authority is duplicated across the two stores.

3. **(clause 3 — P1.6 implement node / P1.7 post-edit gate / P1.15 real-PR surface)** Given the run, When `qds-mkbrk` executes, Then *"The `qds-mkbrk` DAG runs and reaches the Pi-team implement node, which is pi-lens-gated, refuses to emit while `lsp_diagnostics` shows errors on changed files (post-edit gate), and emits a single structured JSON result"* — the implement node output is one structured JSON object and no emit occurred with un-waived dirty diagnostics on the changed-file union. **Clause 3 validates the Warren workflow name before submission: `WarrenClient.listWorkflows()` is called to verify the target workflow exists. If not found, clause 3 fails with `resolved: false, error: 'workflow {name} not registered in Warren'` — a clear, actionable error rather than an opaque API failure.** **P1.15 owns the real-PR surface that the DAG run produces; the DAG-run execution exercised here depends on P1.15 (via P1.16 transitive) for the actual PR output.**

4. **(clause 4 — P1.15 real PR)** Given the completed run, When the gate inspects the result, Then *"A real PR is produced on a sample repo."* — a PR URL/number exists on `./sample-repo`.

5. **(clause 5 — P1.16 audit chain)** Given that PR, When the harness walks the chain, Then *"Audit-chain reconstructability: for that PR, the full §8.1 chain (epic → Seeds → Paperclip issue → cost_events → approvals/`issue_execution_decisions` → heartbeat_runs → Warren run → Pi team → pi-lens → Hindsight) walks end-to-end with no missing hop."* **A dedicated sub-check within clause 5 verifies `heartbeat_runs.retry_count < 8` for the target run. If retry_count >= 8, the gate warns (does not fail) with stderr: 'retry_count >= 8 detected — verify P1.9 restart policy configuration'. This catches P1.9 misconfigurations early.**

6. **(clause 6 — P1.13 ledger / P1.13 roll-up)** Given the issue tree, When the gate reads spend via `GET /issues/:id/cost-summary` (P1.13's verified-correct route; the Paperclip service layer handles companyId scoping internally via `PAPERCLIP_COMPANY_ID` — the public API does not expose companyId in the path), Then *"Per-issue spend within budget: Paperclip shows per-issue-tree spend from `cost_events`, and it is at or under the agent/company budget cap (no silent over-cap)"* — `SUM(cost_events.costCents)` over the `parentId` subtree ≤ the agent/company `budgetMonthlyCents`. **Ownership: Clause-6 per-issue spend data is OWNED by P1.13 (cost aggregation). P1.16 (audit chain) READS clause-6 data for its chain walk but does not own it. P1.17 gate ASSERTS clause-6 results by reading P1.13's cost-summary endpoint. Ownership chain: P1.13 writes → P1.16 reads → P1.17 asserts.** **Cost boundary: Gate reads `costSummary.totalCents` (integer) from P1.13's endpoint. No float conversion needed at the gate level — P1.13 owns the float→cents conversion. Gate compares integer cents against budget thresholds. P1.6 writes raw float; P1.13 converts; P1.17 reads integers.**

7. **(clause 7 — P1.11 memory retain)** Given the run, When the gate queries the dev bank, Then *"The Hindsight dev bank (`{repo}-dev-meta` / `{repo}`) contains findings retained from the run"* — ≥1 retained memory with `document_id == runId` is recallable. **Bank names follow P1.11 Hindsight convention: `{repo}` is the primary bank and `{repo}-dev-meta` is the dev-metadata bank. The `{repo}` slug is derived from `QDS_SAMPLE_REPO` env var by extracting the repo slug (basename of the path or URL). Example: `QDS_SAMPLE_REPO=https://github.com/org/my-repo` → bank name = `my-repo`. If `QDS_SAMPLE_REPO` is a local path (e.g., `./sample-repo`), the basename of the last path segment is used (e.g., `sample-repo`). This matches P1.11's bank creation convention.**

8. **(clause 8 — P1.10 approve/resume)** Given a gated issue, When the gate exercises the HITL path, Then *"Working `executionPolicy` Telegram approve/resume: a gated issue pauses the Warren run, pings Telegram with inline approve/reject, and the human reply resumes the paused run to completion (a reject path likewise halts it cleanly)"* — exercised in `TELEGRAM_MOCK_MODE=gate` by default for automated gate runs. In mock mode, P1.10's approval endpoint auto-approves with a fixed 2s delay (simulating human response). **Clause 8 exercises P1.10's Telegram gateway path ONLY (not the plugin SDK, which is BLOCKED).** In `TELEGRAM_MOCK_MODE=gate`, approval is auto-generated. The "live Telegram plugin" option is deferred and MUST NOT appear as a viable path in Phase 1. For live gate runs (manual `--live-hitl` flag), the real Telegram gateway path is used. CLI fallback (`qds approve --run-id <id>`) is always available regardless of mode. The `approvals`/`issue_execution_decisions` write is recorded in both modes.

## Technical Notes

- **Contracts/Schema:** No new tables. New **gate-report contract** (Zod/JSON): `gatePhase1ReportSchema = { phase: z.literal("1"), pass: z.boolean(), exit_class: z.enum(["transient", "overflow", "logic"]), runId: z.string(), wallClockMs: z.number().int(), durationMs: z.number().default(0), prRef: z.string().min(1),
  failedClauses: z.array(z.number().int().min(1).max(8)).default([]), clauses: z.array({ id: z.number().int().min(1).max(8), name: z.string(), pass: z.boolean(), evidenceRef: z.string(), durationMs: z.number().int() }).length(8) }`. **`exit_class` is mandatory non-null** — it classifies the gate outcome: `"transient"` (infrastructure/timeout failure, retry may help), `"overflow"` (budget/resource cap exceeded), `"logic"` (business-logic or assertion failure). **`prRef` is required for Phase-1**: the gate harness MUST resolve a PR URL/number. If no PR exists, clause 4 fails (no real PR produced) and the gate reports `pass:false`. This is consistent with AC-0 ("no clause may be skipped"). The `prRef` field is non-null in the Phase-1 report schema. **`evidenceRef` is a human-readable string referencing the concrete artifact that proves the clause passed**: e.g., `"issue#${issueId}"`, `"run#${runId}"`, `"pr#${prNumber}"`, `"bank:${bankName}/doc:${docId}"`. Format is descriptive, not machine-parseable — the gate report is for human/audit consumption. **`runId` is the `qds-mkbrk` Warren run ID** — the single Phase-1 demonstration run triggered by the gate harness. It is NOT the gate harness's own run ID (the gate is a CLI tool, not a Warren workflow). `wallClockMs` records total elapsed wall-clock time from gate start to report emission; `durationMs` on each clause records per-clause evaluation time for diagnosability. **Top-level `durationMs` is always populated (measured by the gate harness). Default 0 used only if gate fails before timer starts.** `pass === clauses.every(c => c.pass)` is enforced (the harness cannot report `pass:true` with any failing clause). Backward-compatible: read-only over existing schemas (`issues`, `cost_events`, `approvals`, `heartbeat_runs`, Seeds `.seeds/issues.jsonl`, Hindsight bank).
- **Integration points (each wired & exercised in this story):** (1) drive `/qds` intake (P1.2) → one parent issue (`assigneeAgentId`); (2) read Seeds `.seeds/issues.jsonl` + Paperclip `issues.originKind/originId` for clause 2; (3) WarrenClient submits `POST /api/workflows/qds-mkbrk/run` and reads the SSE response stream for clause-3 DAG execution and clause-5 audit chain results; (4) reuse the P1.16 audit-chain walker for clause 5 (do not reimplement); (5) read `GET /issues/:id/cost-summary` (P1.13's verified-correct route — Paperclip service layer handles companyId scoping internally via `PAPERCLIP_COMPANY_ID`) for clause 6 — **the cost-summary route/field names are owned by P1.13. The gate asserts clause 6 by calling P1.13's `GET /issues/:id/cost-summary` endpoint.** (6) Hindsight recall for clause 7 — **bank names follow P1.11 Hindsight convention: `{repo}` for the primary bank and `{repo}-dev-meta` for the dev-metadata bank. Exact names are owned by P1.11; the gate constructs them from the sample repo's configured name.** (7) invoke the P1.10 approve/resume path for clause 8.
- **Files / functions touched:** `src/gate/phase1-gate.ts:runPhase1Gate` (orchestrate flow + collect evidence), `src/gate/clauses.ts:CLAUSE_1..8` (one assertion fn each, returns `{pass, evidenceRef}`), `bin/qds-gate.ts` (CLI entry, exit-code mapping). Reuses `src/audit/chain-walker.ts` (P1.16), `src/cost/issue-tree-spend.ts` (P1.13/14), `src/hindsight/recall.ts` (P1.11).
- **Guards/limits:** the gate is **fail-closed** — a clause whose evidence cannot be collected (missing run, unreachable Paperclip, empty bank) evaluates to `pass:false`, never silently true; the harness honors a `--wall-clock-cap-ms` so a hung clause times out to a fail, not a hang. **Per-clause timeout: `wallClockCapMs / 8` (evenly divided). If any single clause exceeds its budget, the clause fails with `timedOut: true` and the gate continues to the next clause. This prevents one slow clause from consuming the entire wall-clock budget.** Per §13 / R5, item 15 (P1.18/P1.19 comment loop) is **not** evaluated by this gate.
- **Gate report persistence:** the gate report is written to stdout (the primary output). For post-mortem auditability, the harness also writes the report to `.qds/gate-reports/phase-1-{runId}.json` (creating the directory if needed). This is a convenience path — the stdout output is the authoritative result; the file copy is for easy retrieval without re-running the gate. No database write.
- **Idempotency:** Gate re-runs are idempotent. Before writing, the gate cleans any prior `.qds/gate-reports/phase1-*.json` files (glob delete). The gate report for the current run is overwritten (not appended). Hindsight bank memories are append-only by design and do not conflict across re-runs. Issue state (clause 1) is checked before assertion — duplicate creation is idempotent per P1.2's upsert behavior. Re-running the gate with the same sample repo produces a fresh, clean report without accumulating stale artifacts from prior runs.
- **Parallel-development note (P1.16 dependency):** The gate imports `chain-walker.ts` from P1.16. Development of P1.17 proceeds in parallel with P1.16; at merge time, P1.16 must be merged first. This ordering constraint is captured in the dependency edges.
- **Sample-repo setup:** The gate requires `./sample-repo` to exist with a clean git state. Setup: the gate harness clones or initializes the sample repo before running; teardown is optional (repo persists for manual inspection). A missing `./sample-repo` causes an early exit with a descriptive error (not a false `pass`).
- **Cross-story string alignment:** `originKind='seeds_story'` is the exact string value set by P1.3 Seeds decomposition. The gate asserts this literal string — any typo divergence between P1.3 and this clause is a gate failure.
- **Citation caveat:** File:line references in this story (e.g., `adapters/registry.ts:468-469`) are best-current-knowledge at spec time and may shift during P1.1/P1.2 development. The invariant pattern (bearer-authenticated registered agent) is the contract, not the exact line numbers.

## Security Invariants

> Triggers: auth, cost/budget, tenant. Concrete named invariants only.

- **INV-1 (auth — read as registered agent):** all Paperclip reads the gate performs (issues, cost_events, approvals, heartbeat_runs) are made as the bearer-authenticated registered agent (`PAPERCLIP_API_KEY` + `PAPERCLIP_RUN_ID`, `adapters/registry.ts:468-469` — file:line best-current-knowledge; may shift during P1.1/P1.2 development — the invariant is the bearer-auth pattern, not the exact line number) — the gate never reads via an anonymous/unauthenticated path, and never mutates state (read-only assertions only).
- **INV-2 (cost/budget — no silent over-cap):** clause 6 fails the gate when `SUM(cost_events.costCents)` over the issue subtree **exceeds** the agent or company `budgetMonthlyCents`; an over-cap spend can NEVER yield `pass:true` (no rounding-to-pass, no missing-row treated as zero — a missing cost row is a clause-5 audit failure, not a clause-6 zero).
- **INV-3 (tenant isolation):** every read is scoped to `$QDS_COMPANY_ID` (sourced from `PAPERCLIP_COMPANY_ID` environment variable) and the sample repo's banks (`{repo}`/`{repo}-dev-meta`); the gate never reads or aggregates issues, cost_events, or memory from another company/tenant or another repo's bank. No hardcoded company IDs in the gate code. All Paperclip queries include `WHERE companyId = $QDS_COMPANY_ID`.
- **INV-4 (no secret leakage in evidence):** `evidenceRef` fields carry ids/refs only (issue id, run id, PR number, bank doc id) — never bot tokens, API keys, or raw memory contents; the gate report written to stdout contains no secret value.
