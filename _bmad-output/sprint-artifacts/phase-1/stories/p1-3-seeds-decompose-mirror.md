# P1.3: Seeds-Decompose -> GitHub Issue Mirror (Authority Split)

**Story Points:** 4

## Spec Reference

- PRD §6, §7; FR-MG-3, FR-CP-3
- Phase exit gate: PRD §13 Phase 1 clause 3

## User Story

As a QDS factory operator,
I want Seeds decomposition to persist stories locally and mirror them as GitHub sub-issues,
so that decomposition authority lives in Seeds while assignment/execution authority lives in SwarmClaw, with no duplication.

## Overview

When the Dev Manager receives a decompose request, it invokes Seeds to generate story decomposition. Seeds persists stories to `.seeds/issues.jsonl` as the authoritative source for story definitions, dependencies, and acceptance criteria. A one-directional mirror then writes each story as a GitHub sub-issue via `gh issue create` with a `seeds-mirror` label. SwarmClaw owns assignment and execution tracking; Seeds owns decomposition structure. The mirror is read-only from GitHub's perspective: edits to GitHub issues do not flow back to Seeds.

P1.3 consumes `/api/a2a` as an additive dependency on P1.1 (dev-order: P1.1 must land the route before P1.3's mirror decompose call can succeed end-to-end).

## E2E Slice

**Demonstrable behavior:** Given an intake issue exists, a decompose A2A call produces: (1) `.seeds/issues.jsonl` appended with N story entries (each with id, title, dependencies, acceptance criteria), (2) N GitHub sub-issues created under the parent intake issue, each labeled `seeds-mirror`, (3) the response contains counts and mappings. No dependency or assignment data is duplicated in GitHub beyond a reference.

**Wiring closed:** On completion of this story, a decompose call yields Seeds-persisted stories and GitHub-mirrored sub-issues with a strict one-directional flow, using only code merged by this story. No stub, no `TODO: wire later`, and no sibling story is required to make this behavior real.

**Dependency edges (predecessors):** P1.2 (intake creates GitHub issue), P0.9 (Hindsight memory banks operational).

## Acceptance Criteria

1. **(make-or-break)** Given an intake session exists with a parent GitHub issue, When `a2a.delegate({ targetAgentId: "qds-seeds", params: { task: "decompose", sessionId: "{id}" } })`, Then `.seeds/issues.jsonl` is appended with >= 1 story entry and each story has a corresponding GitHub sub-issue linked to the parent issue.
2. Given Seeds stories are persisted, When the mirror runs, Then each GitHub sub-issue contains the Seeds story ID in its body, title matches the Seeds story title, and label `seeds-mirror` is applied. Dependency edges are stored ONLY in `.seeds/issues.jsonl`, not in GitHub metadata. Dependency edges are also persisted to the Hindsight `resolveBankId(repoSlug)` memory bank so that cross-environment and multi-worktree consumers can query the dependency graph without requiring access to the local `.seeds/` file.
3. Given a GitHub sub-issue is edited by a user, When the next decompose call runs, Then the Seeds entries are NOT overwritten by GitHub content (Seeds is authoritative; mirror is one-directional).
4. Given a valid A2A delegate request with `targetAgentId: "qds-seeds"` and `params.task: "decompose"`, Then the Seeds agent receives the request via P1.1's routing and returns decomposition results with `{ seedsCount, mirroredCount, mappings }`.
5. Given a decomposed story containing a bash code block with `rm -rf /`, the sanitized output replaces the code block with `[code block removed: bash]` and preserves all prose content.
6. Given a decomposed story with no executable content, the sanitized output is identical to the input (passthrough).
7. Given a decompose request that would produce > 20 stories, When Seeds processes the request, Then exactly 20 stories are persisted and the response includes `{ truncated: true, generatedCount: N, persistedCount: 20 }`.

## Technical Notes

- **Contracts/Schema:** Seeds story entry: `{ id: string (seeds-{uuid_v5} — deterministically derived from `{sessionId, storyIndex}` per the Guards/limits section; the literal `seeds-{uuid}` v4 spelling is replaced by v5 deterministic derivation to make decompose idempotent at the storage layer), title: string, description: string (max 2000 characters — longer descriptions are truncated with `[truncated, N chars total]` suffix, matching P1.6's convention), dependencies: string[], acceptanceCriteria: string[] (min 1 item — empty arrays rejected with 400), storyPoints: number (z.number().int().min(1).max(8) — matching the DoD constraint), mirroredIssueNumber: null (always written as `null` and never updated — mirror outcomes live in the append-only `.seeds/mirror-index.jsonl`, see Guards/limits P1.3-R2-3; the field is kept so the JSONL entry and the `mappings` response share one shape), contentHash: string (SHA-256 hex over the canonical JSON of `{title, description, dependencies, acceptanceCriteria, storyPoints}` **as those fields exist after the full egress pipeline — redact → sanitize → canonicalize → hash**, i.e. the exact values persisted; the retry-divergence guard defined in Guards/limits) }`. Stored as JSONL (one JSON object per line) in `.seeds/issues.jsonl`. GitHub sub-issue body: `Seeds ID: {id}\n\n{description}`. Mirror response: `{ seedsCount: number, mirroredCount: number, mappings: Array<{ seedsId: string, mirroredIssueNumber: number | null }>, truncated?: boolean, generatedCount?: number, persistedCount?: number, dependenciesPersisted?: boolean, failures?: Array<{ seedsId: string | null, storyIndex: number, error: string }> }`. `mirroredCount` counts only successfully created GitHub issues (mappings entries where `mirroredIssueNumber` is not null). Failed mirrors appear in `mappings` with `mirroredIssueNumber: null` and in `failures`. `dependenciesPersisted: boolean` (resolves P1.3-M4) is `true` iff every dependency edge was successfully retained to the Hindsight `resolveBankId(repoSlug)` bank; `false` indicates a Hindsight persistence failure (the handler surfaces the failure in logs and the response — **no silent Hindsight failure** — and the caller may retry; gate clause 7 / OQ-4 still applies to the live-Hindsight AC). When the GitHub mirror repository truncates content (e.g., large stories), `mirroredCount` reflects the actual number of stories written, not the requested count. Callers should compare `mirroredCount` to the input count to detect truncation. Two truncation scenarios: (a) >20 stories produced by decomposition → `truncated: true`, compare `persistedCount` to `generatedCount`; (b) GitHub API truncation → compare `mirroredCount` to `seedsCount`. These are independent — both can occur simultaneously.
- **Integration points:** Seeds decomposition module (generates stories), `.seeds/issues.jsonl` (persistence), `gh issue create --repo "{repoSlug}"` (mirror — always repo-pinned, see P1.3-R4-1 in Guards/limits), GitHub parent issue (link via `--body` reference or sub-issue API). The GitHub mirror feature requires the `gh` CLI to be installed and authenticated. If `gh` is not available, mirror operations fail with error code -32018. The Seeds service should check `gh` availability at startup and log a warning if it is missing. Each `gh issue create` invocation has a 30-second timeout. If GitHub API responds with 429 (rate limiting), the mirror pauses for the indicated retry-after duration (max 60s) before retrying once. Total mirror phase timeout: 5 minutes. Failures beyond this are logged and the mirror phase reports partial failure. Hindsight `resolveBankId(repoSlug)` memory bank (store decomposition summary AND dependency edges for recall — dependency edges are written to Hindsight alongside `.seeds/issues.jsonl` to ensure cross-environment availability; `.seeds/issues.jsonl` remains the authoritative local source but Hindsight serves as the shared query layer).
- **Bank ID resolution (P1.3-R2-1):** the `repoSlug` passed to `resolveBankId()` (defined in P0.9, `src/hindsight/schemas.ts:45`) is the **request's** repository, NOT a process-global. The Seeds handler resolves it once, at the top of the decompose call, in this precedence: (1) `params.repo` when the caller supplied it, else (2) the session record's repository (the same resolution the A2A Dispatch Contract above specifies for an omitted `repo`). `process.env.REPO_SLUG` is NOT consulted — a factory process may serve multiple repositories in one lifetime, and reading the env var would persist stories and dependency edges into whichever bank the process happened to start with. The resolved `repoSlug` is threaded explicitly through the JSONL write, the mirror phase, and every Hindsight retain in the call, so all three agree on one bank. If neither source yields a repository, the call is rejected with `-32602` before any write. The literal `{repo}` placeholder is never used at runtime — all bank references resolve through `resolveBankId(repoSlug)`.
- **JSONL write atomicity (P1.3-R2-2):** Stories are buffered in memory and written as a single append per batch. A plain `write()` append is **not** all-or-nothing — a short write, a crash, or a full disk can leave a partial line in `.seeds/issues.jsonl` — so "rollback" here is a concrete recovery step, not a property of `append`:
  1. Before the append, and while holding the session lock (see Concurrent single-flight below), record `preAppendOffset` = the current file size (`fstat().size`).
  2. Write the whole batch, then `fsync` the descriptor.
  3. If the write or the `fsync` fails, `ftruncate(fd, preAppendOffset)` and `fsync` again **before releasing the lock**. This restores the file to its exact pre-batch bytes; the partial line cannot survive.
  Because truncation happens under the same lock that serialises the append, no reader or concurrent decompose observes the partial batch. Batch rollback is therefore all-or-nothing at the file level: `seedsCount` is `0` for a rolled-back batch and every story in it is reported in `failures`. **Crash recovery (the lock cannot cover a process death):** if the process dies between step 2 and step 3 the partial line persists, so readers of `.seeds/issues.jsonl` (and every `.seeds/seeds-archive-*.jsonl`) MUST tolerate a trailing unparseable line — skip it, log it, and treat the preceding lines as the valid history; the next append under the lock truncates to the last newline before writing. JSONL write failure returns -32000 (Internal error) with the response including `failures` array. This is unexpected and not given its own code. (ponytail: offset+truncate under the existing session lock rather than temp-file+rename — the lock is already required for single-flight, so this adds no new synchronisation. Temp-file + atomic rename is the upgrade path if `.seeds/issues.jsonl` ever needs concurrent multi-process writers.)
- **Files / functions touched:** Seeds decomposition handler, `.seeds/issues.jsonl` writer, GitHub mirror service, decompose A2A handler, decompose validation schema.
- **Sub-issue linking strategy:** Sub-issue linking uses `gh issue create` with body-reference links (not the native GitHub Sub-Issues API). The `issues:write` scope is sufficient for this approach. Each story issue includes a body reference to the parent issue (e.g., `Parent: #N`). Native sub-issue API integration is a Phase 2 enhancement.
- **GitHub issue body cap (P1.3-L2):** GitHub Issues enforce a hard **65,536-character** limit on issue bodies (titles are capped at 256 chars). The Seeds schema's 2,000-char `description` cap means a single story body (`Seeds ID: {id}\n\n{description}`) is well under the limit, but mirror operations that concatenate multiple stories into a single issue body (not the default per-story flow but an option for Phase 2 batched mirrors) MUST truncate to 65,536 chars before the `gh issue create` call. `gh` returns a non-obvious validation error on overflow; the mirror service pre-truncates and emits a log line `{ issueBodyTruncated: true, originalLen, truncatedLen: 65536 }` so callers can detect the cut. **P1.3-N3 (measurement reference):** the 65,536 cap is measured on **POST-redaction** text — i.e., the `originalLen` in the truncation log equals the redacted length (after `redactSecrets` + `redactBoundaryPrefix` + Sanitization Contract), not the raw story text. Redaction typically shrinks the body, but Sanitization Contract replacements (`[code block removed: {lang}]`, `[inline code sanitized]`) can grow it relative to the original; measure after both passes, not before.
- **Guards/limits:** Maximum 20 stories per decomposition. **Idempotency at the storage layer (resolves P1.3-M2):** the Seeds story id is derived **deterministically** from the decompose inputs as `seeds-{uuid_v5(namespace, "${sessionId}:${storyIndex}")}`, where `storyIndex` is the 0-based position of the story in the decompose output and `sessionId` is the intake session being decomposed. A client retry with the same `sessionId` reproduces the same set of `seeds-*` ids; the JSONL writer appends only ids that are not already present in `.seeds/issues.jsonl` (or any `.seeds/seeds-archive-*.jsonl`), so retries are deduplicated at the storage boundary instead of relying on caller cooperation. **Content fingerprint (guards the position-derived id):** because the id is derived from `{sessionId, storyIndex}` alone, a retry whose decomposition reordered or rewrote the stories would otherwise reuse an id for different content. Each JSONL entry therefore also persists `contentHash: string` = SHA-256 over the canonical JSON of `{title, description, dependencies, acceptanceCriteria, storyPoints}`. **Hash position in the pipeline (P1.3-R3-1):** the hash is computed at the END of the mandatory egress pipeline — `redactSecrets` + `redactBoundaryPrefix` (INV-3) → Sanitization Contract → canonical JSON → SHA-256 — so it covers the exact bytes written to `.seeds/issues.jsonl` and sent to GitHub/Hindsight. An earlier draft said only "post-sanitization", which left redaction's position ambiguous; hashing pre-redaction text would make a byte-identical retry hash differently whenever an unrelated `process.env` secret rotated (a redacted span changes width), turning an idempotent retry into a false `-32022`. Both the append-time hash and the comparison hash on retry MUST run the same pipeline in the same order. On append, an incoming story whose id already exists is dropped ONLY when its `contentHash` matches the stored one; a mismatch is a hard error (`-32022`, Decompose content mismatch) listing the conflicting ids in `failures[]` — never a silent drop and never an overwrite (the append-only contract forbids mutation). Identical retries therefore stay stable and idempotent; divergent retries fail loudly. This realises the "no duplication at the authority boundary" goal without contradicting the append-only contract: duplicate writes are silently dropped (idempotent) and the response `seedsCount` reflects the count of newly-appended stories (0 on a pure retry). GitHub mirror is skipped for ids whose derived mirror status (last record in `.seeds/mirror-index.jsonl`, per P1.3-R2-3) already carries a non-null `mirroredIssueNumber` — the story entry's own field is always `null` and is never the source for this check. The previous "dedup is caller's job" posture is retracted.
  - **UUID v5 namespace (P1.3-N1):** `namespace` = factory-pinned constant exported from `src/seeds/schema.ts` (e.g. `SEEDS_ID_NAMESPACE`); cross-deployment reproducibility requires the same constant value across environments. Two deployments with different namespace constants produce different `seeds-*` id sets for the same inputs — the constant MUST be pinned at the factory level, not generated per-run.
- **Concurrent single-flight (P1.3-M1):** To prevent two concurrent decompose calls for the same `sessionId` from racing the JSONL append, the Seeds handler acquires a **session-scoped** advisory lock at `~/.seeds/decompose-{sessionId}.lock` (pattern mirrors P0.9 INV-HM6's `~/.hindsight/provision.lock`, but keyed per session so unrelated sessions never contend). The lock path MUST be derived from a sanitized `sessionId` (reject any `sessionId` containing `/`, `..`, or a path separator with `-32602` before the lock is opened — the id becomes a filename). Lock is held for the duration of the parse→JSONL-append→mirror phase and released in a `finally`. If the lock for THAT session is already held, the second caller receives `-32021` (Decompose in progress — retry after backoff); concurrent decomposes for *different* sessions proceed in parallel and MUST NOT see `-32021`. The lock file is best-effort (`O_EXCL` create + PID payload; stale lock detection by PID liveness check); it is advisory and does not replace the storage-layer idempotency above. (ponytail: per-session file locks are process-local — sufficient while Seeds is single-host; a shared lock service is only needed if Seeds goes multi-host.)
- Each story title <= 280 chars. `.seeds/issues.jsonl` is append-only; no in-place mutation of existing entries (idempotent dedup uses read-before-append, not mutation). Mirror is best-effort: if GitHub API fails for one sub-issue, remaining sub-issues still created; failed mirrors logged with `mirroredIssueNumber: null`.
  - **Mirror status is append-only too (P1.3-R2-3).** An earlier draft said `mirroredIssueNumber` starts `null` in the story entry and is "set to the GitHub issue number after successful mirror" — that is an in-place update of a persisted record and directly contradicts the append-only contract on the line above. It is retracted. The story entry's `mirroredIssueNumber` is written **once, as `null`, and never touched again**; it is retained in the schema only so the entry and the `mappings` response share one shape. Mirror outcomes are recorded as separate append-only lines in a sibling file, `.seeds/mirror-index.jsonl`, one per mirror attempt: `{ seedsId: string, mirroredIssueNumber: number | null, attemptedAt: ISO8601, sessionId: string, error?: string }` (`mirroredIssueNumber: null` + `error` for a failed attempt). Same durability rules as `.seeds/issues.jsonl`: append-only, `chmod 0600`, `.gitignore`d, written under the session lock with the offset+truncate recovery above, archived to `.seeds/mirror-index-archive-YYYY-MM-DD.jsonl` at 10 MB.
  - **How readers derive current mirror status.** For a given `seedsId`, scan the mirror-index files in the **defined traversal order below** and take the **last-written record for that `seedsId`** (within one file, line order is append order, so the later line wins; ties within a file cannot occur because appends are serialised by the lock). A `seedsId` with no record has never been mirrored. The `mirroredIssueNumber` in the decompose response `mappings` is this derived value, not the story entry's field — so the response shape is unchanged for callers.
  - **Traversal order across active and archived files (P1.3-R3-3).** Glob order is not append order, so "last record wins" is only well-defined once the file sequence is pinned. Readers MUST traverse: (1) every `.seeds/mirror-index-archive-YYYY-MM-DD.jsonl` in **ascending lexicographic filename order** — which, because the suffix is a zero-padded ISO date, is ascending chronological order — then (2) the active `.seeds/mirror-index.jsonl` **last**. This is globally append-ordered because rotation only ever moves whole older records out of the active file into that day's archive, and same-day re-archival appends to the existing archive rather than overwriting it; therefore every archived record predates every record currently in the active file. Records for a `seedsId` are compared in that concatenated order and the final one wins — never by `attemptedAt`, which is a wall-clock field and not monotonic across clock adjustments. The same ordering rule applies to `.seeds/seeds-archive-*.jsonl` when reconstructing story history.
  - **Mirror create is idempotent across crash and unknown-response windows (P1.3-R3-2).** `gh issue create` is non-idempotent, and the mirror-index append is a *separate* step: if the process dies after GitHub accepts the create but before the record lands — or the 30-second timeout expires leaving the outcome unknown — a naive retry would create a duplicate issue. The mirror therefore uses the Seeds ID already embedded in the issue body as its reconciliation marker rather than a new mechanism. Before every create, and again after any create whose outcome is unknown (timeout, non-2xx with no parsed issue number, transport error), the mirror service runs a **marker search**: `gh issue list --repo "{repoSlug}" --label seeds-mirror --state all --search "\"Seeds ID: {seedsId}\" in:body" --json number`. **`--repo` is mandatory here and on the create (P1.3-R4-1):** per the Bank ID resolution rule above, the target repository is the *request's*, which need not be the one `gh` infers from its working directory. An unpinned search would query the CLI's default repo, miss the marker for a request targeting any other repo, and create the duplicate this mechanism exists to prevent — so both `gh issue list` and `gh issue create` take `--repo "{repoSlug}"` using the same resolved slug threaded through the JSONL write and the Hindsight retains. A hit means the issue already exists — the mirror skips the create, appends a mirror-index record carrying the found `number` (so the durable status catches up with GitHub), and reports it as mirrored. No hit means the create never landed and may be safely re-issued. Because the marker lives in GitHub itself, this is correct even when the crash destroyed all local state for that attempt. Ordering is therefore: **marker search → create (only if no hit) → append mirror-index record**, with the search repeated on any indeterminate create. (ponytail: reuses the `Seeds ID: {id}` body marker and `seeds-mirror` label the mirror already writes — no pending/final two-phase status protocol, which would need its own crash-recovery sweep. A durable pending record is the upgrade path only if GitHub search indexing latency proves too slow to be read-your-writes for this flow.)
  - `.seeds/issues.jsonl` size is monitored but not enforced in Phase 1. Operational note: JSONL files exceeding 10 MB should be archived to `.seeds/seeds-archive-YYYY-MM-DD.jsonl` (using the archive date) and a fresh file started; readers querying local story definitions (e.g., SwarmClaw, Seeds handler) must traverse the active `.seeds/issues.jsonl` and any `.seeds/seeds-archive-*.jsonl` files (glob-matched) for complete history. Compaction is a Phase 2 concern — Phase 1 documents the append-only contract and the 10 MB operational threshold. No automatic rotation in this story. The JSONL file is written by a single process (the Seeds decomposer); the advisory lock above is the explicit enforcement. Concurrent writes to the same file are not supported. The 10 MB archival threshold check and rename are not atomic — the decomposer holds the advisory lock during archival. If an archive file for the current date already exists, the new events are appended to the existing archive (not overwritten). Archive filename format: `seeds-archive-YYYY-MM-DD.jsonl`. Append behavior ensures no data loss from multiple archival events on the same day. Archive files matching `seeds-archive-*.jsonl` are only created by the Seeds decomposer. The glob pattern assumes no other process writes matching files to `.seeds/`.

## Security Invariants

- INV-1: Seeds story content sanitized before GitHub mirror and Hindsight storage (see Sanitization Contract below).
- INV-2: `.seeds/issues.jsonl` is `.gitignore`d (not tracked in version control) and written with file permissions 0600 at runtime via `fs.chmod` after every write batch. File permissions are verified and enforced at the start of each batch, regardless of whether the file was created by this process or pre-exists from a prior run. This ensures that a pre-existing file with loose permissions (e.g., created by another process or manually) is immediately corrected. No world-readable factory data. Git does not preserve restrictive permissions — the file must be excluded from tracking to enforce this invariant.
- INV-3: Mirror operation uses a dedicated GitHub token scoped to `issues:write` on the target repo only; no broader repo permissions. Because the mirror publishes to GitHub (an **external** surface — the highest-leak channel in the factory), all story text is run through `redactSecrets(storyText, process.env)` and `redactBoundaryPrefix` (canonical helpers at `cli-anything/src/runner.ts:178` and `cli-anything/src/runner.ts:244` — P1.3-V1 line citation corrected from `:223` to `:244` after symbol moved; longest-first matching, KMP scan, boundary-prefix leak protection, re-cap on redacted spans) before being sent to the GitHub API, before Hindsight retain, **and before the `.seeds/issues.jsonl` append** — local disk is not exempt. The pipeline runs ONCE, up front, and the redacted values are what every downstream consumer receives: the JSONL writer, the mirror, and the Hindsight retain all serialize the same already-redacted story objects, so a secret can never reach disk merely because the external egress path happened to sanitize later. This is the same ordering the `contentHash` rule (P1.3-R3-1) depends on — the hash is taken at the end of this pipeline over the exact bytes persisted, which is only coherent if persistence consumes the post-redaction text. Redaction is applied to `description`, `title`, and each entry of `acceptanceCriteria`. Sanitization Contract (deny-by-default code-block strip) runs after secret redaction in the same pipeline; both are mandatory pre-egress gates. The Seeds implementation MUST reuse `redactSecrets` / `redactBoundaryPrefix` verbatim — no bespoke secret scrubbing.

## Sanitization Contract

Decomposed story output is sanitized before Hindsight storage and GitHub issue creation. The posture is **deny-by-default**: only an explicit safe set of language tags is permitted in fenced code blocks; all others are stripped.

1. **Fenced code blocks — deny-by-default**: Fenced code blocks with language tags not in the explicit safe set (`typescript`, `json`, `yaml`, `mermaid`, `sql`, `graphql`, `css`, `html`, `xml`, `diff`, `plaintext`) are stripped and replaced with `[code block removed: {language}]`. The safe set is configurable via the environment variable `SEEDS_SANITIZATION_SAFE_LANGUAGES` (comma-separated; default: `typescript,json,yaml,mermaid,sql,graphql,css,html,xml,diff,plaintext`). All other language tags (including `shell`, `bash`, `powershell`, `ruby`, `perl`, `python`, `php`, `lua`, `sh`, `exec`, `go`, `java`, `c`, `cpp`, `rust`, etc.) are stripped to prevent code injection through story content. Preserve the fence markers and language tag for traceability.
2. **Inline shell constructs**: Strip inline code (single-backtick spans) containing path traversal patterns (`..`, `~`), shell operators (`&&`, `||`, `;`, `$()`, backticks), parameter expansion (`${}`), pipes (`|`), newline injection (`\n`, `\r`), heredoc markers (`<<`, `<<<`), redirect operators (`>`, `<`, `>>`, `<<<`), and network URLs in code context. Replace with `[inline code sanitized]`. The inline code strip list is deny-by-default for shell metacharacters. Any inline code containing characters that could influence shell execution is stripped.
3. **HTML injection**: Strip HTML `<script>`, `<iframe>`, `<object>`, `<embed>` tags and their contents. Replace with `[html tag removed: {tag}]`. Rule 3 applies to all prose content. Fenced code blocks in the safe set (including `html`) are preserved verbatim — the consumer's rendering pipeline is responsible for sanitizing HTML code block content. For GitHub Issues rendering, fenced HTML blocks are not executed. Consumers in other contexts (e.g., custom dashboards) must sanitize before rendering.
4. **Preserve safe content**: Non-executable markdown (headers, lists, prose, mermaid diagrams, tables) and code blocks in the safe set are preserved verbatim. Mermaid `click` directives are preserved as an accepted risk. The safe set includes `mermaid` because mermaid diagrams are critical for architecture visualization. Consumers must sanitize `click` directives if rendering in a non-GitHub context.
5. **Passthrough for clean input**: Given a decomposed story with no executable content, the sanitized output is identical to the input.

## Dependency Edge Schema

Each dependency in the `dependencies[]` array of a Seeds story is persisted as a separate Hindsight entry in the `resolveBankId(repoSlug)` memory bank using the following schema:

```typescript
const DependencyEdgeSchema = z.object({
  // Deterministic idempotency key — see "Idempotent edge persistence" below.
  edgeId: z.string().regex(/^seedsdep-[0-9a-f-]+$/),
  sourceStoryId: z.string().regex(/^seeds-[0-9a-f-]+$/),
  targetStoryId: z.string().regex(/^seeds-[0-9a-f-]+$/),
  dependencyType: z.enum(["blocks", "depends_on", "related_to", "parallel_with"]),
  sessionId: z.string(),
  createdAt: z.string().datetime(),
});
```

AC2's reference to Hindsight storage of dependency edges is satisfied by this schema. Each dependency edge is retained as a memory whose content carries `edgeId`, `sourceStoryId`, `targetStoryId`, `dependencyType`, and `sessionId`, so those fields are recoverable from the bank. Retrieval is via `HindsightClient.recall` (`src/hindsight/client.ts`) — a **semantic query with a result limit**, not an exact-key index; exact-key lookup is not part of the Phase-1 client surface.

**Idempotent edge persistence (P1.3-R5-1).** The response contract invites a retry after `dependenciesPersisted: false`, but that flag is all-or-nothing over a *set* of retains: a run that persisted 7 of 10 edges and then lost Hindsight reports `false`, and the caller's retry re-sends all 10. Without a stable identity the 7 already-stored edges are appended a second time, so the bank silently accumulates duplicate edges and the dependency graph over-counts. The schema therefore carries a deterministic `edgeId`:

```ts
edgeId = `seedsdep-${uuid_v5(SEEDS_ID_NAMESPACE, `${repoSlug}:${sourceStoryId}:${targetStoryId}:${dependencyType}`)}`
```

- **Namespace** is the same factory-pinned `SEEDS_ID_NAMESPACE` constant the story ids use (`src/seeds/schema.ts`, P1.3-N1) — one pinned constant, so the same edge derives the same id in every environment.
- **Key components are the stable endpoints plus the repository context.** `repoSlug` is included because bank identity is request-scoped (P1.3-R2-1) and the same story-id pair must not collide across repos. `sessionId` and `createdAt` are deliberately **excluded** — they are per-attempt values, and including either would make every retry mint a fresh id, defeating the whole guard.
- **The write is recall-then-retain, NOT an atomic upsert — the Hindsight API has no upsert.** `HindsightClient` (`src/hindsight/client.ts`) exposes `retain` (append) and `recall` (semantic query) only; there is no conditional write, no update-by-key, and no `edgeId` parameter. This story therefore MUST NOT claim upsert-on-`edgeId` semantics. What it specifies is: before retaining, the handler recalls the `resolveBankId(repoSlug)` bank for each edge's `edgeId` (which is embedded verbatim in the retained content, so it is matchable), and skips edges already found. Only edges not found are written.
- **The guarantee is best-effort duplicate REDUCTION — not idempotency, not even for sequential retries (P1.3-R7-1).** Two independent reasons, and the second is the one that bites: (a) recall-then-retain is a check-then-act pair, so two *concurrent* decomposes of the same repo can both miss and both write; and (b) **`recall` is a relevance-ranked, result-limited semantic query, not an exact-key lookup** (`RecallPayloadSchema.limit` 1..50, `src/hindsight/schemas.ts:80`). An edge that IS in the bank can simply fall outside the returned set — ranked below other matches, or past the limit — so even a strictly sequential retry can fail to see it and append a duplicate. An earlier draft here claimed sequential convergence; that claim assumed an exact-key search the client does not offer, and is retracted. What holds is only: **a recall hit reliably suppresses the append.** A recall miss proves nothing.
- **`edgeId` is therefore a reconciliation key, not a write guard.** Its value is that any duplicate which does slip through is deterministically detectable and collapsible by `edgeId` in a later consolidation pass — the property that makes this recoverable rather than silently corrupting. Exactly-one-record is deferred to a Hindsight exact-key/metadata filter or a conditional-write primitive (P1.3-OQ-6); until one exists, no story may assert it.
- **`dependenciesPersisted` semantics are unchanged:** still `true` iff every edge in the call is present in the bank at the end of the call, `false` on any Hindsight failure — and it remains the partial-failure signal. Retrying on a `false` is still the right action — it is how missing edges get written — but per P1.3-R7-1 it is **not** a safe-because-idempotent retry: it reduces duplicates rather than avoiding them, and any that slip through are collapsed later by `edgeId`. The retry is worth doing because a missing edge is worse than a duplicate one, not because the write is idempotent.
- **Open question (P1.3-OQ-6):** true idempotent persistence — and dedup under concurrent decomposes — needs exact-key lookup or a conditional write in Hindsight. Neither exists in the Phase-1 client surface. This story does not add one; concurrency-safe edge dedup is deferred until Hindsight offers the primitive.

> Dependency edges are stored as JSONL entries. Querying by dependency type requires full scan and filter. For Phase 2, consider adding metadata tags or an index for common query patterns (e.g., `blocks`, `depends_on`).

> `parallel_with` indicates stories that are explicitly safe to run concurrently (no shared state or dependencies).

## Decompose Error Code Taxonomy

- `-32600`: Invalid Request — malformed JSON-RPC envelope
- `-32602`: Invalid params — missing/invalid sessionId, decompose payload
- `-32000`: Internal error — unexpected decomposition failure
- `-32014`: Session not found — sessionId does not exist
- `-32015`: Session not in intake status — decompose requires intake status
- `-32016`: Decomposition failed — no stories generated (empty result)
- `-32017`: Mirror failure (partial) — at least one but not all GitHub issues failed to create. Response `failures[]` lists the failing stories; remaining stories were mirrored successfully.
- `-32019`: Mirror failure (total) — all GitHub issues in the batch failed to create. Response `failures[]` lists every story; `mirroredCount: 0`.
- `-32018`: CLI unavailable — gh CLI not found or not authenticated.
- `-32020`: Payload too large — **client-side classification only; never a wire code (P1.3-R2-4).** The A2A POST body exceeded SwarmClaw's `MAX_BODY_BYTES` cap (1,048,576 bytes / 1 MB; `src/swarmclaw/index.ts:135`). SwarmClaw drains the body and responds **HTTP 413 with the non-JSON-RPC body `{ error: "payload too large" }` and `Connection: close`, before the Seeds handler is dispatched** (`src/swarmclaw/index.ts:70-81`). The Seeds handler therefore never runs and **cannot emit `-32020` on the wire** — an earlier draft implied callers would receive it as a JSON-RPC error, which is not reachable and is retracted. **HTTP 413 is the sole wire-level result.** `-32020` is the code the *client library* assigns locally when it translates that 413 into the caller-facing error, so that callers see one uniform JSON-RPC-shaped error surface; P1.1 defines no transport-layer 413→JSON-RPC mapping and this story does not add one. Client-side strategy: Seeds clients (the Dev Manager) MUST summarise intake context (e.g., truncate long issue bodies, drop attachment content) before A2A dispatch so the decompose payload stays well under 1 MB; on a 413 the client surfaces a retryable error with the message "decompose payload exceeds A2A cap — summarise intake context before retrying". **Ownership (P1.3-R3-4):** that translation is owned by THIS story and lives in `src/dev-manager/handlers/decompose.ts` (already in Files to Modify — it is the Dev Manager's Seeds client, the sole caller that issues the A2A decompose POST). It is not deferred to P1.1 and not owned by any sibling story: P1.1 provides the transport and deliberately defines no 413→JSON-RPC mapping, so if this story does not add the mapping, callers receive a raw HTTP 413. The DoD's 413 body-cap test asserts both halves — SwarmClaw's wire-level 413 and this handler's local `-32020` classification.
- `-32021`: Decompose in progress — the session-scoped advisory lock at `~/.seeds/decompose-{sessionId}.lock` is already held for the requested `sessionId`. Caller should back off and retry. A lock held for a *different* sessionId never produces this code.
- `-32022`: Decompose content mismatch — a retry reused an existing `{sessionId, storyIndex}` id but produced different story content (fingerprint mismatch, see Guards/limits). Response `failures[]` names the conflicting ids.

> Error codes `-32014` through `-32022` are Seeds-specific. Standard JSON-RPC codes apply for protocol errors. A2A-level errors (`-32010` through `-32013`) from P1.1 may propagate if delegation fails. The original `-32014..-32018` range (P0.9-confirmed) is preserved unchanged; `-32019`/`-32020`/`-32021`/`-32022` extend the range for the partial-mirror split (-32017 was split into partial=-32017 + total=-32019), the SwarmClaw body-cap path, the single-flight lock, and the retry content-fingerprint mismatch respectively — none collide with P0.9's hardened bridge codes.

## Observability Contract

- Every decompose operation logs: `{ requestId, operation, sessionId, timestamp, duration, status }`
- **requestId propagation (CC-9):** `requestId` is read from the canonical `x-request-id` HTTP header on the inbound `/api/a2a` request (UUID v4 strict, validated by `src/swarmclaw/index.ts:42-46`). Seeds echoes the same value into the A2A response envelope at `result.requestId` and into the top-level envelope `id` (both populated by P1.1's envelope helper — these are the two canonical response fields per P1.1's Transport Contract; `_meta.requestId` belongs to P0.7's MCP `tools/call` payload (`src/swarmclaw/mcp/tool-bridge.ts:397`) and is NOT part of the A2A envelope). Every log line emitted by the Seeds handler — parse, JSONL write, mirror phase, Hindsight retain — carries the propagated `requestId` so the decompose operation joins end-to-end with P1.1's A2A trace.
- Errors include: `{ code, message, stack?: string }`
- Decompose timing: `parse_ms`, `story_count`, `mirror_latency_ms`, `jsonl_write_ms`
- Mirror partial failures logged per-issue: `{ issueIndex, githubStatus, error }`
