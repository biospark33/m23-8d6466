# P1.6: Pi-Team Implement via CLI-Anything Warren Harness + Captures Structured JSON

**Story Points:** 4

## Spec Reference

- PRD §8, §10; FR-OR-3, FR-EX-6
- Phase exit gate: PRD §13 Phase 1 clause 6

## User Story

As a QDS factory operator,
I want the protocol dispatch_task step to invoke Pi teams via the CLI-Anything Warren harness and capture structured JSON output,
so that the factory pipeline produces machine-readable results from real agent execution.

## Overview

When the qds-factory protocol reaches a dispatch_task phase, SwarmClaw invokes the CLI-Anything harness, which translates the task into a `warren run` command. Warren executes the Pi team inside a burrow, with Mulch-primed context and pi-lens gating. The Pi team produces structured JSON output (exitStatus, changedFiles, test results, summary). This output is captured by the CLI-Anything harness and returned to SwarmClaw as the step result. The wiring covers: protocol step -> harness invocation -> Warren execution -> structured JSON capture -> step output.

## E2E Slice

**Demonstrable behavior:** Given an active qds-factory protocol session, When the dispatch_task step executes, it invokes CLI-Anything harness -> `warren run <agent> <project> -p "<prompt>"` (CC-13 canonical; no `--config` flag) with Mulch-primed Pi team -> Pi agents execute a sample task (e.g., "create a hello-world function") -> structured JSON `{ exitStatus: "success", changedFiles: ["src/hello.ts"], testResults: { passed: 1, failed: 0 }, summary: "...", durationMs: 4200, mulchPrimed: true, artifacts: [] }` is captured as the protocol step output.

**Wiring closed:** On completion of this story, a dispatch_task protocol step yields a single demonstrable Pi team result in structured JSON, using only code merged by this story. No stub, no `TODO: wire later`, and no sibling story is required to make this behavior real.

## Acceptance Criteria

1. **(make-or-break)** Given an active protocol session with a dispatch_task step, When the step executes, Then the CLI-Anything harness is invoked with the task payload and invokes `warren run <agent> <project> -p "<prompt>"` (CC-13 canonical surface — no `--config` flag; team/task params carried in the agent-team extension config the harness materializes into the run workspace), and the step output is structured JSON containing `{ exitStatus: "success"|"transient"|"overflow"|"logic"|"lead_failure", changedFiles: string[], testResults: { passed: number, failed: number }, summary: string, durationMs: number, mulchPrimed: boolean, mulchPrimeError?: string, artifacts: Array<{ name: string, path: string }> }`. The canonical exitStatus enum is 5-value (CC-1): `lead_failure` = harness-classified (lead process exits before merged-JSON emit; `exitCode` reflects lead process exit, not a warren exit code).
2. Given the Pi team completes successfully, When the structured JSON is captured, Then it is stored as the protocol step output and retrievable via the SwarmClaw session status API.
3. Given `warren run` exits with non-zero code, times out, or the lead process exits before merged-JSON emit, When the harness captures the failure, Then the step output is `{ exitStatus: "transient"|"overflow"|"logic"|"lead_failure", error: string, exitCode: number | null, partialOutput: string | null, durationMs: number, mulchPrimed: boolean, mulchPrimeError?: string }` and the protocol engine does not crash. When Warren is killed by a signal, `exitCode` is `null`. `lead_failure` is harness-classified: emitted when the lead process exits **under its own control** before merged-JSON emit, in which case `exitCode` reflects the lead process exit, not a warren exit code. A lead the harness itself killed (RSS watchdog, `userCancel`) is classified by signal origin — `overflow`/`logic` — not `lead_failure`; see the precedence rule in Technical Notes. Consumers must handle `null` exitCode alongside the 5-value exitStatus enum.
4. Given a fresh repository with no prior Mulch expertise in the specified Hindsight bank, When the dispatch_task step executes with Mulch priming, Then the Pi team runs without primed context (empty context is acceptable), the step output includes `mulchPrimed: false`, and execution succeeds with `exitStatus: "success"` — empty bank is not an error condition.

## Technical Notes

- **exitStatus taxonomy (CC-1, aligned with P0.3):** Previous `status: 'failure'` maps to `exitStatus: 'transient'|'overflow'|'logic'|'lead_failure'`. Consumers must handle all four failure modes. This aligns with P0.3's canonical 5-value taxonomy. `"success"` = normal completion. `"transient"` = retryable failure (network, timeout). `"overflow"` = resource limit exceeded. `"logic"` = task logic error. `"lead_failure"` = harness-classified (lead process exits under its own control before merged-JSON emit — a harness-initiated kill maps to `overflow`/`logic` instead; `exitCode` reflects lead process exit, not a warren exit code). P0.3 previously used `exitStatus: 'logic_error'` (corrected to `'logic'` in Round 8 Wave 5b). The canonical CC-1 value is `'logic'`. Any encounter with `'logic_error'` in other stories should be treated as a typo for `'logic'`.
- **Warren CLI surface (CC-2 / CC-13, RECONCILED 2026-07-27 pre-dev review):** the real Warren CLI (0.10.0) has no `--config` flag; canonical invocation is `warren run <agent> <project> -p "<prompt>" [--provider --model]` against a running Warren server, with team/task params carried in the agent-team extension config the harness materializes into the run workspace (not `.canopy/agent.json`). See P0.3 CC-2 (amended) for the authoritative surface. All prior `warren run --config .canopy/agent.json` references in this story have been rewritten to the canonical form.
- **`.canopy/agent.json` ownership (CC-14):** `.canopy/agent.json` is SwarmClaw's agent-config store (CC-14), independent of Warren's `register-agent` registry. Both registries must be populated for an agent to pass invocation-time validation. The SwarmClaw agent-config store holds `agentId`, `model`, `extensions`, `repo`, `mulchBank`, `maxDurationMs`, and `capabilities`; it is consumed by the SwarmClaw protocol engine and the harness adapter, NOT passed to Warren as a CLI flag.
  **Store layout (P1.4-R5-1, canonical):** ONE repo-root file at `.canopy/agent.json` whose top level is an `agents` map keyed by agentId — **not** a per-agent file, and never a `{agentId}.canopy/agent.json` path. The harness adapter reads `agents[agentId]`; a missing key is an unconfigured agent (P1.4 rejects with -32602).

- **Contracts/Schema:** dispatch_task config: `{ taskBrief: string, targetAgentIds: string[], mulchBankId: string, maxDurationMs: number, captureFormat: "structured-json" (only supported value in Phase 1; enum exists for forward compatibility — future: 'yaml', 'toml'; matches P1.4's dispatch_task config) }`. Step output (success): `{ exitStatus: "success", changedFiles: string[], testResults: { passed: number, failed: number, coverage?: number }, testsExecuted?: boolean, summary: string, durationMs: number, mulchPrimed: boolean, mulchPrimeError?: string, artifacts: Array<{ name: string, path: string }> }`. **`testsExecuted` (P1.6-R2-5):** optional boolean, declared here so the Guards/limits rule below has a field to attach to — the guard required it but no schema declared it. Semantics: it MUST be present and `false` whenever `testResults.passed + testResults.failed === 0` (disambiguating 'no tests ran' from 'zero tests exist'); it MAY be omitted, or present as `true`, when the sum is > 0. Consumers MUST treat an absent `testsExecuted` as `true` only when the sum is > 0, and MUST reject output where the sum is 0 and the field is absent or `true`. Step output (failure): `{ exitStatus: "transient"|"overflow"|"logic"|"lead_failure", error: string, exitCode: number | null, partialOutput: string | null, durationMs: number, mulchPrimed: boolean, mulchPrimeError?: string }`. If Mulch priming succeeded before Warren failed, `mulchPrimed` is `true`. If not attempted or failed, it is `false`. The `coverage` field in the Warren output is optional. If present, it must be a non-negative number. If absent, pi-lens validation skips coverage checks. Implementations should not assume coverage is always provided.
- **Integration points:** SwarmClaw protocol engine (dispatch_task phase handler), CLI-Anything harness adapter, Warren CLI (`warren run <agent> <project> -p "<prompt>"` — CC-13 canonical, no `--config` flag), Pi agents (inside burrow), Mulch (context priming from Hindsight bank), pi-lens (output gating/validation), SwarmClaw `.canopy/agent.json` agent-config store (CC-14).
- **Files / functions touched:** CLI-Anything harness adapter (warren invocation), dispatch_task phase handler, structured JSON capture/parser, Warren output adapter, protocol step output store.
- **Guards/limits:** maxDurationMs must be >= 10000ms and <= 600000ms (10s to 10min). changedFiles paths must be relative to, and resolve beneath, the **pinned workspace root** — the single canonical root defined in INV-1, which is also the root every harness read goes through (no path traversal). `testResults.passed` and `testResults.failed` must each be **non-negative integers** (`>= 0`, no fractions, no `NaN`/`Infinity`); non-integer or negative values are rejected by schema validation. When `testResults.passed + testResults.failed === 0`, the output MUST include `testsExecuted: false` to disambiguate 'no tests ran' from 'zero tests exist'. summary must be <= 2000 characters **including any truncation suffix** — the 2,000 is the schema's hard ceiling on the final stored string, not a budget the suffix is added on top of. When the raw summary exceeds it, the adapter truncates the prose to `2000 - len("[truncated, N chars total]")` and appends the suffix, so `summary.length <= 2000` always holds (reserve the suffix length before cutting; the suffix width varies with N). `partialOutput` follows the same rule at its own ceiling: truncated to 10000 characters total, suffix `[truncated, N bytes total]` included in that 10000. Exit code 0 treated as exitStatus "success" **only when the merged-JSON envelope was emitted** — a lead that exits 0 on its own with no envelope is `lead_failure` (precedence rule P1.6-R5-1/R6-2 below the mapping table; a signal-terminated lead is classified by signal origin instead); non-zero mapped per Warren Exit Code Mapping table below.
- **pi-lens scope clarification:** In this story, "pi-lens gating" refers to output validation at the harness layer (schema validation of the structured JSON output), not P0.5's TDI diagnostic tooling. The harness validates: (1) output parses as valid JSON, (2) `exitStatus` is one of the 5-value enum (CC-1: `"success"|"transient"|"overflow"|"logic"|"lead_failure"`), (3) `changedFiles` is a string array, (4) `testResults.passed` and `testResults.failed` are non-negative integers, (5) `mulchPrimed` is a boolean, (6a) each `changedFiles` path must not contain `..` segments after normalization, and (6b) each `artifacts[].path` must not contain `..` segments after normalization — both must be relative to the **pinned workspace root** (INV-1, the same root the harness reads through), and absolute paths or paths escaping that root are rejected. Malformed output is captured as `exitStatus: "logic"` with the raw output in `partialOutput`.
- **Warren Exit Code Mapping:**

  | Warren Exit Code | exitStatus | Meaning |
  |-----------------|------------|---------|
  | 0 | "success" | Normal completion — **only if the merged-JSON envelope was emitted.** A lead that exits 0 on its own with no envelope is `lead_failure`; a signal-terminated lead never reaches this row. See the precedence rule below the table. |
  | 1 | "logic" | Task logic error (test failure, assertion failure) |
  | 2 | "transient" | Retryable failure (network timeout, API rate limit) |
  | 3 | "overflow" | Resource limit exceeded (budget, turn cap, memory) |
  | != 0 and not in {1,2,3}, including signals and negative codes | "transient" | Unknown failure — treated as retryable by default. Signal-terminated processes default to `transient` **regardless of whether an envelope was emitted** (signal origin is evaluated at precedence step 1, ahead of the missing-envelope rule). Harness-initiated signals (RSS watchdog, userCancel) override that default via signal-origin metadata — see signal-origin paragraph below. |
  | lead process exits before merged-JSON emit (any exit code, including 0) **and the harness did not kill it** | "lead_failure" | Harness-classified (P1.6-N2, CC-1). Emitted when the lead process exits on its own before producing the merged-JSON output the harness expects to capture, regardless of the lead process's own exit code. A lead the *harness* terminated (RSS watchdog, `userCancel`) is classified by signal origin instead — see precedence step 1. `exitCode` in the failure output reflects the lead process exit, not a warren exit code. Distinct from `logic`/`transient`/`overflow` because the harness cannot attribute the failure to a warren-recognized category — the protocol surface simply never materialized. |

  **Precedence rule (P1.6-R5-1, amended P1.6-R6-2) — the table rows are NOT independent; evaluate in this order:**
  1. **Signal termination → classified by signal origin, never by the envelope.** Harness-initiated: RSS watchdog → `overflow`; `userCancel`/`requestedShutdown` → `logic`. Unknown/external origin (kernel OOM, other processes) → `transient`, the catch-all row's safe retryable default. This is evaluated **first, before the envelope check**, because a kill is itself positive evidence about how the run ended: when the harness killed the lead it *knows why*, and the absent envelope is a consequence of that kill rather than independent evidence. Deferring to the envelope check would collapse every watchdog kill, user cancel, and external signal into `lead_failure` and discard the one authoritative signal the harness has.
  2. **Merged-JSON envelope missing on a process that exited normally → `lead_failure`.** Applies to every non-signalled run and wins over every exit-code row in that case, *including exit code 0*. A lead that exits 0 on its own without emitting the envelope is a `lead_failure`, never a `success`: the protocol surface the harness was told to capture never materialized, so there is no output to call successful. Row `0 | "success"` applies only when the envelope IS present.
  3. **Exit-code row lookup** ({0,1,2,3} then the catch-all row).

  In one line: **how the process died outranks whether it emitted an envelope, which outranks its exit code.** `lead_failure` is reserved for a lead that exited *under its own control* without producing the protocol surface — a killed lead is classified by the kill.

  Exit codes are mapped by the harness adapter. If Warren exits with a signal (SIGKILL, SIGTERM), the harness consults signal-origin metadata **before** checking for the merged-JSON envelope (precedence step 1) — a harness-initiated kill almost never leaves an envelope behind, so deferring to the envelope check would collapse every watchdog and cancel into `lead_failure`. The mapping: (1) if the harness-level RSS watchdog flag is set (watchdog killed the process for exceeding 4GB RSS), map to `exitStatus: "overflow"`; (2) if a `userCancel`/`requestedShutdown` flag is present (explicit user-initiated termination), map to `exitStatus: "logic"`; (3) if signal origin is unknown (including kernel OOM, which a user-space harness cannot portably detect), default to `exitStatus: "transient"` (safe retryable default). The exit code mapping distinguishes harness-initiated signals (RSS watchdog, userCancel — tracked via internal flag) from externally-initiated signals (kernel, other processes — no metadata available). Externally-initiated signals always map to `transient`. The "signal-origin metadata" reference applies only to harness-initiated kills.
- **Timeout alignment (CC-7):** maxDurationMs must be ≤ P1.1 timeoutMs upper bound (900s post-CC-7 fix). P1.6 max 600s is well within P1.1's 900s limit. The harness enforces maxDurationMs as a hard wall; Warren receives it via the manifest.

The step does not fail due to priming unavailability. `mulch_prime_ms` records the elapsed time until failure. The `mulchPrimeError` field contains the error message. ## Security Invariants

- INV-1: `warren run` scoped to the session's repository via the `repo` field in the SwarmClaw `.canopy/agent.json` agent-config store (CC-14); no cross-repo file access. The harness adapter reads `repo` from the agent-config store and materializes the run workspace accordingly.
  **Canonical root (P1.6-R6-1) — there is exactly ONE.** The directory the harness materializes from `repo` is the **pinned workspace root**, and it is the single canonical root for *both* path validation and every subsequent harness read. "Repo root" and "workspace root" elsewhere in this story are the same directory and are not two distinct roots: the workspace IS the session repository, pinned to a resolved absolute path once at step start and never re-resolved from a string thereafter. Validating `changedFiles` and `artifacts[].path` against one root while reading through another is explicitly forbidden — that split is precisely the traversal hole INV-2's beneath-root walk exists to close, so the walk MUST be rooted at the same pinned handle the validation used.
- INV-2: changedFiles paths validated against path traversal using decode-then-check in two stages: (1) **Pre-decode:** inspect the raw path for any percent-encoded `..` sequences (e.g. `%2e%2e`, `%2E%2E`) and evidence of double-encoding (e.g. `%252e` or any percent-encoded percent signs) — reject immediately if found. (2) **Post-decode:** URL-decode the path, normalize Unicode (NFC), then reject paths containing literal `..` segments, absolute paths, symlinks, and Unicode-normalized traversal sequences. The pre-decode check catches double-encoded traversals before they survive the first decode; the post-decode literal check catches anything that decoded to `..`. Symlink detection uses two complementary mechanisms: (1) **Path validation** (lstat-based) inspects paths reported by Warren's structured JSON output before the harness processes them. This is best-effort — it detects pre-existing symlinks at validation time but cannot prevent symlink creation between validation and use. (2) **File-read operations** performed by the harness itself (e.g., capturing partial output, reading artifacts) MUST resolve the path **beneath a pinned workspace root**, not merely refuse a final-component symlink. `O_NOFOLLOW` alone is NOT sufficient and MUST NOT be described as eliminating traversal: it only causes the OS to refuse the **last** path component when that component is a symlink. Every *parent* directory in the path is still resolved normally, so an attacker who controls any intermediate directory can replace it with a symlink and redirect the open to a file outside the workspace — `O_NOFOLLOW` does not see that. The required protection is a **beneath-root walk**: open the pinned workspace root once (`fs.opendir` / `O_DIRECTORY`), then walk the path one component at a time with `openat`-style relative opens, each carrying `O_NOFOLLOW`, so **no** component — parent or leaf — can be a symlink out of the root; equivalently, resolve the real path (`fs.realpath`) and re-assert it is a prefix-match under the pinned root **using the resolved handle for the subsequent read**, never re-opening by string (re-opening by path reintroduces the TOCTOU the walk exists to close).
  **Fail closed where the walk is unavailable.** Node exposes no portable `openat`; where a beneath-root walk cannot be performed on the running platform, the harness MUST refuse the read and classify the step `exitStatus: "logic"` with the path reported — it MUST NOT silently degrade to bare `O_NOFOLLOW`, and it MUST NOT degrade to lstat + open, which is a check-then-use pair with a real TOCTOU window and is not presented here as closing one. The lstat-based path-validation TOCTOU remains an accepted limitation for the *validation* pass only (pass (1) above, which inspects paths Warren reports rather than gating the harness's own reads), since the harness does not control Warren's internal file operations — Warren runs inside its own sandbox (burrow) and is responsible for its own path safety.
- INV-3: Warren process runs with resource limits enforced by the harness-level RSS watchdog (checking memory every 200ms and sending SIGTERM if RSS > 4GB). After sending SIGTERM, the watchdog waits 5 seconds. If the Warren subprocess has not exited, SIGKILL is sent. The exit code maps to `exitStatus: 'overflow'` with `partialOutput` capturing any output received before termination, consistent with the Warren Exit Code Mapping table's treatment of resource-limit violations. **This holds even though the merged-JSON envelope is absent** — a watchdog-killed lead almost never emits one, and precedence step 1 (P1.6-R6-2) evaluates the harness's own kill metadata ahead of the missing-envelope rule, so a watchdog kill is `overflow`, never `lead_failure`. The 200ms interval limits the window in which a fast-allocating process can exceed the cap undetected; it balances enforcement responsiveness against the overhead of reading `/proc/[pid]/statm` (Linux) or `ps` (macOS) at high frequency. Note: `child_process.execFile` does not support a `resourceLimits` option — that option is specific to `worker_threads`. If a future refactor switches to `worker_threads` or a runtime that supports per-process resource limits, `resourceLimits` can be applied then. CPU limiting is advisory (monitoring only) in Phase 1 — the harness logs CPU usage but does not kill for CPU overuse. Full cgroup-based enforcement is a Phase 2 concern when running in container environments.
- INV-4 (P1.6-N4): `maxDurationMs + 5s routing margin ≤ P1.1 timeoutMs`. The dispatch_task `maxDurationMs` upper bound (600s) plus a 5s routing margin (for SwarmClaw→harness→Warren handoff and capture overhead) must remain within P1.1's `timeoutMs` upper bound (900s post-CC-7 fix). 600s + 5s = 605s < 900s — invariant holds with 295s headroom. Deviations to either bound MUST preserve this invariant; if P1.1's `timeoutMs` is lowered below 605s in a future amendment, P1.6's `maxDurationMs` upper bound must be lowered correspondingly.
