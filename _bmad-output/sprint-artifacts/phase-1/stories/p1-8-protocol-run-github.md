# P1.8: Drive Protocol Run + Capture Correlated to GitHub Issue

**Story Points:** 3

## Spec Reference

- PRD §3.1, §3.3; FR-MG-4, FR-OR-5, FR-OR-7
- Phase exit gate: PRD §13 Phase 1 clause 8

## User Story

As a dev manager,
I want to start a protocol run for a GitHub issue and see live execution state correlated to that issue,
so that I can track parallel/compare/decide/summarize phases and their outputs bound to the issue.

## Overview

The dev manager selects a GitHub issue and initiates a SwarmClaw protocol run. SwarmClaw executes the phases of the `qds-factory` template P1.4 ships — dispatch_task → parallel → compare → decide → summarize — streaming execution state at each phase transition (canonical 5-phase list, N-P1.8-2, reconciled to P1.4's template). All telemetry (phase, status, agent assignments, outputs) is correlated to the originating GitHub issue number. The dev manager can observe live progress and final output without needing a separate dashboard — the correlation is intrinsic to the run record.

> **Predecessor note (CC-12):** This story consumes the `/api/a2a` route that P1.1 ADDS to SwarmClaw (P0.7 ships only `/api/agents`, `/api/mcp-servers`, `/test`, `/invoke`). Run initiation issues a JSON-RPC 2.0 call to `/api/a2a` with the `x-request-id` HTTP header set (CC-9). This story does NOT register or alter any `/api/a2a` route handler — it is purely a consumer.
>

## Acceptance Criteria

1. **(make-or-break)** Given a GitHub issue exists and the dev manager initiates a protocol run with its issue number, When SwarmClaw processes the run, Then each phase transition (dispatch_task → parallel → compare → decide → summarize — canonical 5-phase list) emits a state event containing `runId`, `repoSlug`, `issueId`, `requestId`, `phase`, `status`, and `timestamp` (CC-9 requestId propagation; `repoSlug` per P1.8-R2-8 — issue numbers are repo-scoped).

   > **`x-request-id` direction (CC-9).** The header is used on BOTH legs and the two must not be conflated:
   > - **Inbound (request header, client → SwarmClaw):** the dev-manager client SHOULD send `x-request-id` on the run-initiation POST to `/api/a2a`. SwarmClaw honours that value **only if it is a strict UUID v4**; otherwise (absent, malformed, or non-v4) SwarmClaw generates a fresh one (`src/swarmclaw/index.ts:42-46`). A client must therefore read the requestId back from the response rather than assume the value it sent was kept.
   > - **Outbound (response header, SwarmClaw → client):** SwarmClaw echoes the resolved value in the `x-request-id` response header on every response, including errors (`src/swarmclaw/index.ts:53`).
   > - **State events:** the `requestId` on every state event is the **resolved** value — i.e. what SwarmClaw returned in the response header, not necessarily what the client sent.
2. Given a protocol run is in progress, When the dev manager queries run state by `(repoSlug, issueId)`, Then the response includes current phase, assigned agents, phase outputs so far, and elapsed time — all correlated to that issue in that repository, and runs for the same issue number in a DIFFERENT repository are excluded from the result.
3. Given a protocol run completes the summarize phase, When the run finishes, Then the final output is persisted with the `(repoSlug, issueId)` correlation and is retrievable by that pair. Retrieval by issue number alone is NOT supported — it is ambiguous across repositories (P1.8-R2-8).
4. Given the SwarmClaw service is **provably unreachable** — the initiation request failed before SwarmClaw could accept it (DNS failure, `ECONNREFUSED`, TLS handshake failure, or connect timeout: the connection was never established, so no bytes of the request were delivered) — When a run is attempted, Then the dev-manager client returns `runId: null` and does not cache or retry the request. No run state exists on the SwarmClaw side because the request never landed, so `runId: null` loses no correlation.

   > **Ambiguous initiation failures are NOT covered by the `runId: null` path (P1.8-R2-9).** A failure after the request was sent — socket reset mid-flight, read timeout awaiting the response, a 5xx from an intermediary — is **indeterminate**: SwarmClaw may have accepted and persisted the run before the client lost the response. Returning `runId: null` there would silently orphan a live run. The client MUST instead reconcile, using the `requestId` it sent as the idempotency key:
   > - **Idempotency key.** The client generates a strict UUID v4 `requestId` per initiation attempt and sends it as `x-request-id` (CC-9). SwarmClaw persists it on the `ProtocolRun` (the existing `ProtocolRun.requestId` field) and treats initiation as idempotent on `(repoSlug, requestId)`: a repeat initiation carrying a `requestId` already recorded returns the EXISTING run rather than creating a second one. This is enforced by the unfiltered unique index and transactional upsert in **INV-RUN-1b**, not by INV-RUN-1's `(repoSlug, issueId)` partial index — see that invariant for why a read-then-insert check is insufficient and why the window must outlive run completion. Note the CC-9 caveat in AC1 — SwarmClaw only honours a client-supplied `x-request-id` when it is a strict UUID v4, so a client relying on this MUST send a valid v4 or it will get a server-generated id it cannot reconcile against.
   > - **Reconciliation.** On an ambiguous failure the client does NOT return `runId: null`. It queries `GET /api/runs?repoSlug={slug}&requestId={uuid}`. A match → the run landed; adopt its `runId` and continue. No match → the run did not land; the client MAY safely re-issue the initiation with the SAME `requestId` (idempotent by the rule above).
   > - **Outcome if reconciliation itself fails** (SwarmClaw still unreachable): the client surfaces an explicit `status: 'indeterminate'` result carrying the `requestId` — never `runId: null`, which is reserved for the provably-pre-acceptance case — so the caller can retry reconciliation later instead of assuming no run exists.

## Technical Notes

- **Contracts/Schema (N-P1.8-1, N-P1.8-2, N-P1.8-3, N-P1.8-5):**
  - `ProtocolRun { runId: string, repoSlug: string, issueId: number, requestId: string, phases: PhaseRecord[], status: 'running' | 'completed' | 'failed', createdAt: ISO8601, completedAt?: ISO8601 }`.
  - **Issue identity is `(repoSlug, issueId)`, never `issueId` alone (P1.8-R2-8).** GitHub issue numbers are unique only *within* a repository — `#42` exists in every repo the factory touches. An earlier draft keyed runs, queries, telemetry, and the uniqueness constraint on `issueId` alone, which lets a run for `#42` in one repository collide with, or be returned alongside, a run for `#42` in another. `repoSlug` (the `owner/name` slug, the same value P1.3 threads through `resolveBankId(repoSlug)`) is therefore a required field on `ProtocolRun`, a required member of every state event payload, a required query parameter on the by-issue route, and part of the uniqueness constraint (INV-RUN-1) and every telemetry record. Run initiation MUST reject a request that omits `repoSlug` with 422 rather than defaulting it — a silently-defaulted repository is exactly the cross-repo mix-up this rule exists to prevent. `runId` remains globally unique on its own, so `GET /api/runs/{runId}` needs no repo scoping.
  - `PhaseRecord { phase: ProtocolPhase, status: PhaseStatus, agents: agentId[], output?: PhaseOutput, startedAt: ISO8601, completedAt?: ISO8601 }` (P1.8-V1: `agentId` per P1.1 INV-2 regex `^[a-z0-9][a-z0-9-]{0,126}[a-z0-9]$`; validated via `RegisterAgentSchema` — see detail below).
  - `ProtocolPhase = 'dispatch_task' | 'parallel' | 'compare' | 'decide' | 'summarize'` (canonical 5-phase list — matches the `qds-factory` template P1.4 registers, whose AC1 asserts `phaseCount: 5`). P1.4's Phase-to-PI Extension Mapping also defines an `a2a_delegate` phase kind, but it is NOT part of the `qds-factory` v1.0.0 template, so a run of that template never emits it; this story's E2E asserts the 5 phases the template actually contains. (Run *initiation* still goes over the `/api/a2a` HTTP route — that is a transport call, not a protocol phase. Do not confuse the two.) Should a future template add `a2a_delegate`, extend this union together with P1.4's `phaseCount`.
  - `PhaseStatus = 'pending' | 'running' | 'completed' | 'failed'`.
  - `PhaseOutput { exitStatus: ExitStatus, exitCode?: number | null, changedFiles?: string[], artifactUri?: string, summary?: string }` — **`ExitStatus` is imported, never re-declared (P1.8-R2-10).**
    - **`exitCode` is `number | null`, not `number` (P1.8-R5-1).** P1.6 defines its failure output as `exitCode: number | null` and uses `null` for signal-terminated Warren processes. An earlier draft here narrowed the field to `number`, which made a propagated P1.6 failure unrepresentable — the executor would have had to drop the field or coerce `null` to a fake numeric code, both of which destroy the "killed by a signal" signal. The union is therefore required. Requiredness, aligned across statuses: `exitCode` is **absent** when `exitStatus` is `success`; it is **present** (possibly `null`) for every failure status, `lead_failure` included — on `lead_failure` it carries the lead process exit code, which is itself `null` when the lead was signalled. Consumers MUST distinguish absent (`undefined` — no process outcome) from `null` (process terminated by signal, no exit code exists); neither may be read as `0`. Single source of truth: the `ExitStatus` type exported from `cli-anything/src/types.ts` (`export type ExitStatus` at `cli-anything/src/types.ts:79`), which is the canonical P1.1 CC-1 5-value taxonomy (`"success" | "transient" | "overflow" | "logic" | "lead_failure"`). Earlier drafts spelled that union inline here; that duplicate is retracted, because an inline copy lets this story drift silently from P1.1 when the taxonomy changes. Values are listed in this sentence for readability only — the type is authoritative. On `lead_failure`, `exitCode` carries the lead process exit code (harness-classified; emitted by the harness supervisor when the lead exits before merged-JSON output).
  - Each entry in `PhaseRecord.agents` MUST match the P1.1 agentId regex `^[a-z0-9][a-z0-9-]{0,126}[a-z0-9]$` (import `RegisterAgentSchema` from P0.7 / P1.1's registry module for runtime validation; reject malformed agentIds with 422 at assignment time). This closes the agentId-grammar gap (N-P1.8-5) by constraining PhaseRecord.agents to the same grammar that P1.1's INV-2 enforces on registration.
- **Integration points:**
  - **Run initiation → `/api/a2a`** (the JSON-RPC 2.0 A2A delegation endpoint P1.1 adds, CC-12). This route does **delegation only**; P1.1 defines no run-state semantics on it. The initiation call SHOULD set the `x-request-id` HTTP header (UUID v4 strict, `src/swarmclaw/index.ts:42-46`) and the resolved requestId propagates through every state event emitted by this story (CC-9).
  - **Run-state queries → this story's own run routes**, NOT `/api/a2a`: `GET /api/runs/{runId}` and `GET /api/runs?repoSlug={owner/name}&issueId={n}` (AC2's query-by-issue — **both** parameters required; a request supplying `issueId` without `repoSlug` is rejected with 422 rather than returning cross-repo matches, P1.8-R2-8), served from `src/api/routes/run-routes.ts` in Files to Modify. A third read route, `GET /api/runs?repoSlug={owner/name}&requestId={uuid}`, serves the AC4 reconciliation lookup (P1.8-R2-9) and lives in the same module. These are additive REST routes owned by P1.8; reading run state MUST NOT be modelled as an A2A delegation.
  - GitHub issue metadata for correlation.
  - **Hindsight run persistence → `resolveBankId(repoSlug)`** (P0.9 helper, canonical per P1.3: *"the literal `{repo}` placeholder is never used at runtime — all bank references resolve through `resolveBankId()`"*). `{repo}` in earlier drafts of this story was a placeholder for that call, not a literal bank name.

## Security Invariants

- INV-RUN-1: A protocol run cannot be initiated for an issue that already has a run in `running` status — enforced by partial unique index `ON runs(repoSlug, issueId) WHERE status='running'` (P1.8-V2 reword: a partial filtered index, not a composite unique constraint, so completed/failed runs coexist with a new running run. P1.8-R2-8: the index key is the `(repoSlug, issueId)` pair, not `issueId` alone — keyed on `issueId` alone it would wrongly block a run for `#42` in repo B while `#42` in repo A is running).
- INV-RUN-1b: Initiation is idempotent on `(repoSlug, requestId)` — enforced by an **unfiltered** unique index `ON runs(repoSlug, requestId)` plus a transactional get-or-create on the initiation path (P1.8-R3-5). AC4's reconciliation contract requires "a repeat initiation carrying a `requestId` already recorded returns the EXISTING run", but INV-RUN-1's partial index is keyed on `(repoSlug, issueId) WHERE status='running'` and therefore enforces nothing here: it does not cover `requestId` at all, and it stops filtering once the run is terminal. Without this constraint two concurrent retries can both pass a read-then-insert check and double-create, and a retry arriving after the original run completed hits neither guard. The index is **unfiltered** deliberately — the idempotency window must outlive the run, so a post-completion retry still resolves to the original run rather than starting a second one. Insert is a single atomic upsert (`INSERT ... ON CONFLICT (repoSlug, requestId) DO NOTHING` followed by a read of the winning row, or the equivalent `INSERT ... RETURNING` + conflict-read), never a `SELECT`-then-`INSERT`; the loser of the race returns the winner's run and reports success. Note this constraint applies to the **resolved** requestId (CC-9): a client that sends a non-v4 `x-request-id` gets a server-generated one and thus no idempotency, which AC4 already warns about. INV-RUN-1 remains in force independently — the two guards answer different questions (`requestId` = "is this the same initiation attempt?", `issueId` = "is this issue already being worked?").
- INV-RUN-2: Run state events are append-only — no mutation of historical phase records after they are persisted.
- INV-RUN-3: Run telemetry is scoped to the originating issue — cross-issue data leakage is prohibited.
