# P1.10: Gated issue pauses the run; a Telegram approve tap resumes it

**Story Points:** 4

## Spec Reference

- PRD §6.3 (Orchestration — Warren DAG) + §6.6 (Comms); FR-OR-6 (pause at approval node → resume on approval / halt-clean on reject, no partial/corrupt state), FR-CM-2 (surface approval gate as Telegram msg with inline approve/reject buttons, resume paused run on tap)
- Supporting: FR-CP-5 (`executionPolicy` defines when a human-approval gate is required), FR-CP-6 (persist every approval + execution-gate decision); NFR-SEC-1, NFR-SEC-2
- Phase exit gate: PRD §13 Phase-1 — human-in-the-loop gate drives the run (gate→ping→resume), with the §12.2 OQ-3 fallback honored
- **§12.2 OQ-3 context:** OQ-3 ("BLOCKED-on-creds — Telegram plugin SDK first-class messaging primitive") means the Paperclip plugin SDK does not yet provide a native inline-button API. The approval surface therefore routes through the Hermes-driven Telegram gateway (built inside this story per AC-4), which uses the standard Telegram Bot API `sendMessage` with `reply_markup.inline_keyboard` directly. The "fallback" is from the (unavailable) plugin SDK path to the Hermes gateway path — both produce identical approval decisions; the `via` field in the callback record distinguishes them for auditability.

## User Story

As an external stakeholder approving high-risk work,
I want a gated issue to pause its Warren run, ping me on Telegram with inline approve/reject buttons, and resume (or halt-clean) when I tap,
so that a human decision genuinely drives the run and the outcome is persisted as an auditable approval (G1 accountability; G4 human-on-the-loop control).

## Overview

A vertical slice through the §6.6 comms front-door into the §6.3 pause/resume seam. It cuts: an issue carrying an `executionPolicy` gate (`issues.executionPolicy` jsonb `issues.ts:52`) → a Warren approval node that **pauses** the run (Warren `RESUMABLE={failed,paused}` `workflow-run.ts:29-32`) → a Telegram message with inline approve/reject buttons → the tap's callback → resume on approve OR clean halt/cancel on reject, with the decision persisted to `approvals` (`approvals.ts:5-28`) + `issue_execution_decisions`. Because OQ-3 is BLOCKED-on-creds and the Paperclip plugin SDK has **no first-class messaging/inline-button primitive** (R3/R4), the approval surface routes through the **Hermes-driven Telegram gateway** (Hermes owns the bot token, sends the inline buttons, handles the callback, and resumes the paused run as the bearer-authenticated agent) — this is an explicit AC/Technical-Note, not an assumed plugin path. One atomic 4-pt unit: a single gated run that pauses, pings, and resumes/halts on a real tap. **This story absorbs the Hermes-Telegram gateway wiring** (Telegram webhook endpoint registration + bot token bootstrap) that was originally scoped under killed story P0.8; no external predecessor provides that gateway — P1.10 builds it. All FRs cited in the Spec Reference (FR-OR-6, FR-CM-2, FR-CP-5, FR-CP-6) are current and actionable by this story — P0.8's killed scope was absorbed here, so its former FRs are now this story's responsibility.

## E2E Slice

**Demonstrable behavior:** An issue with an `executionPolicy` requiring approval launches a Warren run; the run reaches the approval node and **pauses** (run state `paused`). The Hermes-Telegram gateway sends the chat an inline approve/reject message. On an **approve** tap, the callback resumes the paused run (state leaves `paused`, run completes) and writes one `approvals` row (`status:"approved"`, `decidedByUserId`, `decidedAt`) + an `issue_execution_decisions` record. On a **reject** tap, the run **halts/cancels cleanly** (no partial/corrupt state) and writes `status:"rejected"`. The decision visibly drives the run — the run never advances past the gate without a recorded tap.

**Wiring closed:** On completion of this story, a gated issue's run **pauses at the approval node, pings Telegram with inline buttons, and an approve tap resumes it to completion (reject halts clean)** — with the decision written to `approvals` + `issue_execution_decisions` — using only code merged by this story (the approval-node pause hook, the gateway send/callback handler, and the resume/halt + decision-writer). No stub, no `TODO: wire later`, and no sibling story is required to make this behavior real. The Hermes-Telegram gateway wiring (webhook endpoint, bot registration, inline-button send) is built inside this story — it was originally scoped under killed story P0.8 and is now absorbed here. Each integration point is independently verifiable: **(a) Telegram → Gateway:** webhook route `POST /hermes/telegram/callback` receives callback, verifies secret token header, extracts `decisionToken`; **(b) Gateway → Paperclip:** user resolution via `telegram_user_map` lookup (`telegramUserId → paperclipUserId`), decision write to `issue_execution_decisions`; **(c) Gateway → Warren:** resume/halt via `WarrenClient.post('/api/workflows/{workflowName}/run', { runId, resumeFromNode })`; **(d) Gateway → Notification:** approval result sent to stakeholder via the originating channel.

**Dependency edges (predecessors):** None. The Hermes-Telegram gateway wiring (webhook endpoint, bot registration, inline-button send) and the launcher substrate are both absorbed into this story — no external predecessor provides them.

## Acceptance Criteria

> ≥3 scenarios, Given/When/Then. Exactly one tagged (make-or-break) and binary.

1. **(make-or-break)** Given an issue whose `executionPolicy` requires approval and a launched Warren run, When the run reaches the approval node and a stakeholder **taps approve** on the Telegram inline message (or its Hermes-gateway equivalent), Then the run leaves `paused` and **resumes to completion**, AND exactly one `approvals` row exists with `status:"approved"` + non-empty `decidedByUserId`/`decidedAt` AND a matching `issue_execution_decisions` record — i.e. the human tap provably drove the run from pause to completion.
2. Given the same paused run, When the stakeholder **taps reject**, Then the run **halts/cancels cleanly** with no partial or corrupt working state (FR-OR-6), and an `approvals` row is written with `status:"rejected"` — never a silent continue or a stuck-paused run. AC-2 satisfaction requires ALL four conditions: **(a)** issue status = `halted`, **(b)** run status = `halted` in Warren, **(c)** reject decision recorded in `issue_execution_decisions`, **(d)** stakeholder notified via the originating channel. Partial satisfaction (e.g., 3 of 4) = AC-2 FAIL.
3. Given the gated run reaches the approval node, When no decision has been recorded yet, Then the run **stays paused** and does NOT advance past the gate — the gate cannot be skipped by absence of a tap. "Stays paused" is verified within a 5-second polling window: pause a run, send NO approval, poll issue status every 500ms for 5s, assert status remains `paused` throughout.
4. Given Telegram is BLOCKED-on-creds (OQ-3, R4), When the gate fires, Then the approval surface is served by the **Hermes-driven Telegram gateway fallback** (Hermes sends the inline message and handles the callback as the registered bearer-authenticated agent), and the resume/halt + `approvals`/`issue_execution_decisions` write happens **identically** through that path — the gate is never bypassed or assumed-approved because the plugin is unavailable.

## Technical Notes

- **Contracts/Schema:** Consumes existing `issues.executionPolicy` jsonb (`issues.ts:52`), `approvals` (`approvals.ts:5-28`: `status`/`payload`/`decisionNote`/`decidedByUserId`/`decidedAt`), and `issue_execution_decisions` (schema enumerated below). The `decidedAt` field serves as the human-response timestamp — no separate `respondedAt` field is needed. **Telegram callback_data payload:** `callback_data` is a base64url-encoded decision token (max 64 bytes), NOT a JSON blob — Telegram enforces a 64-byte hard limit on `callback_data` and a JSON payload would exceed ~160 bytes. Full context (`issueId`, `runId`, `timestamp`) is stored server-side in `issue_execution_decisions` keyed by `decisionToken`. Telegram inline keyboard buttons carry only `decisionToken`. On callback receipt, the gateway decodes the token, looks up the full decision context, and dispatches to the approval handler. **`issue_execution_decisions` table schema:** `{ decisionToken (PK, text), issueId (FK→issues.id), runId (text, UNIQUE), decidedByUserId (FK→users.id, nullable before decision), decision ('approve'|'reject'), decidedAt (timestamptz), via ('telegram_gateway'|'cli'|'ttl_auto_reject'), createdAt (timestamptz) }`. **`via` enum:** `'telegram_gateway'` (P1.10 Hermes gateway path), `'cli'` (manual CLI approval), `'ttl_auto_reject'` (timeout). `'telegram_plugin'` is deferred pending plugin SDK availability and MUST NOT be implemented in P1.10. **`decidedByUserId` resolution:** `decidedByUserId` stores the **Paperclip user ID**, NOT the Telegram user ID or chat ID. Resolution chain: Telegram callback `callback_query.from.id` identifies the individual who tapped (NOT `chat.id`, which is shared by all members of a group chat — using `chat.id` would be a security vulnerability in group contexts). The gateway looks up `from.id` in `telegram_user_map` table (`telegramUserId → paperclipUserId`). If no mapping exists, the decision is rejected with `403` and the human is prompted to link their account via a `/link` bot command (the `/link` command stores the mapping from the caller's `from.id`, not `chat.id`). The `telegram_user_map` table schema: `{ telegramUserId (PK, text — the Telegram user ID from `callback_query.from.id`), paperclipUserId (FK→users.id), linkedAt (timestamptz) }`. Backward-compatible: an issue with no `executionPolicy` gate runs unchanged (no pause). **`executionPolicy` structure:** `{ approval: { required: boolean, timeoutMs?: number, notifyChannel?: "telegram"|"cli" } }`. `notifyChannel: 'cli'` means the approval request is printed to the Warren run's stderr (visible in `qds status` output); no separate CLI notification service exists. `cli` channel is always available as fallback when Telegram is unavailable. When `approval.required: true`, the Warren run pauses at the approval node and the gate fires. All other `executionPolicy` values (or absent/empty `approval` block) are pass-through — no pause, no notification. `timeoutMs` is optional; when present it sets the auto-reject TTL (see Approval timeout (TTL) in Guards/limits).
- **Integration points (each wired & exercised in this story):** (1) approval-node **pause** on the Warren run (`RESUMABLE={failed,paused}` `workflow-run.ts:29-32` — RESUMABLE status set refers to Warren run statuses defined in P1.6 WarrenClient; `paused` is resumable. P1.9 uses `retryCount >= 8` for restart policy. P1.10's approve/resume operates on Warren run status (not Paperclip issue status). The `paused` Warren status is set by P1.10's execution policy gate; `running` is set on approve; `halted` on reject); (2) **Hermes-driven Telegram gateway** sends the inline approve/reject message and handles the callback — per R3/R4 the Paperclip plugin SDK has no native inline-button primitive, so this is the load-bearing surface (BLOCKED-on-creds → gateway fallback, explicit per AC 4); (3) **resume** the paused run on approve / **clean halt-cancel** on reject — gateway resumes via `WarrenClient.post('/api/workflows/{workflowName}/run', { runId, resumeFromNode })`; the resume API is P1.6's WarrenClient SSE endpoint, and resume re-enters the DAG at the paused node with the approval decision injected as node input; (4) persist the decision to `approvals` + `issue_execution_decisions`, rolled to `issues.status`. Resume runs only as the registered agent (`PAPERCLIP_API_KEY` + `PAPERCLIP_RUN_ID`, `adapters/registry.ts:468-469`). **Telegram inline keyboard:** the Hermes Telegram gateway uses `sendMessage` with `reply_markup.inline_keyboard` (Telegram Bot API native). This is a standard Telegram API feature — no custom inline-button SDK required. **Webhook route:** `POST /hermes/telegram/callback` — this is the endpoint registered with Telegram's `setWebhook` API. It receives the `Update` object, extracts `callback_query`, decodes the `decisionToken` from `callback_data`, looks up the full decision context from `issue_execution_decisions`, resolves the Paperclip user ID via `telegram_user_map`, and dispatches to the approval handler. This route must be registered in the Hermes router before the e2e test runs.
- **Files / functions touched:** `src/orchestration/approval-node.ts` (pause hook + resume/halt), `src/hermes/telegram-gateway-approval.ts` (inline send + callback → decision), `src/db/approvals.ts:recordApprovalDecision` (write `approvals` + `issue_execution_decisions`). References `issues.ts:52`, `approvals.ts:5-28`, `workflow-run.ts:29-32`. **Citation caveat:** file:line references are best-current-knowledge at spec time and may shift during implementation; they remain useful as entry points but should not be treated as stable anchors.
- **Callback authentication (H1):** Every incoming Telegram webhook callback is verified before processing. Two verification modes: (1) Telegram `secret_token` header equality — the gateway verifies the incoming `X-Telegram-Bot-Api-Secret-Token` header value exactly equals the configured `secret_token` set during `setWebhook` (simple string equality, no HMAC computation); (2) alternatively, a per-run callback secret embedded in the inline-button `callback_data` and verified on receipt. Unverified callbacks are rejected with `403` and logged. This prevents any POST with the right JSON shape from resuming a run. **Rate-limiting:** `POST /hermes/telegram/callback` is rate-limited to 10 requests/minute per Telegram bot ID. Uses Telegram's `secret_token` webhook verification (set during `setWebhook`) to reject unauthenticated requests before rate-limit counting. **Replay protection:** each `decisionToken` is single-use — once consumed by a decision write, subsequent callbacks with the same token return `409 Conflict` and are logged.
- **Telegram outage handling (H4):** When the Telegram API is unreachable (send or receive), the Hermes gateway logs the failure at `ERROR` level and the run stays `paused` — consistent with INV-3 (gate cannot be bypassed). The outage is surfaced via a dedicated health-check endpoint `GET /hermes/telegram/health` that returns `{ ok: boolean, lastError?: string }`. Any decision made during the outage is recorded with `via` set to the actual decision path (`'cli'` or `'ttl_auto_reject'`), never `'telegram_gateway'` — the `via` enum tracks the decision channel, not the infrastructure condition. As a manual fallback surface, a CLI command `qds approve --run <runId> --decision approve|reject` allows an operator to record a decision directly when the Telegram path is down; the CLI path exercises the same resume/halt + decision-writer logic. CLI `qds approve --run-id <id>` uses Paperclip `local_trusted` auth mode (same as all CLI commands). The CLI reads `PAPERCLIP_COMPANY_ID` and authenticates via the service layer. No bearer token needed at app level.
- **CI-mockable path (H5):** A `TELEGRAM_MOCK_MODE` env var (or `--mock-telegram` CLI flag) activates a mock Telegram adapter. In mock mode, the gateway reads decisions from a JSON file (path in `TELEGRAM_MOCK_DECISIONS_FILE`, default `tests/fixtures/mock-telegram-decisions.json`) instead of opening a real webhook. The mock adapter exercises the identical resume/halt + decision-writer + idempotency logic as the live path. DoD requires at least one e2e test run under mock mode.
- **Guards/limits:** the run cannot advance past the approval node without a recorded decision (no timeout auto-approve); the Telegram callback carries the bot token from env only; resume/halt are authenticated and idempotent on `runId` (a duplicate tap does not double-resume or write a second conflicting `approvals` row). **First-decision-wins on `runId`:** the first approve/reject callback for a given `runId` is the authoritative decision; all subsequent callbacks for the same `runId` receive an `"already_decided"` response and no-op — the idempotency key is `runId`, resolving the concurrent-tap race (INV-4 strengthened). **Approval timeout (TTL):** a configurable TTL (default 24 h) starts when the run enters `paused`. **timeoutMs resolution priority:** `executionPolicy.approval.timeoutMs` → env var `APPROVAL_TIMEOUT_MS` → hard-coded default `3600000` (1 hour). Explicit executionPolicy > env var > hard-coded default. If no decision arrives before expiry, the run auto-rejects (halts cleanly) and an `approvals` row is written with `status:"rejected"` and `decisionNote:"auto_reject_ttl"`. Absence of response is NOT auto-approve (consistent with INV-3). **TTL auto-reject vs human approve race condition:** ordered comparison rule — TTL auto-reject checks `decidedByUserId IS NULL` (within transaction) before writing. Human approve writes `decidedByUserId` first (within the same transaction scope). First write wins: if TTL fires after human approval, the `IS NULL` check fails and auto-reject is skipped. Timestamp ordering: `decidedAt` resolves ties — earliest `decidedAt` wins. **Non-paused run guard:** a callback targeting a run whose state is no longer `paused` (already completed/halted/cancelled) is rejected with a `409 Conflict` response — no state transition occurs on a non-paused run. **Issue status transitions:** on approve, issue status transitions from `paused` to `running`; on reject (human or TTL auto-reject), from `paused` to `halted`; on TTL auto-reject, from `paused` to `halted`. **Status transitions confirmed against P1.1/P1.2 Paperclip `IssueStatus` enum:** `paused→running` (on approve), `paused→halted` (on reject), `paused→halted` (on TTL auto-reject). These exact enum values must match the Paperclip `IssueStatus` type defined in P1.1/P1.2; if P1.1/P1.2 uses different strings, this story aligns to those exact values.

## Security Invariants

> Triggers: auth, secrets/env. Concrete named invariants only.

- **INV-1 (NFR-SEC-2 authenticated resume):** the paused run is resumed (or halted) only by the registered, bearer-authenticated agent (`PAPERCLIP_API_KEY` + `PAPERCLIP_RUN_ID`, `adapters/registry.ts:468-469`); every **human-initiated** `approvals`/`issue_execution_decisions` write carries an authenticated `decidedByUserId` — never an anonymous or unauthenticated resume. **Automated decisions** (via `'ttl_auto_reject'`) keep `decidedByUserId` as `NULL` — there is no human actor, and the `via` field identifies the decision path as system-initiated. The authenticated-decidedByUserId requirement applies only when `via` is `'telegram_gateway'` or `'cli'`.
- **INV-2 (NFR-SEC-1 secrets hygiene):** the Telegram bot token and chat ids are read from env/secret refs only (`config/telegram.env.example` documents names, holds no real values); no token, chat id, or callback secret is hardcoded or written to stdout, logs, or the `approvals.payload`/`decisionNote` fields.
- **INV-2b (callback authentication):** every incoming Telegram callback is verified (secret_token header equality against the configured value set during `setWebhook`, or per-run callback secret) before any decision is processed. Unverified callbacks are rejected with `403` and logged. No unauthenticated POST can resume or halt a run.
- **INV-3 (gate cannot be bypassed):** the run cannot advance past the approval node without a persisted decision — there is no timeout-auto-approve and no code path that resumes on absence of a tap; an unavailable Telegram plugin routes to the Hermes-gateway fallback, never to an assumed-approved continue (the core HITL guarantee).
- **INV-4 (idempotent decision):** resume/halt is idempotent on `runId` — a replayed or duplicate inline-button callback does not double-resume the run nor write a second conflicting `approvals` row. The first decision on a `runId` wins authoritatively; all subsequent callbacks for the same `runId` receive an `"already_decided"` response and produce no state change, resolving the concurrent-tap race (two humans tapping simultaneously yields exactly one decision).
