# P1.14: Per-run outcome record from native sites + deterministic router selection logged

**Story Points:** 3 *(note: 11-field schema + 7 native-site readers + aggregation logic + idempotent upsert may warrant 5SP at implementation time if scope proves larger than estimated)*

## Spec Reference

- PRD §6.9 (Self-optimization & learning — v4 foundation), §6.7 (Accountability & yield), §9.4.0 (native-first / token-frugal principles); FR-ACT-2, FR-LEARN-28, FR-LEARN-29
- FR-MG-9: retry classification taxonomy (retry_class derivation). See §12.2 of PRD.
- Supporting: NFR-REL-4 (Layer-B writes idempotent, key on `runId`), NFR-OBS-6(a) (every served config reconstructable — rationale persisted alongside `heartbeat_run`), NFR-COST-3 (v4 learning tax is zero added inference), NFR-PERF-7 (router selection ≤200 ms p95)
- Phase exit gate: rides PRD §13 Phase-1 (FR-LEARN-28/29 are the Layer-B substrate wired in Phase 1 atop the cost ledger + router already built); per §6.8 this is the v4 self-optimization foundation.

## User Story

As the **Operator / Self-improvement lead**,
I want **a per-run outcome record keyed on `runId` assembled from native recording sites (cost_events + heartbeat_runs + pi-lens) plus the deterministic router selection rationale logged with no extra LLM call**,
so that **the Layer-B self-optimization substrate is captured per run at zero added inference cost (goal G3 measurable improvement, G4 token-frugal).**

## Overview

This slice cuts through the native ledger/trace stores → an idempotent outcome-record write → the persisted router rationale. On run completion, the system reads each FR-LEARN-28 field **from its native site** — `cost_events` for per-role/per-model `cost_cents`+`input/output/cached_tokens` (via `agentId`/`model`/`heartbeatRunId`), `issues` (via `executionRunId` FK join per P1.16 §8.4 hop 2) / `heartbeat_runs.status` for `first_pass_accept`, `heartbeat_runs` for `wall_clock_ms`/`retry_count`/`retry_class`/`exit_class` — and writes ONE outcome record `{task_type, archetype, per_role_model_tier, cost_cents, input_tokens, output_tokens, cached_tokens, first_pass_accept, exit_class, retry_count, retry_class, wall_clock_ms}` as an **idempotent upsert on `runId`** (NFR-REL-4). In the same write it persists the FR-LEARN-29 router selection rationale (signature inputs + chosen archetype/tier + the binding constraint) so the served config is reconstructable (NFR-OBS-6a). There is **NO extra inference call** — every value is read from data the run already produced (§9.4.0). One atomic unit because an outcome record is only "captured per run" if it is keyed-idempotent AND its config is reconstructable in the same write; either alone leaves the substrate incomplete.

## E2E Slice

**Demonstrable behavior:** After a `qds-piv-loop` run completes, calling `recordOutcome(runId)` reads `cost_events` (cost+tokens, aggregated by `heartbeatRunId`), `heartbeat_runs` (timing/retries), and `issues` (via `executionRunId` FK join to `heartbeat_runs`, for accept signal) and upserts one outcome record keyed on `runId`, alongside the router selection rationale. Re-invoking `recordOutcome(runId)` for the same `runId` **upserts the identical row, never duplicating** (NFR-REL-4). A read of the record returns all twelve FR-LEARN-28 fields (including `exit_class`) plus the router rationale; no `cost_events` row is written by this step (zero added inference — the learning tax is one event-driven retain, not an LLM call).

**Wiring closed:** On completion of this story, `recordOutcome(runId)` produces **one idempotent outcome record (twelve FR-LEARN-28 fields including `exit_class`, all read from native sites) + the persisted FR-LEARN-29 router rationale, re-runnable with zero duplicates and zero added `cost_events`** — using only code merged by this story (native-site readers + idempotent upsert + rationale persistence). No stub, no `TODO: wire later`, and no sibling story is required to make this behavior real. Predecessors, if any, are dependency edges (listed below), not unfinished wiring inside this story.

**Dependency edges (predecessors):** P1.5 (the `qds-model-router` produces the selection object whose rationale this story persists alongside the outcome record). P1.13 (the per-run `cost_events` rows that supply `cost_cents`+token fields keyed by `heartbeatRunId`). Both are dependency edges, not unfinished wiring inside this story.

## Acceptance Criteria

> ≥3 scenarios, Given/When/Then. Exactly one tagged (make-or-break) and binary.

1. **(make-or-break)** Given a completed run with ≥1 `cost_events` row, a `heartbeat_runs` trace, and an `issues` (via `executionRunId` FK join) accept signal, When `recordOutcome(runId)` is invoked, Then exactly **one** outcome record keyed on `runId` exists carrying all twelve FR-LEARN-28 fields (`task_type, archetype, per_role_model_tier, cost_cents, input_tokens, output_tokens, cached_tokens, first_pass_accept, exit_class, retry_count, retry_class, wall_clock_ms`) with each numeric field equal to its native-site source (`cost_cents` = `SUM(cost_events.costCents)` for that `heartbeatRunId`), AND **no new `cost_events` row was written by this step**. (Binary: single row + field-equality to native sources + zero added cost rows.)
2. Given an outcome record already written for a `runId`, When `recordOutcome(runId)` is invoked again (retry), Then the record is **upserted, not duplicated** — exactly one row for that `runId` remains and its contents are identical (idempotent on `runId`, NFR-REL-4). **Comparison semantics:** idempotency comparison uses integer `cost_cents` (already converted from float by P1.13). No floating-point comparison needed — cents are integers. Other fields use strict equality. Re-invocation with identical source data produces bitwise-identical outcome record.
3. Given identical run inputs (same runId, same heartbeat_runs data), When `recordOutcome(runId)` is invoked, Then the outcome record output is bitwise identical on repeated invocations (idempotent) — this is P1.14's idempotency guarantee, distinct from P1.5's router determinism. The FR-LEARN-29 rationale (signature inputs + chosen archetype/tier + the binding constraint, e.g. `boundBy:"blast_radius_floor"`) is persisted and reconstructable for that `runId` (NFR-OBS-6a).

## Technical Notes

- **Contracts/Schema (Zod/TS):** `OutcomeRecord` = `{ runId: string, task_type: string | null, archetype: "A".."F", per_role_model_tier: Record<RoleAlias, ModelTierAlias> (key from P1.5 router archetype-role mapping, e.g. `"lead"`, `"worker"`; value from P1.5 router model tier decision, e.g. `"claude-sonnet-4-6"` — no agents.role column required), cost_cents: number, input_tokens: number, output_tokens: number, cached_tokens: number, cost_data_available: boolean (**single semantic rule:** `false` = cost data could not be read — timeout, missing `heartbeat_runs` row, or DB error. `true` = cost data was successfully read from native sites, even if all values are zero. A run with zero `cost_events` rows but a valid `heartbeat_runs` row has `cost_data_available: true` and `cost_cents: 0`. These are distinct from a run where the cost read itself failed.),
timeout_fields: z.array(z.string()).optional() (present only when the M1 30s timeout triggers; lists which native-site reads timed out, e.g. `["cost_events","heartbeat_runs"]`, so the timeout guard can write `cost_data_available: false` alongside the list of timed-out sources), first_pass_accept: boolean (computed: `retry_class === null AND exit_class === "transient"`), exit_class: "transient"|"overflow"|"logic" (mandatory non-null per verified-correct element — answers "why did the current run terminate?"), retry_count: number, retry_class: "transient"|"overflow"|"logic"|null, wall_clock_ms: number }`. Primary key / upsert key = `runId` (NFR-REL-4). Stored as an additive `heartbeat_runs.usageJson.outcomeRecord` key (no new table — backward-compat: rows without the key unaffected). Router rationale persisted alongside (reuse P1.5's `usageJson.routerSelection`). Zod validation schema: `outcomeRecordSchema = z.object({ runId: z.string().min(1) /* Warren assigns runId at DAG submission; format is opaque string, not necessarily UUID. Validation is non-empty string only. */, task_type: z.string().nullable(), archetype: z.enum(["A","B","C","D","E","F"]), per_role_model_tier: z.record(z.string(), z.string()), cost_cents: z.number().int().nonnegative(), input_tokens: z.number().int().nonnegative(), output_tokens: z.number().int().nonnegative(), cached_tokens: z.number().int().nonnegative(), cost_data_available: z.boolean(), timeout_fields: z.array(z.string()).optional(), first_pass_accept: z.boolean(), exit_class: z.enum(["transient","overflow","logic"]), retry_count: z.number().int().nonnegative(), retry_class: z.enum(["transient","overflow","logic"]).nullable(), wall_clock_ms: z.number().int().nonnegative() })` — this is the validation schema for the `heartbeat_runs.usageJson.outcomeRecord` value.
- **Native recording sites (FR-LEARN-28, no synthetic source):** `cost_events` → `cost_cents` (`SUM(costCents)`), `input/output/cached_tokens` (sum of token columns) and `per_role_model_tier` (from `agentId`/`model`), aggregated by `heartbeatRunId`; `heartbeat_runs` → `wall_clock_ms` (timing cols), `retry_count` (`processLossRetryCount`/`retryOfRunId` lineage), `retry_class` (from FR-MG-9 classification); `issues` (via `originKind`/`originId`) → `first_pass_accept` derivation context; P1.15 run-log sink → per-agent output (for cross-reference). **No `activity_log` table exists in any Phase-1 story** — all accept/retry signals come from `heartbeat_runs` status + `issues` fields. **No extra LLM call** — values are read, not generated (§9.4.0 principle 2).
- **Integration points (each wired & exercised):** (1) read `cost_events` aggregated by `heartbeatRunId`; (2) read `heartbeat_runs` timing/retry lineage; (3) read `issues` (via `executionRunId` FK join to `heartbeat_runs`) for accept signal / `originKind`; (4) read P1.5 router selection rationale; (5) idempotent upsert keyed on `runId`.
- **Determinism (FR-LEARN-29):** the router selection consumed here is the deterministic §7-default pick under the blast-radius floor + risk-tier constraint (P1.5); this story does not re-decide it, only records its rationale — and asserts re-running yields an identical choice (NFR-PERF-7 fail-safe to §7 default on error).
- **Files / functions touched:** `outcome-recorder.ts:recordOutcome`, `native-site-readers.ts` (cost_events/heartbeat_runs/issues readers), `outcome-record.schema.ts`.
- **Citation caveat:** File:line references are best-current-knowledge at spec time and may shift during implementation. The derivation logic (which native site supplies which field) is the contract, not the exact line numbers.
- **Guards/limits:** zero added inference (NFR-COST-3 v4 structural compliance — verified by confirming every field in the outcome record has a documented derivation from an existing native field, with no new API calls and no new LLM invocations; testable via (a) code review confirms no external API calls in the outcome-record builder, and (b) the 12-field schema maps 1:1 to the documented sources in these Technical Notes); upsert is idempotent on `runId` (NFR-REL-4).
- **Invocation mechanism (H1):** `recordOutcome` is invoked as a Warren DAG post-step hook in the finalize node (after all agent nodes complete). It runs in-process (no HTTP call) using the Paperclip service layer. Invocation: `recordOutcome(runId: string): Promise<void>` — called from the finalize node's teardown. This is the only invocation path; there is no REST endpoint or CLI trigger for outcome recording.
- **Terminal-status precondition guard (H2):** `recordOutcome` MUST verify `heartbeat_runs.status` is terminal (`'completed'`|`'halted'`|`'failed'`) before writing. If status is `'running'` or `'paused'`, `recordOutcome` throws with a clear error (`"Run {runId} is not terminal (status={status}), cannot record outcome"`) and does NOT write a partial record. Terminal status is the precondition for outcome record creation — this prevents partial/inconsistent records for in-flight runs.
- **retry_class vs exit_class (CC-3):** `retry_class` is distinct from `exit_class` (verified-correct R2 CC-2). `retry_class: null` means "no retry attempted, this is the first pass"; non-null values (`"transient"`|`"overflow"`|`"logic"`) mirror the `exit_class` of the *retried* run (i.e., the reason that run was retried). The outcome record's own `exit_class` field is mandatory non-null per R2 CC-2 — these are two separate fields with different semantics. `retry_class` answers "was this a retry and why?"; `exit_class` answers "why did the current run terminate?". **Naming collision note:** retry_class and exit_class share the same enum values ('transient'|'overflow'|'logic') but represent different concepts. exit_class = how the run exited. retry_class = how the retry (if any) was classified. When retry_class is null, no retry was attempted (first pass). Code must read both fields independently — they are NOT aliases.
- **per_role_model_tier dependencies & storage location (CC-4):** `per_role_model_tier` requires P1.5 model router output (role assignment) and P1.6 Warren node output (model used per agent) — the role column is derived from those upstream sources, not synthesized here. **Storage location:** outcome record is stored as a JSONB key within `heartbeat_runs.usageJson.outcomeRecord`, not as a separate file or table. P1.15 owns the run-log file; P1.14 owns the `outcomeRecord` JSONB key within the `heartbeat_runs` row. There is no "alongside P1.15" relationship — the outcome record lives in `heartbeat_runs`, the run-log lives wherever P1.15 puts it.
- **per_role_model_tier alias alignment (P1.14-M4):** `per_role_model_tier` captures the model the **ROUTER** assigned (from P1.5's model tier decision), NOT the model the worker actually used (which may differ if P1.6 overrides at runtime). Source: P1.5 router decision stored in `usageJson.modelTier` at route time. P1.14 reads the router's assignment, not P1.6's runtime override. Values use the same generational model aliases as P1.5's model router (e.g., `"claude-sonnet-4-6"`, `"openrouter/z-ai/glm-4.6"`). No translation or normalization — the value is the raw model string from the router's tier decision.
- **first_pass_accept derivation:** `first_pass_accept` is a boolean computed from native fields: `retry_class === null AND exit_class === "transient"`. Semantically: the run completed on its first attempt (no retry) and terminated normally (not overflow or logic error). This is derivable from fields already in the outcome record — zero added inference, no external threshold required.
- **task_type source & runId→issueId join path:** `task_type` is read from the Paperclip issue's `originKind` field, set during P1.3 Seeds decomposition (e.g., `"seeds_story"`, `"seeds_task"`). This is a read of an existing native field — no new source required. If the issue lacks `originKind`, `task_type` defaults to `null` (consistent with orphan-run guard L7). **Join path:** `issues` has `executionRunId` FK→`heartbeat_runs.id` (established by P1.16 §8.4 hop 2). Resolution: `SELECT i.id, i.originKind FROM issues i JOIN heartbeat_runs hr ON i.executionRunId = hr.id WHERE hr.runId = $1 AND i.companyId = $2`. No separate `latestRunId` column is needed — the existing `executionRunId` FK provides the join path, avoiding a redundant denormalized column. If no match is found, `task_type` is nullable (`null` default).
- **Missing cost_events guard (INV-5):** When a completed run has zero `cost_events` rows for its `heartbeatRunId`, the outcome record's cost/token fields (`cost_cents`, `input_tokens`, `output_tokens`, `cached_tokens`) are set to `0` with `cost_data_available: true` (the read succeeded, returning an empty set — distinct from a failed/timed-out read where `cost_data_available: false` per the single semantic rule on line 40). Zero `cost_events` may indicate a P1.13 violation (every run should write ≥1 `cost_events` row); the outcome record faithfully records what the native sites returned, and downstream consumers flag zero-cost runs for investigation.
- **Timeout guard (M1):** `recordOutcome` has a 30-second wall-clock timeout. If any native-site read exceeds 30s, the outcome record is written with `cost_data_available: false` and a `timeout_fields` array listing which sources timed out. Partial data is still recorded. This prevents a hung native-site read from blocking the finalize node indefinitely.
- **Retry cost aggregation (M5):** In retry scenarios, multiple heartbeat_runs rows may exist for the same runId. recordOutcome aggregates cost across ALL heartbeat_runs for the given runId (SUM across retries). The outcome record's `cost_cents` reflects total cost across all retries, not just the final attempt.
- **heartbeatRunId discovery (M6):** recordOutcome discovers heartbeatRunIds via: `SELECT id FROM heartbeat_runs WHERE runId = $1 AND companyId = $2 ORDER BY createdAt ASC`. Multiple rows = multiple retries. Cost aggregation sums across all matching rows.
- **Archetype values (M7):** Archetype values ('A'..'F') are defined by P1.5's model router archetype classification. P1.14 reads the archetype from the outcome record's `router_rationale.archetype` field (written by P1.5 at route time). P1.5 owns the archetype definition; P1.14 consumes it. See P1.5 Technical Notes for archetype definitions.
- **Wall-clock budget (L6):** recordOutcome wall-clock budget: ≤500ms (native-site reads) + ≤100ms (aggregation + JSONB write). Total ≤600ms. Exceeding this triggers the timeout guard (M1) and writes a partial record. This satisfies NFR-COST-3's zero-added-inference constraint with a concrete execution envelope.
- **Orphan run guard (L7):** If heartbeat_runs exists for runId but no matching issues row (via executionRunId FK join), recordOutcome logs a warning and writes the outcome record with `task_type: null`. The outcome record is still valid — task_type is nullable for this exact scenario. No other field is altered; the guard touches only `task_type`.

## Security Invariants

> Triggered: cost/budget (the outcome record reads ledger cost/spend; the substrate must not add spend nor mis-attribute cost).

- **INV-1 (cost/budget — zero added inference):** `recordOutcome` performs NO LLM/tool call that incurs spend — it only reads native ledger/trace rows and upserts a record; a test asserts `recordOutcome` writes **0 new `cost_events` rows** (NFR-COST-3 v4: the learning tax is one event-driven retain, never an extra inference).
- **INV-2 (cost/budget — faithful cost attribution):** `cost_cents` in the outcome record equals `SUM(cost_events.costCents)` for the run's `heartbeatRunId` exactly — the record never fabricates or rounds cost away from the ledger source of truth (NFR-ACC-3: cost derived solely from `cost_events`).
- **INV-3 (idempotency — no duplicate-write inflation):** the upsert keys on `runId`; a retried run cannot create a second outcome record (NFR-REL-4), so a re-run never double-counts cost or inflates the Layer-B substrate.
- **INV-4 (secrets):** the persisted outcome record and router rationale contain no model/provider API key or bearer token — only field values read from native rows.
- **INV-5 (cost/budget — missing cost_events guard):** when `cost_events` rows are absent for a completed run's `heartbeatRunId`, the outcome record's cost fields are set to `0` with `cost_data_available: true` (read succeeded, empty set). A failed or timed-out `cost_events` read yields `cost_data_available: false` with `timeout_fields` listing the failed source. This makes the distinction between "zero cost because none recorded" and "zero cost because the read failed" mechanically detectable downstream.
