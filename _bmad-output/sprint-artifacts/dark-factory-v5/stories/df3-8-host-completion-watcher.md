## User Story

As the factory operator who dispatched an unattended run and then closed the laptop,
I want the *next* host invocation — whenever that is — to pick the finished run up after the fact and walk it to the same approvable pause it would have reached had I stayed connected,
so that reaching the pause depends on the host coming **back**, not on the host staying **up** for the whole run.

## Overview

`fleet observe [<run-id>|--all]` is a bounded, re-entrant, **exiting** invocation that finds finished
in-box runs the host never watched and drives DF3.7's chain for each one. It adds no observer and no
chain: it enumerates candidates (open record, live listable box), takes the same per-run invocation
lock the run-scoped verbs already take, re-reads the approval extension **inside** that lock, and
calls DF3.7's composition. Nothing is scheduled by this story — `--all` is idempotent precisely so
the operator's own `cron`/`launchd` can run it, which is the only shape that keeps DF3.7's
INV-IBOX-16 literally true on its *"no watcher process"* limb. While it is holding a box's attention anyway it
counts one thing the arc currently measures nowhere: how often a box reboots after dispatch, the
tmpfs marker-loss window DF3.7 knowingly accepts and left without a revisit trigger.

**What this does not deliver, stated before an AC implies otherwise.** The schedule runs on the
operator's own machine, so a laptop that is closed runs no `cron` tick either: this story does not
make the *host* unattended, it removes the requirement that the host stay attached **for the
duration of the run**. The honest claim is bounded twice — a finished run reaches the pause on the
first host invocation after it settles, and only while its box is still alive and its tmpfs marker
still there. Both windows close when an operator runs `sandbox-reap --yes` against a record past
`staleAfterMs`, and losing that race is AC3's typed refusal rather than a synthesized pause. Nothing
here bounds the bill; DF3.7 was right about that and this story does not claim otherwise.

## E2E Slice

**Demonstrable behavior:** Given an in-box run started by `fleet run <run-id>` and never observed in
the foreground, When the starting process has exited and DF1.10's engine later writes
`/run/qds-run/<runId>/journal/final.json`, Then a
separate `fleet observe --all` invocation reads that marker through `readMarkerVerdict`, acquires the run
lock, finds no `extensions.approval`, and calls DF3.7's chain — leaving `<runsDir>/<runId>.bundle`
present, `closedAt` set, and `extensions.approval.state = "awaiting-approval"` written **only** by
the gate through `reverify()`'s own `requestApproval`. Observable artifacts: one
`{ event: "run-observed", runId, sweep_ms }` line per driven run, one
`{ event: "sweep-complete", candidates_enumerated, runs_observed, runs_unsettled, runs_engine_dead, box_reboot_after_dispatch, runs_lost_to_reboot, uptime_unknown }` line, and a diff in which
`approval-gate.ts`, `approvers.ts`, `push.ts` and `run-record.ts`'s approval-extension block have
zero changed lines.

**Wiring closed:** On completion of this story, a run whose host disconnected at any point after
dispatch reaches an approvable pause on the first host invocation after it settles — no operator
attendance during the run, and no second command once the schedule exists — using only code merged
by this story plus DF3.7's observer and
chain composition, DF3.1's verb/exit-code surface and per-run lock, DF1.10's in-box engine and its
terminal marker, and DF2.6's unmodified reaper. **No stub, no `TODO: wire later`.** The **schedule**
is out of scope by construction and stays the operator's: this story ships a verb and documents a
cron line, never a process.

**Dependency edges (predecessors):** DF1.10, **DF2.2** (`readBoxFile`, for both the marker and `/proc/uptime` — an Infra Prereq of this story), DF2.6, DF3.1, DF3.7. **Not a predecessor, but the story that closes AC2(e)'s residue: DF2.11** — the sweep ships and is correct without it; what DF2.11 removes is the unlocked-reaper race this story documents and cannot fence. DF1.10 is a *direct* edge, not
one inherited through DF3.7: AC7's detachment is produced by DF1.10's `fleet run <run-id>`, which
starts `qds-run@<runId>.service` and returns without holding the run (DF1.10 AC1) — the only shape in

> **Not an edge — DF3.2 (fleet lock):** `src/fleet/fleet-lock.ts` is the single-*operator* mutex

## Acceptance Criteria

1. **(make-or-break — the host learns after the fact, and the chain stays single)** Given a settled marker on a box whose dispatch invocation is long gone, When `fleet observe` runs, Then the run reaches `awaiting-approval` by **calling DF3.7's chain composition**, and this story's module re-implements no step of harvest → teardown → `reverify()` and adds no second automatic **entry point** to it — it is a second *caller* of the one entry point (AC5), which is a different and openly-paid-for thing. DF3.7's AC1 static import fence is **extended verbatim to `src/fleet/observe.ts`**: it imports none of `approval-gate.ts`, `approvers.ts`, `push.ts`, `run-record.ts`'s approval-extension block, asserted by the same grep test. *Negative control: an implementation that inlines its own harvest→teardown→reverify sequence reaches the same state, passes a naive "did it reach awaiting-approval?" test, forks the one chain the arc has, and MUST fail this one.*
2. The sweep is serialized per run, the lock is taken **by the sweep and never inside DF3.7's module**, and the pre-flight is re-read **inside** it. <br />**(a)** Candidates are records with `closedAt` unset whose box is live and listable; they are driven **one at a time**, never concurrently. <br />**(b)** `src/fleet/observe.ts` acquires the per-run invocation lock itself and calls DF3.7's composition already holding it, passing that acquisition's `RunLockHandle` and `maxTicks: 1` in `deps` (DF3.7's Files to Modify defines both) — one marker read per candidate, never the foreground window; DF3.7 AC5's "record already carries `extensions.approval`" refusal is evaluated **after** acquisition, never before. The acquisition may **not** be pushed down into `src/fleet/run-completion.ts`: `acquireRunLock` is explicitly not re-entrant (`RunLockReentrantError`, `scripts/lib/run-lock.ts` — the `RunLockReentrantError` class, thrown by the `moduleState().held.has(lock)` guard at the head of `acquireRunLock`), and DF3.7 ships `observeAndDriveChain` lock-agnostic by construction with "the caller already holds `<runsDir>/<runId>.lock`" as its documented precondition — so a lock inside the shared composition would refuse whichever sibling caller already holds it. <br />**(c) N observers, one run — decided by one lock, not by a convention per caller.** Every automatic caller of the chain — this sweep, DF3.7's single-run `fleet observe <run-id>`, and DF6.1a's fix run — acquires the **same** per-run invocation lock through the **same** code path before any pre-flight read; the losers get `RunLockedError`, which the **single-run** form `fleet observe <run-id>` reports as DF3.1's exit 5 ("refused before provisioning", `verbs.ts:117-124`) and which the **sweep** records as a counted `lock-refused` skip inside a pass that still exits 0 (AC6) — the exit code belongs to the invocation, and a sweep's invocation did not fail. Either way the loser re-observes idempotently on the next tick. The argument does not depend on how many callers there are, only on all of them taking the lock, so a future fourth caller inherits the exclusion by using the entry point rather than by being enumerated here. Two honest residues, neither closed by this story: a hand-run `scripts/reverify.ts` takes no run lock, and `fleet dispatch`'s own acquisition is deliberately **non-fatal on failure** (`scripts/fleet.ts:1966-1985` — "a refusal here must NOT abort the mint"), so F106 is narrowed, not retired. <br />**(d)** A **stale** lock is a different event from a busy one and is reported as one: `RunLockedError` already distinguishes them and carries the `rm` line for the dead-holder case (`scripts/lib/run-lock.ts:54-64`). A sweep killed mid-chain leaves a real lock file behind, and no later tick clears it — so a stale refusal is a named, remediated outcome, never folded into the benign skip count. <br />**(e) What the mutex does NOT exclude, stated because AC3 is about exactly that process.** `sandbox-reap --yes` calls `teardownSandbox` **directly** (`src/providers/reaper.ts:726`) and takes **no run lock** — unlike every other destructive path in the repo (`scripts/sandbox-teardown.ts:230`, `scripts/fleet.ts:4257`). A mutex cannot exclude a process that never looks at it, so a reap that fires while this sweep is mid-chain on the same run races two `teardownSandbox` calls on one box: two harvests for one `<runsDir>/<runId>.bundle`, two destroys, two `closedAt` writes, and a `reverify()` against a bundle the loser may have half-written. This story **does not close that**, and does not need to: **DF2.11 ("Teardown Run-Lock Capability + Read-Only Cost Ledger") owns the fix** and closes it structurally rather than by discipline — `teardownSandbox` takes a **required `RunLockHandle`**, so an unlocked call fails to compile and non-holders go through `withRunLock(...)`. That is why this story keeps `src/providers/reaper.ts` byte-identical (INV-IBOX-18) instead of adding a seventh-and-a-half per-caller acquisition: per-caller discipline is exactly how the next call site forgets. Until DF2.11 lands, this story owes three things: (i) never claiming the exclusion it does not have — AC2's guarantee is scoped to callers of DF3.7's entry point and says so; (ii) a `--help` line, **temporary and marked as such pending DF2.11**, stating that `sandbox-reap --yes` must not be run against a fleet while a sweep is in flight; and (iii) AC3's `completion-unwitnessed` arm for the one case the sweep can actually detect — a collection that landed before it acquired the lock. *Negative control: a story text or an implementation that presents the per-run lock as excluding the reaper asserts an exclusion no code enforces, and MUST fail.* *Negative controls, all three MUST fail: an implementation that checks the extension before acquiring the lock lets two overlapping cron ticks both enter `reverify()` on the same run, turning `src/reverify/worktree.ts:319`'s pid guard (TECH_DEBT F106) from latent to live and passing every single-process test; one that acquires the lock inside `run-completion.ts` breaks every sibling caller that already holds it — DF3.7's `fleet observe <run-id>` and DF6.1a's fix run — with `run-lock-reentrant`, while passing every sweep-only test; and one that counts a stale lock as a busy skip reports a permanently unobservable run as healthy on every tick forever.*
3. Given DF2.6's `stale-record` → `teardown` arm collects an open record past `staleAfterMs` (4 h default) with harvest, destroy, revoke and `closedAt` but **no `reverify()`**, Then this story changes **not one reaper input**: no `staleAfterMs` edit, no suppression file, no reprieve, and `src/providers/reaper.ts` is byte-identical after. **The guarantee is the refusal, not the interval.** There is no scheduled reaper to outrun — `sandbox-reap` is an operator CLI, dry-run unless `--yes` (`scripts/sandbox-reap.ts:7-9`) — so a default sweep interval derived from `staleAfterMs` reduces exposure and is documented as the heuristic it is, named in code with the derivation and the reaper citation on it so an operator who lowers `staleAfterMs` sees what else moves. It may **not** be stated as winning a race. What is load-bearing is being **correct when it loses**, and there is exactly one point at which that can be observed: the record re-read **inside** the run lock (AC2b). A record that was a candidate at enumeration and reads `closedAt` set at that re-read was collected between the two — by the reaper, or by a concurrent `fleet teardown`. It is re-entered at the `reverify()` leg **only if this invocation had already witnessed the marker itself** before the collection, and is otherwise refused with a typed `completion-unwitnessed` payload naming the collection. A record closed *before* enumeration is never a candidate at all (AC2a) and this arm does not concern it — the sweep has no witness for it and never will, and reconstructing one from a bundle is what INV-IBOX-18 forbids. This story persists no observation record, so "witnessed" means witnessed by the running invocation and nothing is reconstructed. Once **DF2.11** lands, the window narrows to "collected before we acquired the lock", which is what makes this arm cleanly testable — a second process holds the lock while the first enumerates. *Negative controls, all three MUST fail: an implementation that routes any closed record carrying a bundle into the gate promotes a run killed mid-flight on evidence no marker ever witnessed; one that grants finished boxes a reaper reprieve, which removes the only bound the bill has and edits a merged story's classifier; and one whose test for this arm hand-constructs a state its own enumeration can never reach, which asserts nothing about the code path that fires in production (`tests/fleet/observe.test.ts`).*
4. **(the revisit trigger this story takes ownership of)** Given each live candidate box, Then the sweep reads `/proc/uptime` through the **same** `readBoxFile` — adding no substrate command string under `src/fleet/` — and counts `box_reboot_after_dispatch` alongside `runs_observed` into this story's evidence JSON. <br />**(a) The arithmetic is a duration comparison, and a naive one is inverted.** `store.create` stamps `createdAt` **before** `driver.create()` boots the VM — both run inside `provisionAdmittedRun`'s `within("create", …)` span (`src/fleet/dispatch.ts`), cited by symbol rather than by line because that region also carries EEXIST/`run-id-in-use` handling and a line cite there rots — so a first boot *always* postdates `createdAt` and "derived boot time is later than `createdAt`" would count **every** box as rebooted. A reboot is instead `uptimeSeconds < (hostNow − createdAt) − PROVISION_LAG_MARGIN_MS`: the box has been up for less time than the run has existed, by more than a **named** margin covering provisioning and first-boot lag. Uptime is a *duration*, so host↔box clock skew never enters; only `hostNow` and the host-stamped `createdAt` do. **`hostNow` is sampled immediately before each candidate's `/proc/uptime` read, never once per pass**: a serial pass can span minutes, and a per-pass `hostNow` drifts the comparison against every candidate but the first — toward false negatives for the ones read late. The evidence JSON carries the raw `hostNow`, `createdAt` and `uptimeSeconds` per box alongside the derived `(hostNow − createdAt) − uptimeSeconds`, so the margin can be re-derived from data rather than re-argued. Anything inside the margin is `uptime_unknown`, never "no reboot". <br />**(b) It measures the window, and on the candidate in hand it also DECIDES.** A reboot destroys a marker only if one had already been written, so the *counter* claims exactly that much and is never reported as a confirmed loss. But for that candidate the reboot is **terminal regardless**: `/run` is tmpfs so any marker is gone, and the unit has `Restart=no` and **no `[Install]` section** (`oci/exedev/systemd/qds-run@.service:169`, `:277-285` — "an ENABLED instance is pulled in by multi-user.target on EVERY subsequent boot, re-walking phases whose git commits and LLM spend already happened"), so no engine will restart and no marker will ever appear. A candidate with a confirmed reboot (`uptimeSeconds < (hostNow − createdAt) − PROVISION_LAG_MARGIN_MS`) **and** an absent marker is refused for that pass with a typed `{ code: "run-lost-to-reboot", message, remediation }` naming the box, the run and `fleet teardown <runId>`, reported **once per pass** with its own `runs_lost_to_reboot` counter and never folded into the benign skip count. The box is left **alive and listable** with its `$HOME` evidence intact (DF2.2 INV-5) — the refusal is the operator's cue, not this story's licence to destroy. **The refusal does not retire the candidate, and the reason is stated rather than hidden:** a liveness reading cannot separate "started, then rebooted" from "never started, then rebooted". Both read `inactive`/`unknown`, because the unit carries **no `[Install]` section** (`oci/exedev/systemd/qds-run@.service:277-289`) and is therefore never re-loaded after a boot — the same fact that makes a started run's reboot terminal makes a never-started run's reboot indistinguishable from it. Retiring on that reading would permanently refuse a run `fleet run <runId>` would still start correctly, so the sweep reports and keeps it. Exact retirement needs the `startedAt` stamp DF3.7's Technical Notes flag to the arc owner as a DF1.10 seam; **until that exists this arm reports, and `run-engine-dead` below is the arm that retires.** `uptime_unknown` is never this arm. <br />**(d) `run-engine-dead` is the arm that retires, because `failed` is unambiguous.** DF3.7 AC2(d) issues `run-engine-dead` only on `unitActivity === "failed"` — an engine that started and died, which `Restart=no` (`qds-run@.service:169`) guarantees no marker will ever follow. That is the arc's **most common** permanently-unobservable candidate and it carries no reboot signal at all, so the sweep gives it the disposition AC4(b) cannot safely give the reboot case: reported once per pass with its typed payload, counted in `runs_engine_dead` on the `sweep-complete` line, and **excluded from subsequent enumeration** on the strength of that re-derived reading (nothing persisted). It is never a benign skip. *Negative controls, all MUST fail: an implementation that retires `run-lost-to-reboot` on a liveness reading that cannot tell a never-started run from a dead one, which permanently refuses a run `fleet run` would have started; one that folds either `run-lost-to-reboot` or **`run-engine-dead`** into the benign skip count, which parks the arc's most common dead run at the head of an oldest-first queue and reports every tick as healthy with `runs_observed: 0`; one that counts the reboot and reports nothing actionable, leaving the run to end at the reaper's witness-less collection — the outcome this story exists to end; one comparing derived boot time against `createdAt` with no margin; and one that **destroys** the box on either arm, violating INV-5 and INV-IBOX-18.* <br />**(c) The counter is per distinct `runId` per sweep and the threshold is over distinct `runId`s, not summed sweep lines.** Nothing is persisted, so a box rebooted once and re-observed on twenty ticks emits twenty lines; the story says so and defines the denominator rather than letting an aggregator infer it. **Named revisit threshold: 2 distinct runs, or 2 % of distinct observed unattended runs, whichever comes first** — evaluated against the accumulated `_bmad-output/evidence/df3-8/` set at the arc retro, by the arc owner, which is where the trigger stops being a number in a file. Reaching it reopens DF3.7's rejected `$HOME`-persistent marker (its Technical Notes: *"Revisit only if a measured reboot rate makes the loss window material"*) as an ADR appendix. *Negative controls, all three MUST fail: an implementation comparing derived boot time against `createdAt` with no margin, which counts every healthy box and trips the threshold on its second observation; one that reports a reboot as a confirmed marker loss, overstating its evidence; and one that ships the watcher with no counter, leaving the trigger unowned — the exact state this story exists to end.*
5. Given the delivered artifact, Then it is a verb and not a process: one bounded pass, a typed exit, no PID file, no launchd plist, no systemd user unit, no `--daemon` flag, nothing that stays resident. **DF3.7's INV-IBOX-16 has three limbs and this story is honest about each.** *No watcher process* and *no new state* are preserved **literally** — a scheduled *invocation* is not a watcher process, the scheduling entry is documented in `--help` and shipped nowhere, and no second expiry clock is added (the sweep reads DF2.6's ceiling and owns it not; a candidate by definition carries no approval extension, so there is no `expiresAt` in play). The third limb reads, as corrected in DF3.7's own text, *"at most one automatic caller at a time, each holding the per-run invocation lock"* — so this story is a **sanctioned caller, not an amendment**: it takes the per-run invocation lock around the shared composition (AC2b), which is what that limb requires of every caller and is strictly stronger for `src/reverify/worktree.ts:319`'s precondition than "one caller by convention" ever was. Nothing here is reinterpreted silently, and no clause in DF3.7 is left to amend. *Negative controls, both MUST fail: an implementation that ships any always-on host supervision — a plist, a user unit, or a loop flag holding the process open — adds a second supervision surface beside DF2.10's; and one that adds an automatic caller **without** taking the lock, which is the price the limb charges and the one thing that makes the mutex real.*
6. **The exit table is DF3.7's, cited and not restated.** `observe`'s `exitCodes: [0, 1, 2, 4, 5, 6]` are declared once on DF3.7's verb descriptor (`src/fleet/verbs.ts`) because that registry is a contract DF3.5's skill-contract test compares against what the verb returns (`verbs.ts:86-90`), and an undeclared code lands in a generated skill's default branch. `--all` adds **no** code: in a sweep, a per-run refusal — `completion-unwitnessed`, `run-lost-to-reboot`, `run-engine-dead`, `box-unreachable`, a busy or stale lock — is **counted and reported on its own line**, never the sweep's exit code (and never a *benign* skip: AC4(b) and AC4(d) give the two permanently-unobservable arms their own counters and once-per-pass reporting), and a partial pass that hit `max-candidates-per-pass` or the wall-clock budget still exits **0**. Only a failure to complete the pass itself is non-zero. Given any per-run outcome, Then it is typed `{ code, message, remediation }` and no box is destroyed on an absent, unreadable or unparseable read — DF3.7's AC2 classification and AC3's `run-completion-unobserved` payload are consumed unchanged and never converted into a teardown by this story. A sweep that drove **zero** runs exits **0**: nothing to do is not a failure, and a cron line that mails the operator on every quiet tick is a line the operator disables. <br />**The documented cron line names its working directory, and the verb refuses at start-up if it is not a git worktree.** `reverify()` resolves its tree as `deps.hostRoot ?? process.cwd()` (`src/reverify/runner.ts:217`), cron runs from `$HOME` and launchd from `/`, and this line is the one artefact whose correctness is entirely this story's. The documented form is `*/N * * * * cd /path/to/QDS-Factory && bun scripts/fleet.ts observe --all --driver exedev >> ~/.qds/observe.log 2>&1`, and the sweep resolves `hostRoot` **once, before any candidate is driven**, asserts it, and passes it explicitly into every chain call (DF3.7's Technical Notes state the same precondition for the single-run form). *Negative control, MUST fail: a verb that discovers an unusable host root inside `reverify()` has already harvested, destroyed the box and set `closedAt`; every scheduled run then ends closed with no pause and no path back, while the sweep reports `runs_observed` per tick and reads as healthy — strictly worse than the witness-less collection this story exists to end.* *Negative control: an implementation that exits non-zero on an empty sweep trains the operator to ignore the schedule and MUST fail this one.*
7. Given the evidence for this story, Then the detachment is **real**, not simulated: the host process exits **before** DF1.10's in-box engine writes the marker, and a separate `fleet observe` invocation drives the chain to the pause. The exit is produced by DF1.10's `fleet run <run-id>` — start the per-run systemd unit, return — and **not** by backgrounding a host process, which would leave a host process to fail and prove nothing. **Scheduling caveat, same as DF3.7's:** this needs DF1.10's real in-box engine on a re-pinned image to have landed; until it does there is no marker written by anything but a test's own hand, and a planted marker is explicitly not evidence for this AC. A FakeDriver suite is legitimate unit coverage for candidate selection, the lock discipline and the uptime arithmetic, and MUST NOT be the sole evidence for AC1 (DF3.4 AC6's no-doubles rule).

## Technical Notes

- **Contracts/Schema:** this story persists **nothing**. No observation record, no sweep cursor, no field on DF2.1's run record, no new marker. The marker is the state **for a run the chain has not yet driven**, and `closedAt` is the state for one it has — the chain's own teardown destroys the box and the tmpfs marker with it, so what keeps a driven run out of the next pass is AC2(a)'s candidate filter, not the marker. Between the two, every sweep is a fresh read with nothing persisted; that is what makes `--all` safely re-entrant. One honest exception to "leaves nothing behind": a sweep killed mid-chain leaves the run-lock file it took, which is a real artifact and is why AC2(d) reports a stale refusal as its own outcome rather than a benign skip. Its only new emissions are log/evidence counters.
- **Ordering against the reaper, and what the numbers do and do not buy.** Marker written at *t*; the reaper classifies `createdAt + staleAfterMs` (4 h default) as stale **whenever an operator next runs `sandbox-reap --yes`** — it is a threshold, not a timer, so there is no wall-clock deadline to beat. Deriving the documented sweep interval from `staleAfterMs` therefore reduces the exposure window and nothing more; it is a named constant carrying the derivation and the reaper citation so an operator who lowers `staleAfterMs` sees what else moves, and it is not a correctness argument. A run collected first is not lost data (the reaper harvests), it is lost *witness*: AC3's typed refusal, not a synthesized pause.
- **Region ownership on shared files, and the one place the lock may not go.** `src/fleet/observe.ts` is new and this story's own, and it is where `acquireRunLock` is called. That is the upgrade trigger `scripts/lib/run-lock.ts:931-932` names — "library callers bypass the lock … an embedder (not a CLI) becomes a supported caller" — and this story is that embedder, so the note is retired rather than left standing false. `acquireRunLock` returns the resolved lock path (`:934`, `:950`), which is the value DF2.11 brands as `RunLockHandle` and which this story passes into DF3.7's `deps.runLock` and thence, unchanged, to `teardownSandbox`; its `held` map and signal-release handler are process-global (`:938-951`), which is what makes serial acquire/release across a pass safe in one process and is why the pass is serial (AC2a). `src/fleet/run-completion.ts` is **DF3.7's** and this story **does not modify it**: DF3.7 already ships `observeAndDriveChain` acquiring no lock, because `acquireRunLock` is not re-entrant (`RunLockReentrantError`, `scripts/lib/run-lock.ts`) and every caller takes the lock itself — an acquisition pushed down there would refuse whichever sibling already holds it. The classifier, the poll, the window and the typed payloads are untouched, and `run-lock.ts` is not among the four fenced modules, so DF3.7's AC1 fence is unaffected. `src/fleet/verbs.ts` and the `scripts/fleet.ts` verb-dispatch block are **DF3.1's**: this story **adds only** the `--all` flag on DF3.7's `observe` descriptor and the sweep's block, minting no exit code. `src/providers/reaper.ts` and `src/providers/quota.ts` are **DF2.6's** and are read, never written.
- **Guards/limits.** Every bound but two is inherited: the per-read deadline and byte cap come from `readBoxFile`, the unusable-tick and skip-tick limits from DF3.7's shared classifier, the lock timeout from `run-lock.ts`, and the sweep interval is derived from `staleAfterMs`. **The observation window is the one bound this story does NOT inherit.** DF3.7's window is a foreground *wait* for a run that has not settled yet, deliberately sized past the 1 h fan-out ceiling; a sweep is not a wait. Each candidate gets **one** marker read and, on `absent`, **one** liveness probe, then the sweep moves on — a run that has not settled is simply a candidate again on the next tick, which is what makes `--all` re-entrant. Inheriting DF3.7's window would park one run's lock for hours and serialise the whole pass behind a run that had not finished (AC2a drives candidates one at a time), and the next tick would find every remaining candidate locked. The two bounds this story does mint, named rather than implied: `PROVISION_LAG_MARGIN_MS` (AC4a) and a **max-candidates-per-pass**. The latter bounds a **count, not a duration**: each candidate costs up to two `DEFAULT_PER_CALL_DEADLINE_MS` reads and, if settled, a full chain including `reverify()`'s test suite, all serially (AC2a) — so the pass also carries a **wall-clock budget, checked between candidates**, and exceeding either is the same counted, logged partial pass. Overlapping sweeps are safe by the lock (AC2c) but wasteful, so the documented cron interval is stated to exceed the observed worst-case pass in the live e2e's own evidence, in the same voice `PROVISION_LAG_MARGIN_MS` is set. A partial pass is never a truncation the operator has to infer — and because a driven run gains `closedAt` and leaves the candidate set, the next tick makes progress; a candidate that *refuses* every pass does not, so enumeration is ordered oldest-`createdAt`-first and the partial-pass line names the count left behind, so a permanently refusing head cannot silently starve the tail. The substrate produces two permanently-refusing cases, and they are bounded differently on purpose: an engine that started and died is retired by AC4(d)'s `run-engine-dead` arm on the unambiguous `failed` reading, which is what keeps this paragraph's ordering argument true in practice; a box rebooted after dispatch is *reported* once per pass by AC4(b) but not retired, because that reading cannot be separated from a run that was never started, so it costs one pass's two reads per tick until an operator acts on the refusal. That residual cost is the price of not killing startable runs, and it is stated here rather than left for a dev to discover.
- **`/proc/uptime` is a file, deliberately.** Reading it through `readBoxFile` means the reboot measurement inherits the same bounded-read discipline as the marker and adds **zero** `sh -c` strings under `src/fleet/` (`src/fleet/dispatch.ts:63-66`'s DoD). Unparseable or absent uptime is `unknown`, counted separately, and never scored as "no reboot" — a measurement this story exists to make must not be quietly floored at zero. DF1.11's per-engine-start `boot_id`/uptime row corroborates the same fact from inside the box and is cited, not required: the sweep must work on a box whose engine never started. **Open measurement, recorded rather than asserted:** the 2026-08-31 probe does not contain a provisioning-to-first-boot duration, so `PROVISION_LAG_MARGIN_MS` has no measured basis yet. It is set from the first live e2e's own observed lag with a stated multiple, and the evidence JSON carries the raw `(hostNow − createdAt) − uptimeSeconds` per box so the margin can be re-derived from data instead of re-argued — a counter whose threshold rests on a guessed constant would be the same unowned assumption this story exists to retire.
- **Considered and rejected: a resident host watcher.** A long-lived process is permitted on the operator machine and would poll more tightly. It is rejected because it buys nothing the operator's `cron` does not already give — the runs this story serves take minutes to hours, not seconds — while costing a supervision surface (start, restart, log rotation, staleness) beside DF2.10's systemd unit, and while forcing DF3.7's INV-IBOX-16 to be reworded from "no watcher process" to "no watcher process except this one". The re-entrant verb keeps **that limb** literally true. It also buys nothing on the case the user story opens with: a resident process on a closed laptop is as absent as a `cron` tick on one. Revisit only if a measured observation latency, not a hypothesis, makes the interval material.
- **Deviation/assumption (Deviation 1, restated where an implementer will look):** DF3.7 AC3 cites the reaper's `record-claim-refused` arm, which guards **destroy**; the arm that actually fires on an aged **open** record is `stale-record` → `teardown`, which harvests and closes without ever calling `reverify()`. The correction is about *which arm and what it costs* (the witness), and it explicitly **does not** correct DF3.7's billing sentence — `sandbox-reap` is dry-run unless `--yes`, so an unobserved box does bill until an operator acts. No invariant is weakened: DF3.7's INV-IBOX-14/15 are inherited exactly as written, and INV-IBOX-16 already reads "at most one automatic caller at a time, each holding the per-run invocation lock", which this story satisfies rather than amends (AC5). The one DF3.7 edit this correction still asks for is its AC3 arm citation, a one-clause edit to that story and not a change to this one's shape.

## Observability Contract

- Every sweep logs `{ requestId, runId, event, sweep_ms }` — `event ∈ run-observed | candidate-skipped | lock-refused | completion-unwitnessed | run-lost-to-reboot | run-engine-dead | sweep-complete`, **plus every event DF3.7's module emits on the invocation's own channel, unchanged** — this story mints no second vocabulary for a line DF3.7's code writes. Marker bytes are never echoed and no credential material is read or logged.
- `requestId` is the sweep invocation's own and is stamped on every per-run line, while each driven run's chain carries the run's **own** `dispatchRequestId`, read off the run record's correlation stamp exactly as DF3.7's Observability Contract specifies (`stampCorrelation`, `src/fleet/dispatch.ts:2667`) — the sweep did not dispatch the run and cannot mint that id. So a run observed by a sweep joins to its pause on the record's key, which is the one DF5.3 already uses, with no second key minted here; errors carry `{ code, message, remediation }`.
- Sub-timings and counters: `sweep_ms`, `chain_ms` per driven run, plus `candidates_enumerated`, `runs_observed`, `runs_unsettled`, `runs_engine_dead`, `box_reboot_after_dispatch`, `runs_lost_to_reboot`, `lock_refused`, `completion_unwitnessed` and `uptime_unknown` on the `sweep-complete` line, which together account for `candidates_enumerated` minus any partial-pass remainder — a pass over 30 candidates of which 28 are still running must report that, not `runs_observed: 2` with no denominator — `runs_lost_to_reboot` counts the AC4(b) terminal refusals and is a strict subset of `box_reboot_after_dispatch`, so the measurement and the decision stay separately readable. `chain_ms` is **absent, not `0`**, on a run that was skipped — `0` is a lie shaped exactly like an instantaneous chain (`src/fleet/approval-gate.ts:1124-1137`, deferred item D8).

## Security Invariants

- **INV-IBOX-17 (a sanctioned caller, and the mutex it takes):** the sweep is a *caller* of DF3.7's chain and never a parallel implementation of it, and DF3.7's AC1 import fence extends to `src/fleet/observe.ts` unchanged, so this module cannot acquire the ability to write `extensions.approval` even if a later edit wanted to. It is **one of the three automatic callers** DF3.7's corrected INV-IBOX-16 sanctions (that story's single-run verb, this sweep, DF6.1a's fix run), and it pays the same price each of them pays: one run at a time, each under the per-run invocation lock taken by the caller — `observe.ts` here, never inside DF3.7's module, because the lock is not re-entrant — with DF3.7 AC5's pre-flight re-read **inside** the lock. That ordering is the whole invariant — evaluated outside it, two sweeps both pass and F106's one-process-per-invocation precondition (`src/reverify/worktree.ts:319`) stops holding. **What the lock does not fence, said as plainly as DF3.7 said it:** a hand-run `scripts/reverify.ts` takes no run lock and is unfenced today and after this story; `fleet dispatch`'s own acquisition is non-fatal on refusal (`scripts/fleet.ts:1966-1985`); and `sandbox-reap --yes` takes no run lock at all (AC2e, `src/providers/reaper.ts:726`), so it is the one destructive path this mutex cannot exclude. F106 is narrowed, not retired, and stays exactly as DF5.1 scoped it. DF3.4's **INV-APPROVE-6** and DF3.7's **INV-IBOX-14** are inherited untouched.
- **INV-IBOX-18 (nothing is witnessed twice, and nothing is witnessed by inference):** the sweep never synthesizes a completion, never tears down or destroys a box on an absent, unreadable or unparseable read (DF3.7 **INV-IBOX-15**, inherited verbatim), and never treats a bundle, a `closedAt`, or a reaper collection as evidence that a run finished. It also changes no input to DF2.6 and leaves `src/providers/reaper.ts` byte-identical: no `staleAfterMs` edit, no suppression, no reprieve, and **no lock acquisition added there** — a box that must die on the ceiling still dies, and the sweep's answer to losing that race is a typed refusal, not a rescue. The cost of that byte-identity is stated rather than hidden: because the reaper calls `teardownSandbox` directly with no run lock (`:726`), a concurrent `sandbox-reap --yes` can tear down a box this sweep is mid-chain on, which no invariant in this story prevents (AC2e). The reaper-side fix belongs to **DF2.11**, which makes `teardownSandbox` take a required `RunLockHandle` so an unlocked call cannot compile; until it lands the residue is documented, `--help`-warned as temporary, and not claimed closed.
- **INV-IBOX-19 (no process ships, the reach is bounded honestly, and the accepted risk is counted):** the delivered artifact is a bounded, exiting invocation; scheduling lives in the operator's `cron`/`launchd` and is documented, never installed — which keeps INV-IBOX-16's *no watcher process* and *no new state* limbs literally true rather than reworded. Nothing supervises the host watcher and nothing is claimed to: a tick that never runs because the machine is off is indistinguishable from one that never existed, and the reach of this story is therefore "the first host invocation after the run settles, while the box lives", not "unattended host". The tmpfs marker-loss window DF3.7 accepts stops being an unowned assumption: `box_reboot_after_dispatch` is counted per distinct run per sweep, published in `_bmad-output/evidence/df3-8/`, and carries a named threshold with a **named owner and review point** (the arc owner, at the arc retro, over distinct runs across the evidence set) whose breach reopens the `$HOME`-persistent-marker decision. An accepted risk with a counter but no reader is still an assumption wearing a risk's clothes.
