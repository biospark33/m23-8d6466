# DF3.8: Host-Side Completion Watcher — Unattended Runs Reach the Gate

**Story Points:** 4
**Sprint:** v5-S3 (in-box restoration arc, story 5 of 5 — the one that makes the arc's product claim true rather than merely reachable)

That arm guards **destroy** only. Default `staleAfterMs` = `14_400_000` ms / 4 h (`src/providers/quota.ts:49`). **DF3.7's billing sentence stands and is not corrected here:** the reaper is an operator-run CLI, **dry-run by default** and mutating only under `--yes` (`scripts/sandbox-reap.ts:5-9`, `:50-51`), and `staleAfterMs` is a threshold applied at whatever moment a sweep runs (`reaper.ts:459`), never a clock that fires. So the box does bill until an operator acts — and when that operator acts, what they get is not a spared box but a **silent collection without a witness**: the run is harvested and closed and never reaches an approvable pause. Ending that witness-less collection, not bounding the bill, is why this story exists

## User Story

As the factory operator who dispatched an unattended run and then closed the laptop,
I want the *next* host invocation — whenever that is — to pick the finished run up after the fact and walk it to the same approvable pause it would have reached had I stayed connected,
so that reaching the pause depends on the host coming **back**, not on the host staying **up** for the whole run.

## Overview

`fleet observe [<run-id>|--all]` is a bounded, re-entrant, **exiting** invocation that finds finished
in-box runs the host never watched and drives DF3.7's chain for each one. It adds no observer and no
chain: it enumerates candidates (open record, live listable box), takes the same per-run invocation
lock the run-scoped verbs already take, re-reads the approval extension **inside** that lock, and
calls DF3.7's composition. Nothing is scheduled by this story — `--all` is idempotent precisely so
the operator's own `cron`/`launchd` can run it, which is the only shape that keeps DF3.7's
INV-IBOX-16 literally true on its *"no watcher process"* limb. While it is holding a box's attention anyway it
counts one thing the arc currently measures nowhere: how often a box reboots after dispatch, the
tmpfs marker-loss window DF3.7 knowingly accepts and left without a revisit trigger.

**What this does not deliver, stated before an AC implies otherwise.** The schedule runs on the
operator's own machine, so a laptop that is closed runs no `cron` tick either: this story does not
make the *host* unattended, it removes the requirement that the host stay attached **for the
duration of the run**. The honest claim is bounded twice — a finished run reaches the pause on the
first host invocation after it settles, and only while its box is still alive and its tmpfs marker
still there. Both windows close when an operator runs `sandbox-reap --yes` against a record past
`staleAfterMs`, and losing that race is AC3's typed refusal rather than a synthesized pause. Nothing
here bounds the bill; DF3.7 was right about that and this story does not claim otherwise.

## E2E Slice

**Demonstrable behavior:** Given an in-box run dispatched **without** `--await-completion`, When the
dispatching process has exited and DF1.10's engine later writes `/run/journal/final.json`, Then a
separate `fleet observe --all` invocation reads that marker through `readBoxFile`, acquires the run
lock, finds no `extensions.approval`, and calls DF3.7's chain — leaving `<runsDir>/<runId>.bundle`
present, `closedAt` set, and `extensions.approval.state = "awaiting-approval"` written **only** by
the gate through `reverify()`'s own `requestApproval`. Observable artifacts: one
`{ event: "run-observed", runId, sweep_ms }` line per driven run, one
`{ event: "sweep-complete", runs_observed, box_reboot_after_dispatch }` line, and a diff in which
`approval-gate.ts`, `approvers.ts`, `push.ts` and `run-record.ts`'s approval-extension block have
zero changed lines.

**Wiring closed:** On completion of this story, a run whose host disconnected at any point after
dispatch reaches an approvable pause on the first host invocation after it settles — no operator
attendance during the run, and no second command once the schedule exists — using only code merged
by this story plus DF3.7's observer and
chain composition, DF3.1's verb/exit-code surface and per-run lock, DF1.10's in-box engine and its
terminal marker, and DF2.6's unmodified reaper. **No stub, no `TODO: wire later`.** The **schedule**
is out of scope by construction and stays the operator's: this story ships a verb and documents a
cron line, never a process.

**Dependency edges (predecessors):** DF3.1, DF3.7, DF2.6, **DF1.10**. DF1.10 is a *direct* edge, not
one inherited through DF3.7: AC7's detachment is produced by DF1.10's `fleet run <run-id>`, which
starts `qds-run@<runId>.service` and returns without holding the run (DF1.10 AC1) — the only shape in
the arc where the dispatching process can exit before the marker exists. Backgrounding a host
process instead would prove nothing this story claims.

> **Not an edge — DF3.2 (fleet lock):** `src/fleet/fleet-lock.ts` is the single-*operator* mutex
> fan-out takes across a whole race. This sweep needs per-*run* granularity and takes the run lock
> instead. Importing `FleetLock` here would serialize the sweep against every other fleet operation
> for no safety this story does not already have.

## Acceptance Criteria

1. **(make-or-break — the host learns after the fact, and the chain stays single)** Given a settled marker on a box whose dispatch invocation is long gone, When `fleet observe` runs, Then the run reaches `awaiting-approval` by **calling DF3.7's chain composition**, and this story's module re-implements no step of harvest → teardown → `reverify()` and adds no second automatic **entry point** to it — it is a second *caller* of the one entry point (AC5), which is a different and openly-paid-for thing. DF3.7's AC1 static import fence is **extended verbatim to `src/fleet/observe.ts`**: it imports none of `approval-gate.ts`, `approvers.ts`, `push.ts`, `run-record.ts`'s approval-extension block, asserted by the same grep test. *Negative control: an implementation that inlines its own harvest→teardown→reverify sequence reaches the same state, passes a naive "did it reach awaiting-approval?" test, forks the one chain the arc has, and MUST fail this one.*
2. The sweep is serialized per run, the lock is taken **by the sweep and never inside DF3.7's module**, and the pre-flight is re-read **inside** it. <br />**(a)** Candidates are records with `closedAt` unset whose box is live and listable; they are driven **one at a time**, never concurrently. <br />**(b)** `src/fleet/observe.ts` acquires the per-run invocation lock itself and calls DF3.7's composition already holding it; DF3.7 AC5's "record already carries `extensions.approval`" refusal is evaluated **after** acquisition, never before. The acquisition may **not** be pushed down into `src/fleet/run-completion.ts`: `acquireRunLock` is explicitly not re-entrant (`RunLockReentrantError`, `scripts/lib/run-lock.ts:64-77`, guard at `:951`) and `fleet dispatch` holds that same lock for its whole invocation (`scripts/fleet.ts:1760-1766`, taken at `:1908`), so a lock inside the shared composition would refuse DF3.7's own `--await-completion` path. <br />**(c) Two observers, one run — decided, not asserted.** A live foreground `--await-completion` observer wins by holding the dispatch invocation's lock; the sweep loses at `acquireRunLock` with `RunLockedError` → **DF3.1's exit 5**, a counted skip and not a sweep failure, and the next tick re-observes idempotently. The one honest residue: dispatch's own acquisition is deliberately **non-fatal on failure** (`scripts/fleet.ts:1905-1918` — "a refusal here must NOT abort the mint"), so in that window the foreground chain runs unlocked and the exclusion degrades to exactly the F106 residue DF3.7 documented. This story narrows that residue and does not claim to have closed it. <br />**(d)** A **stale** lock is a different event from a busy one and is reported as one: `RunLockedError` already distinguishes them and carries the `rm` line for the dead-holder case (`scripts/lib/run-lock.ts:57-64`). A sweep killed mid-chain leaves a real lock file behind, and no later tick clears it — so a stale refusal is a named, remediated outcome, never folded into the benign skip count. *Negative controls, all three MUST fail: an implementation that checks the extension before acquiring the lock lets two overlapping cron ticks both enter `reverify()` on the same run, turning `src/reverify/worktree.ts:319`'s pid guard (TECH_DEBT F106) from latent to live and passing every single-process test; one that acquires the lock inside `run-completion.ts` breaks `fleet dispatch --await-completion` with `run-lock-reentrant` while passing every sweep-only test; and one that counts a stale lock as a busy skip reports a permanently unobservable run as healthy on every tick forever.*
3. Given DF2.6's `stale-record` → `teardown` arm collects an open record past `staleAfterMs` (4 h default) with harvest, destroy, revoke and `closedAt` but **no `reverify()`**, Then this story changes **not one reaper input**: no `staleAfterMs` edit, no suppression file, no reprieve, and `src/providers/reaper.ts` is byte-identical after. **The guarantee is the refusal, not the interval.** There is no scheduled reaper to outrun — `sandbox-reap` is an operator CLI, dry-run unless `--yes` (`scripts/sandbox-reap.ts:5-9`) — so a default sweep interval derived from `staleAfterMs` reduces exposure and is documented as the heuristic it is, named in code with the derivation and the reaper citation on it so an operator who lowers `staleAfterMs` sees what else moves. It may **not** be stated as winning a race. What is load-bearing is being **correct when it loses**: a record the reaper already closed is re-entered at the `reverify()` leg **only if this invocation witnessed the marker itself**, and is otherwise refused with a typed `completion-unwitnessed` payload naming the collection. This story persists no observation record, so "witnessed" means witnessed by the running invocation and nothing is reconstructed. *Negative controls, both MUST fail: an implementation that routes any closed record carrying a bundle into the gate promotes a run killed mid-flight on evidence no marker ever witnessed; and one that grants finished boxes a reaper reprieve, which removes the only bound the bill has and edits a merged story's classifier.*
4. **(the revisit trigger this story takes ownership of)** Given each live candidate box, Then the sweep reads `/proc/uptime` through the **same** `readBoxFile` — adding no substrate command string under `src/fleet/` — and counts `box_reboot_after_dispatch` alongside `runs_observed` into this story's evidence JSON. <br />**(a) The arithmetic is a duration comparison, and a naive one is inverted.** `store.create` stamps `createdAt` **before** `driver.create()` boots the VM (`src/fleet/dispatch.ts:2787-2788`), so a first boot *always* postdates `createdAt` and "derived boot time is later than `createdAt`" would count **every** box as rebooted. A reboot is instead `uptimeSeconds < (hostNow − createdAt) − PROVISION_LAG_MARGIN_MS`: the box has been up for less time than the run has existed, by more than a **named** margin covering provisioning and first-boot lag. Uptime is a *duration*, so host↔box clock skew never enters; only `hostNow` and the host-stamped `createdAt` do. Anything inside the margin is `uptime_unknown`, never "no reboot". <br />**(b) It measures the window, not a loss** — a reboot destroys a marker only if one had already been written, and the story claims exactly that much. <br />**(c) The counter is per distinct `runId` per sweep and the threshold is over distinct `runId`s, not summed sweep lines.** Nothing is persisted, so a box rebooted once and re-observed on twenty ticks emits twenty lines; the story says so and defines the denominator rather than letting an aggregator infer it. **Named revisit threshold: 2 distinct runs, or 2 % of distinct observed unattended runs, whichever comes first** — evaluated against the accumulated `_bmad-output/evidence/df3-8/` set at the arc retro, by the arc owner, which is where the trigger stops being a number in a file. Reaching it reopens DF3.7's rejected `$HOME`-persistent marker (its Technical Notes: *"Revisit only if a measured reboot rate makes the loss window material"*) as an ADR appendix. *Negative controls, all three MUST fail: an implementation comparing derived boot time against `createdAt` with no margin, which counts every healthy box and trips the threshold on its second observation; one that reports a reboot as a confirmed marker loss, overstating its evidence; and one that ships the watcher with no counter, leaving the trigger unowned — the exact state this story exists to end.*
5. Given the delivered artifact, Then it is a verb and not a process: one bounded pass, a typed exit, no PID file, no launchd plist, no systemd user unit, no `--daemon` flag, nothing that stays resident. **DF3.7's INV-IBOX-16 has three limbs and this story is honest about each.** *No watcher process* and *no new state* are preserved **literally** — a scheduled *invocation* is not a watcher process, the scheduling entry is documented in `--help` and shipped nowhere, and no second expiry clock is added (the sweep reads DF2.6's ceiling and owns it not; a candidate by definition carries no approval extension, so there is no `expiresAt` in play). The third limb — *"the observer is the only automatic caller of the host chain … the invariant is 'no new automatic caller'"* — this story **knowingly becomes the second automatic caller of**, and pays for it in the same breath: DF3.7 declined to take any lock, and this story takes the per-run invocation lock around the shared composition (AC2b), so the arc trades "one caller by convention" for "one caller at a time by mutex", which is strictly stronger for `src/reverify/worktree.ts:319`'s precondition. Claiming all three limbs unchanged would be the dishonest version. The clause needs a one-line amendment in DF3.7, recorded here and in that story's own text, not silently reinterpreted. *Negative controls, both MUST fail: an implementation that ships any always-on host supervision — a plist, a user unit, or a loop flag holding the process open — adds a second supervision surface beside DF2.10's; and one that adds the second automatic caller **without** taking the lock, which is the trade named above with nothing paid for it.*
6. Given any per-run outcome, Then it is typed `{ code, message, remediation }` and no box is destroyed on an absent, unreadable or unparseable read — DF3.7's AC2 classification and AC3's `run-completion-unobserved` payload are consumed unchanged and never converted into a teardown by this story. A sweep that drove **zero** runs exits **0**: nothing to do is not a failure, and a cron line that mails the operator on every quiet tick is a line the operator disables. *Negative control: an implementation that exits non-zero on an empty sweep trains the operator to ignore the schedule and MUST fail this one.*
7. Given the evidence for this story, Then the detachment is **real**, not simulated: the host process exits **before** DF1.10's in-box engine writes the marker, and a separate `fleet observe` invocation drives the chain to the pause. The exit is produced by DF1.10's `fleet run <run-id>` — start the per-run systemd unit, return — and **not** by backgrounding a host process, which would leave a host process to fail and prove nothing. **Scheduling caveat, same as DF3.7's:** this needs DF1.10's real in-box engine on a re-pinned image to have landed; until it does there is no marker written by anything but a test's own hand, and a planted marker is explicitly not evidence for this AC. A FakeDriver suite is legitimate unit coverage for candidate selection, the lock discipline and the uptime arithmetic, and MUST NOT be the sole evidence for AC1 (DF3.4 AC6's no-doubles rule).

## Technical Notes

- **Contracts/Schema:** this story persists **nothing**. No observation record, no sweep cursor, no field on DF2.1's run record, no new marker. The marker remains the state (DF3.7 AC3) and every sweep is a fresh read; that is what makes `--all` safely re-entrant. One honest exception to "leaves nothing behind": a sweep killed mid-chain leaves the run-lock file it took, which is a real artifact and is why AC2(d) reports a stale refusal as its own outcome rather than a benign skip. Its only new emissions are log/evidence counters.
- **Ordering against the reaper, and what the numbers do and do not buy.** Marker written at *t*; the reaper classifies `createdAt + staleAfterMs` (4 h default) as stale **whenever an operator next runs `sandbox-reap --yes`** — it is a threshold, not a timer, so there is no wall-clock deadline to beat. Deriving the documented sweep interval from `staleAfterMs` therefore reduces the exposure window and nothing more; it is a named constant carrying the derivation and the reaper citation so an operator who lowers `staleAfterMs` sees what else moves, and it is not a correctness argument. A run collected first is not lost data (the reaper harvests), it is lost *witness*: AC3's typed refusal, not a synthesized pause.
- **Region ownership on shared files, and the one place the lock may not go.** `src/fleet/observe.ts` is new and this story's own, and it is where `acquireRunLock` is called. `src/fleet/run-completion.ts` is **DF3.7's**: this story adds only a **lock-agnostic re-entrant entry point** that the sweep calls with the lock already held — it acquires nothing, because `acquireRunLock` is not re-entrant (`RunLockReentrantError`, `scripts/lib/run-lock.ts:64-77`) and DF3.7's own `--await-completion` path already runs inside `fleet dispatch`'s hold (`scripts/fleet.ts:1908`), so an acquisition pushed down here would refuse the sibling's shipped flow. The four-kind classification, the poll, the window and the typed payloads are untouched, and `run-lock.ts` is not among the four fenced modules, so DF3.7's AC1 fence is unaffected. `src/fleet/verbs.ts` and the `scripts/fleet.ts` dispatch block are **DF3.1's**: this story **adds only** the `observe` descriptor, its flags and its exit mapping (reusing 5 for the refused lock, not minting a new code). `src/providers/reaper.ts` and `src/providers/quota.ts` are **DF2.6's** and are read, never written.
- **Guards/limits.** Every bound but two is inherited: the per-read deadline and byte cap come from `readBoxFile`, the unusable-tick limit and observation window from DF3.7, the lock timeout from `run-lock.ts`, and the sweep interval is derived from `staleAfterMs`. The two this story does mint, named rather than implied: `PROVISION_LAG_MARGIN_MS` (AC4a) and a **max-candidates-per-pass** so one pass cannot run unboundedly long against a large fleet. Exceeding the latter is a counted, logged partial pass, never a truncation the operator has to infer — and because a driven run gains `closedAt` and leaves the candidate set, the next tick makes progress; a candidate that *refuses* every pass does not, so enumeration is ordered oldest-`createdAt`-first and the partial-pass line names the count left behind, so a permanently refusing head cannot silently starve the tail.
- **`/proc/uptime` is a file, deliberately.** Reading it through `readBoxFile` means the reboot measurement inherits the same four-kind discipline as the marker and adds **zero** `sh -c` strings under `src/fleet/` (`src/fleet/dispatch.ts:63-66`'s DoD). Unparseable or absent uptime is `unknown`, counted separately, and never scored as "no reboot" — a measurement this story exists to make must not be quietly floored at zero. DF1.11's per-engine-start `boot_id`/uptime row corroborates the same fact from inside the box and is cited, not required: the sweep must work on a box whose engine never started. **Open measurement, recorded rather than asserted:** the 2026-08-31 probe does not contain a provisioning-to-first-boot duration, so `PROVISION_LAG_MARGIN_MS` has no measured basis yet. It is set from the first live e2e's own observed lag with a stated multiple, and the evidence JSON carries the raw `(hostNow − createdAt) − uptimeSeconds` per box so the margin can be re-derived from data instead of re-argued — a counter whose threshold rests on a guessed constant would be the same unowned assumption this story exists to retire.
- **Considered and rejected: a resident host watcher.** A long-lived process is permitted on the operator machine and would poll more tightly. It is rejected because it buys nothing the operator's `cron` does not already give — the runs this story serves take minutes to hours, not seconds — while costing a supervision surface (start, restart, log rotation, staleness) beside DF2.10's systemd unit, and while forcing DF3.7's INV-IBOX-16 to be reworded from "no watcher process" to "no watcher process except this one". The re-entrant verb keeps **that limb** literally true. It also buys nothing on the case the user story opens with: a resident process on a closed laptop is as absent as a `cron` tick on one. Revisit only if a measured observation latency, not a hypothesis, makes the interval material.
- **Deviation/assumption (Deviation 1, restated where an implementer will look):** DF3.7 AC3 cites the reaper's `record-claim-refused` arm, which guards **destroy**; the arm that actually fires on an aged **open** record is `stale-record` → `teardown`, which harvests and closes without ever calling `reverify()`. The correction is about *which arm and what it costs* (the witness), and it explicitly **does not** correct DF3.7's billing sentence — `sandbox-reap` is dry-run unless `--yes`, so an unobserved box does bill until an operator acts. No invariant is weakened: DF3.7's INV-IBOX-14/15 are inherited exactly as written, and INV-IBOX-16's third limb is amended openly in AC5 rather than reinterpreted. Both DF3.7 edits — the AC3 arm citation and the INV-IBOX-16 "only automatic caller" clause — are one-clause edits to that story, not changes to this one's shape.

## Observability Contract

- Every sweep logs `{ requestId, runId, event, sweep_ms }` — `event ∈ run-observed | candidate-skipped | lock-refused | completion-unwitnessed | sweep-complete`. Marker bytes are never echoed and no credential material is read or logged.
- `requestId` is the sweep invocation's own and is stamped on every per-run line, while each driven run's chain continues to carry its `dispatchRequestId` onto the gate's `pause` event — so a run observed by a sweep joins to its pause on the key DF5.3 already uses, with no second key minted here; errors carry `{ code, message, remediation }`.
- Sub-timings and counters: `sweep_ms`, `chain_ms` per driven run, plus `runs_observed`, `box_reboot_after_dispatch` and `uptime_unknown` on the `sweep-complete` line. `chain_ms` is **absent, not `0`**, on a run that was skipped — `0` is a lie shaped exactly like an instantaneous chain (`src/fleet/approval-gate.ts:1131-1136`, deferred item D8).

## Security Invariants

- **INV-IBOX-17 (a second automatic caller, and the mutex that pays for it):** the sweep is a *caller* of DF3.7's chain and never a parallel implementation of it, and DF3.7's AC1 import fence extends to `src/fleet/observe.ts` unchanged, so this module cannot acquire the ability to write `extensions.approval` even if a later edit wanted to. It **is** the second automatic caller DF3.7's INV-IBOX-16 forbade, and the price is paid in kind: one run at a time, each under the per-run invocation lock taken by `observe.ts` (never inside DF3.7's module — the lock is not re-entrant), with DF3.7 AC5's pre-flight re-read **inside** the lock. That ordering is the whole invariant — evaluated outside it, two sweeps both pass and F106's one-process-per-invocation precondition (`src/reverify/worktree.ts:319`) stops holding. **What the lock does not fence, said as plainly as DF3.7 said it:** a hand-run `scripts/reverify.ts` takes no run lock and is unfenced today and after this story, and `fleet dispatch`'s own acquisition is non-fatal on refusal (`scripts/fleet.ts:1905-1918`), so F106 is narrowed, not retired, and stays exactly as DF5.1 scoped it. DF3.4's **INV-APPROVE-6** and DF3.7's **INV-IBOX-14** are inherited untouched.
- **INV-IBOX-18 (nothing is witnessed twice, and nothing is witnessed by inference):** the sweep never synthesizes a completion, never tears down or destroys a box on an absent, unreadable or unparseable read (DF3.7 **INV-IBOX-15**, inherited verbatim), and never treats a bundle, a `closedAt`, or a reaper collection as evidence that a run finished. It also changes no input to DF2.6: no `staleAfterMs` edit, no suppression, no reprieve — a box that must die on the ceiling still dies, and the sweep's answer to losing that race is a typed refusal, not a rescue.
- **INV-IBOX-19 (no process ships, the reach is bounded honestly, and the accepted risk is counted):** the delivered artifact is a bounded, exiting invocation; scheduling lives in the operator's `cron`/`launchd` and is documented, never installed — which keeps INV-IBOX-16's *no watcher process* and *no new state* limbs literally true rather than reworded. Nothing supervises the host watcher and nothing is claimed to: a tick that never runs because the machine is off is indistinguishable from one that never existed, and the reach of this story is therefore "the first host invocation after the run settles, while the box lives", not "unattended host". The tmpfs marker-loss window DF3.7 accepts stops being an unowned assumption: `box_reboot_after_dispatch` is counted per distinct run per sweep, published in `_bmad-output/evidence/df3-8/`, and carries a named threshold with a **named owner and review point** (the arc owner, at the arc retro, over distinct runs across the evidence set) whose breach reopens the `$HOME`-persistent-marker decision. An accepted risk with a counter but no reader is still an assumption wearing a risk's clothes.
