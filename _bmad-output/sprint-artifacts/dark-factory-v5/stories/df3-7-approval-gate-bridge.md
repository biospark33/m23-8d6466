## User Story

As the factory operator who dispatched an unattended run,
I want the host to notice by itself that the in-box run has finished and to walk the harvest, teardown, re-verify and approval chain that already exists,
so that an autonomous run ends at a pause I can approve rather than at a live box nobody is watching.

## Overview

`fleet observe <run-id>` observes one box's terminal marker and, on seeing it, runs the
chain the operator runs by hand today. The observer is a bounded poll of `boxMarkerPath(runId)`
through the **shipped** `readMarkerVerdict`, whose four verdicts fan-out's race and `fleet status`
already share — `absent` means not finished yet, `skip` is a probe that produced no reading and is
counted on its own laxer streak, `unusable` (unreadable at `cat`, oversized, unparseable, or a
foreign `runId`) is counted toward `MARKER_UNUSABLE_TICKS_LIMIT`, and `settled` carries a boolean
`ok`. An `absent` marker is then disambiguated by `unitActivity`, because a `Type=simple` unit with
`Restart=no` can be dead with no marker and absence alone cannot tell that from "still walking". On a
settled marker the host runs harvest → teardown → `reverify()`, and reverify's own single call to
`requestApproval` does what it does today. This story adds one module and one bounded verb: **zero** lines change in
`approval-gate.ts`, `approvers.ts`, `push.ts` or `run-record.ts`'s approval-extension block, no state is
added, no daemon is introduced, and nothing flows back into the box — approval authorizes a *push*,
never a continuation.

## E2E Slice

**Demonstrable behavior:** Given a run started by `fleet run <run-id>` (DF1.10 AC1 — the host process
that started the unit has already returned), When `fleet observe <run-id>` is invoked and DF1.10's
engine settles and writes `/run/qds-run/<runId>/journal/final.json` (`{runId, ok:true, completedAt}`,
0600, by temp+rename), Then the observer's next poll reads it through `readMarkerVerdict`, runs `teardownSandbox`
(harvest → destroy → revoke → `closedAt`) and then `reverify()`, whose existing
`port.requestApproval` call leaves the record at `awaiting-approval` with its proposal, reportId,
headSha and `expiresAt`. Observable artifacts: `<runsDir>/<runId>.bundle` present, the record's
`closedAt` set, `extensions.approval.state = "awaiting-approval"` written **only** by the gate, one
`event: "pause"` line carrying `dispatchRequestId`, and the observer's own
`{ event: "run-complete", runId, marker_poll_ms }` line — plus a diff in which `approval-gate.ts`
has zero changed lines.

**Wiring closed:** On completion of this story, an in-box run reaches an approvable pause from
**one** operator command against a run the host is no longer attached to (`fleet observe <run-id>`),
using only code merged by this story plus DF1.10's
in-box engine and its terminal marker, DF3.4's gate and lock protocol, and DF5.1's `ApprovalPort` /
`recordApprovalPort(store)` seam at the reverify call site. **No stub, no `TODO: wire later`.** The
**decision** side is unchanged and stays operator-driven: `fleet approve|reject` and DF5.2's push
are untouched.

**Dependency edges (predecessors):** DF1.10, **DF2.2** (`readBoxFile`), **DF2.11** (the required `RunLockHandle` on `teardownSandbox` — this story is its eighth call site), **DF2.10** (the image and unit that ship no `QDS_*` path variable and declare the per-run `RuntimeDirectory`), **DF3.1** (the verb registry and the `scripts/fleet.ts` dispatch block this story adds `observe` to), DF3.4, DF5.1.

> **Not an edge — DF1.11 (steering round trip):** this story reads a completion marker, never a
> steering file. Touching `/run/steering`, `attach.ts` or `steering.ts` from here collides head-on
> with DF1.11 and is out of scope in both directions.

## Acceptance Criteria

1. **(make-or-break — the host learns the run finished; the gate learns nothing new)** Given an in-box run that writes its terminal marker, When the observer sees it, Then the host runs the **existing** chain — harvest → teardown → `reverify()` → the gate's own `requestApproval` — and the record reaches `awaiting-approval` through that path alone, with **zero changed lines** in `src/fleet/approval-gate.ts`, `src/fleet/approvers.ts`, `src/pr/push.ts` and `src/providers/run-record.ts`'s approval-extension block, verified by diff — and, because a diff is a review step and not a runnable one, enforced at test time by a **static import fence** over `src/fleet/run-completion.ts`'s own **direct import specifiers**: it imports `src/fleet/approval-gate.ts`, `src/fleet/approvers.ts`, `src/pr/push.ts` and `src/fleet/index.ts` (the barrel — `src/fleet/index.ts:8-20` — which star-exports eight fleet modules including `status.ts`, and `status.ts:54` imports `expiredState` from `approval-gate.ts`, so naming the barrel pulls the gate module into this module's import graph even though the barrel re-exports none of the gate's own symbols) **not at all**, and imports `src/providers/run-record.ts` **only** for `RunRecordStore`/`RunRecord` — never for a symbol that writes the approval extension, which AC5's pre-flight read requires and a whole-module ban would forbid. The fence is on **direct specifiers, not transitive reach**: the chain calls `reverify()`, which reaches the gate through DF5.1's `ApprovalPort` seam (`src/reverify/approval.ts:26` imports `requestApproval` from `../fleet/approval-gate.ts`), and that path *is* the design. Asserted by a grep test in the repo's own idiom (DF3.6's `src/phase-engine/` DoD grep; `runMarkerPath` is withheld from the phase-engine barrel, `src/phase-engine/index.ts`, and fan-out deliberately does not import it at all — `src/fleet/fanout-primitive.ts:685-700`). *Negative control: an implementation that reads Consequence 4's pre-Appendix-A "awaiting marker" phrasing as an approval state and writes `extensions.approval.state = "awaiting-approval"` from the bridge reaches the same state, passes a naive "is it awaiting?" test, bypasses `pauseRun`'s bundle, R5-C and INV-APPROVE-6 guards, and MUST fail this one; and a fence written to match **transitively**, which fails on the correct implementation and will be weakened until it catches nothing — the worse failure, because the DoD's Security box is then checked by a test that asserts nothing. Both controls live in `tests/fleet/run-completion.test.ts`.*
2. **The observation contract is the shipped classifier, consumed as code, not restated.** The observer reads through **`readMarkerVerdict(driver, vm, boxMarkerPath(runId), deadlineMs, runId)`** (`src/fleet/fanout-primitive.ts:925`) — the same function `fleet status` (`src/fleet/status.ts:1296`) and the fan-out race (`probeArm`, `:1216`) use, which DF1.10 AC5 requires the callers to share as code rather than agree on by inspection. It re-derives no mapping of its own, and the four **verdicts** are `absent | skip | unusable | settled`, which are *not* `readBoxFile`'s four kinds — the verdict is about what the reading PROVES, not which leg produced it. <br />**(a)** `absent` means *not finished yet* and resets the unusable streak — but only a probe that answered cleanly is `absent`: every non-zero presence-probe exit other than 1 (255 = ssh never connected, 137 = SIGKILLed at the budget) is **`skip`**, because treating those as a clean read reset the corruption streak on every tick of a dead box (`classifyMarkerRead`, `:774-803`). `skip` resets nothing and is counted on its own, deliberately laxer streak against **`PROBE_SKIP_TICKS_LIMIT`** (=6, `:101`); a transport failure is often transient where a parse failure is permanent. A **filled** skip streak is terminal for this invocation and typed: `{ code: "box-unreachable", message, remediation }` naming the box, the run and the last probe's `code`/exit, at **exit 1** (transient — the box may answer a later invocation), leaving the box alive and listable and mutating no record field. It is a distinct code from AC3's `run-completion-unobserved`, which means "the window expired while the box kept answering `absent`"; conflating the two tells an operator the host never looked when in fact the box never answered. Because a single-run observer has **no second arm to corroborate against** — fan-out applies this limit only when something answered on the same tick (`fanout-primitive.ts:91-99`) — the streak is terminal only after six consecutive skips **and** at least `PROBE_SKIP_TICKS_LIMIT × (DEFAULT_POLL_INTERVAL_MS + DEFAULT_PER_CALL_DEADLINE_MS)` (90 s on the AC5 defaults) has elapsed since the last tick that reached the box; six sub-second `Connection refused` probes are a wifi blip, not a dead box. `unusable` — unreadable at `cat`, oversized, unparseable, non-boolean `ok`, a `runId` naming another run, a `cat` that was never issued because the presence probe spent the whole shared budget (`marker-read-budget-exhausted`), a present-but-non-string `runId`, or a body that parses to `null`/a primitive (the enumeration is illustrative; the function is authoritative, and `skip` likewise covers a `BoxFileRead` kind this build does not classify) — is counted against **`MARKER_UNUSABLE_TICKS_LIMIT`** (=3, `:68`) via `markerUnusableGivesUp` (`:959`), after which the run is abandoned to AC3's arm rather than polled to the window ceiling. `unreadable` is emphatically **not** a skipped tick: the box answered *twice* on that tick, and the shipped docblock (`:805-834`) records that logging it as an unanswered probe "asserts the opposite of what happened". `settled` carries a boolean `ok`. <br />**(b)** A non-zero `cat` is a **refusal, never empty bytes** — `readBoxFile` models it as `unreadable{exitCode, stderr}`, a distinct kind from `content` (`src/providers/exedev/transport.ts:128-138`) — and never a completion. **`expectedRunId` is passed on every read**: a marker naming a different run is `unusable / marker-run-mismatch` (`:891-899`), never `settled`. Omitting it re-opens the wrong-box defect the classifier's own docblock records — a box whose id collided with another record's live box read THAT box's marker and reported `ok` for a run that never started. <br />**(c)** `ok:false` is a settled-but-failed run and the chain still harvests and tears down — but `ok` is **not a veto and is never fed to reverify**. DF5.1 re-judges the tree independently and returns before the gate only on **its own** non-green verdict (`src/reverify/runner.ts:421`), so an `ok:false` run whose tree re-verifies green legitimately reaches the pause, and an `ok:true` run whose tree re-verifies red does not. Deriving the approval outcome from the marker instead would collapse the two-layer doctrine INV-IBOX-15 exists to preserve. <br />**(d) An absent marker is disambiguated by the unit's own liveness, never by absence alone.** On an `absent` verdict the observer probes `unitActivity(driver, vm, runId, deadlineMs)` (`src/fleet/run.ts:437`) — the same one-probe seam `fleet run` and `fleet status` share (`src/fleet/status.ts:35,1309`), so the three verbs can never disagree about whether one unit is up. `active` means *still walking phases* and the poll continues. **`failed` is the one terminal reading**: the unit is `Type=simple` with `Restart=no` (`oci/exedev/systemd/qds-run@.service:58,169`) and `run.ts`'s own docblock states the consequence — "the unit simply sits `failed` and no marker is ever written" — so the observer stops immediately with a typed `{ code: "run-engine-dead", message, remediation }` naming the box, the run and `systemctl status qds-run@<runId>.service`. **`inactive` and `unknown` are explicitly NOT terminal.** `unitActivity` returns them for a unit systemd has never loaded as well as for one that exited (`src/fleet/run.ts:466-480` — the `default` branch's own comment: "Includes `unknown` (systemd's own word for a unit it has never loaded)"), and a box that `fleet dispatch` provisioned but `fleet run` has not started yet reads exactly that. Treating either as terminal would refuse every run in the ordinary dispatch→run window. Both are counted on the `skip` streak of (a), so an unreachable or never-started box is still bounded — by `box-unreachable` or by AC3's window, never by a false death certificate. The residual case an engine that exits **0** without writing a marker produces is `inactive` and is bounded the same way; distinguishing it from "never started" would need a start stamp the run record does not carry today (see Technical Notes). The box is left **alive and listable** on every one of these arms (DF2.2 INV-5); nothing is destroyed on a liveness reading. *Negative controls, all MUST fail: an implementation that re-derives the verdict mapping inside `run-completion.ts` forks the one classifier DF1.10 AC5 requires be shared and drifts the moment `fanout-primitive.ts` changes; one that treats an EACCES `unreadable` as a skipped tick polls a box to the window ceiling while it bills; one that treats `probeExit: 255` as a clean absence resets the streak on every tick of a dead box; one that omits `expectedRunId` drives the chain from a foreign run's marker; one that treats a failed read as "not there yet" polls a dead box to the ceiling, and one that treats it as completion tears down a live run; one that polls an absent marker to the window ceiling without ever asking whether the unit is up reports `run-completion-unobserved` — "the host never saw it" — for a run whose engine died forty minutes in, sending the operator to debug the host; one that treats `unitActivity` returning `inactive` or `unknown` as `failed` issues a death certificate for every box that has been dispatched but not yet `fleet run`, and abandons a healthy run on one dropped ssh; and one that increments the skip streak and never reads it polls an unreachable box to the window ceiling while it bills, passing every "255 is not a clean absence" test.*
3. Given a marker written but never observed (host disconnect, window expiry), Then the command exits with a typed `{ code: "run-completion-unobserved", message, remediation }` payload naming the box and the run, leaves the box **alive and listable** with its evidence (DF2.2 INV-5), mutates **no** record field, and is safely re-runnable: **on this arm** the box is still alive and the marker still there, so re-observing is idempotent because the marker is the state. (Once the chain has run, the marker is gone with the box; what makes a *driven* run non-repeatable is `closedAt`, not the marker — see DF3.8 AC2(a)'s candidate filter. Two mechanisms, not one.) The remediation names re-observation explicitly. A record left at `pausing` by a crashed chain is **not** this arm: its box is already gone, so `fleet observe <run-id>` takes AC5's `promoteStrandedPause` path and never polls at all. The story states plainly that **no existing timer covers this run**: it has no approval extension to expire, and the reaper is operator-run and dry-run by default — so the box bills until an operator acts on the typed refusal, and the story says that rather than implying a sweeper will collect it. What that operator action yields is the sharper hazard (corrected per DF3.8 Deviation 1): the `record-claim-refused` arm (`src/providers/reaper.ts:805-811`) guards **destroy** only; an open record older than `staleAfterMs` (4 h default, `src/providers/quota.ts:49`) classifies `stale-record` → `teardown` (`aged()` at `reaper.ts:510`; three classification sites — `:531-539` VM, `:575-582` key, `:587-595` record), which harvests and closes the run with **no `reverify()` and no gate** — a witness-less collection. DF3.8 exists to end it. *Negative control: an implementation that synthesizes a completion, destroys the box on an unobserved run, or adds a second expiry clock inside the gate MUST fail this one.*
4. **(the marker path is derived once, host-side, from the box-side mirror)** Given the marker path, Then the observer computes it as **`boxMarkerPath(runId)`** (`src/fleet/fanout-primitive.ts:701`), the same host-side derivation `fleet status` (`src/fleet/status.ts:1296`) and the fan-out race (`:1046`) already use, and **never** as `runMarkerPath()` — which reads the HOST's `QDS_RUN_ROOT` and is correct only for code running IN the box (the engine writing the marker). This is not a preference: an ambient `QDS_RUN_ROOT` redirecting a box probe is a shipped, measured defect (`fanout-primitive.ts:685-700` — "every `test -f` went to the wrong in-box path, missed cleanly, and `fleet status` reported a whole fleet as `running` regardless of what the runs had done"), and `boxMarkerPath` is immune to it **by construction** rather than by a start-up check, which is why this story adds no ambient-env refusal. The image half is closed too: DF2.10 AC6 ships an image and unit that set no `QDS_*` path variable (cited, not assumed), so the two legs are three derivations of one grammar by design — kept honest by `assertRunIdPathComponent` (`src/phase-engine/journal.ts:110-123`), pinned by `tests/fleet/fanout-primitive.test.ts` and by the shape regex `BOX_MARKER_PATH_RE` (`fanout-primitive.ts:713`), and this story adds no fourth. A reboot before observation destroys the tmpfs marker and the run lands in AC2(d)'s liveness arm or AC3's window arm; the path is never re-derived, never assumed, and never reconstructed from a live-box heuristic. *Negative controls, both MUST fail: an implementation calling `runMarkerPath()` host-side, which polls a host-shaped path against a box and reads `absent` forever under any ambient `QDS_RUN_ROOT`; and one that inlines its own `/run/qds-run/...` literal, which is a fourth derivation the three-way agreement test does not cover.*
5. Given a run whose record already carries `extensions.approval` in a state that is **`awaiting-approval` or terminal**, When the observer would start the chain, Then it refuses instead, with a typed `{code: "approval-already-registered", …}` naming the state. **`pausing` is explicitly NOT a refusal, and it does not enter the marker poll either.** A `pausing` record is **post-teardown by construction** (the ordering at Technical Notes "Ordering is untouched"; `refuseLiveInfraOnDecidable`, `src/fleet/approval-gate.ts:1112-1123`, refuses to promote a record that "is open and still names" a box or key), so its box and its tmpfs marker are already gone and polling `boxMarkerPath(runId)` against it can only produce `skip` ticks. On a `pausing` record the observer therefore **skips the observe and teardown legs entirely and calls `promoteStrandedPause(runId, deps)`**, which calls `reverify(runId, {hostRoot, runsDir})` and nothing else — the gate compares the bound reportId byte-for-byte (`src/reverify/runner.ts:436-460` — "`pausing` never expires and nothing else promotes it, so the run would be stranded for good") and promotes. This is the same `reverify()`-leg re-entry DF3.8 AC3 names for its reaper-collected arm: **one mechanism, two callers.** Refusing `pausing` strands the run; so does polling a destroyed box for it. This is a **cheap pre-flight refusal, not a mutual exclusion**, and the story claims exactly that much: it removes the one *automatic* second entry to `reverify()` this seam could add, preserving the one-production-entry / one-process-per-invocation precondition `src/reverify/worktree.ts:319`'s pid guard rests on (TECH_DEBT F106). What it does **not** fence is an operator running `scripts/reverify.ts` by hand against a run that carries no extension yet — no lock covers that today, this story takes none, and F106 is left exactly as DF5.1 scoped it: neither widened nor silently declared closed. *Negative controls, all MUST fail: an implementation that starts the chain on a record already carrying `awaiting-approval` or a terminal state passes a naive "is it awaiting?" test; one that **refuses** on `pausing` leaves a run stranded forever with no operator-visible remediation; one that runs the **marker poll** on a `pausing` record polls a destroyed box to the window ceiling and reports `run-completion-unobserved` for a run one `store.set` from the pause; one that runs `teardownSandbox` a second time on a record whose `closedAt` is already set; and one that claims to fence the manual caller MUST name the lock it takes.*
6. Given the evidence for this story, Then the chain is proven end to end against a **real box** whose marker was written by DF1.10's real in-box engine — not planted by the test, not produced by a FakeDriver. A FakeDriver suite is legitimate unit coverage for the classifier's verdicts, both streaks and the liveness arm, and MUST NOT be the sole evidence for AC1 (DF3.4 AC6's no-doubles rule).

## Technical Notes

- **Contracts/Schema:** the marker is `{ runId: string, ok: boolean, completedAt?: string }` and nothing else, at `/run/qds-run/<runId>/journal/final.json`. `completedAt` is **optional on the wire**: `JournalFile.completedAt` is optional and `JSON.stringify` drops an `undefined` value (`src/phase-engine/journal.ts:309,381`), so a legitimately settled marker may carry two fields. The observer decides on `ok` alone — the shipped classifier reads exactly `runId` and `ok` — and a validator that required `completedAt` would classify a settled run as `unusable` and abandon it at the streak limit. The path itself is created by the unit's `RuntimeDirectory=qds-run/%i/journal qds-run/%i/trace` (`oci/exedev/systemd/qds-run@.service:158`) and survives the engine's exit because of `RuntimeDirectoryPreserve=yes` (`:160`) — so the marker is readable after the run settles and until the box is destroyed or rebooted. It deliberately does **not** carry the engine's exit status, verdict, or any evidence: reverify re-judges the tree host-side and DF5.1 owns the verdict, so the smaller payload keeps the marker out of the trust path. The observer's own log line is `{ requestId, runId, event, marker_poll_ms }` — it adds no field to DF2.1's run record.
- **Ordering is untouched because the marker sits strictly before the sequence:** marker → host observes → harvest/destroy/revoke/`closedAt` → `reverify()` green → `requestApproval` → `pausing` → (no teardown owed) → `awaiting-approval`. The box's death is *upstream* of `pausing`, exactly as in the shipped flow, so INV-APPROVE-6's no-seam guard, the R5-C keyHash guard and `refuseLiveInfraOnDecidable` all keep meaning what they mean today.
- **Region ownership on shared files.** `src/fleet/run-completion.ts` is new and this story's own. `src/fleet/verbs.ts` and the `scripts/fleet.ts` verb-dispatch block are **DF3.1's**: this story **adds only** the `observe` verb descriptor with its flags and full exit table, the matching `scripts/fleet.ts` block, and the typed refusal prints — no existing verb, exit code or gate event changes shape. `src/providers/exedev/transport.ts` is **DF2.2's** and is reused unmodified. There is no host-side shim left to retire — `scripts/pipeline-run-remote.ts` was deleted by DF1.10 AC7, and `journal.ts:60-63` records that `QDS_RUN_ROOT` now has no production writer at all. This story carries its own live test.
- **Guards/limits.** Per-read deadline (`DEFAULT_PER_CALL_DEADLINE_MS` = 10_000) and byte cap come from `readBoxFile` as-is, and `MARKER_UNUSABLE_TICKS_LIMIT` = 3 is reused verbatim (`src/fleet/fanout-primitive.ts:55,68`). Fan-out's `DEFAULT_POLL_INTERVAL_MS` (5 s, `src/fleet/fanout-primitive.ts:52`) is **imported, not re-minted** — the section it lives under is headed "INV-6 finite caps (imported constants — never mirrored literals)", and `PROBE_SKIP_TICKS_LIMIT`'s own wall-clock reasoning (`:85-93`) is priced against it. The **observation window** is therefore this story's only new number, named in code rather than implied. It is operator-settable on the verb and has to be: fan-out's `DEFAULT_FANOUT_CEILING_MS` (1 h, `:58`) is race-shaped and an unattended run routinely outlives it, so inheriting it would silently abandon exactly the runs this story exists for. Window expiry is AC3's typed refusal — never a silent give-up and never an unbounded wait holding a lock. No lock is held across teardown (the gate's own rule) and the observer takes no approval lock at all. The window is the **foreground form's**, and DF3.8's sweep deliberately does not inherit it — a sweep is not a wait; see DF3.8 AC2(a).
- **`reverify()`'s two environmental preconditions, stated because the chain composes it rather than re-implements it.** `reverify(runId, deps)` resolves `hostRoot = deps.hostRoot ?? process.cwd()` (`src/reverify/runner.ts:217`) and `runsDir` via `resolveRunsDir` (`:218`). The chain therefore passes `hostRoot` **explicitly** — the repo root the verb was invoked against, resolved and asserted to be a git worktree **before** harvest runs, never discovered after teardown has already destroyed the box. A cwd that is not a repo is a **start-up refusal** (`{code: "reverify-host-root-unusable", …}`, exit 5), never a `verdict: "error"` after the box is gone: at that point the run has `closedAt` set, no bundle path back to a pause, and no box to re-run against — strictly worse than the witness-less collection DF3.8 exists to end.
- **Considered and rejected: a `$HOME`-persistent marker.** R9 recommends `$HOME` for durability, and it would survive a reboot. It is rejected here because the box path is one grammar with a host-side mirror (`boxMarkerPath`) and a box-side writer (`runMarkerPath`): making it persistent means setting `QDS_RUN_ROOT` in the box only, which re-creates precisely the split-brain DF1.11's INV-IBOX-13 forbids for the steering root, and it would fork the path fan-out's live-proven probe already uses. Reboot-before-observation is instead handled honestly by AC3. Revisit only if a measured reboot rate makes the loss window material.
- **DF1.10's review round 1 hardened the marker surface this story polls — read it before implementing.** Two changes matter here. (1) **Marker identity is now checked.** `markerReplayRefusal` resolved the marker via `runMarkerPath()` — one path per marker *root*, not per run — and parsed the body while reading only `.ok`, never comparing the `runId` sitting in the same object. A foreign run's verdict could be mirrored, and `/run` being tmpfs meant a reboot erased the guard entirely. The engine now refuses a foreign marker with **`ENGINE_MARKER_FOREIGN`** and a journal-with-rows-and-no-marker with **`ENGINE_JOURNAL_ORPHANED`**, backed by a durable `$HOME` sentinel that the tmpfs marker cannot provide. Both are **new contract surface this bridge will meet**: a run that ends in either refusal writes no usable marker, which the shared classifier (AC2) sees as `absent`/`unusable`, and the operator-facing explanation lives in the engine's refusal, not in the observer. (2) **The image-side amplifier is CLOSED, not filed.** `RuntimeDirectory=journal trace` used **literals in a template unit**, so every instance shared `/run/journal` and `RuntimeDirectoryPreserve=yes` carried run A's marker into run B. The unit now declares `RuntimeDirectory=qds-run/%i/journal qds-run/%i/trace` ([#217](https://github.com/Quantum-Digital-Solutions/QDS-Factory/issues/217) item F-D1, image half; `oci/exedev/systemd/qds-run@.service:158`) — `%i` is the instance name, which is the runId, so two units can no longer share a root by construction. "The marker at this path belongs to this run" is therefore a **filesystem** property as well as a code one, and `Preserve=yes` is now what makes the marker readable *after* the engine exits rather than a cross-run leak. The engine derives the same tree from its sole argv (`runMarkerRoot(runId)`) and no `QDS_*` path variable bridges the two — the unit's own docblock cites AC4 of this story for that rule, and DF2.10's AC6 build-time scan enforces it, which is why AC4 needs no run-time ambient-env refusal.

- **Open seam, flagged rather than resolved by heuristic: the run record carries no "was this unit ever started" stamp.** `fleet run` reads the record (`src/fleet/run.ts:509`) and never writes it, so the host cannot distinguish "dispatched, not yet started" from "started, exited 0, wrote no marker" — both read `inactive`/`unknown`. This story does not need that distinction (AC2(d) treats only `failed` as terminal, and everything else is bounded by the skip streak or AC3's window), and it does **not** invent one. DF3.8's terminal `run-lost-to-reboot` arm *does* need it, and is bounded accordingly in that story. **Owner: the arc owner**, as a DF1.10 seam question — a `startedAt` stamp written by `fleet run` would make both arms exact. Not a blocker for either story as specified.
- **This story carries no story-local deviations.** Consequence 4's completion-marker reading is ADR **Appendix A (2026-09-08)**, not a deviation; the next reviewer who needs one starts at **Deviation 1**.

## Observability Contract

- Every observation logs `{ requestId, runId, event, marker_poll_ms }` — `event ∈ run-complete | marker-absent | marker-skip | marker-unusable | run-engine-dead | box-unreachable | pause-promoted | run-completion-unobserved`. The marker's bytes are never echoed and no credential material is read or logged.
- `requestId` propagates from the **invoking** process onto every observer line. The **chain** separately carries the run's own `dispatchRequestId`, read off the run record's correlation stamp (`stampCorrelation`, `src/fleet/dispatch.ts:2667`), which is what the gate's `pause` event carries. The two are the same value when the observer runs in the invocation that dispatched the run and **different** when a DF3.8 sweep drives it — the sweep did not dispatch the run and cannot mint that id — so the join key is always the **record's**, never the invocation's. No second key is minted; errors carry `{ code, message, remediation }`.
- Sub-timings: `marker_poll_ms`, `chain_ms`. `chain_ms` is **absent, not `0`**, when no chain ran — `0` is a lie shaped exactly like an instantaneous chain, the same reason the gate omits `teardown_at_pause_ms` rather than zeroing it (`src/fleet/approval-gate.ts:1124-1137`, deferred item D8).

## Files to Modify

- `src/fleet/run-completion.ts` (new — the bounded observer and the chain composition; the only new module in this story. It **acquires no lock**, by construction and from day one: `acquireRunLock` is not re-entrant (`scripts/lib/run-lock.ts:951`) and every caller — this story's single-run verb, DF3.8's sweep, and DF6.1a's fix run — takes the lock itself before calling in. The exported entries are `observeAndDriveChain(runId, deps): Promise<ChainOutcome>` and `promoteStrandedPause(runId, deps): Promise<ChainOutcome>` (AC5's post-teardown `reverify()` leg, also the entry DF3.8 AC3 re-enters a reaper-collected run at — one mechanism, two callers). It is a **precondition**, asserted in both docblocks, that the caller already holds `<runsDir>/<runId>.lock`.
  `deps` is `{ driver, store, runsDir, hostRoot, runLock, maxTicks?, windowMs? }`. **`hostRoot` is required**, resolved and asserted a git worktree by the caller before any box is touched, never discovered inside `reverify()`. **`runLock` is the caller's `RunLockHandle`** (DF2.11), passed to `teardownSandbox` unchanged: the module still acquires **nothing** — holding a handle and taking a lock are different acts — and the handle is what turns "the caller already holds the lock" from a docblock precondition into a **compile-time** one. *Ordering: if DF2.11 has not merged when this story starts, the parameter is added anyway typed `string`, and DF2.11 narrows it to the brand; this story is the eighth `teardownSandbox` call site DF2.11 enumerates.* **The poll bound is the caller's**, expressed as `maxTicks` (unset = poll to `windowMs`): `fleet observe <run-id>` passes the operator's window, DF3.8's sweep passes `maxTicks: 1`, because a sweep is not a wait. A module-constant window neither caller can override MUST fail DF3.8's serialisation test. `ChainOutcome` is a discriminated union the caller can count and log without re-deriving: `{ kind: "driven"; markerOk: boolean; chainMs: number }` · `{ kind: "unsettled"; verdict: MarkerVerdict; markerWitnessed: false }` · `{ kind: "refused"; code: string; message: string; remediation: string; markerWitnessed: boolean }`. `markerWitnessed` is what DF3.8 AC3's `completion-unwitnessed` arm turns on; it is **never** persisted and means "witnessed by THIS invocation")

## Security Invariants

- **INV-IBOX-14 (gate ownership is unchanged, and provably so):** the approval gate stays host-owned; this story changes zero lines in `src/fleet/approval-gate.ts`, `src/fleet/approvers.ts`, `src/pr/push.ts` and `src/providers/run-record.ts`'s approval-extension block, and writes no `extensions.approval` field. **"Provably" means a runnable check, not a reviewer's eye**: the AC1 import fence fails the suite if `src/fleet/run-completion.ts` ever names one of those modules — or the `src/fleet/index.ts` barrel, which reaches `approval-gate.ts` through `status.ts:54`'s `expiredState` import rather than by re-exporting the gate — in a **direct** import specifier, so the bridge cannot acquire the *ability* to write the namespace even if a later edit wanted to. The fence is on direct specifiers only; the transitive path to the gate through DF5.1's `ApprovalPort` is the design and must not fail it. The marker is a run-**completion** signal, never an approval state. DF3.4 **INV-APPROVE-6** (an open record naming a `vmName` or `keyHash` cannot promote without a teardown seam) is inherited untouched and must not be weakened to let a bridge promote earlier.
- **INV-IBOX-15 (the marker is a signal, not evidence):** it carries `{runId, ok, completedAt}` at 0600, published by temp+rename so its bytes never exist half-written. Nothing downstream treats it as verification — DF5.1's host re-verify remains the independent second layer of the two-layer evidence doctrine this placement restores. The observer never synthesizes a completion, never destroys or tears down a box on an absent, unreadable or unparseable read, and an unobserved run fails **open on the infrastructure** (box alive, listable, evidence intact) and **closed on the gate** (no approval registered).
- **INV-IBOX-16 (one reverify *entry point*, no daemon, no new state):** this story ships the single entry point `observeAndDriveChain` and the invariant is **"at most one automatic caller at a time, each holding the per-run invocation lock"**, *not* "exactly one caller". Three automatic callers are sanctioned and none of them is a second implementation: this story's `fleet observe <run-id>`, DF3.8's `--all` sweep, and DF6.1a's fix run. **The lock lives in the caller, never in this module** — `acquireRunLock` is not re-entrant (`scripts/lib/run-lock.ts:951`), so an acquisition pushed into the shared composition would refuse the sibling that already holds it. Every caller refuses when the record already carries a terminal or `awaiting-approval` extension (AC5), so no *unlocked* automatic entry to `reverify()` exists and its one-process-per-invocation precondition (`src/reverify/worktree.ts:319`, F106) stays exactly as narrow as DF5.1 left it. The invariant is **not** "no concurrent reverify is possible" — a hand-run `scripts/reverify.ts` is unfenced today and stays unfenced; claiming otherwise would retire F106 without paying for it. It introduces no watcher process, no second expiry clock, and no persisted field; the run record's approval namespace stays exactly as DF3.4 closed it, and `awaitDecision` gains no production caller.
