# P1.11: `qds-hindsight-prime` recall-before / retain-after — the L2 per-story memory loop

**Story Points:** 4

## Spec Reference

- PRD §6.2 / §6.5 + §9.1 (loop L2 — per-story); FR-MG-6, FR-MG-7, FR-MEM-2
- Supporting: NFR-PERF-4 (recall ≤2s p95 cloud / ≤1s self-host, proceed-unprimed-on-timeout), NFR-REL-3 (retain idempotent, `document_id=runId`), NFR-SEC-5 (Hindsight calls send `Authorization: Bearer`), NFR-OBS-3 (handoff logged with issue-id)
- Phase exit gate: PRD §13 Phase-1 clause 9 — "a run recalls relevant prior bank entries into the node system prompt before execution and retains its learnings after." (FR-MG-6/7, FR-MEM-2)

## User Story

As the Hermes Dev manager driving a `qds-piv-loop` run for a `{repo}` issue,
I want the run to recall relevant prior `{repo}` bank entries into the implement node's system prompt before it executes and retain that run's learnings after it finishes,
so that each story benefits from accumulated prior learnings and feeds its own back (G3 — the factory learns), closing the L2 per-story memory loop on a real run.

## Overview

This slice cuts through Hermes (run-start/run-finish hooks) → Hindsight bank-scoped REST (`/v1/default/banks/{bank_id}/memories/recall` and `/memories/retain`) → the Pi-team implement node's primed system prompt (`--append-system-prompt` via `--context-path`) → the `{bank_id}` shared bank (slug derived from repo name per P0.9). On `agent.run.started` the `qds-hindsight-prime` step recalls by issue title+desc against the per-repo `{bank_id}` bank and injects the fused result into the node prompt BEFORE execution; on `agent.run.finished` it retains the run output to the same bank with `document_id = runId` (Hindsight replaces on matching `document_id` → idempotent upsert). It is one atomic 4-pt unit because the loop is not demonstrable until BOTH halves round-trip on a real run — recall-before that primes the prompt AND retain-after that lands a queryable `document_id == runId` document — splitting them would leave a half-loop (recall with nothing to recall, or retain that never primes).

## E2E Slice

**Demonstrable behavior:** Running a `qds-piv-loop` run on a `{repo}` issue causes (1) a `POST /v1/default/banks/{bank_id}/memories/recall` BEFORE the implement node executes whose fused result is injected into the node's system prompt, and (2) a `POST /v1/default/banks/{bank_id}/memories/retain` AFTER the run finishes with `document_id` equal to the Paperclip `runId` — so a follow-up `recall` (or document fetch) on `{bank_id}` returns a document whose `document_id == runId`.

**Wiring closed:** On completion of this story, a real `qds-piv-loop` run recalls prior `{repo}` bank entries into the implement node's system prompt before execution AND retains the run output to `{repo}` with `document_id == runId` (re-fetchable after the run), using only code merged by this story. No stub, no `TODO: wire later`, and no sibling story is required to make this behavior real. Predecessors, if any, are dependency edges (listed below), not unfinished wiring inside this story.

**Dependency edges (predecessors):** P0.9 (Hindsight host decided — self-host default / cloud opt-in, OQ-4; `{repo}` + `{repo}-dev-meta` banks exist; retain→recall→reflect round-trip proven on a throwaway bank), P1.6 (the Pi-team implement node exists and accepts a primed system prompt via `--context-path` / `--append-system-prompt`). The Mulch house-style prime is the SEPARATE sibling story **P1.12** (different store, dependency-independent — not wired here).

## Acceptance Criteria

1. **(make-or-break)** Given a `qds-piv-loop` run for a `{repo}` issue with `runId = R`, When the run executes end-to-end, Then a `recall` against `{repo}` is issued BEFORE the implement node runs (its result text appears in the node's system prompt) AND after the run a document with `document_id == R` is retrievable from the `{repo}` bank. (Binary: recall precedes node exec in the run log AND a `{repo}` document exists with `document_id == R`.)
2. Given the same run is RE-RUN with the same `runId = R` (e.g. a retry), When retain fires again, Then the `{repo}` bank holds exactly ONE document for `document_id == R` (Hindsight upsert/replace on matching `document_id`) — no duplicate (NFR-REL-3).
3. Given the `{repo}` bank is empty (cold-start, day-1) OR recall exceeds its NFR-PERF-4 latency budget, When recall runs, Then it returns an empty/timed-out result and the node proceeds UNPRIMED with a logged warning (recall is an enhancement, never a hard dependency) — never a hang and never a halt.
4. Given a recall for repo `{repoA}`, When prior entries exist only in a different repo's bank `{repoB}`, Then the recall is scoped to `{repoA}` and returns ZERO `{repoB}` entries — no cross-repo bleed into the prompt (tenant isolation).

## Technical Notes

- **Retain timing (P1.11-L1):** Retain fires immediately on `agent.run.finished` — no debounce. The retain call is synchronous within the finish hook (awaits completion or timeout before the hook returns). There is no batching or delay.
- **Contracts/Schema (JSON):** Recall request → `POST /v1/default/banks/{bank_id}/memories/recall` body `{ query: <issue title+desc>, budget: "mid", max_tokens: <=4096 }` (NFR-PERF-4); retain request → `POST /v1/default/banks/{bank_id}/memories/retain` body wraps an `items` array of `MemoryItem` objects plus `update_mode` — the body MUST be `{ "update_mode": "append", "items": [{ "document_id": "<runId>", "content": "<extracted key facts from run output>", "metadata": { "source": "qds-hindsight-prime", "runId": "<runId>", "issueId": "<issueId>", "extracted_at": "<timestamp>" } }] }` (NOT a flat object without the `items` wrapper — the `/memories/retain` batch endpoint rejects bare `document_id`/`content` with 422). The `items` array is mandatory; `update_mode` defaults to `"append"` (explicit to avoid implicit behavior) (per H3 — extracted facts, not raw merged JSON). Hindsight replaces on matching `document_id` → idempotent upsert, NFR-REL-3. Bank id (`{bank_id}`) is a slug derived from the repo name per P0.9 — NOT `{repo}-dev-meta` (meta-banks are the L4 path, out of scope here).
- **Recall response shape (P1.11-V-M-1):** Recall response: `{ results: Array<{ content: string, score: number, document_id: string }>, fused_text: string }`. The wrapper uses `fused_text` as the injected context string. If `fused_text` is empty, treat as cold-start (AC-3). `results` is informational for logging only.
- **Zod request schemas (P1.11-V-M-2):** `RecallRequestBody = z.object({ query: z.string(), budget: z.literal('mid'), max_tokens: z.number().int().max(4096) })`; `RetainRequestBody = z.object({ update_mode: z.literal('append'), items: z.array(RetainItem) })`; `RetainItem = z.object({ document_id: z.string(), content: z.string(), metadata: z.object({ source: z.string(), runId: z.string(), issueId: z.string(), extracted_at: z.string() }).strict() })`. DoD Contract checkbox covers validation of these schemas.
- **CC-6 Ordering Note (P1.11 + P1.12 context-path merge):** P1.11 recall runs BEFORE P1.12 Mulch prime. P1.11 writes recalled Hindsight memories to `--context-path`. P1.12 appends Mulch expertise to the same file. The Pi-team implement node reads the merged context-path containing both Hindsight recall content and Mulch expertise.
- **Integration points (each wired & exercised):** (1) `agent.run.started` → recall, result fused (RRF + cross-encoder, 4-strategy) and injected into the implement node's system prompt via `--context-path` → `--append-system-prompt` (P1.6 surface); (2) `agent.run.finished` → retain with `document_id = runId`; (3) every Hindsight call carries `Authorization: Bearer <token>` from env/secret ref (`HINDSIGHT_CP_DATAPLANE_API_KEY` primary; `HINDSIGHT_API_KEY` legacy alias, per P0.9 INV-1, NFR-SEC-5); (4) the recall→prime and retain handoffs are logged with the issue-id correlation (NFR-OBS-3) — this is audit-chain hop #10 (`run → memory`, `document_id == runId`, r3 §B).
- **Files / functions touched:** the `qds-hindsight-prime` step (recall-on-start, inject-into-prompt), the retain-on-finish hook, the Hindsight client wrapper (bearer auth + base_url self-host/cloud switch), the recall-timeout/empty-bank fallback path.
- **Guards/limits:** recall budget `mid`, `max_tokens ≤ 4096`, p95 ≤2s cloud / ≤1s self-host, MUST NOT block the node beyond the `RECALL_TIMEOUT_MS` timeout (NFR-PERF-4 — dedicated recall budget of 5s cloud / 2s self-host, independent of `PI_COMS_TIMEOUT_MS`; on timeout proceed unprimed with a logged warning) → contrast with the retain timeout `QDS_RETAIN_TIMEOUT_MS` (5s), which is a separate, much shorter budget. The recall hard cutoff is `RECALL_TIMEOUT_MS` (5s cloud / 2s self-host, dedicated — independent of `PI_COMS_TIMEOUT_MS`; on timeout, proceeds unprimed with a logged warning); the retain hard cutoff is `QDS_RETAIN_TIMEOUT_MS` (5s). Recall result count cap: the recall request includes `max_tokens <= 4096` (already specified). Additionally, the recall endpoint returns at most 20 documents per request (Hindsight default). If more than 20 match, they are ranked by relevance and truncated. The fused result text is capped at 4096 tokens — if the raw fusion exceeds this, later-ranked entries are dropped. This prevents prompt-bloat from excessive recall matches.
- **Bank ID derivation (P1.11-H1/H5):** Bank ID is derived from the repo slug: `org/repo` → `org-repo` (forward slashes replaced with hyphens, lowercased). Example: `Quantum-Digital-Solutions/QDS-Factory` → `quantum-digital-solutions-qds-factory`. This matches the Mulch domain derivation convention from P1.12. If the repo has no org prefix (bare name), the bank ID is the lowercased repo name. Special characters (dots, underscores, plus signs) are preserved as-is. Only forward slashes are replaced with hyphens. The bank ID is always lowercased. Characters not matching `[a-z0-9._+-]` are stripped. Maximum length: 63 characters (truncated if longer). **Empty-string guard:** if the derived bankId is `""` after all transformations (e.g., a repo name made entirely of stripped characters), the wrapper throws a `ValidationError` with message `"bankId derivation produced empty string for repo: {originalRepo}"` and the run does NOT proceed. This is a configuration error — a repo identifier must produce a valid bank ID. Callers must handle this by logging the error and proceeding without Hindsight (same as unreachable-fallback per P1.11-H6).
- **Recall-before freshness (P1.11-H2):** Recall is always executed before the run (no staleness check). Every Pi-team run triggers a fresh recall to get the latest stored memories. The recall does NOT check timestamps — it always fetches. This ensures the implement node always has current context.
- **Retain stores extracted facts (P1.11-H3):** Retain stores extracted key facts from the run's merged JSON output (e.g., 'The project uses Zod for validation', 'Auth is Clerk-based'), NOT the raw LLM output or full merged JSON. The extraction is done by parsing the structured result fields, not by storing verbatim text.
- **Auth env var standardization (P1.11-H4):** Hindsight API auth uses `HINDSIGHT_CP_DATAPLANE_API_KEY` env var as the primary Bearer token source (set by P0.9). `HINDSIGHT_API_KEY` is accepted as a legacy alias (logged as deprecation warning when used), matching P0.9 INV-1 precedence. All Hindsight calls send `Authorization: Bearer ${HINDSIGHT_CP_DATAPLANE_API_KEY}`. No other env var names are used for server auth. `HINDSIGHT_API_LLM_API_KEY` (the LLM-provider key) is a separate credential and is NOT used as the server-auth token. `update_mode` values: `"append"` (default) adds new items to the bank without removing existing entries — idempotent on matching `document_id` (replaces the matching document, leaves others untouched). `"replace"` clears all existing items in the bank before writing — destructive, NOT used by this story. P1.11 always uses `"append"` (explicit in the body, never omitted). The `"replace"` mode is reserved for P0.9 bank initialization and is not invoked by the per-run retain hook.
- **Hindsight unreachable fallback (P1.11-H6):** if the Hindsight server is completely unreachable (connection refused, DNS failure, not just timeout), the recall step returns an empty result and logs a warning with the error details. The run proceeds unprimed. This is the same behavior as the timeout case (AC-3) — Hindsight is always an enhancement, never a hard dependency. The retain step is also best-effort: if Hindsight is down on retain, the run completes normally and the retain failure is logged. Retain failures do NOT affect exit_class — the run succeeded even if the memory write failed.
- **exit_class for Hindsight failures (P1.11-H7):** recall timeout/unreachable → `"logic"` (run proceeds unprimed, not a transient retry). retain failure → `"logic"` (run completed successfully, memory write is best-effort). Neither recall nor retain failures produce `"transient"` exit_class — the run always completes, and Hindsight is never on the critical path.
- **Retain timeout budget (P1.11-V-M-3):** Retain call timeout: 5 seconds (configurable via `QDS_RETAIN_TIMEOUT_MS`). On timeout, log warning and return — the finish hook does not block beyond 5s on Hindsight. Matches NFR-PERF-5 advisory precedent from P1.12's 3s Mulch record timeout.
- **MemoryItem type (P1.11-V-L-4):** `{ document_id: string (required), content: string (required), metadata: { source: string (required), runId: string (required), issueId: string (required), extracted_at: string ISO-8601 (required) } }`. No optional fields. Additional metadata keys are NOT allowed — the schema is strict.
- **Hindsight HTTP error classification (P1.11-V-L-1):** 401/403 → logged as ERROR (config issue — `HINDSIGHT_CP_DATAPLANE_API_KEY` may be wrong), proceed unprimed. 404 on recall → cold-start (bank doesn't exist yet, proceed unprimed with info log). 429/5xx → proceed unprimed with warning. Retain: all non-2xx → log and proceed (best-effort). None trigger `"transient"` retry.
- **Retain on failed runs (P1.11-V-L-3):** Retain fires on ALL runs (success and failure). For failed runs, `content` is set to the error summary (e.g., 'Schema validation failed: exit_class logic'), not the full trace. This allows future recalls to learn from failure patterns. Test covers retain-after-failure with truncated error content.

## Security Invariants

- **INV-1 (tenant):** Recall and retain are bank-scoped to the run's own `{repo}` — the bank id is derived from the issue's repo, never a wildcard or cross-repo bank; a recall for `{repoA}` MUST NOT return `{repoB}` entries (AC-4). Cross-repo bank ids are rejected, not silently coerced.
- **INV-2 (tenant):** Retain writes ONLY to the run's `{repo}` bank with `document_id = runId`; a run for `{repoA}` can never write a document into `{repoB}`'s bank (no cross-tenant write).
- **INV-3 (secrets/auth):** Every Hindsight call sends `Authorization: Bearer <token>` sourced from env/secret ref (`HINDSIGHT_CP_DATAPLANE_API_KEY` primary; `HINDSIGHT_API_KEY` legacy alias with deprecation warning, per P0.9 INV-1 precedence, NFR-SEC-5); the token is NEVER hardcoded, logged, or written into the retained memory content. `HINDSIGHT_API_LLM_API_KEY` (the LLM-provider key) is NOT used as the server-auth token — the two are not conflated.
- **INV-4 (idempotency/integrity):** Retain keys on `document_id = runId` so a retried run upserts (replaces) rather than duplicating (NFR-REL-3) — exactly one document per `runId`, keeping the audit-chain hop #10 link unambiguous.

- [ ] **Security:** INV-1/INV-2 (tenant: per-repo bank isolation, recall pulls no cross-repo entry, retain writes only own bank) and INV-3 (Bearer from secret ref, never logged) each enforced and tested.
