# P0.3: `pi-team-launch.sh` mixed-model team emits one merged JSON node-output

**Story Points:** 4

- Phase exit gate: PRD §13 Phase-0 clauses 1 ("`pi-team-launch.sh "refactor X" ./ctx` returns a single merged JSON object on stdout") and 2 ("Run logs show ≥2 named agents exchanging ≥2 coms … messages")

**Notation convention:** Throughout this story, "coms" (lowercase) is the canonical spelling for the Pi in-node communication system. Never "COMS" or "comms".

## User Story

As an Operator standing up the Dark Code Factory execution layer,
I want a launcher that runs a guarded 3-agent mixed-model Pi team and emits exactly one merged JSON object to stdout,
so that a Warren run has a single live entry point that yields one structured node-output from a real team (G1 lights-out execution; G2 auditability).

## Overview

This slice authors `pi-team-launch.sh` (does NOT exist on disk — §5.5 item 3 / R4 §5) and cuts vertically through: launcher CLI → 3 named `pi` subprocesses (`--cname <run-id>-<role>`, mixed providers: 1 Anthropic-native judgment role + 2 OpenRouter constrained roles, GLM + Kimi) → in-node coms exchange → lead schema-validates each worker reply (coms `response_schema` is parse-only, §4.6/R4 §1) → lead merges into a single JSON object with mandatory `changed_files: string[]` → launcher validates the merged object and writes it (and ONLY it) to stdout; all logs/diagnostics go to stderr (stdout is captured verbatim as the run's structured output). Hard guards (budget/turn/wall-clock/`coms_await` timeout) are spawned-and-owned here but loopy-kill guards are implemented here; proof covered by e2e kill-guard test in DoD. This is one atomic 4-pt unit because the merged-JSON-to-stdout capability is not demonstrable until launch + coms + lead-validation + merge + stdout-discipline all run together; splitting any leaves leftover wiring.

**Role-to-model mapping format:** The `--role-model` flag uses the format `--role-model <role>=<provider>/<model-id>`. The provider prefix is mandatory and must be one of `anthropic` (for Anthropic-native models) or `openrouter` (for OpenRouter-routed models). Examples: `--role-model architect=anthropic/claude-sonnet-4-6`, `--role-model impl=openrouter/z-ai/glm-4.6`, `--role-model reviewer=openrouter/moonshotai/kimi-k2`. The `<role>` segment must be one of the three canonical role names: `architect`, `impl`, `reviewer`. Invalid or duplicate role names cause the launcher to exit non-zero with a diagnostic.

**Lead role definition:** The `architect` role is the designated lead. Behaviorally, the lead: (1) initiates the coms exchange by sending the task to workers, (2) collects each worker's `coms_await` reply, (3) schema-validates every reply (rejecting any missing `changed_files: string[]`), (4) merges all validated replies into a single JSON object, and (5) returns the merged object to the launcher for final validation. The lead does NOT delegate validation or merge responsibility. If the lead itself fails or times out, the launcher emits no stdout and exits non-zero with `exit_class:"logic"`.

**Subprocess isolation and cleanup:** The launcher spawns each Pi subprocess as a child process and tracks all PIDs. On any exit path — success, validation failure, guard trip, or signal — the launcher performs mandatory cleanup: (1) sends SIGTERM to all remaining child PIDs, (2) waits up to 5 seconds for graceful exit, (3) sends SIGKILL to any surviving children, (4) removes any temporary files (e.g. per-role stdout capture files in `$TMPDIR`), and (5) logs the cleanup summary to stderr. This applies to both the happy path (after merged output is written) and all error paths. The launcher also traps SIGINT/SIGTERM to ensure cleanup runs on external signals.

## E2E Slice

**Demonstrable behavior:** `pi-team-launch.sh --task "refactor X" --context-path ./ctx --archetype C --role-model architect=anthropic/claude-sonnet-4-6 --role-model impl=openrouter/z-ai/glm-4.6 --role-model reviewer=openrouter/moonshotai/kimi-k2 --budget-cap-cents 50 --turn-cap 12 --wall-clock-cap-ms 480000` runs a live 3-agent mixed-model team; stdout is exactly ONE JSON object parseable by `jq -e .` carrying `changed_files` (string[]), `result`, `partial` (bool), `exit_class`; the stderr log shows ≥2 named agents (`<run-id>-architect`, `<run-id>-impl`, …) exchanging ≥2 coms messages. Coms mode is discovered via `PI_COMS_MODE` env var or `config/pi-coms.json` fallback (see Technical Notes). The `--budget-cap-cents` value is in **US cents** (e.g. `50` = $0.50). The `--archetype` flag accepts: `C` (code-heavy, default), `R` (research-heavy), `D` (design-heavy). If `--archetype` is omitted, the default is `C`. The archetype selects per-role system-prompt templates and turn-allocation weights; it does NOT change the role-to-model mapping. Subprocess retries: the launcher performs **0 retries** on PI subprocess failure — each subprocess runs exactly once. A failed subprocess triggers the cleanup protocol and the launcher exits non-zero with `exit_class:"logic"`.

**Wiring closed:** On completion of this story, `pi-team-launch.sh --task "refactor X" --context-path ./ctx …` produces a single `jq`-parseable merged JSON object on stdout (with `changed_files: string[]`) and a stderr log evidencing ≥2 named agents exchanging ≥2 coms messages, using only code merged by this story (the launcher script, the lead merge+validate logic, `spawn-role.ts` per-role spawning). No stub, no `TODO: wire later`, and no sibling story is required to make this behavior real. Predecessors, if any, are dependency edges (listed below), not unfinished wiring inside this story.

## Acceptance Criteria

> ≥3 scenarios, Given/When/Then. Exactly one tagged (make-or-break) and binary.

1. **(make-or-break)** Given a live API key for the Anthropic role and an OpenRouter key for the GLM/Kimi roles, When `pi-team-launch.sh --task "refactor X" --context-path ./ctx --archetype C --role-model architect=anthropic/claude-sonnet-4-6 --role-model impl=openrouter/z-ai/glm-4.6 --role-model reviewer=openrouter/moonshotai/kimi-k2 --budget-cap-cents 50 --turn-cap 12 --wall-clock-cap-ms 480000` is run, Then BOTH sub-clauses must pass: **(a) stdout format assertion:** stdout contains exactly one JSON object (`jq -e 'has("changed_files") and (.changed_files|type=="array")'` exits 0; `jq -e . | wc -l` confirms a single top-level value); **(b) coms evidence assertion:** the stderr run-log shows ≥2 distinct `--cname` agents exchanging ≥2 coms messages. The coms evidence is verified by grepping stderr with the explicit pattern `coms_(send|await)` which must match ≥2 lines, and the agent-name extraction pattern `\[cname: [^\]]+\]` must yield ≥2 distinct cname values. Both (a) and (b) are required for a pass but are independently diagnosable — a failure in either sub-clause is reported with its specific assertion label for targeted debugging.
2. Given each of the three roles uses its assigned provider, When the lead receives each worker's `coms_await` reply, Then the lead **explicitly schema-validates** the reply before accepting it (parse-only coms ⇒ lead validates, §4.6/R4 §1); a reply missing the mandatory `changed_files: string[]` field causes the lead to re-request or **fail the node as a logic error** (logged `exit_class:"logic"`), never silently accept it.
3. Given the lead-merged object fails the launcher's final merged-schema validation, When the launcher is about to write stdout, Then the launcher **writes nothing to stdout and exits non-zero** (no partial/invalid JSON ever reaches the node-output channel), with the validation failure logged to stderr.

## Technical Notes

- **Contracts/Schema:** Merged-output JSON contract (the node-output) = `{ changed_files: string[] (set-union of all workers, mandatory), result: object, partial: boolean, exit_class: "transient"|"overflow"|"logic", waivers: { rule_id: string, reason: string, approved_by?: string }[] }`. Full waiver schema (e.g. approval workflows, expiry) is deferred to Phase 1+. Each worker `response_schema` MUST carry `changed_files: string[]` (omission = node failure, CORRECTNESS-C). Express as a TS/Zod contract used by the lead validator and the launcher final-gate validator. Backward-compat: net-new file, no existing node-output consumers to break. **`partial` field semantics:** `partial` is `true` when the team produced output but one or more workers did not complete their full turn allocation (e.g. a budget/turn/wall-clock guard tripped mid-exchange, or a worker returned a schema-invalid reply that the lead could not recover from). When `partial` is `true`, `changed_files` contains only the set-union from workers that completed successfully, `result` contains a `summary` noting which roles were incomplete, and `exit_class` reflects the reason for incompleteness (e.g. `"overflow"` for budget trip, `"logic"` for validation failure). `partial` is `false` only when all three workers completed and passed lead validation. **Merged-output edge-case validation rules:** (1) `changed_files` MAY be an empty array `[]` — this is valid (workers made no file changes); (2) `result: null` is INVALID — `result` must be a non-null object containing at minimum a `summary: string` field representing the agent's work output; an empty object `{}` is invalid (a null or empty result means no meaningful work was done and must be surfaced as `exit_class:"logic"`); (3) `exit_class` is mandatory and MUST be a non-null string — one of `"transient"|"overflow"|"logic"` (absent or null `exit_class` = rejected at the launcher final-gate, no stdout emitted).
- **Coms path discovery:** The launcher discovers P0.2's coms architecture decision via the `PI_COMS_MODE` env var (values: `socket`|`subprocess-rpc`), set by P0.2's installer into the runtime environment. If `PI_COMS_MODE` is absent, the launcher falls back to reading `config/pi-coms.json` (written by P0.2's setup). If neither source is available, the launcher logs a diagnostic to stderr and exits non-zero (coms mode is required, not optional). The `--coms-mode` CLI flag overrides both sources for manual testing.
- **Integration points (each wired & exercised in this story):** (1) per-role `pi` subprocess spawn via `src/launcher/spawn-role.ts` with `--cname <run-id>-<role>` (extension flag `coms.ts:536`; fallback chain frontmatter `name:` → `agent-<6chars>`); `spawn-role.ts` is responsible for constructing the per-role `pi` CLI invocation from parsed `--role-model` / `--append-system-prompt` / budget-env args, and returning the child PID to the launcher for guard-tracking; (2) `--role-model <role>=<provider>/<model-id>` repeatable, GLM/Kimi forced via `openrouter` provider prefix, Anthropic native via `anthropic` provider prefix (R4 §9 — Pi natively supports ONLY anthropic+openrouter); (3) in-node coms exchange via the P0.2-selected path; (4) lead per-reply schema validation → launcher final merged-object validation → single stdout write (stdout carries the validated merged JSON (captured verbatim); all subprocess logs/diagnostics go to stderr); (5) `--append-system-prompt` per-role system prompts; (6) `--context-path` carries the Mulch/Seeds bundle.
- **Files / functions touched:** new `scripts/pi-team-launch.sh` (orchestrates spawn/cname/role-model/stdout-discipline); new `src/launcher/merge-output.ts` (lead merge + Zod validate); new `src/launcher/output-contract.ts` (Zod schema + TS type).
- **Guards/limits:** `--budget-cap-cents` (value is in **US cents**, e.g. `50` = $0.50 USD), `--turn-cap` (integer, max agent turns per role), `--wall-clock-cap-ms` (milliseconds, MUST be ≤ the caller's own timeout budget), `coms_await` per-call timeout (`PI_COMS_TIMEOUT_MS`, default 30 min `coms.ts:32`; TDD-Trio recommended start 8 min). **Subprocess retry policy:** 0 retries — each PI subprocess is launched exactly once; failure triggers cleanup and non-zero exit. Guards are spawned/owned by the launcher process here. The loopy-kill guards (budget/turn/wall-clock caps) are IMPLEMENTED in this story — the launcher wires them into each subprocess. The dedicated kill-proof story P0.4 was killed per the Warren decision, so the proof obligation falls to the e2e test in this story's DoD (see final DoD item). Full Warren-integration kill-proof (hardened process-group kill, orphan detection) is deferred to a future phase.
- **Context-path handling:** The launcher resolves `--context-path` to an absolute path (via `realpath`), validates that the directory exists and contains at least one `.jsonl` file (Mulch/Seeds expertise bundle), and exits non-zero with a diagnostic to stderr if the path is missing or empty. This guard ensures every team launch has a real priming bundle rather than silently running un-primed.
- **Budget cap propagation:** Per-role budget caps are propagated as `BUDGET_CAP_ROLE_<N>` env vars to each PI subprocess (e.g. `BUDGET_CAP_ROLE_0`, `BUDGET_CAP_ROLE_1`, `BUDGET_CAP_ROLE_2`); the launcher sets them from parsed CLI flags `--budget-role0-cents`, `--budget-role1-cents`, `--budget-role2-cents` (each value in **US cents**, mapped to `BUDGET_CAP_ROLE_0`/`_1`/`_2` respectively). If a per-role flag is omitted, the global `--budget-cap-cents` value is used as the fallback for that role (capped at 50 cents / $0.50 if even the global flag is omitted). All budget values are in **US cents** (consistent with `--budget-cap-cents`).
- **run-id generation:** `run-id` is generated by the launcher as a UUID v4, or accepts `--run-id <id>` for caller-specified IDs. Must be unique per launch and stable across all subprocess cnames and log lines. The launcher validates caller-supplied IDs for uniqueness (no collision with recent runs in the log directory) and falls back to UUID v4 generation if absent.
- **Context-path and P0.9 relationship:** The launcher only validates directory structure and `.jsonl` presence (format-agnostic). Actual Mulch/Seeds content schema is a P0.9 concern. No hard dependency on P0.9 for launcher execution — the launcher will accept any directory containing `.jsonl` files as a valid context bundle.
- **Model ID pinning:** Use generational alias (e.g. `claude-sonnet-4-6`) not date-pinned IDs (e.g. `claude-sonnet-4-20250514`) to avoid retirement breaks. Date-pinned model IDs retire on a fixed schedule; generational aliases auto-resolve to the current stable variant.
- **HONESTY (R4):** The make-or-break AC (AC-1) CANNOT pass without `ANTHROPIC_API_KEY` and `OPENROUTER_API_KEY` both present and valid — coms live 2-agent round-trip needs a paid LLM turn (only contract-load is proven without keys). If keys are absent at run time, the e2e test exits with BLOCKED-on-creds status (not skipped, not false-pass, no mock/stub/unkeyed path exists for AC-1).

## Security Invariants

> Triggers: secrets/env, cost/budget. Concrete named invariants only.

- **INV-1 (secrets/env):** API keys (`ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`) are read from the environment / env-merge passed in by the bash node (`env: { ...process.env, ...node.env }`), **never** hardcoded in `pi-team-launch.sh` or written to stdout, the merged JSON, or any logged line (NFR-SEC-1). The launcher redacts any value matching a key pattern before logging to stderr.
- **INV-2 (secrets/env, stdout discipline):** Only the validated merged JSON object is written to stdout; all subprocess logs, coms traces, and diagnostics go to **stderr** — no secret-bearing subprocess log can leak onto the node-output channel.
- **INV-3 (cost/budget):** Every Pi role's spend is bounded by the launcher-owned `--budget-cap-cents`; the launcher passes per-role caps into each subprocess and never delegates the cap to the agent (the agent cannot lift its own ceiling). Cap-enforcement under a loopy prompt is tested by the e2e kill-guard test in this story's DoD.
- **INV-4 (provider routing):** GLM/Kimi roles are forced through `openrouter` (never a forged "anthropic" provider for a non-Anthropic model), so per-role provider attribution stays truthful for the downstream `cost_events` emitter.
