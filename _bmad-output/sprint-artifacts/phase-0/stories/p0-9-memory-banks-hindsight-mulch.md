# P0.9: Mulch pin + Hindsight memory banks round-trip

**Story Points:** 4

## Spec Reference

- PRD §6.5 (Memory & decomposition); FR-MEM-1, FR-MEM-4; partial FR-MEM-2 (retain/recall round-trip); NFR-PERF-4, NFR-SEC-5
- Phase exit gate: PRD §13 Phase-0 clause 7 (Hindsight retain→recall→reflect round-trips on the chosen bank) + clause 8 (OQ-4 decision recorded)
- PRD §12.1 item 6 (pin tooling + decide Hindsight host + wire banks); R4 §6–§7 (R4 §6: pin external tooling versions; R4 §7: self-host Hindsight deployment architecture, arm64 OpenSSL path); R3 §B hop 10 (R3 §B hop 10: memory-bank provisioning is the 10th audit-chain hop, ensuring retained learnings resolve to a real bank).

## User Story

As a Dev|QA|Maintenance manager (Hermes),
I want a memory substrate that round-trips retain→recall→reflect on a provisioned `{repo}` bank, with the `{repo}-dev-meta` meta-bank also created and Mulch expertise imported,
so that runs can prime prompts from prior learnings and the §8.1 audit chain's memory hop (G2 accountability, G3 learning) resolves to a real bank.

## Overview

This slice cuts Hermes → Hindsight (memory) + Mulch (priming store). It (a) **records the OQ-4 cloud-vs-self-host decision** on cost/latency/data-residency grounds — the local self-host stack is BLOCKED on env (arm64 OpenSSL/arch mismatch, R4 §7), so the decision is the spec deliverable and the round-trip is the proof against the *chosen* endpoint; (b) provisions the two banks `{repo}` and `{repo}-dev-meta` via the bank-scoped API; (c) proves a full `retain → recall → reflect` round-trip on `{repo}`; (d) imports Mulch expertise (`ml` binary from `@os-eco/mulch-cli`) into the priming store. Pins Seeds 0.5.9 (`/usr/local/bin/sd`) and Mulch 0.10.7 (`ml` binary, also aliased as `mulch`) — both public npm packages under the `@os-eco` org. One atomic 4pt unit because the round-trip is not demonstrable until banks exist, the host is chosen, and auth is wired together.

## E2E Slice

**Demonstrable behavior:** `node scripts/memory/provision-banks.ts --repo qds-factory` provisions banks `qds-factory` and `qds-factory-dev-meta`, then runs a `retain → recall → reflect` round-trip against the chosen Hindsight endpoint: it POSTs a known fact to `/v1/default/banks/qds-factory/memories` (with a caller-supplied `document_id`), recalls it via `/v1/default/banks/qds-factory/memories/recall` (the retained fact appears in the top result's `document_id` field), and `/v1/default/banks/qds-factory/reflect` returns a response with a non-empty `text` field. Stdout is a single JSON object `{ host: "self-host"|"cloud", banks: ["qds-factory","qds-factory-dev-meta"], roundTrip: { retained: true, recalledId: "<id>", reflected: true }, mulchImported: <n>, oq4: { decision, rationale } }`.

**Wiring closed:** On completion of this story, running `provision-banks.ts --repo qds-factory` produces the single JSON object above (with `roundTrip.retained===true`, a non-null `recalledId` matching the caller-supplied `document_id`, and `reflected===true` meaning the reflect response's `text` field is a non-empty string) against the OQ-4-chosen endpoint, using only code merged by this story (provisioning script, Hindsight client wrapper with Bearer auth, OQ-4 decision record, Mulch import call). No stub, no `TODO: wire later`, and no sibling story is required to make this behavior real. Predecessors, if any, are dependency edges (listed below), not unfinished wiring inside this story.

**Dependency edges (predecessors):** P0.7 (acquisition/install groundwork — tooling pin baseline). If the self-host stack remains env-blocked at run time, OQ-4 resolves to **cloud** (`api.hindsight.vectorize.io`) as the proving endpoint and the decision record states so; the round-trip is identical (only `base_url`+Bearer differ, R4 §7).

## Acceptance Criteria

> ≥3 scenarios, Given/When/Then. Exactly one tagged (make-or-break) and binary.

1. **(make-or-break)** Given the OQ-4-chosen Hindsight endpoint and a valid Bearer token from env, When `provision-banks.ts --repo qds-factory` runs, Then both banks `qds-factory` and `qds-factory-dev-meta` exist AND the emitted JSON has `roundTrip.retained===true`, a non-null `roundTrip.recalledId` equal to the caller-supplied `document_id` from the retain request, and `roundTrip.reflected===true` (§13 Phase-0 clause 7 satisfied). **Round-trip success criteria (P0.9-H1 resolution):** `roundTrip.recalledId` must equal the `document_id` that was supplied in the retain request body — exact string match against the `document_id` field on the top `RecallResult` from the recall response, not merely "some non-null id returned". Note: the retain response returns `{ success, bank_id, items_count }` (no `document_id`); the `document_id` is tracked from the caller's retain request body. `roundTrip.reflected===true` means the reflect endpoint (`POST /v1/default/banks/{bank_id}/reflect`) returned a response whose `text` field is a non-empty string — not merely HTTP 200 with an empty body. The reflect response schema is `{ text: string (required), based_on?, structured_output?, usage?, trace? }`. The emitted JSON schema includes `recalledId: string` which is the caller-supplied `document_id`, verified by matching it against `RecallResult.document_id` in the recall response after the retain response confirms success (`success: true`).
2. Given the script runs, When it finishes, Then an OQ-4 decision record is written to `docs/decisions/oq-4-hindsight-host.md` capturing `decision` (cloud|self-host), and the rationale columns cost/latency/data-residency, and the emitted JSON `oq4.decision` matches it (§13 clause 8).
3. Given Mulch expertise exists at `.mulch/expertise/*.jsonl`, When the script imports it, Then `mulchImported` equals the count of imported records (>0 when records exist) and `ml prime` over the imported domain returns a non-empty priming prompt. **Test fixture:** create one record via `ml record test-domain --type convention "test fact for provisioning verification"`, then `ml prime test-domain` must produce output containing the recorded text "test fact for provisioning verification". The script asserts `ml prime` exits code 0 AND stdout is a non-empty string containing the recorded content — no arbitrary character-length threshold.
4. Given the Bearer token is absent OR the chosen endpoint is unreachable, When the script runs, Then it exits non-zero with a logged reason — never a silent success. On any HTTP 4xx or 5xx response from the Hindsight API (including a 401 which logs `Hindsight auth failed — check HINDSIGHT_CP_DATAPLANE_API_KEY`), the provisioning script must attempt a compensating delete for each bank already created in this run (calls `DELETE /v1/default/banks/{bank_id}` for each successfully created bank), then exit non-zero while logging the HTTP status code and response body (truncated to 256 chars). No retry. If any compensating delete itself fails, the script must still exit non-zero but must also log an explicit `partial-state` report listing the bank IDs that could not be cleaned up, so callers can detect and act on residual state.

## Technical Notes

- **Contracts/Schema:** Hindsight bank-scoped REST (identical cloud vs self-host, only `base_url`+Bearer differ — R4 §7): retain `POST /v1/default/banks/{bank_id}/memories`, recall `POST /v1/default/banks/{bank_id}/memories/recall`, reflect `POST /v1/default/banks/{bank_id}/reflect`. Client wrapper is a TS type `HindsightClient` with `createBank(bankId: string, opts?: {reflect_mission?: string, retain_mission?: string}): Promise<BankResult>` (uses `PUT /v1/default/banks/{bank_id}` — idempotent upsert, returns existing bank if already created, confirmed via OpenAPI spec `create_or_update_bank` operationId). Note: the OpenAPI `CreateBankRequest` body marks `name`, `disposition`, and `mission` as deprecated — use `reflect_mission` and `retain_mission` instead. The provisioning script passes `{reflect_mission, retain_mission}` (no deprecated fields). Other client methods: `retain(bankId, {document_id: string (REQUIRED for round-trip verification — caller-supplied, tracked for recall match), text, tags?})`, `recall(bankId, {query: string, budget?: Budget, max_tokens?: number, types?: string[], tags?: string[]})` where `Budget` is the string enum `"low"|"mid"|"high"` (defaults to `"mid"`), `max_tokens` defaults to 4096, `types` filters fact types (`["world","experience"]` by default), and `tags`/`tags_match` filter by tag visibility (see OpenAPI `RecallRequest`); `reflect(bankId, {query})`. **RetainResponse:** `{ success: boolean, bank_id: string, items_count: number }` — does NOT return `document_id`; the caller tracks its own supplied `document_id`. **RecallResponse:** `{ results: RecallResult[] }` where each `RecallResult` has `document_id` among its fields — the provisioning script matches `RecallResult.document_id` against the caller-supplied value. **ReflectResponse:** `{ text: string (required, non-empty), based_on?: object, structured_output?: object, usage?: object, trace?: object }` — `reflected===true` means `text` is a non-empty string. There is NO `mental_model` top-level key in the reflect response. Bank ids: `{repo}` (primary bank for code-context memories: retained facts, architectural decisions, debug learnings) and `{repo}-dev-meta` (companion meta-bank for manager-level meta-lessons, operational metrics, and cross-run operational insights — the `{repo}` bank feeds per-run prompts while `{repo}-dev-meta` feeds the management/supervisory layer). Idempotent retain keys on `document_id` (Hindsight replaces on match — NFR-REL-3 basis). **P0.9-H3 resolution — Bank creation endpoint (2026-06-06):** The provisioning script calls `createBank()` explicitly for BOTH banks (`{repo}` and `{repo}-dev-meta`) BEFORE the retain/recall/reflect round-trip, ensuring deterministic idempotency. The `PUT /v1/default/banks/{bank_id}` endpoint (operationId: `create_or_update_bank`) accepts a `CreateBankRequest` body where the current (non-deprecated) fields are `reflect_mission`, `retain_mission`, `retain_extraction_mode`, `retain_custom_instructions`, `retain_chunk_size`, `enable_observations`, and `observations_mission` — all optional (Hindsight auto-fills defaults). The older `name`, `disposition`, `disposition_*`, `mission`, and `background` fields still exist but are marked deprecated in the OpenAPI spec; the provisioning script avoids them. The endpoint returns a `BankProfileResponse` with `bank_id`, `name`, `disposition`, `mission`, etc. The call is idempotent: re-creating an existing bank returns its current profile without error. Auto-creation on first retain is a fallback safety net, but explicit creation via `PUT` is the primary path. The `HindsightClient.createBank()` method wraps this endpoint and is called at the start of the provisioning script for both banks, before any retain/recall/reflect operations.
  > **P0.9-B3 resolution — Cloud vs self-host API shape (2026-06-06):** CONFIRMED IDENTICAL. The Hindsight OpenAPI spec (v0.7.2, open source at `vectorize-io/hindsight`) defines all endpoints under `/v1/default/banks/{bank_id}/...` for both cloud (`api.hindsight.vectorize.io`) and self-host (default `localhost:8888`). The same server binary serves both; only `base_url` and auth mechanism differ (cloud requires Bearer token from `HINDSIGHT_CP_DATAPLANE_API_KEY`; self-host may run without auth in dev). Evidence: (1) OpenAPI spec in `hindsight-docs` skill `references/openapi.json` — single spec, no per-deployment path variants; (2) context7 `/vectorize-io/hindsight` documents auto-create bank on first retain — `client.retain(bank_id="my-bank", content="...")` works against either endpoint without prior `POST /v1/default/banks`; (3) explicit bank creation via `PUT /v1/default/banks/{bank_id}` or `POST /v1/default/banks` also available on both. **Bank creation mechanism:** Banks auto-create on first `retain` call (no explicit creation required). The provisioning script SHOULD explicitly create banks via `PUT /v1/default/banks/{bank_id}` for deterministic idempotency, but the round-trip will also work if banks are implicitly created on first retain. The `HindsightClient` wrapper uses `base_url` as the sole deployment-specific config — no path branching needed.
- **P0.9-B2 resolution — Mulch tool verification and fallback (2026-06-06):** Mulch is a REAL, published CLI tool. npm package `@os-eco/mulch-cli` by jayminwest (GitHub: `jayminwest/mulch`, part of `os-eco` ecosystem). Version 0.10.7 is the pinned release (latest at time of writing). The primary binary is `ml` (also aliased as `mulch`). Key commands: `ml learn` (no flags — suggests domains from changed files), `ml record <domain> --type <convention|pattern|failure|decision|reference|guide> "content"` (stores an insight), `ml prime [domain]` (outputs formatted context; domain is optional, filters to one domain if provided). Expertise data is stored as JSONL in `.mulch/expertise/<domain>.jsonl` (git-tracked, append-only). **Mulch record JSONL structure:** Each record in a `.mulch/expertise/<domain>.jsonl` file is a JSON object with fields: `id` (auto-generated, e.g. `"mx-3f8a2b"`), `type` (e.g. `"convention"`, `"pattern"`, `"failure"`, `"decision"`), `domain` (string), `content` or `description` (string — the expertise text), `resolution` (string, for failure types), `evidence` (object with optional `commit`, `issue` keys), `tags` (array of strings), `classification` (e.g. `"foundational"`, `"tactical"`), `recorded_at` (ISO datetime), `outcomes` (array of outcome objects). The provisioning script does NOT write JSONL directly — it uses `ml record` to create records, ensuring schema validation and file locking are handled by the CLI. **Installation:** `npm install -g @os-eco/mulch-cli` (or pin to 0.10.7 via `@os-eco/mulch-cli@0.10.7`). The binary installs to the global npm bin path as `ml`; the story references `/usr/local/bin/ml` (with `mulch` as an alias) which is standard for global npm installs on macOS. **Fallback when Mulch is absent:** Mulch is an enhancement, NOT a make-or-break gate (it does not appear in AC-1). The provisioning script MUST handle Mulch absence gracefully: if `ml` is not on PATH or `.mulch/expertise/*.jsonl` does not exist, the script sets `mulchImported: 0` in the emitted JSON, logs a single warning (not an error), and continues. The round-trip retain/recall/reflect succeeds regardless. Mulch import is only exercised in AC-3 ("Given Mulch expertise exists...") which is conditional on data existing. **Sample data for testing:** If `.mulch/expertise/` is absent at dev time, the test fixture creates records via `ml record test-domain --type convention "test fact for provisioning verification"` to exercise the import path; this is a test concern, not a production requirement.
  > **P0.9-H2 resolution — Mulch import mechanism (2026-06-06):** The provisioning script calls Mulch commands in this sequence for each domain found in `.mulch/expertise/`: (1) `ml learn` — no arguments; auto-detects changed files and suggests relevant domains. The script uses this to discover available domains, or alternatively reads domain names from `.mulch/expertise/*.jsonl` filenames (e.g. `typescript.jsonl` → domain `typescript`). (2) `ml record <domain> --type <type> "content"` — stores an insight into the named domain. Used to import seed expertise from existing JSONL files via `--batch` or `--stdin` mode: `ml record <domain> --batch <file>` reads a JSON array of records and atomically writes them with file locking. (3) `ml prime [domain]` — outputs formatted priming context; exit code 0 and non-empty stdout confirm the domain is populated. When called without a domain argument, `ml prime` outputs context from ALL domains. The provisioning script calls these steps for each domain: batch-import via `ml record <domain> --batch` (or per-record `ml record <domain> --type <type> "content"`) → validate via `ml prime <domain>`. The count of successfully primed domains is emitted as `mulchImported`. **Fallback:** If `.mulch/expertise/` is absent or contains no `.jsonl` files, the script skips ALL Mulch calls and sets `mulchImported: 0`. If any individual domain fails at the import or prime step, that domain is skipped with a logged warning; the script does NOT abort — remaining domains continue. **Mulch prime verification:** `ml prime <domain>` must return exit code 0 AND non-empty stdout containing the recorded content. Failed prime (non-zero exit or empty stdout) for a domain logs a warning and increments a `mulchPrimeFailures` counter but does NOT abort — the overall script succeeds as long as the retain/recall/reflect round-trip passes (Mulch is enhancement, not make-or-break).
- **Integration points (each wired & exercised in this story):** Hindsight client → chosen endpoint with `Authorization: Bearer <token>` (token from `HINDSIGHT_CP_DATAPLANE_API_KEY` / SDK `api_key`, NOT `HINDSIGHT_API_LLM_API_KEY`, NFR-SEC-5); bank-create (explicit `PUT /v1/default/banks/{bank_id}`) + retain + recall + reflect exercised in sequence; Mulch import via `ml record <domain> --type <type> "content"` (or `--batch`) to populate domains from `.mulch/expertise/<domain>.jsonl`, then `ml prime [domain]` to confirm (with graceful fallback to `mulchImported: 0` if Mulch or data absent — see P0.9-B2 resolution above); tooling pin assertions for `sd 0.5.9` + `ml` (Mulch 0.10.7).
- **Files / functions touched:** `scripts/memory/provision-banks.ts` (entrypoint + JSON emit), `src/memory/hindsight-client.ts` (`retain`/`recall`/`reflect`, Bearer header), `src/memory/oq4-decision.ts` (decision record writer).
- **Guards/limits:** recall uses `budget:"mid"`, `max_tokens<=4096`, must return within ≤2s p95 cloud / ≤1s p95 self-host (NFR-PERF-4); on recall timeout the *caller* proceeds unprimed with a logged warning — but for THIS provisioning round-trip a recall timeout fails the make-or-break (the proof requires a real recall). Self-host local stack is env-blocked → OQ-4 may resolve cloud; record the unblock command (arm64 OpenSSL at `/opt/homebrew/opt/openssl@3` OR external `HINDSIGHT_API_DATABASE_URL`).
- **Tooling pin exact package names:** Mulch: `@os-eco/mulch-cli` (v0.10.7, npm package by jayminwest, binary: `ml` at `/usr/local/bin/ml`, also aliased as `mulch` — both names point to the same installed binary; `ml` is the canonical short name used throughout this story). Seeds: `@os-eco/seeds-cli` (v0.5.9, binary: `/usr/local/bin/sd`). Both are public npm packages under the `@os-eco` org; the npm names above are canonical — verify during dev that the packages exist on the registry at the pinned versions.
- **Bank isolation enforcement:** Bank isolation is enforced at the CODE level via `HindsightClient`. The client wraps retain/recall/reflect calls with a runtime assertion that the `bankId` parameter matches one of the two provisioned bank ids (`{repo}` or `{repo}-dev-meta`). Any call targeting an unrecognized bank id throws before the HTTP request is sent. This is a client-side guard; Hindsight's server does not enforce cross-bank isolation (a single Bearer token has access to all banks under the account). The guard prevents accidental cross-writes in the provisioning script.

## Security Invariants

> Concrete named invariants — `N/A` is FORBIDDEN (secrets/env + tenant triggers apply).

- **INV-1 (secrets/env):** The Hindsight server-auth token is read from env/secret ref (`HINDSIGHT_CP_DATAPLANE_API_KEY` or SDK `api_key`), never hardcoded; it is NOT conflated with `HINDSIGHT_API_LLM_API_KEY` (the LLM-provider key — NFR-SEC-5). Env var precedence: `HINDSIGHT_CP_DATAPLANE_API_KEY` (primary), `HINDSIGHT_API_KEY` (legacy alias, logged as deprecation warning when used). The token value is never written to stdout, logs, the OQ-4 decision file, or any Hindsight memory document.
- **INV-2 (tenant — per-repo bank isolation):** Bank ids are tenant boundaries: code memories go ONLY to `{repo}` and manager meta-lessons ONLY to `{repo}-dev-meta`; the provisioning round-trip retains/recalls against the `{repo}` bank exclusively and never cross-writes into the `*-meta` bank (and vice-versa). No call targets a bank id derived from unsanitized external input.
- **INV-3 (secrets/env):** All memory calls send `Authorization: Bearer <token>` when the chosen endpoint is auth-protected (NFR-SEC-5); a 401/missing-token path exits non-zero (AC-4), never falls back to an unauthenticated call.
