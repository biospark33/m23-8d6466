# Blind Hunter — pr135 chunk-pipeline.diff (scripts/pipeline-run.ts, ~712 changed lines)

Adversarial review of the diff chunk only; no repo context consulted. Line numbers are diff-relative.

## Findings

### HIGH

1. **[HIGH] Second Ctrl-C after run settlement exits 2 and lies about a settled run** — diff lines 566–586. The `terminated` second-signal branch (`process.exit(2)`) carries the stale justification "no marker was written and the exit code must not claim the run settled". That is only true pre-`finish`. Trigger: `run.finish()` returns (marker on disk), the run-end solicitation or `residentSpawn.stop()` is in flight, operator hits Ctrl-C once (runSettled branch, returns), then again during the final stop/`writeResident` refresh — the second hit lands in the `terminated` branch and exits 2. A poller sees exit 2 = "never settled" for a run whose terminal marker exists. The `terminated` branch needs a `runSettled` guard (exit 0/1 per the result, or at least not 2).

2. **[HIGH] Timeout/terminate-written terminal marker precedes the resident-block seed — the exact race the seed claims to close** — diff lines 394–398, 808–812. The gated loop's own comment admits "the terminal marker may already be on disk (maxDurationMs overflow or run.terminate)". But `innerJournal.writeResident(residentTelemetryOf())` is only seeded at line 812, *after* `walkPhases` returns. Trigger: budget overflow writes the terminal marker at T1 mid-walk; the walk unwinds, the seed lands at T2. In the T1→T2 window (which includes any slow phase-body cancellation grace) a poller reading the marker finds a settled journal with **no resident block at all** — the invariant stated at line 808 ("a poller that reads it must never find a settled journal with no resident block") is violated on precisely the crash/timeout path it was written for. The seed must happen before `walkPhases`, not just before `finish`.

3. **[HIGH] No `finally`: any throw after `startResident` orphans the resident subprocess and skips both resident-block writes** — diff lines 674–684 vs 756–777, 812. `residentSpawn.stop()` and the seeded `writeResident` exist only on the happy path. Trigger: resident armed and spawned, then `walkPhases` throws (a phase body propagates a non-gate error — the gated loop explicitly rethrows anything that isn't a `GateFailureError`, and `runCommand`/dispatch bodies have other failure modes), or the pre-finish `writeResident` itself throws ("this write may still throw through", line 811). Control jumps to the module-level catch → `process.exit`, with the pi child never stopped (the signal handlers are bypassed on an exception path) and no resident block on disk. The spawn-to-stop region needs try/finally, not sequential cleanup.

### MEDIUM

4. **[MEDIUM] Retry composition may double-authorize attempts (body-level loop × engine retry)** — diff lines 384–399. The gated body implements its own `for (attempt…)` retry loop keyed on `spec.retries`, with a comment saying it "mirrors retry.ts:284-287 for code phases". If `walkPhases`/the engine also applies its retry discipline to a *failing phase body* (the normal reading of "DF1.3's retry discipline"), a code phase with `retries=N` now runs up to (N+1) inner attempts, and the whole body is then retried by the engine up to N more times — (N+1)² executions, double-counted attempts, and the resident solicited per inner failure. Assumption: engine retry covers code-phase bodies; the diff alone cannot rule it out, and the "mirrored … for code phases" phrasing suggests the author believed it does not. Verify against retry.ts/walkPhases before merge.

5. **[MEDIUM] Resident `abort` at post_gate_failure can be overridden by an engine-level retry** — diff lines 411–434. The abort path rethrows the caught `GateFailureError` to "settle the phase". If the engine retries failed phase bodies (same assumption as #4), the body is re-invoked from attempt 1 and the command runs again — the resident's abort declined one retry, the engine granted another. The abort directive is then recorded in the trace but ineffective. Same verification target as #4.

6. **[MEDIUM] First signal during the run-start solicitation does not stop the in-flight pi call** — diff lines 589–603, 742–754. The `runSettled` fast-kill branch exists only post-finish; the pre-finish first-signal path is `run.terminate(sig)` alone. Trigger: SIGINT arrives while `solicitResident(…, "run_start", …)` is awaiting a hung pi call. `run.terminate` aborts phase bodies that don't exist yet; nothing stops the resident child, so the process waits out the pi timeout despite the kill request — the exact pathology the `runSettled` branch was added to fix, one hook earlier. Assumption: steering's caller is not wired to the run's AbortSignal (the diff gives no evidence it is).

7. **[MEDIUM] "Accepted retry guidance … for the engine-authorized attempt that consumes it" — nothing consumes it** — diff lines 218–219, 437–439. A `retry` directive's guidance is pushed into `resident.promptContext`, which is only ever read by *subsequent solicitations* (it's prompt text for the resident, not input to the retried command). The retried attempt re-runs the identical command with identical env; the guidance has no mechanical effect on it, so a deterministic gate failure retried under a `retry` directive fails identically. Either the doc comment overclaims (doc bug) or a wiring step that injects guidance into the attempt is missing (functional bug).

8. **[MEDIUM] `closedRosterIds()` collects `role.name` values but the directive surface is a `rosterId` — possible identity mismatch** — diff lines 238–256, 243. The closed set is built from `loadRoster(...).roles[*].name`, keyed per dispatch_task phase's `spec.roster` file. The solicitation validates `directive.rosterId` against this set. If a "roster id" in DF1.5/DF3.5 terms denotes the roster (file/slug) rather than an individual role's name within it, every legitimate `select_roster` is rejected as a gate-bypass attempt and the feature is dead on arrival; conversely if roles are the intended unit, naming a pick "rosterId" invites producers to send the wrong key. Assumption: cannot see steering.ts/roster schema from this chunk. Also unverifiable here: case/normalization — ids are inserted verbatim (`ids.add(role.name)`), so any case-folding the agent side does not match.

9. **[MEDIUM] `--no-resident` leg does not reproduce the pre-diff flow for code phases with `testCommand`** — diff lines 368–380 vs the removed line 368 (`return ({ signal }) => runCommand(...)`). Before this chunk, a code phase's body was always the bare `runCommand`. Now, whenever `journal` is passed (and main always passes it, line 766) and `spec.testCommand` is non-empty, the body is wrapped in `commandGate` + a retry loop **regardless of the resident flag** — the flag only skips solicitation. AC1a equivalence between the two new legs holds, but the `--no-resident` leg is *not* the old deterministic flow: gates that never ran before now run, and failures that used to settle on first exit now retry. Any existing manifest whose code phases declare a `testCommand` changes behavior on upgrade. Assumption: `gatedBody` was not already applied to code phases elsewhere pre-diff (the "closes the R2 gap" comment says it was not).

10. **[MEDIUM] `select_roster` directives from post_gate_failure / run_end are silently dropped after being counted as accepted** — diff lines 403–464. The gated-loop directive switch handles only `abort` and `retry`; the run-end call (lines 823–831) discards the directive entirely. But the solicitation ctx at those points still carries `rosterIds`, and `solicitResident`'s observability line computes `accepted` from the telemetry counter — a `select_roster` returned at post_gate_failure would increment `directives`, log `accepted: true`, and vanish (never written to `rosterChoice.pending`). If the port's schema can emit `select_roster` at points other than run_start, this is a silent drop wearing an accepted receipt; if it cannot, passing `rosterIds` at those points is dead surface inviting exactly this.

11. **[MEDIUM] `residentSpawn.exitStatus()` awaited before `stop()` with no visible timeout, post-settlement** — diff lines 838–843. If `exitStatus()` waits on process exit and the resident's pi call is wedged, this await blocks the settled run's cleanup indefinitely; only a signal (via the runSettled branch) unwinds it, and a second signal then trips finding #1. Assumption: `exitStatus()`'s semantics are not visible in the chunk; if it is a non-blocking probe, downgrade to LOW.

### LOW

12. **[LOW] `rosterChoice.pending` set after the last dispatch_task phase is never consumed or recorded** — diff lines 474–494. A `select_roster` accepted at run_start when the manifest has no dispatch_task phases, or a pick that survives past the final dispatch_task phase, sits in `pending` until process exit — no trace row, no rejection, no warning. The pick is counted accepted in telemetry yet had no effect and left no record.

13. **[LOW] Trace `phaseId` keyspace is inconsistent between directive rows and roster-choice rows** — diff lines 422 vs 488. Code-phase directive traces use `phaseId: bodyCtx.phaseId` (engine id); the dispatch_task roster-choice trace uses `phaseId: spec.name` (manifest name). Consumers joining trace rows on `phaseId` get two different identifier domains under one field name.

14. **[LOW] run_start `abort` settles via `run.finish(!terminated)` with zero outcomes — exit code depends on `Run.finish` empty-run semantics** — diff lines 749–757, 814. The comment asserts "finish settles the empty run not-ok" (exit 1). If `Run.finish(true)` with an empty outcomes list computes an *ok* verdict (vacuous success is a common default), a resident-aborted run exits 0 and the marker claims success for a run that executed nothing. Unverifiable from this chunk; one-line check of `Run.finish`.

15. **[LOW] `void onSignal(sig)` — an async signal handler whose rejection is unobservable** — diff lines 566, 607–608. The `stop()` calls are individually guarded, but `run.terminate(sig)` is not; if it throws, the `void`-ed promise rejects unhandled (process-level `unhandledRejection` behavior) from inside a signal handler.

16. **[LOW] run_end directive is solicited, counted in telemetry, then discarded — no trace row records it** — diff lines 823–831. Unlike the post_gate_failure path (which traces abort/retry via `resident_directive` rows), the run_end directive leaves only the stderr `resident_solicit` line. The journal's refreshed resident block shows an incremented directive count with no corresponding event row anywhere in the trace store.

17. **[LOW] Boolean-flag grammar split (`tokenizeArgs` + `parseValueFlags`) changes pre-existing argv error behavior for the whole CLI** — diff lines 514–524. All value flags now flow through `tokenizeArgs` first; any divergence between the two grammars (e.g., `--flag=value` forms, unknown-flag handling, a value that literally equals `--no-resident`) now takes the tokenizer's code path, not `parseValueFlags`'s. `--no-resident` polarity itself is correct (`!noResident` gates arming, lines 627–630). Behavior-change risk to existing invocations is speculative; flagged for the lib/cli-args.ts spec, not from evidence of a bug.

18. **[LOW] EAGAIN on a full pipe is silently retried-zero-times and the line tail dropped** — diff lines 97–107. `writeAll` loops on short writes but swallows all errors including EAGAIN; on a non-blocking full stderr pipe the *entire* remainder of an observability line is dropped with no counter or marker, so `resident_solicit` / `resident_disabled` lines can vanish exactly under the backpressure conditions where observability matters. Documented as deliberate ("sidecar"), but a dropped-line counter would cost one integer.
