## Findings

### 1. MED | Stale-claim unlink: the `process.on("exit")` hook re-runs the unconditional claim `rmSync` after the `finally`'s release, across `await` points — deleting a SUCCESSOR engine's claim | scripts/pipeline-run.ts:2594-2602, 3504, 3542-3551

Evidence:

```ts
// 2594-2602
const releaseEngineClaim = (): void => {
  try {
    fs.rmSync(claim.claimPath, { force: true });
  } catch { /* best-effort ... */ }
};
process.on("exit", releaseEngineClaim);
```

```ts
// 3504 (top of main's finally) — then AWAITED sidecars follow:
releaseEngineClaim();
if (residentSpawn !== undefined) {
  try { await residentSpawn.stop(); } catch { }        // 3514 — event-loop yield
  ...
  try { residentBlock.exitStatus = await residentSpawn.exitStatus(); } catch { }  // 3522
}
try { innerJournal.writeResident(residentBlock); } catch { }  // 3532
```

```ts
// 3542-3551 (bootstrap)
if (import.meta.main) {
  let code = 2;
  try { code = await main(Bun.argv.slice(2)); }
  catch (err) { writeAll(2, `pipeline-run: ...`); }
  process.exit(code);   // fires the `exit` hook → releaseEngineClaim AGAIN
}
```

Why real (traced): `releaseEngineClaim` has no ownership revalidation — the second call
removes whatever file is at `<markerRoot>/journal/engine.claim`, whenever it runs. The
`finally` releases the claim at its top (3504) and then performs `await`ed sidecars
(resident stop = SIGKILL + await process exit, exitStatus probe, final writeResident —
a real wall-clock window), after which the bootstrap's `process.exit` (3551) fires the
still-registered `exit` hook for a second, unconditional `rmSync`. Interleaving on a
shared marker root (the current pinned image's shared `RuntimeDirectory`, per this same
diff's F-D1 comment — the per-instance isolation "rides the re-pin (#217)"):

1. Engine A acquires the claim; a throw unwinds the walk **without a marker** (the
   realistic arms: `JournalWriteError` from any `writePhase`/`promotePhase`/`finish`
   flush — journal.ts:261 — or `writeTerminalMarker`'s rethrow after ENOSPC,
   phase.ts:476-487).
2. A's `finally` releases the claim (3504), then yields at `await residentSpawn.stop()`.
3. Engine B (a different run on the same root) starts: marker absent →
   `journalReclaimRefusal` on B's OWN journal → ENOENT → `null` → proceed →
   `acquireEngineClaim` O_EXCL create **succeeds** (A's claim was just removed) — B
   holds the claim and walks.
4. A resumes, `main` rejects, the module catch writes one line, `process.exit(2)` fires
   the `exit` hook → `fs.rmSync(claimPath, { force: true })` **deletes B's claim**.
5. The root is now silently unclaimed while B walks: any engine C acquires and walks
   CONCURRENTLY with B — the exact F-D1 concurrent double-spend the claim exists to
   close, with B unaware its guard is gone. (Even without C, B's marker-write race
   window is re-armed.)

The normal SETTLED path is not exploitable (after `run.finish` the marker exists, and
any successor is refused `ENGINE_MARKER_FOREIGN`/mirrored at the replay guard before
ever reaching `acquireEngineClaim`), so the exposure is precisely the no-marker exit
paths — throws out of the walk/settle, and the second-signal `process.exit` that can
land during the finally's awaits (2886-2911, where the finally has already released but
the exit hook fires once more). The code's own contract states "it is removed on every
exit path" and "only an unhandled kill escapes both" — an exit hook that deletes
another engine's claim breaks the second claim exactly as surely as no claim at all.

Minimal fix: make the release ownership-checked. Capture the exact claim bytes written
at acquire (`{ runId, pid: process.pid, startedAt }`, 1823-1826) and only unlink when
the file still carries THIS engine's claim:

```ts
const claimBody = `${JSON.stringify({ runId: ids.runId, pid: process.pid, startedAt: new Date().toISOString() })}\n`;
const releaseEngineClaim = (): void => {
  try {
    if (fs.readFileSync(claim.claimPath, "utf8") === claimBody) {
      fs.rmSync(claim.claimPath, { force: true });
    }
  } catch { /* absent or no longer ours: nothing to remove */ }
};
```

(An inode compare against a retained acquire-time fd is stronger still; the
content/`startedAt` compare is the smallest diff. `process.removeListener("exit",
releaseEngineClaim)` after the finally's release also closes the observed interleaving,
but the ownership check covers every variant, including signal-exit orderings.)

## Verified clean

- `journalReclaimRefusal` uses `statSync` (follows symlinks) where the marker uses
  `lstatSync`: traced both arms — symlink-to-file → `readMarkerBytes`' `O_NOFOLLOW`
  → ELOOP → `ENGINE_JOURNAL_UNREADABLE` (fail-closed); dangling symlink → ENOENT →
  proceed → `FileJournal.flush` writes temp+`renameSync` (journal.ts:243-252), and
  rename REPLACES the symlink rather than following it — no redirection, no hang.
- Journal path being a FIFO: `readMarkerBytes` opens `O_NONBLOCK` (no park); reads
  empty/EAGAIN → treated as the empty-journal proceed; `FileJournal` then replaces the
  FIFO via rename. A FIFO carries no durable evidence, so nothing is lost.
- `--journal` aliasing the marker/claim path is NOT in the new alias guard — traced the
  guard's comment: it claims only "engine-log vs {journal, marker, claim}"; the
  journal-vs-marker aliasing hazard is pre-existing and reachable only via a hand-built
  argv; the guard implements exactly what its comment says.
- Unreadable claim beside orphaned rows skips the liveness probe and prints the
  harvest/teardown remediation — annotated deliberate in the catch ("no claim (or an
  unreadable one): the rows-alone diagnosis below stands"); reaching it requires the
  0600, fsynced, same-user claim file to fail its own bounded read.
- pid reuse in the claim-liveness probe (`kill -0`, EPERM = alive) — annotated
  deliberate at length, remediation names the pid-reuse caveat.
- `requestIdIsIdentity` gating on both the marker and journal identity checks — traced
  consistent, and the both-`--run-id`-and-`--request-id` mirror-theft scenario is
  documented and refused (ENGINE_MARKER_FOREIGN).
- Front-door `replayRefusalExit` passing `{runId}` alone vs inner main's
  `{runId, requestId, requestIdIsIdentity: !runIdGiven}`: derived argv always carries
  `--run-id` → gate false at both doors — same identity decision at both; double-run of
  the guard is idempotent (second run only when the first returned null).
- Mirror exit codes: every refusal arm traced — mirror 0/1 only where the marker is
  this run's and carries a boolean `ok`; all other arms 2. Matches the "no fourth
  code" contract; `engine_refused_claim` always 2/error.
- `emitEngineEvent` key ordering: `...extra` spread first, identity keys (`level`,
  `event`, `runId`, `requestId`, `phaseId`) after — a stray `extra` key cannot shadow
  identity or level. Level follows exit code / verdict exactly as documented.
- `writeAll`'s engine-log tee loop bound `spins <= bytes.length`: every iteration
  advances ≥1 byte (0-progress breaks), so a 1-byte-at-a-time sink completes exactly —
  no half-JSON truncation; deliberately no dropped-bytes counter for the copy.
- `openEngineLog` open-new-before-close-old ordering: a failed second open keeps the
  working old descriptor and tees the warning into it; `O_APPEND` overlap harmless.
- `ObservedJournal` discipline: phase.ts verified to write each phase twice
  (open row at phase.ts:247, settled row at 422) and settle BOTH branches through
  `promotePhase` (423-427) — `phase_started` fires once (names-map guard),
  `phase_settled` fires for fail and success; delegation precedes every emit.

  `unreachableKind: never` exhaustiveness check is real and compiler-enforced; the

- `IN_BOX_RUN_ID_RE` blocks `..`, separators, NUL, leading dot (first char must be
  alnum); byte-identical to `RESIDENT_RUN_ID_RE` (resident.ts:45) — the `--run-id`
  validation cannot die later in `startResident`.
- Marker-size hazard through `--request-id`: correlated runs settle under a strict
