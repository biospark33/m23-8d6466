## Findings

1. MED | `artifactsLost` omitted on open-row arms; the in-code justification ("closed-carrying rows") is factually wrong about the write order | src/fleet/status.ts:967-988 (helper), :1066 and :1082 (spread sites), :1094/:1096/:1103 (arms missing it) | `artifactsLostFields`' docblock claims the extension only ever sits on closed-carrying records: "Spread onto exactly the two arms whose records can carry one (both are closed-carrying rows — teardown's failure arm writes the extension on its way past `close`)." Traced to the writer: the extension is stamped in the artifacts step — src/providers/teardown.ts:300-310 `deps.store.set(ctx.runId, { extensions: { teardown: { schemaVersion: 1, artifactsCode: code, ... } } })` — which is step 2 of 6; `closedAt` is only set by the `close` step at teardown.ts:749 (`await runStep(ctx, "close", ...)`), and `runArtifactsStep`'s catch deliberately does NOT rethrow, so teardown proceeds past the loss write. If any later step (revoke/verify/destroy) then throws — teardown's documented fail-closed posture: "a throw aborts the whole sequence, box left alive, record left open" (teardown.ts:331) — the record is left OPEN, indefinitely, with `extensions.teardown.artifactsCode` set and no `closedAt`. `rowForRecord` then renders it under the `boxUnknown` (status.ts:1094), `boxMissing` (:1096), or `live` (:1103) arm — none of which spreads `...artifactsLostFields(rec)` (only the approval arm :1066 and the closed arm :1082 do). The same window exists on the happy path for any `fleet status` run between steps 2 and 6. Why real: the #221 field's stated whole point (status.ts:205-207) is that "an absent field is how a consumer tells 'torn down clean' from 'torn down, evidence lost'" — on an aborted teardown (box still alive, record open, evidence already lost) the row reads as clean, exactly the state where the operator most needs the signal; and the comment that justifies limiting the spread is wrong about the mechanism, so the omission is unguarded by any test or annotation that knows it exists. | Minimal fix: spread `...artifactsLostFields(rec)` onto the three open-row returns in `rowForRecord` (status.ts:1094, :1096, :1103) — or move the spread into `base` and drop the two per-arm spreads — and correct the docblock's "on its way past `close`" claim to "during the artifacts step, step 2 of 6".

## Verified clean

- `rowSlotPump` handoff accounting: traced double-release-while-waiting (active stays consistent at 7 after two releases + one resumed waiter), interleaved acquire between release and waiter resumption (queues, no overcommit past 8), and release-in-`finally` (no slot leak on rejection); all acquires issue synchronously in the single `built.map` batch before any release, matching the in-code claim.
- `inBoxState` deadline math: `until` taken before the read, probe budget `Math.max(1, until - Date.now())` mirrors `readBoxFile`'s own floor (transport.ts:178); `readMarkerVerdict` never rejects (its catch maps any throw to `skip`, fanout-primitive.ts:930-932).
- Verdict mapping is total: `MarkerVerdict`'s 4 kinds and `UnitActivity`'s 4 values each have exactly one arm; nothing upgrades a doubtful read to `ok` (wrong-run marker → `unusable` → `unknown` via `classifyMarkerRead`'s `expectedRunId`).
- `markerReader` binds both methods and requires `exec` AND `execTimed`, so `unitActivity`'s `typeof driver.execTimed !== "function"` fallback to the 120 s `exec` (run.ts:453-455) is unreachable on the marker path; `MarkerReadDriver` (transport.ts:140-155) is structurally identical to `StartRunDriver`, and `log`'s `LogEntry` index signature accepts `marker_read_ms`.
- `statusAll` fallback path: `settled.map` is index-aligned with `records`/`built`; the fallback reuses the pre-built row (no second `rowForRecord` run), pins its sort instant, logs `row-read-failed` with a sanitized diagnostic inside try/catch; `withInBoxState` returning a NEW object for live rows means the pin lands on the row the comparator actually sees.
- Non-live rows and reader-less live rows skip the pump entirely (no queueing behind live rows' marker deadlines); output order preserved by `allSettled` index mapping.
- `statusRun` shares `rowForRecord` + `withInBoxState`, so the two entry points cannot disagree; `assertFleetRunId` at entry makes `runUnitName`'s grammar throw unreachable there, and in `statusAll` a grammar-bad runId from an injected store lands in the per-row rejection fallback rather than killing the sweep.
