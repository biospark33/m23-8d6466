## Findings

1. LOW | `fleet.run` event line logs `runId: "(none)"` (sentinel string) instead of `null` when the positional is absent | scripts/fleet.ts:2786 | `logStart` builds `runId: bounded(runIdArg)`, and `bounded`/`boundedEcho(undefined)` returns the literal `"(none)"` (`src/providers/step-log.ts:299-300`: `if (s === undefined) return "(none)"`). Reachable: `fleet run` with no `<run-id>` passes `runIdArg === undefined` into the catch, which calls `logStart("error", { outcome: "refused", exitCode: 2 })`. | Why real (traced): every sibling emitter of this same log schema in this file maps an ABSENT run id to `null`, never to a sentinel string — `logVerb` (fleet.ts:1304 `runId: runId === undefined ? null : bounded(runId)`) and `gateEvent` (fleet.ts:3111, identical form). A `fleet.run` sweep that filters `runId == null` (or parses run ids out of the field) sees a phantom run named `(none)` — and worse, an operator who actually typed the 6 chars `(none)` as a positional would be indistinguishable. The `bounded` call was annotated for rawness, not for the undefined shape, so this is not the deliberate part. | Minimal fix: `runId: runIdArg === undefined ? null : bounded(runIdArg)` in `logStart`.

2. LOW | `dispatchRequestId` is logged RAW (unsanitized, unbounded) into the `fleet.run` structured line — the one record-derived join key every other emitter sanitizes | scripts/fleet.ts:2788, 2834 | `dispatchRequestId = res.requestId` (line 2834) is `rec.requestId` straight off the run record (`src/fleet/run.ts:580` `const requestId = rec.requestId === undefined ? {} : { requestId: rec.requestId }`), and `logStart` spreads it verbatim: `...(dispatchRequestId === undefined ? {} : { dispatchRequestId })` (line 2788). The store's read validation types it as a bare `"string"` with NO length cap (`src/providers/run-record.ts:98` `requestId: "string"` in `CORE_FIELDS`; `assertKind` fleet-side checks `typeof value !== "string"` only, run-record.ts:744-747), so a hand-edited or torn record can put an arbitrarily long string there. | Why real (traced): every other consumer of this exact field treats it as record-supplied foreign text and bounds it — `gateEvent` (fleet.ts:3119 `sanitizeLabel(gateDispatchRequestId, 128)`), the attach completion line (fleet.ts:4012 `dispatchRequestId: sanitizeLabel(res.requestId, 128)`), status rows (`src/fleet/status.ts:1004` `requestId: sanitizeOptional(rec.requestId, MAX_REQUEST_ID)`), and approval-gate (`src/fleet/approval-gate.ts:1209` `boundedEcho(ctx.dispatchRequestId)`). `runRun`'s own `logStart` docblock sells the field as the DF1.10/INV-4-bis join key — the exact reason those four call sites cap it. `runRun` is the sole outlier, on a verb whose header claims parity with attach. | Minimal fix: `...(dispatchRequestId === undefined ? {} : { dispatchRequestId: sanitizeLabel(dispatchRequestId, 128) })`.

3. LOW | The nested `startRun` re-read's stated contract ("a retry honestly might work, and 1 is the right verdict") is false for errno-coded errors: `report` stamps them exit 2 "never retry" | scripts/fleet.ts:2827-2833 | The catch around `startRun` re-reads via `assertRunExists` and, if the record is back, rethrows the ORIGINAL error on the theory that "a retry honestly might work, and 1 is the right verdict for it". But the original error from `startRun`'s `deps.store.get(runId)` is the raw fs error with the errno PRESERVED (`src/providers/run-record.ts:2479-2484`: `err.code = code` re-attached), and `report`'s untyped branch maps any `PERMANENT_ERRNOS` code — ENOENT, EACCES, ENOTDIR, EISDIR, EROFS, … (fleet.ts:556) — to exit 2 with "this failure is identical on every retry" (fleet.ts:640-655). So on the exact sub-path the comment describes (record vanished for read #2, back again for read #3), the invocation exits 2, not 1. | Why real (traced): read #1 (`assertRunExists`, fleet.ts:2814) and read #3 both went through `getRecord`'s classifier, but the rethrown read #2 error bypasses it by design — and `report`'s errno table was built for errors "no layer classified", which is false here: the re-read DID classify the condition as cleared. Exit 2 tells automation the invocation is permanently wrong when this process has just observed the opposite. LOW because it needs a three-read race on one record file (a rewrite via the store's link/rename dance is the plausible producer) and nothing was mutated either way. | Minimal fix: in the nested catch, when the re-read SUCCEEDS, strip the errno classification before rethrowing (e.g. rethrow `new Error(e.message)` without the `.code`, or wrap in a FleetError(1, …)), so `report` gives the documented transient verdict.
