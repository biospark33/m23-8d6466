# Blind Hunter — Z1 Round 2

Target: `_bmad-output/workflow-state/code-review/z1-r2/z1-r2.diff` (branch delta post round-1 fixes). Diff-file-only review.

- **Post-pin manifest row `rev` is never validated — the alarm and the authorship test enforce two different truths** — HIGH — Validator: `if (!postPin && typeof row.rev !== "string")` requires `rev` only for pre-pin rows, and `const expected = postPin ? pin : (row.rev as string)` makes `row.rev` dead data for post-pin rows. A post-pin row carrying a garbage/wrong `rev` passes `validateEvidenceForkRevs` green. Meanwhile the authorship test separately asserts `expect(newest.rev).toBe(PIN)` over the real manifest. So the module docblock's claim "the alarm's only product is truth" is false at the row level: the alarm certifies stamps only, and row-rev truth lives in a different test entirely. A bump-PR author who fat-fingers a post-pin row's rev gets green from the alarm and a confusing failure from an unrelated "authorship invariants" describe — if they run it at all.
- **The committed manifest references 5 evidence files that are currently untracked — merge as-is = red CI** — HIGH — The manifest's last 5 rows name `2026-09-30T15-19-10-429Z-…` through `2026-09-30T15-20-38-997Z-…`; in the branch state those files are untracked (`??`) while only `fork-rev-manifest.json` is staged (`A`). The new CI test `runAlarm(REAL_EVIDENCE_DIR, REAL_MANIFEST_PATH)` expects `{ ok: true }`; on a fresh checkout missing those 5 files, all 5 rows become ghost rows ("manifest row … has no evidence file (F-009)") and the "real corpus validates green" test fails everywhere except the author's laptop. The alarm's green gate silently depends on evidence JSONs traveling in the same PR as the manifest.
- **Writer's stamp-ownership guard is top-level-only while the alarm's finder is fully recursive — a nested caller stamp poisons the alarm** — MED — Harness: `if ("swarmclawForkRev" in payload)` checks one depth; validator: `findStampedRevs` recurses every object and array. A caller embedding `{ meta: { swarmclawForkRev: "…" } }` passes `writeEvidence`'s "the writer owns the stamp" guard, lands on disk, and the alarm then treats it as a stamp needing a bracket — producing a spurious "unmapped evidence file" or a false drift failure. The guard's depth and the alarm's read depth disagree; the comment's ownership claim holds only at depth 0.
- **Status-vocabulary "closure" is one-directional containment — ~13 of 16 words can never fail here** — MED — The only check is `expect(STATUS_VOCABULARY).toContain(rowOut.state)` inside probes that emit at most: empty fleet (nothing), outage (`listUnavailable`), one open record (one state). Words like `orphan`, `boxUnknown`, `timed-out`, `pausing`, `engine-failed`, `recordsSkipped` are never emitted by any probe, so renaming or removing them cannot fail this suite — yet the docblock claims "a new word, or a renamed one, fails here by name." The vocabulary list is also never asserted equal to anything from `status.ts`; dead entries rot silently and the "closed enumeration" pin is aspirational, not enforced.
- **Asymmetric automation: the stamp is written automatically, the manifest row is hand-curated — routine red is the designed steady state** — MED — Post-merge, every `writeEvidence` call stamps and creates a file that the alarm demands a manifest row for ("unmapped evidence file … add its rev from round provenance"). Every live E2E round therefore reds the suite (including the real-corpus green test, which reads the working tree) until someone hand-writes rows. The alarm converts "you ran an experiment" into "your test suite is red" — a fatigue pattern that trains developers to ignore exactly the failures the alarm exists to surface.
- **INV-Z1-2 test name over-claims what registry membership can prove** — MED — Test name: "the allowed verb set is exactly status and result … every other verb outside this contract (INV-Z1-2)". The body asserts only `verbs.filter(v => OBSERVE_VERBS.includes(v.verb))` maps to `["result","status"]` — i.e., both verbs exist in the 16-verb registry. Nothing in this test constrains what the fork may call; the actual closure lives in fork-side prose ("Z2's consumer harness"), which this diff cannot enforce. The test grants false confidence that provisioning/approval exclusion is "proven" here.
- **`Date.parse` rollover: a non-instant pinnedAt/citing passes the "real instant" gate** — MED — The F-003 guard is `ISO_Z.test(pinnedAt) || Number.isNaN(Date.parse(pinnedAt))`. `"2026-02-30T00:00:00Z"` matches the shape and `Date.parse` rolls it to March 2 — not NaN — so an impossible calendar date is accepted as the post-pin boundary, shifting every bracket by days. Same hole for `citing.timestamp` (the F-004 check), letting a rollover timestamp flip pre/post classification. The comment "not a real ISO-Z instant" claims more than the check delivers; the alarm whose "only product is truth" accepts fictional dates.
- **q1 observe tests are pairwise identical invocations mutating a shared `store`** — MED — Tests 1 and 2 both call `assertObserveSurface(run, outLines, errLines, observeDeps(), { verb: "result" })` and tests 3 and 4 both call it with `{ verb: "status" }` — byte-identical bodies under different names. Each result call runs `deps.store.create("qds-20260928-obsv01")` against the same `store` binding captured by `observeDeps()`; each status call runs the empty-fleet probe (`expect(empty.lines).toHaveLength(0)`) then `store.create("…obsv02")`. Either the store is reset by a per-test hook invisible to this diff (then the duplicates are pure redundant runtime and the distinct test names are misleading — "missing-record answer is exit 4" names one slice of a monolith), or the second create / leftover open record collides. Four test names promise four targeted assertions; the code runs the same monolith twice, twice.
- **The writer launders staleness while its comment indicts caller laundering** — MED — Harness comment: "a caller-supplied stamp would launder a recorded rev." But the writer stamps `SWARMCLAW_FORK_REV` — the exported pin — regardless of which fork rev the round actually ran against. If the fork advanced with no evidence round (explicitly undetectable per INV-Z1-1), a post-pin round against the newer fork is stamped with the stale pin, and the alarm then enforces stamp==pin: green "truth" about the wrong fork. The design concedes this in the module docblock, but the harness comment's framing pretends the laundering concern was solved rather than relocated to the one writer nobody audits.
- **Rows for existing-but-unstamped files are never bracket-validated; their timestamps feed the "newest row" computation** — LOW — A manifest row whose file exists but carries no stamp hits `if (stamps.length === 0) continue;` before any timestamp check, so its `citing.timestamp` can be arbitrary garbage forever — while the authorship test's `newest = rows.reduce(...)` string-compares exactly those unvalidated timestamps to pick "the pin is exactly the newest round's rev." Corrupted metadata in an unstamped row silently decides which row is "newest" for AC4's equality target.
- **F-012 lint proves string presence, not behavior** — LOW — The AC7 guard reads the harness source and checks `body.includes("swarmclawForkRev: SWARMCLAW_FORK_REV")` up to the next `export`. A future refactor that deletes the real stamp but leaves the string in a comment (or an error message edited to include it) satisfies the lint. The "enforcing link" is a text match on one file, not a behavioral check that evidence files actually carry the stamp.
- **`writeEvidence`'s new non-object throw is a runtime contract change with zero coverage in this diff** — LOW — Existing call sites that pass arrays (a natural evidence shape) now throw at runtime during live rounds; the only new test touching `writeEvidence` is the source-lint, which checks stamping, not the payload guard. The strictness is reasonable; shipping it untested means first contact is a live E2E failure, not CI.
- **Null-payload error misreports the type** — LOW — `` `got ${Array.isArray(payload) ? "Array" : typeof payload}` `` renders `typeof null` → "got object" for the null rejection. A debugging message whose first job is to name the offending value names it wrong.
