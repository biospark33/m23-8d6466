# Blind review — src/fleet/approval-gate.ts (new file, PR150 chunk)

- **[HIGH]** Acquire-side lock reclaim reintroduces the exact rename-vacancy race the release path was rewritten to eliminate — `chunk-src-gate.diff:248-277`
  - Trigger: a stale lock from a provably-dead holder (content `R`), while waiter A is mid-reclaim and waiter B completes a reclaim first and enters `body()` with a fresh lock (content `B1`, inode `iB`). A's `renameSync(lockPath, claimPath)` at line 250 then moves **B's live lock** off-path. A reads `B1 !== R` and enters the restore branch (lines 263-277). Between the rename and the `writeFileSync(lockPath, content, { flag: "wx" })` restore at line 268, `lockPath` is **vacant**: any waiter C polling with `openSync(lockPath, "wx", ...)` (line 190) creates a lock legitimately and enters `body()` **concurrently with B**. Mutual exclusion — the property the `withApprovalLock` header (lines 90-101) states as the entire point of D11 — is violated.
  - Secondary damage in the same branch: the restore creates a **new inode** with B's content. B's fenced release (line 363) compares `statSync(lockPath).ino === ownIno`, sees a different inode, and silently leaves the restored file on disk — a lock naming B's live pid that no waiter will reclaim until B's pid dies (or is proven dead), i.e. a wedge lasting the lifetime of a long-lived fleet process, curable only by `fleet unlock --force`.
  - Evidence: the module's own release-path comment (lines 307-317) describes this defect verbatim — "Between the rename and the restore there is no file at `lockPath`, so a third waiter creates one legitimately... The rename was the bug" — but the acquire-side reclaim still does rename-away-then-restore. No atomic undo of a rename exists, so the mismatch branch has no correct recovery as written.
  - Severity: HIGH (narrow timing window, but it breaks the lock's core guarantee and leaves a wedge behind)

- **[MEDIUM]** A `pausing` record bound to a reportId that never returns strands the run permanently — the resume arm only un-strands same-report crashes — `chunk-src-gate.diff:859-875`
  - Trigger: `requestApproval` writes `pausing` for report R1, then crashes during teardown (the designed recoverable state). The pipeline later comes back with a **different** report R2 (new commits, new harvest, regenerated report id — the normal reason a reverify re-runs). Every subsequent `requestApproval(R2)` hits lines 869-871: `String(existing?.reportId ?? "") !== reportId` → `{ outcome: "pause-in-progress" }`, record byte-identical, forever.
  - Evidence: the header (lines 20-23) and the arm's own comment (lines 862-865) celebrate that "without that arm one crashed teardown stranded the run for good" — but the arm is keyed on reportId equality. Nothing else exits `pausing`: `expiredState` deliberately never expires it (lines 599-601), `submitDecision` returns `not-decidable` (line 1108), `sweepExpired` skips it (lines 1188-1190), and no operator verb in this module clears an extension (only the lock, via `reclaimApprovalLock`). A crashed teardown followed by any new report is exactly the stranded-forever scenario the module claims to have eliminated, with hand-editing the record still the only exit.
  - Severity: MEDIUM

- **[LOW]** The `pausing`→promote resume path skips `assertBundlePresent`, contradicting the function's own "checked on both write paths" invariant — `chunk-src-gate.diff:871-875, 882, 931, 1008-1034`
  - Trigger: a run in `pausing` whose bundle file `<bundleDir>/<runId>.bundle` is deleted during the crash/recovery window (operator cleanup, retention sweep). A resume with the matching reportId returns `{ outcome: "requested", promote: true }` (line 874) and the promote re-lock (lines 1020-1034) only checks `state === "pausing"` — the gate promotes to decidable `awaiting-approval` bound to a report whose bundle no longer exists.
  - Evidence: `assertBundlePresent` (lines 674-680) exists because "a report naming a run whose bundle is gone is bound to nothing... and nothing later re-checks"; it is called on the rebind path (line 882) and the fresh-pause path (line 931) but not on the resume path, which is a third route to the same decidable state.
  - Severity: LOW (requires external bundle deletion; failure surfaces later at push time, not as a wrong decision)

- **[LOW]** `reclaimApprovalLock` reports `outcome: "absent"` when a successor replaced the lock under it — misreporting a still-wedged run to operators/scripts — `chunk-src-gate.diff:469-481`
  - Trigger: operator runs `fleet unlock <run-id>`; between the inspection (lines 444-445) and the fenced removal (line 470-472), the original holder exits and a legitimate successor acquires `lockPath`. The inode/content conjunction fails, the function falls through to `return { outcome: "absent", path }` (line 481).
  - Evidence: the function's own header (lines 447-448) defines the verb's job as "this run is not wedged when you are done" — but `absent` is returned while a *new* lock still wedges the run. A script keying on `outcome === "absent"` as "not wedged" is misled; the honest answer here is "refused"/"changed", since the successor's liveness was never inspected.
  - Severity: LOW

- **[LOW]** The EEXIST branch of the acquire loop swallows every non-`claimed` error (EACCES, EMFILE, an internal TypeError) as "vanished — just retry", then misreports it as lock contention — `chunk-src-gate.diff:282-290`
  - Trigger: `statSync`/`readFileSync` on the lock fails for any reason other than ENOENT while `claimed === false` — e.g. permissions changed on the directory, fd exhaustion. The `catch` at line 282 drops it ("vanished between the open and the stat/read — just retry", line 284), the loop spins for the full 5 s, then throws `approval lock ... held for over 5000ms` (lines 287-289), sending the operator to `fleet unlock` for a fault that has nothing to do with a lock holder.
  - Evidence: only ENOENT-after-vanish is the benign case the comment describes; every other errno is folded into the same silent retry with no diagnostic, and the eventual error names the wrong cause.
  - Severity: LOW

- **[LOW]** `awaitDecision` accepts `pollMs: 0` (or negative) — a synchronous-read busy-spin that can block the event loop for the default 24 h window — `chunk-src-gate.diff:1216-1227`
  - Trigger: a caller passes `{ pollMs: 0 }` (or a computed poll that bottoms out at 0). `opts.pollMs ?? 1_000` (line 1216) only substitutes for nullish values, so 0 passes through; the loop then runs `readApprovalIfPresent` (a synchronous file read, line 1219) and `Bun.sleep(0)` in a tight spin until `deadline` — `waitMs` defaulting to `DEFAULT_TIMEOUT_MS` = 24 h (line 1217).
  - Evidence: no floor/validation on `pollMs` or `waitMs` anywhere in the function, unlike the careful clamping applied to `timeoutMs` in `resolveTimeoutMs` (lines 1039-1047). `waitMs: 0` is benign (immediate `null`); `pollMs: 0` is not.
  - Severity: LOW
