# Edge Case Hunter — src/fleet/approvers.ts + src/fleet/attach.ts (PR 150)

- **[MEDIUM]** Attach length guard checks raw chars against the wrong constant; fold still silently truncates — `src/fleet/attach.ts:319`
  - Trigger: a message of exactly 4 000 chars containing any character `sanitizeForMessage` expands — `\n` (→2 chars), `"` (→2), `\x7f`/C1/U+2028/U+2029 (→6). E.g. 2 000 newlines, or a 4 000-char message with a few dozen quotes/newlines.
  - Evidence: `attach.ts:319` refuses only `message.length > DIRECTIVE_TEXT_CHAR_CEILING` (raw, pre-sanitize), with the comment at `attach.ts:317-318` claiming this prevents "silently losing its tail". The fold at `src/phase-engine/steering.ts:519` slices `sanitizeForMessage(message).slice(0, ATTACH_MESSAGE_CHAR_CEILING)` — i.e. it caps the SANITIZED text. `sanitizeForMessage` (`src/phase-engine/types.ts:77-84`) is JSON.stringify plus a `\uXXXX` pass, so any 4 000-raw-char message with escapable characters sanitizes to >4 000 chars and is truncated at fold with no refusal, no error, and an `attach-acked` outcome. Two layered defects: (1) live today — the guard compares pre-sanitize length, the fold caps post-sanitize length; (2) latent — `attach.ts:32` imports `DIRECTIVE_TEXT_CHAR_CEILING` while the fold caps at `ATTACH_MESSAGE_CHAR_CEILING`, which `steering.ts:36-45` explicitly declares "its OWN constant, deliberately not DIRECTIVE_TEXT_CHAR_CEILING… equal today by coincidence, not by contract"; tuning either side silently re-opens the tail-loss the comment claims is closed. The CLI mirror at `scripts/fleet.ts:2905-2909` repeats the same wrong comparison.
  - Severity: MEDIUM

- **[MEDIUM]** scrypt cost ceiling bounds N and r independently; verify path admits a ~4 GiB / minutes-long verification, and a `scryptSync` throw escapes as an untyped error — `src/fleet/approvers.ts:321`
  - Trigger: an allowlist entry (hand-edited, or written by anything that can reach the 0600 file) with in-schema extremes `N: 1048576` (2^20, allowed at `approvers.ts:114`), `r: 32` (allowed at `approvers.ts:122`... `.max(32)`), `p: 16`. Then any `fleet approve` for that approver.
  - Evidence: scrypt's memory requirement is `128·N·r` — at the admitted maximums that is 2^32 bytes (4 GiB) per verification, and `maxmem = 256·N·r` (`approvers.ts:191`) is set to 2^33 so node's own limit does NOT refuse it. CPU scales a further ×p (×16). `authenticateApprover` calls `scryptToken(entry.salt, token, {N, r, p})` at `approvers.ts:321` with NO try/catch, despite the schema comment at `approvers.ts:114-115` itself noting "a throw on the verify path is a refusal an operator cannot read". A throw (ENOMEM, or OpenSSL's overflow/param rejection at the 2^32 boundary) propagates through `authenticateFromStdin` to the CLI (`scripts/fleet.ts:2557`), where `report()` (`scripts/fleet.ts:513`) classifies a code-less bare Error as exit 1 `transient` — "retry me" — against the module header's contract that every allowlist failure is a fail-closed exit 5 with nothing mutated. A non-throwing entry instead blocks the event loop for minutes per decision. The module's own DoS rationale (diff comment above `V2EntrySchema`) only bounds N alone; the N·r product is unbounded up to 4 GiB.
  - Severity: MEDIUM

- **[LOW]** `enrolApprover("__proto__")` returns `ok: true` with a live token but silently writes nothing — `src/fleet/approvers.ts:427`
  - Trigger: `fleet enrol --approver __proto__` (first enrolment of that id into any file that does not already contain an own `__proto__` key).
  - Evidence: `approvers` is built by spread (`approvers.ts:400`, or `{}` fresh at `:396`), so it has no own `__proto__` property. `approvers[id] = entry` at `approvers.ts:427` then invokes the inherited `Object.prototype.__proto__` SETTER, changing the object's prototype instead of adding a key. `JSON.stringify({version: 1, approvers})` at `:435` omits prototype state, so the written allowlist lacks the entry entirely — yet the verb returns `{ ok: true, approverId: "__proto__", token, … }` (`:452`) and the once-shown token can never authenticate (`authenticateApprover`'s `Object.hasOwn` lookup at `approvers.ts:307` correctly finds nothing). Re-enrolment never hits the `approver-already-enrolled` guard (`:415`, hasOwn is false each time), so it "succeeds" forever. `Object.hasOwn` was used everywhere an id is READ (`:307`, `:415`) but the WRITE at `:427` was missed; the schema's `z.string().min(1)` id constraint (`approvers.ts:138`) does not exclude it. Fails closed (no privilege gained), but the verb lies about a security enrolment.
  - Severity: LOW

- **[LOW]** Concurrent enrolments silently lose entries (read-modify-write with no lock) — `src/fleet/approvers.ts:398-439`
  - Trigger: two `fleet enrol` processes for different approver ids overlapping on the same host (e.g. an operator and a provisioning script).
  - Evidence: `enrolApprover` reads+parses the allowlist (`:400`), merges its entry in memory (`:427`), then atomically renames a temp over the live path (`:439`). There is no lock (contrast `RunRecordStore.withLock`, `src/providers/run-record.ts:1528`). Two overlapping runs each read the same base file; the last `renameSync` wins and the first enrolment's entry vanishes — while BOTH operators were handed a token and told `ok: true`. The first token is dead from that instant. Atomic rename makes the write crash-safe but not interleaving-safe.
  - Severity: LOW

- **[LOW]** Ack read re-transfers the whole acks file every poll tick, unbounded for the box's lifetime — `src/fleet/attach.ts:196`
  - Trigger: a box that lives long and acks many messages (the engine leg appends every ack to `$root/acks.ndjson` forever and never truncates — `attach.ts:454-457`), then each `fleet attach` polls `cat "$root/acks.ndjson"` (`attach.ts:196`, `ACK_READ_SCRIPT`) every 500 ms up to 30 s.
  - Evidence: the module capped the INBOX read (`INBOX_READ_CAP_BYTES`, `attach.ts:216` / `readInboxTail`) precisely because "its size is bounded by nothing but the tmpfs it sits on", but the acks file has the identical unbounded-append shape and the host-leg read of it has no cap — each of up to ~60 ticks pulls the entire file's stdout through the driver exec. If a driver caps stdout, the tail (where the newest, matching ack lives) can be truncated away, turning a delivered message into a 30 s poll and a `no-ack` report. LOW because ack lines are ~120 bytes and realistic ack counts keep the file small.
  - Severity: LOW

## Checked and cleared (no finding)

- TOCTOU stat→read in `readGuardedFile`: explicitly documented as accepted residual risk at `src/providers/allowlist-path.ts:21-27`; ancestor walk covers every dir from `dirname(path)` up to and including `hostRoot` (`allowlist-path.ts:141-172`) and runs before the file stat, so `enrolApprover`'s absent-file arm still lands in a walked directory.
- `enrolApprover` absent-file arm: distinguished via `code === "-unreadable" && !existsSync(path)` (`approvers.ts:411`); the `-unreadable` arm also fires for non-regular files and unreadable existing files, but `existsSync` (F_OK) returns true for those, so they propagate as refusals rather than "start fresh" — the comment's claim holds.
- `constantTimeEqual` (`approvers.ts:149-152`): sha256 of both sides before `timingSafeEqual` makes every compare 32 bytes regardless of input length; safe.
- Empty/missing allowlist, malformed JSON, unknown id, empty id: all fail closed with distinct codes; `{"version":1,"approvers":{}}` authorizes nobody. Duplicate JSON keys collapse to last-wins in `JSON.parse` — benign under a 0600 self-owned file.
- Token stdin edges: fd-type allow-list (`approvers.ts:497-508`), per-chunk cap, idle window + overall deadline, reader cancelled on every refusal, empty-after-trim refused — all sound. Binary/non-UTF8 stdin decodes with replacement chars and fails closed at the hash compare.
- attach newline guard (`attach.ts` APPEND_SCRIPT): torn JSON writes end in printable ASCII, never NUL/`\n`, so the `tail -c1` test fires correctly; multibyte splits likewise end in a non-`\n` byte.
- attach run-state guard: approval extension is only written at gate time (`src/fleet/approval-gate.ts:8-14`), so a healthy running run has `state === undefined` and attach proceeds; `assertRunExists` (`scripts/fleet.ts:2869`) handles unknown runIds before `attachToRun` (whose `store.get` throws on absence — `src/providers/run-record.ts:2417-2430`).
- Ack-write failure after delivery (half-applied steering): handled by the separate `delivered`/`acked` sets with ack retry and `reportInboxFault` (`src/phase-engine/steering.ts:395-408, 537-552`).
- Concurrent attaches: single `cat >>` O_APPEND write per message (line ≤ ~16 KB at the ceiling, under cat's read buffer); no interleave. Box-unreachable mid-attach: `unreachableTicks` cap at 3 abandoned execs, distinct `box-unreachable` reason — sound.
- `driver.exec(vm, argv, stdin?)` signature matches both call sites (`src/providers/driver.ts:198`); `withTimeout` attaches the no-op catch before the race, so late rejections are pinned (`src/providers/timeout.ts:46-57`).
