# Blind Hunter — chunk-src-engine.diff (PR150)

- **[MEDIUM] A single over-budget attach line is a permanent head-of-line blocker with no eviction path** — `src/phase-engine/steering.ts` (diff lines 24, 240–253)
  - Trigger: an attach message whose sanitized line exceeds `ATTACH_FOLD_CHAR_BUDGET` on its own. The line is built from caps that sum past the budget: `"operator attach "` prefix + id sliced to `DIRECTIVE_ID_CHAR_CEILING` (256) + `": "` + message sliced to `ATTACH_MESSAGE_CHAR_CEILING` (4_000) ≈ 4 274 chars, while the budget is `PROMPT_CHAR_CEILING / 2` (line 24). If `PROMPT_CHAR_CEILING` < ~8 548 the max legal line never fits even with `foldedChars === 0`. The per-message cap does not protect against the per-line total.
  - Evidence: the budget check is `if (foldedChars + line.length > ATTACH_FOLD_CHAR_BUDGET) { ...reportInboxFault...; break; }` (241–253) — `break`, before `delivered.add(messageId)` and before the ack, so the message is never folded, never acked, and never skipped. Because the queue is oldest-first and the loop breaks rather than discarding the oversized entry, EVERY later solicitation re-drains the same head message, breaks again, and no message behind it is ever delivered for the run's lifetime. `reportInboxFault` fires once (deduped, see next finding) and then the blockage is silent; `fleet attach` keeps reporting the head message — and everything queued behind it — as "stays queued". There is no path that evicts or dead-letters a message that can never fit.
  - Severity: MEDIUM (conditional on the actual value of `PROMPT_CHAR_CEILING`, which is outside this diff; if it is ≥ ~8 548 a single line always fits when the budget is fresh and this degrades to the intended exhaustion semantics)

- **[MEDIUM] Fault dedupe never resets on channel recovery — a recurring identical fault is reported exactly once per run lifetime** — `src/phase-engine/steering.ts` (diff lines 136–137, 176–177)
  - Trigger: inbox drain throws fault A (e.g. `"steering inbox drain timed out after 5000ms"` — a timeout message that is byte-identical on every occurrence); channel recovers (a later drain succeeds); the same stall recurs. The operator is told about the first incident only.
  - Evidence: `if (sanitized === lastPushedFault) return; lastPushedFault = sanitized;` (176–177). `lastPushedFault` is written on push and cleared NOWHERE — not on a successful `drain` (208), not on a successful `ack` (260–261). The dedupe comment (132–136) justifies suppressing repeats "across every solicitation" of an unbroken outage, but the implementation cannot distinguish "same fault, still broken" from "same fault, broke again after recovery", so the second incident — a new fact — is swallowed. Timeout faults all stringify identically, making this the common case, not a corner.
  - Severity: MEDIUM

- **[LOW] Ack retry records the wrong `SteeringPoint`** — `src/phase-engine/steering.ts` (diff lines 256–261)
  - Trigger: message folds at `run_start`, its ack write fails, and the retry lands at a later solicitation (`post_gate_failure` / `run_end`).
  - Evidence: on the retry pass the message is in `delivered`, so the fold block is skipped, but the retry calls `deps.inbox.ack(messageId, point)` with the CURRENT solicitation's `point` (260) — a solicitation whose prompt context this message never reached (it reached an earlier one). The file's own comment (192–198) defines the ack as "this message reached a solicitation's prompt context" and insists it be written "HERE, at fold time"; the retry path acks at a non-fold point, so the acks file attributes the delivery to the wrong steering point. Any consumer correlating acks to points reads a false fact.
  - Severity: LOW

- **[LOW] Retired-field migration can shed the very id it exists to preserve** — `src/providers/run-record.ts` (diff lines 723–726)
  - Trigger: a record whose on-disk `supersededReportIds` already holds `STRINGS_MAX_ELEMENTS` (256) entries when the first post-migration write folds the legacy scalar in.
  - Evidence: `entry[into] = shedStrings(extPath(ns, into), [legacy, ...history]) as string[];` (726). `shedStrings` drops from the HEAD (628: `return value.slice(dropped)`), and the migration deliberately puts `legacy` AT the head (725: "HEAD: the scalar predates every element the array writer appended"). With 257 elements the shed count is 1 and the dropped element is `legacy` itself. The migration's own contract — "a migration in an audit trail may not lose an id" (688–689) — is violated in exactly the state (append-only history at its bound) the shedding machinery exists for. It is announced on stderr by `shedStrings`, but the note says "dropping the N oldest" without naming the id, so the lost audit entry is not attributable.
  - Severity: LOW

- **[LOW] Head-fold ordering assumption breaks under mixed-version writers** — `src/providers/run-record.ts` (diff line 725)
  - Trigger: rolling-upgrade window where an OLD build (still writing the scalar `supersededReportId`) and a NEW build (writing the array) both write the same run's approval namespace. Sequence: new build migrates and deletes the scalar → old build rebinds and re-creates the scalar (it doesn't know `retired`) → new build's next write migrates again.
  - Evidence: the second migration folds at the head on the justification "the scalar predates every element the array writer appended" (725) — but in this sequence the re-created scalar POSTDATES the existing array elements, so the rebind history is persisted in the wrong order in an audit trail whose value is its ordering. Nothing detects or repairs the inversion.
  - Severity: LOW
