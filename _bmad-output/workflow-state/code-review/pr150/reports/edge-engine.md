# Edge Case Hunter — chunk-src-engine (steering.ts, run-record.ts, step-log.ts, reverify/approval.ts)

- **[HIGH] A crashed teardown strands the run in `pausing` forever — the AC1(c) resume arm can never fire from the only caller** — `src/fleet/approval-gate.ts:865` × `src/reverify/runner.ts:244-245`
  - Trigger: `requestApproval` registers `state: "pausing"` and the process dies (or teardown throws) before promotion. The operator re-runs `reverify(runId)` — the documented recovery path — and the new green verdict reaches the gate again.
  - Evidence: the resume arm is keyed on a byte-equal reportId: `if (String(existing?.reportId ?? "") !== reportId) return { outcome: "pause-in-progress" };` (approval-gate.ts:865). But the sole production caller (runner.ts:413-417, reached via this chunk's rewired `recordApprovalPort` → `gateRequestApproval`, approval.ts:73-77) mints a FRESH `reverifyId` on every invocation — `rv-${runId}-${started.toISOString()…}-${Math.random()…}` (runner.ts:244-245), timestamp + random suffix. Two real reverify runs of the same run never share a reportId, so every post-crash retry takes the `pause-in-progress` branch and leaves the record byte-identical. Nothing else exits `pausing`: the module header says so ("Nothing else in this module leaves `pausing`", approval-gate.ts:16-17), `expiredState` deliberately never expires it (:594-595), and `submitDecision` calls it not-decidable (:1102). The header states the arm exists because "without that arm one crashed teardown stranded the run for good" — with an unreachable precondition the stranding is still total, and `scripts/reverify.ts` even exits 0 (green verdict, only an `approval-pause-in-progress` flag). The tests only ever exercise resume with a hand-repeated literal (`reportId: "rv-1"`, tests/fleet/approval-gate.test.ts:216-233), which no real caller produces. The equality check is right for a genuine concurrent-pause collision but misclassifies the common crash-resume case as one.
  - Severity: HIGH

- **[MEDIUM] `fleet attach`'s length refusal checks the wrong constant and the wrong length — escape-heavy 4000-char messages are silently truncated by the fold today, and any tuning of either ceiling breaks the guarantee entirely** — `src/fleet/attach.ts:319` × `src/phase-engine/steering.ts:519,36-45`
  - Trigger: an operator attaches a message of exactly ≤4000 raw chars containing many escapable characters (newlines, `\x7f`, U+2028…). Example: 4000 chars with 1500 newlines.
  - Evidence: attach.ts refuses only when `message.length > DIRECTIVE_TEXT_CHAR_CEILING` (attach.ts:319, raw pre-sanitize length) and justifies it with "The fold caps at the same ceiling; refusing here means an operator is told their message was too long instead of silently losing its tail" (:317-318). Both halves of that claim are false. (1) The fold caps at `ATTACH_MESSAGE_CHAR_CEILING`, a constant steering.ts deliberately decoupled with "Equal today by coincidence, not by contract" (steering.ts:36-45) — tuning either number silently voids the refusal. (2) The fold slices AFTER sanitizing: `sanitizeForMessage(message).slice(0, ATTACH_MESSAGE_CHAR_CEILING)` (steering.ts:519), and `sanitizeForMessage` is `JSON.stringify` plus a `\uXXXX` pass (types.ts:77-84), expanding `\n` to 2 chars and `\x7f` to 6 — the new constant's own header says capping pre-sanitize "let a 4 000-char message store ~24 000". So the 4000-char escape-heavy message passes the CLI refusal and loses its tail mid-prompt with no operator signal. The fix belongs on the caller side but the mismatch is created by this chunk's new, decoupled constant.
  - Severity: MEDIUM

- **[MEDIUM] The awaited `onInboxError` observer has no deadline — a hung async observer wedges the serialized solicit chain, the exact failure mode `INBOX_CALL_TIMEOUT_MS` was added to prevent** — `src/phase-engine/steering.ts:460`
  - Trigger: a consumer passes the explicitly-invited async shape, `onInboxError: async (e) => { await appendToStalledMount(e); }`, and the append never settles (stalled NFS/fuse, a wedged trace store).
  - Evidence: `reportInboxFault` does `await deps.onInboxError?.({...})` (steering.ts:460) with no `withDeadline` wrapper. The new constant's own rationale applies verbatim: "solicit serializes every solicitation through one chain — so a hung inbox … wedges every LATER solicitation with no timeout, no onInboxError and no diagnostic" (steering.ts:52-58); the chain is at :567-572. A hung observer means `solicitSerialized` never returns, the chain never advances, and every later `solicit` (gate-retry seam, pipeline-run.ts:789) queues forever with no fault recorded anywhere — worse than the inbox case, because this path is reached precisely when a fault is being reported. The shipped observer (pipeline-run.ts:1722-1733) is synchronous, so this needs a future/async consumer, but the type `=> void | Promise<void>` (steering.ts:333) invites exactly that.
  - Severity: MEDIUM

- **[LOW] `onInboxError` dedupe never resets — the same fault recurring after a healthy interval is silent** — `src/phase-engine/steering.ts:455-456`
  - Trigger: the inbox channel breaks with detail D (fires once), the operator fixes it (drains succeed, fault clears), and the channel later breaks again with the identical detail D (e.g. the same EACCES on the same acks file).
  - Evidence: `lastPushedFault` is a run-lifetime latch compared by exact string equality: `if (sanitized === lastPushedFault) return; lastPushedFault = sanitized;` (steering.ts:455-456). The comment (:411-415) says "A DIFFERENT fault still fires — the dedupe is on the detail" — but a SAME fault in a new episode is also suppressed, so the operator who fixed the channel once gets no notification when it breaks again. A recovery should clear `lastPushedFault` (a successful drain/ack is observable in `drainInbox`).
  - Severity: LOW

- **[LOW] A `pausing` resume promotes with the ORIGINAL crashed attempt's `requestedAt`/`expiresAt` — the window is restamped on rebind but not on resume, against the gate's own stated rationale** — `src/fleet/approval-gate.ts:866-868` vs `:833-838`
  - Trigger: `pausing` registered at T, teardown crashes, and the resume lands at T+23h59m (or later). The promotion writes only `state` (:1014-1028), so the record enters `awaiting-approval` already at/past its deadline; the next `submitDecision` or `sweepExpired` persists terminal `timed-out` (:1094-1097, :1180-1187).
  - Evidence: the resume branch is explicitly "No write: the resume re-runs teardown and promotes, and the promotion is the only mutation it makes" (:866-868), while the rebind path restamps both timestamps "on EVERY write of the pair, never on the first alone … a report bound at T+23h59m would time out a minute later" (:833-838) — the resume path produces exactly the outcome that sentence exists to prevent. Note this is currently masked by the HIGH finding above (a real caller can never satisfy the resume precondition); it becomes live the moment that is fixed, so the two should be repaired together.
  - Severity: LOW

## Checked and dismissed

- `assertNoSecret` recursion (run-record.ts:652-655): circular/self-referential arrays cannot reach it — `assertKind` runs first on every write path (:879-880, :1516-1517) and rejects non-string elements before recursion; read mode never calls it (deliberate, :864-871). Nested objects-in-arrays hit the `typeof !== "string"` return one level down. No stack-overflow or skip hole.
- Retired-field migration (run-record.ts:892-927): fold-first/drop-second is correct, dedupes on `history.includes`, prepends the legacy id at the head (correct oldest-first), drops over-length legacy values loudly instead of bricking later writes, and runs inside the same locked `set()`. The legacy value bypasses `assertNoSecret` at fold time, but it was scanned when originally written by the older build; only hand-edited disk evades, and read mode already tolerates that. Dismissed.
- `detached` aliasing (run-record.ts:808-810): write path shallow copy is sound post-`assertKind`; read-mode aliasing is unreachable (assertWellFormed discards the result, readRecord returns the parsed record itself — :2437-2438). Dismissed.
- `shedStrings` head-shed vs audit trail: announced on stderr, bounded, freshest 256 survive; acknowledged in the gate's own ceiling note (approval-gate.ts:893-902). Dismissed.
- Steering fold/ack ledger: `delivered`/`acked` split is correct; ack retries survive the budget `break` because delivered messages are always earlier in the oldest-first queue; budget-exhausted messages correctly stay un-acked so `fleet attach`'s "stays queued" remains true; drain timeout loses nothing (full re-read next solicitation). Dismissed.
- `withDeadline` (steering.ts:428-441): losing-promise catch attached before the race, timer cleared in `finally`. Sound.
- Record rewritten between check and use in the gate: all read-decide-write sequences hold `withApprovalLock`; the post-teardown promotion re-reads state under a fresh lock (:1014-1023) and reports the true state rather than assuming. Sound.
- `reverify/approval.ts` adapter: `recordApprovalPort(store)` default (no `teardown`/`bundleDir`) is fail-closed — an open record still naming a `vmName` refuses promotion loudly (approval-gate.ts:992-996), and runner.ts:406's default constructs a fresh writable store when `deps.store` is absent. Sound.
- `boundedEcho` (step-log.ts:292-297): redact-then-cap order is correct; `redactSecrets` processes the full string before the 96-char slice, so no secret past the boundary leaks. Dismissed.
