# Blind CLI review — PR150 (chunk-src-cli, chunk-src-verbs-status)

- **[MEDIUM]** `approvalRowFields` claims the gate's single expiry rule but re-derives `timed-out` itself — `src/fleet/status.ts` (chunk-src-verbs-status.diff:183-205)
  - Trigger: a paused (`awaiting-approval`) record whose `expiresAt` is unparseable, or any case where `expiredState`'s rule and a bare `Date.parse(expiresAt) - Date.now() > 0` disagree (clock edge, future grace handling, garbage timestamp treated as expired by the gate).
  - Evidence: the hunk's own comment says "The expiry RULE is `expiredState`'s, imported rather than re-implemented, and that is a fix rather than a tidy-up… so the two can never disagree about whether a window closed." But the code uses the import only as a pausing-detector: `const effective = expiredState(approval, new Date()); if (effective === "pausing") { … }` — and for every non-pausing case it discards `effective` and re-implements expiry inline: `const expiresAt = … Date.parse(approval.expiresAt)…; const remaining = expiresAt - Date.now(); return { state: remaining > 0 ? "awaiting-approval" : "timed-out", … }`. Concretely: if `expiredState` returns `"timed-out"` for a record whose `expiresAt` fails `Date.parse` (NaN), this function still returns `state: "awaiting-approval"` with no `expiresInMs` — so `fleet status` shows a run as decidable while `submitDecision`/`sweepExpired` treat it as expired. That is exactly the status-vs-gate disagreement the comment says this change eliminates; the fix only covers the `pausing` half of the original bug.
  - Severity: MEDIUM

- **[MEDIUM]** approve/reject build the writable store (chmod 0700, temp sweep, O_EXCL probe) *before* authentication on the default-dir path, contradicting the block's stated invariant — `scripts/fleet.ts` (chunk-src-cli.diff:322-324, 395-402)
  - Trigger: `fleet approve <run-id> --approver <id>` with no `--dir` (the common case) and an invalid/refused token.
  - Evidence: the probe is `new RunRecordStore({ ...storeOpts, ...(dir === undefined ? {} : { create: false }), requestId })` — i.e. for the default dir the "probe" is the full writable construction, and it runs before `await (deps?.authenticate ?? authenticateFromStdin)(…)` (line 379). The later comment claims the writable store is "built only once the run is confirmed AND the caller has authenticated … none of that should happen for a caller who never proved they may decide anything", but `const store = dir !== undefined && deps?.store === undefined ? …writable… : probe;` means on the default-dir path the side effects already happened pre-auth. The attach block in this same diff calls the `create: dir === undefined` pattern "exactly backwards: the default dir is the one an operator never named and is the one this verb has the least business chmod'ing 0700, sweeping temps in, or probing for O_EXCL" — the approve probe does precisely that for unauthenticated callers.
  - Severity: MEDIUM

- **[MEDIUM]** `onInboxError` trace payload is `"{}"` for any real `Error`, defeating the observability the hunk exists to provide — `scripts/pipeline-run.ts` (chunk-src-cli.diff:872-879)
  - Trigger: any steering-inbox fault where `e` is an `Error` instance (the normal case).
  - Evidence: `payloadJson: JSON.stringify(e)`. `Error.prototype.message`/`stack` are non-enumerable own properties, so `JSON.stringify(new Error("disk full"))` serializes to `"{}"`. The comment says "An unreadable steering channel is an operational fault the operator has to be able to see" — the emitted `steeringInboxError` line will carry no message, no code, no path. The operator sees THAT an error occurred and nothing about what it was.
  - Severity: MEDIUM

- **[LOW]** No visible TTY guard on the approver-token stdin read at the `approve`/`reject` call site, while `attach` guards the same fd for a non-secret — `scripts/fleet.ts` (chunk-src-cli.diff:379 vs 705-707)
  - Trigger: `fleet approve <run-id> --approver <id>` typed interactively with stdin still attached to the terminal (operator forgot the pipe).
  - Evidence: attach refuses up front — `if ((messageFlag === undefined || messageFlag === "-") && process.stdin.isTTY) throw usageError("no message on stdin", …)` — with a comment spelling out the hazard: "the terminal — in canonical mode, echo on — puts everything they type in the meantime into their scrollback." The token read at line 379 (`authenticateFromStdin(process.cwd(), approverId)`) has no such guard at the call site. If the callee does not itself refuse a TTY or disable echo (its body is not in this diff, so this is unverifiable from the diff alone), an interactively typed secret token is echoed into terminal scrollback — worse than the message case attach protects against.
  - Severity: LOW

- **[LOW]** `GATE_OK_OUTCOMES` claims "status ok ⇔ the invocation exits 0 … the exit-0 set exactly", but those same outcomes exit 6 when the completion line is lost — `scripts/fleet.ts` (chunk-src-cli.diff:221-245, 505, 662, 836)

  - Severity: LOW
