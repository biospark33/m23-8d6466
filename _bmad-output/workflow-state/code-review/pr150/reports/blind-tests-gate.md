# Blind Hunter review — pr150 / chunk-tests-gate.diff

Scope: `tests/fleet/approval-gate.test.ts` (new file, 1962 lines in-diff). Diff-only; no source read.

- **[MEDIUM] The EPERM liveness test is vacuous when the suite runs as root (or in a pid namespace owning pid 1)** — diff lines 783-799
  - Trigger: the security-critical property is "`isLockHolderDead` must return dead on ESRCH *only*, never on EPERM" — otherwise any process can steal a live foreign holder's lock. The test gets its EPERM by signalling pid 1 and assuming it is root-owned (`process.kill(1, 0)` raises EPERM "for any non-root caller"). When the suite runs as root — the default in most Docker CI — `kill(1, 0)` *succeeds*, the liveness predicate takes its "alive" branch, and the test passes without ever exercising the EPERM arm. The same holds in a pid namespace where pid 1 is the test user's own init. A regression that treats any kill error as "dead" ships green in exactly the environments most likely to run this suite.
  - Evidence: lines 786-789 ("pid 1 is init/launchd: root-owned, so `process.kill(1, 0)` raises EPERM rather than ESRCH for any non-root caller. That is the whole point") — the comment states the preconditions the assertions silently depend on; nothing in the test skips loudly or asserts the precondition (`try { process.kill(1,0); } catch (e) { assert e.code === "EPERM" }`) before relying on it.
  - Severity: MEDIUM

- **[MEDIUM] Hand-built `pausing` fixtures omit every timestamp, and the resume-promotion test never asserts `expiresAt` — a promotion that strands the run passes green** — diff lines 230-245 (resume), 255-265, 293-294, 459-460
  - Trigger: every `pausing` fixture is constructed as `{ state: "pausing", proposal, reportId, headSha }` — no `expiresAt`, no `requestedAt`, no `schemaVersion`. The fresh-registration test (lines 136-139) asserts a registration *does* carry an `expiresAt`, so if production's evidence-first `pausing` write stamps one too, these fixtures are a state production cannot produce, and the resume path is only exercised against a thinner record than reality. Worse, the resume test's own invariant ("a resume writes nothing but the promotion", line 242-243) is asserted only via `state`/`reportId`/`supersededReportIds`; nothing asserts `expiresAt` after promotion. A resume that promotes to `awaiting-approval` while leaving `expiresAt` absent or stale-from-original-request produces a record that — per the unparseable/missing-`expiresAt` arm this same file pins (lines 543-551: malformed or missing expiry "does not expire the run") — never times out and is stranded forever, and every assertion here stays green.
  - Evidence: fixture at line 231 (`extensions: { approval: { state: "pausing", proposal: "p", reportId: "rv-1", headSha: SHA_A } }`); post-resume assertions at lines 240-245 check `state`, `reportId`, `supersededReportIds` only. The crash-window test (lines 120-123) likewise asserts the stranded `pausing` record's `state`/`reportId`/`headSha` but not whether it carries an expiry, so the fixture-vs-production gap is never closed from either side.
  - Severity: MEDIUM

- **[MEDIUM] Error-path log lines never have their field set pinned — the "never a raw error" guarantee is only proven for the success line** — diff lines 1837-1878 vs 1917-1947
  - Trigger: the final D1 test pins the *closed* key set of a pause log line and proves a proposal shaped like an API key cannot reach the sink — but only on the `outcome: "requested"` path. Both error-path tests ("a throw still emits", "the INV-APPROVE-6 refusal is reported as an event") assert with `toMatchObject` only, which tolerates extra keys. - **[MEDIUM] The cross-process rebind race test cannot reliably produce the interleaving it claims to prove — broken locking passes** — diff lines 1548-1595
  - Trigger: the test's stated purpose is to catch two concurrent rebinds each reading `[]` and writing `[rv-1]`, losing a displaced id. But each child, once past the gate file, runs a critical section of fast, near-synchronous file IO (construct store → acquire → read → write → release) with no injected yield or pause inside it. Two processes released within ~4ms of each other will, with high probability, execute strictly sequentially even with the lock removed entirely — the loser simply never overlaps the winner's read-modify-write window. Additionally the `await Bun.sleep(400)` (line 1577) only *assumes* both children are parked on the gate; on a loaded CI box a slow spawn means the second child starts after the gate exists and runs strictly after the first — again serial, again green with broken locking. This is a race test that is structurally likely to pass precisely when the race it hunts is present; its value is probabilistic, not demonstrated.
  - Evidence: child body at lines 1566-1571 is a straight-line `requestApproval` with no barrier between "read extensions" and "write extensions"; the release mechanism (line 1577-1578) synchronizes *start*, not *overlap*. The comment at lines 1554-1559 acknowledges one process can't interleave the bodies but never shows the two-process version actually does.
  - Severity: MEDIUM

- **[LOW] `expect(line.duration).toBe(Number(line.durationMs))` asserts two fields from the same implementation against each other** — diff line 1799

It's a near-tautology masquerading as a timing assertion in a test titled "the contract's fields".
