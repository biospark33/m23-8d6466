# Blind review — pr150 chunk: src/fleet/approvers.ts + src/fleet/attach.ts

- **[MEDIUM]** `enrolApprover` read-modify-write race silently drops a concurrently enrolled approver — `approvers.ts:395-445` (diff lines 395-458)
  - Trigger: two `enrolApprover` invocations run concurrently on the same host (two terminals, or an operator script plus a manual rotate). Both read the allowlist (line 395), both build their own `approvers` object, both write a distinct temp file (line 437, pid+random suffix, so no collision), and both `renameSync` onto the live path (line 445). The second rename wins and the first enrolment's entry is gone — with no error on either side, and the first operator holding a token that verifies against nothing.
  - Evidence: the whole read→merge→write sequence (lines 395-445) runs under no lock. The same diff demonstrates the codebase has and uses the right primitive — `attach.ts`'s own comment at diff lines 927-932 names `withApprovalLock` as the lock the approval gate mutates state under. Enrolment mutates a security allowlist with the same read-modify-write shape and takes nothing. The atomic rename makes each individual write safe but makes the lost-update completely silent.
  - Severity: MEDIUM

- **[LOW]** `readAck` dereferences the parsed row outside the try — a line of `null` in acks.ndjson crashes the ack poll with an uncaught TypeError — `attach.ts:894-901` (diff lines)
  - Trigger: an acks file line that `JSON.parse` accepts but that is not an object — concretely the literal `null` (with optional trailing whitespace). `JSON.parse("null")` succeeds, `row` becomes `null`, and `row.messageId === messageId` two lines later throws `TypeError: Cannot read properties of null`. The throw escapes `readAck`, escapes the poll loop, and becomes the exact "untyped throw reaches `report()` → classified transient → exit 1 → retry me" path this module warns about at diff lines 971-977.
  - Evidence: diff lines 894-901 — the `try { row = JSON.parse(line) } catch { continue }` wraps only the parse; `parsedAny = true; if (row.messageId === messageId)` sits outside it. The same diff's `drain()` (lines 1074-1081) does the property access *inside* its try, so the author knew the pattern needed guarding in one place and missed it in the other. Reachability is thin — `ack()` only ever writes object lines, and a torn `{"messageId":…` fragment fails the parse — so it needs an in-box writer or manual edit to land `null`, hence LOW not MEDIUM.
  - Severity: LOW

- **[LOW]** Over-ceiling message throws a bare `Error`, which by this module's own account is classified "transient, retry" — but a length violation is permanent — `attach.ts:951-955`
  - Trigger: `attachToRun` called with `message.length > DIRECTIVE_TEXT_CHAR_CEILING` (e.g. a 4 001-char paste).
  - Evidence: diff lines 951-955 `throw new Error("attach refused: message is … over the … ceiling")`. Either the throw is wrong or the report() note is; they can't both be right.
  - Severity: LOW

- **[LOW]** The scrypt parameter ceiling still permits a ~4 GiB allocation on the verify path, contradicting the ceiling's stated DoS rationale — `approvers.ts:116-123, 197`
  - Trigger: an allowlist entry with `N: 1048576` (2^20, the schema max) and `r: 32` (the schema max). Both pass `V2EntrySchema`, including the power-of-two refine. `scryptSync` then allocates roughly `128 * N * r` = 4 GiB per verification, and the computed `maxmem` (line 197: `256 * N * r` = 8 GiB) explicitly authorises it. Every `fleet approve` on that host hangs or dies on memory before it can refuse.
  - Evidence: diff lines 116-123 (`.max(1 << 20)` on N, `.max(32)` on r) and line 197. The comment block at lines 101-106 motivates the ceiling as preventing exactly this — "an entry claiming `N: 2^30` is a 137 GB allocation … a denial of service written into a config file" — but the admitted envelope is still a 4 GiB allocation; the ceiling stops the absurd case and keeps the merely-hostile one. Mitigating: writing the entry requires write access to a 0600 host-local file the path guard already defends, so the realistic attacker is an operator hand-editing, which the same comment names as a concern for the floor.
  - Severity: LOW
