# Edge Case Hunter — src/fleet/approval-gate.ts (PR150, chunk-src-gate)

- **[HIGH] The AC1(c) `pausing` resume is unreachable from the only production caller — one crashed pause strands the run permanently, and the operator UX contradicts itself** — `src/fleet/approval-gate.ts:853-869`
  - Trigger: `requestApproval` writes `state: "pausing"` (approval-gate.ts:928-943), then the process dies or `deps.teardown` throws before the promote at :1014-1028. Any later re-verify of the run.
  - Evidence: the resume arm fires only when `String(existing?.reportId ?? "") !== reportId` is FALSE (approval-gate.ts:865) — i.e. the retry must re-present the *same* `reportId`. But the single shipped caller, `src/reverify/runner.ts:413`, mints a fresh `reverifyId` per invocation (`rv-${runId}-${timestamp}-${random}`, runner.ts:244-245) and calls `requestApproval` exactly once with it. `scripts/fleet.ts` has zero `requestApproval` call sites (grep-confirmed; :2942 is a comment). So a crashed pause's bound reportId is never re-presented: every retry gets `pause-in-progress` (approval-gate.ts:865) forever, `expiredState` deliberately never expires `pausing` (:593-594), `submitDecision` answers `not-decidable` (:1102), and no verb/sweep moves the record. The module header (:20-23) claims the resume arm is exactly what prevents this stranding. Compounding it, `src/fleet/status.ts:451-456` DISPLAYS a `pausing` record as `awaiting-approval`, while the approve verb's remediation for `not-decidable`/`pausing` is "re-run once `fleet status` reports awaiting-approval" (scripts/fleet.ts:2639-2641) — a condition the operator already sees as true. Round-6's fix note ("`approval-pause-in-progress` now fires only on the genuine collision") treats a non-matching reportId as concurrency; it is in fact the ordinary sequential retry after a crash. Only recovery is hand-editing the record JSON, which nothing surfaces.
  - Severity: HIGH

- **[MEDIUM] The resume path never restamps `requestedAt`/`expiresAt` — a delayed resume promotes into a shortened or already-closed window, and a closed one turns terminal `timed-out`** — `src/fleet/approval-gate.ts:838, 866-868, 1025`
  - Trigger: pause crashes leaving `pausing`; the same-reportId resume arrives near or past the original `expiresAt` (default 24h).
  - Evidence: a fresh `expiresAt` is computed at :838, but the resume arm returns `{ outcome: "requested", promote: true }` with an explicit "No write" (:866-867), and the promote writes only `{ state: "awaiting-approval" }` (:1025) — `store.set` merges field-by-field, so the *original* `expiresAt` survives. The module's own comment (:833-838) mandates stamping the pair on every write precisely so a stale window is not inherited — that rationale covers rebinds (:908-920 does restamp) but not the resume, which is the path with the longest possible gap. If the original deadline has passed, the promoted record is immediately derived `timed-out` (`expiredState` :589-602), the next `submitDecision` (:1094-1098) or `sweepExpired` (:1176-1188) persists it as terminal, and the run can never be approved. Nested behind the HIGH above in production, but real in the module's own contract and exercised by its tests.
  - Severity: MEDIUM

- **[LOW] The resume arm promotes without the bundle-existence check the other two write paths run** — `src/fleet/approval-gate.ts:853-869 vs 876, 925`
  - Trigger: `deps.bundleDir` set; pause crashes; `<runId>.bundle` is deleted/GC'd before the resume; resume re-runs teardown and promotes.
  - Evidence: `assertBundlePresent` is called on the rebind path (:876) and the fresh-pause path (:925) — its own header (:659-667) says "checked on BOTH write paths" — but the resume arm (:853-869) and the promote tail (:1014-1028) never call it, so a run is promoted to decidable bound to a report whose bundle is gone, the exact condition the guard exists to refuse. Impact is currently capped because no production caller passes `bundleDir` (`recordApprovalPort(store)` at runner.ts:406 passes no opts — grep-confirmed no other construction), so the guard is inert end-to-end today; it becomes live the moment a caller wires the seam the interface advertises.
  - Severity: LOW

- **[LOW] Two concurrent same-reportId callers both pass the resume arm and run `deps.teardown` concurrently; teardown's artifact pull races on fixed shared host paths** — `src/fleet/approval-gate.ts:868, 998-1010`
  - Trigger: two processes call `requestApproval` for the same run with the same `reportId` while the record is `pausing` (or one fresh-registers and the second resumes while the first is mid-teardown — the lock is deliberately not held across teardown, :998).
  - Evidence: both calls reach `await deps.teardown(runId, { noHarvest: true })` (:1008) concurrently. `teardownSandbox` is sequentially idempotent (first-close-wins, `src/providers/teardown.ts:334-350`) but not concurrency-safe: its step 2 runs even with `noHarvest` (:404-407) and `pullArtifacts` copies to fixed paths `<runId>-artifacts.tgz` / `<runId>-artifacts` that are "rebuilt, never merged" (`src/providers/harvest.ts:610-617`, rmSync at :633-634), so interleaved rebuild/extract can throw `HarvestError` from one side or leave a silently mixed artifacts dir — which a later re-run never heals, because a closed record skips the artifacts step. The lock header (:104-106) contemplates two concurrent reverifies of one run, but those mint distinct reportIds, so production reachability is low; the module contract admits it directly.
  - Severity: LOW

- **[LOW] A persisted timeout and a derived timeout report two different `decidedAt` values for the same decision** — `src/fleet/approval-gate.ts:1139-1150 vs 1160-1167`
  - Trigger: run expires; `awaitDecision` (or `fleet status`) observes the derived timeout before any writer sweeps it.
  - Evidence: `derivedTimeout` reports `decidedAt = expiresAt` (:1164) with a comment justifying the anchor as keeping two readers consistent; `writeTimeout` persists `decidedAt = at` — the moment the sweep/decision *noticed* (:1144). So `awaitDecision` (:1218) returns one decision time and the record later persists another, and the stated consistency property holds only until the first persist. Cosmetic audit-trail drift, not a state-machine hazard.
  - Severity: LOW

- **[LOW] `awaitDecision` has no floor on `pollMs` — `pollMs: 0`/negative spins a hot loop for the whole wait (default 24h)** — `src/fleet/approval-gate.ts:1210-1221`
  - Trigger: `awaitDecision(deps, runId, { pollMs: 0 })` (or negative).
  - Evidence: `const pollMs = opts.pollMs ?? 1_000` (:1210) applies no clamp, the loop body is one synchronous record read plus `await Bun.sleep(pollMs)` (:1221), and `waitMs` defaults to `DEFAULT_TIMEOUT_MS` = 24h (:1211). A zero/negative sleep degenerates to a yield, so the loop re-reads and re-parses the record file at full speed for up to a day. Caller-controlled and no shipped caller passes `pollMs`, hence LOW; a `Math.max(pollMs, …)` floor is the one-line fix.
  - Severity: LOW

## Checked and dropped

- Lock acquire/reclaim/release races (`withApprovalLock`): reclaim is fenced on nonce content + atomic rename, release on inode+content; the residual two-syscall windows are documented in the header and reachable only via deliberate `fleet unlock --force`. `LEGACY_RUN_ID_RE` (`^[a-z0-9][a-z0-9-]*$`) makes the lock/reclaim paths traversal-proof.
- `store.set` merge semantics, ENOENT-coded `get`, post-close extension writability, `shedStrings` 256-cap: all verified against `src/providers/run-record.ts` (:826-932, :1477-1523, :773-779) and match the gate's assumptions.
- Boundary inputs: empty/whitespace `reportId`/`headSha` rejected pre-lock (:820-828); `timeoutMs` clamped both ends including non-finite (:1033-1041); `expiresAt == now` not expired (`>` at :601) — consistent on both read and decide paths; `capText` surrogate-safe at exact bounds (:565-579); decision enum, blank `approverId`, and the reserved `system:timeout` id all refused pre-lock (:1066-1082).
- `assertNoSecret` rejecting secret-shaped proposal/reason text: loud, pre-write, pre-teardown, and shared store policy (INV-2) — the shipped caller's proposal (`runner.ts:414`) cannot trip it; intended behavior, not a mismatch.
- Crash between register and teardown / between teardown and promote: leaves `pausing` by design; the R5-C keyHash guard (:976) and INV-APPROVE-6 no-teardown-seam guard (:992) both fail closed before the irreversible step. (The recoverability of that designed state is the HIGH finding above.)
