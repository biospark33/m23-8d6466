# Edge Case Hunter — CLI chunks (scripts/fleet.ts, scripts/pipeline-run.ts, src/fleet/verbs.ts, src/fleet/status.ts, src/fleet/dispatch.ts)

- **[HIGH] `--rotate` is a dead flag: enrol never forwards it, so rotation through the CLI is impossible** — `scripts/fleet.ts:2713`
  - Trigger: `fleet enrol --approver alice --rotate` for an already-enrolled approver (also the prescribed recovery after an exit-6 lost token).
  - Evidence: the flag is declared in the registry (`src/fleet/verbs.ts` — `enrol` entry, `{ name: "--rotate", valueType: "boolean" }`), so `tokenizeArgs`/`parseArgv` accept it into `bools`. But the enrol block calls `(deps?.enrol ?? enrolApprover)(process.cwd(), approverId)` (`scripts/fleet.ts:2713`) and **never reads `bools.has("--rotate")`** anywhere in the file (grep confirms the only `bools.has` calls are `--force` at :2786 and `--no-harvest` at :3272). The call site cannot be trivially fixed by adding a third argument either: `enrolApprover`'s signature is `(hostRoot, approverId, file = DEFAULT_APPROVERS_FILE, opts = {})` (`src/fleet/approvers.ts:370-375`), so `rotate` must arrive as the 4th argument. Result: the invocation parses cleanly, then hits `approver-already-enrolled` exit 5 whose remediation says "pass --rotate to mint a NEW token" (`approvers.ts:416-424`) — the exact flag the operator already passed. The exit-6 remediation "re-run with --rotate to mint a replacement" (`scripts/fleet.ts:2742`) is equally unactionable, so an approver whose minted token failed to print is permanently bricked short of hand-deleting the allowlist entry. The `deps.enrol` seam type (`(hostRoot, approverId) => ApproverEnrolment`, `scripts/fleet.ts:279`) has no rotate parameter, so the in-process tests can't catch it; the only rotate coverage is direct-library (`tests/fleet/approvers.test.ts:1000`) — no test drives `--rotate` through the CLI.
  - Severity: HIGH

- **[LOW] The new `--dir ""` guard is unreachable — the parser refuses empty flag values first** — `scripts/fleet.ts:379-386`
  - Trigger: `fleet status --dir ""` (or `--dir=`) — an unset `--dir "$RUNS_DIR"`.
  - Evidence: the added guard throws a named usageError for `dir === ""`, with a comment stating "an unset `--dir "$RUNS_DIR"` is how it happens — is already exit 2 by way of `statSync("")` raising ENOENT". Neither is what happens: `dir` comes only from `flags.get("--dir")` (`scripts/fleet.ts:1511`), and `parseValueFlags` rejects empty values in both forms — space form: `if (typeof v !== "string" || v.length === 0 || v.startsWith("--")) throw` (`scripts/lib/cli-args.ts:72-75`); `=` form: `if (v.length === 0) throw "${flag} requires a non-empty value"` (`cli-args.ts:62-64`) — so the invocation exits 2 with "--dir requires a non-empty value" before `run()`'s verb dispatch ever calls `assertRecordsDirUsable`. The guard and its comment are dead code built on a wrong premise (harmless, but the "names the actual fault" claim never fires).
  - Severity: LOW

- **[LOW] approve/reject: the default-dir store is the WRITABLE construction and it is built before authentication, contradicting the block's own invariant** — `scripts/fleet.ts:2573-2580`
  - Trigger: `fleet approve <run-id> --approver x` with no `--dir` (default records dir) and a bad/absent token.
  - Evidence: the probe is `new RunRecordStore({ ...storeOpts, ...(dir === undefined ? {} : { create: false }), requestId })` — with `storeOpts = {}` when `--dir` is omitted (`scripts/fleet.ts:1512`), `create` defaults to true (`src/providers/run-record.ts:980`), so the pre-auth probe IS the writable construction: mkdir, `chmodSync(dir, 0o700)`, stale-temp sweep, O_EXCL probe (`run-record.ts:1091-1097`). The comment at `scripts/fleet.ts:2573-2576` claims the writable store is "built only once the run is confirmed AND the caller has authenticated … none of that should happen for a caller who never proved they may decide anything" — true only for a NAMED `--dir`; the default dir gets the full writable construction for any unauthenticated caller. Impact is small (the default dir is the fleet's own and 0700 is its intended posture), but the stated security ordering does not hold for the most common invocation.
  - Severity: LOW

- **[LOW] `approvalRowFields` re-implements the expiry comparison it claims to import, recreating the drift vector it documents fixing** — `src/fleet/status.ts:461-471`
  - Trigger: latent today; fires if `expiredState`'s rule ever changes (e.g. a grace period or a different strictness) — `fleet status` would again disagree with `submitDecision`/`sweepExpired` about whether a window closed.
  - Evidence: the header comment says "The expiry RULE is `expiredState`'s, imported rather than re-implemented, and that is a fix rather than a tidy-up" (status.ts, above `approvalRowFields`), and describes the `pausing` divergence it eliminated. But for the `awaiting-approval` arm the function discards the `effective` value it just computed and re-derives the verdict itself: `const expiresAt = Date.parse(...); const remaining = expiresAt - Date.now(); state: remaining > 0 ? "awaiting-approval" : "timed-out"` (`status.ts:465-471`). Today the two rules are equivalent (both strict `>`), so the only live divergence is the millisecond-exact boundary (`now === expiresAt`: `expiredState` says not expired, `approvalRowFields` says `timed-out`); the issue is that the "single source of truth" claim in the comment is not what the code does for the non-`pausing` arm.
  - Severity: LOW
