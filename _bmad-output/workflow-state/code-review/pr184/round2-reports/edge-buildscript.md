# Edge Case Hunter — /tmp/pr184-r2/chunk-buildscript.diff (scripts/build-exedev-image.ts, tests/scripts/*)

Method: exhaustive path walk of the diff's added/changed code, verified against the real files on feature/df2.10 (`scripts/build-exedev-image.ts`, `oci/exedev/Dockerfile`, `scripts/lib/cli-args.ts`, `.dockerignore`). Findings only; handled paths discarded silently.

## F1 [HIGH] SIGINT/SIGTERM handlers are unreachable for the entire run — a direct kill is now ignored until the build finishes, and CI escalation to SIGKILL leaks everything

`scripts/build-exedev-image.ts:259-268` registers `process.on("SIGINT"/"SIGTERM", …)`, but `main()` is fully synchronous end-to-end (`spawnSync` chains, sync fs, sync hashing). Node/Bun deliver signal callbacks only on an event-loop turn, and this process never yields to the event loop between module load and process exit. Consequences the handlers were added to prevent:

- Interactive Ctrl-C still "works" only by accident: the foreground process group SIGINT kills the docker *child*, `run()` sees a non-zero status and `die(2)`s (exit code 2, not the promised 130/143 — the "128+signal" convention at line 263-266 is dead code).
- A signal sent to the bun PID alone — exactly what CI cancellation does (GitHub Actions signals the root process, not the group) — is *absorbed*: the pre-diff default (immediate termination) was replaced by a handler that cannot fire, so SIGINT and SIGTERM are now no-ops for up to the full ten-QEMU-minute build. CI then escalates to SIGKILL, under which neither the signal handler nor the `process.on("exit")` hook at line 259 runs: the registered `runDir` (~1.6 GB archive), `treeDir`, and any `leaked.containers` all leak, and the orphaned `docker buildx build` child keeps running on the runner.

Failure scenario: cancel the publish workflow mid-build → runner receives no exit from bun within the grace period → SIGKILL → stranded builder container work, leaked `oci/.build/exedev/run-*` with a partial 1.6 GB tar (see F6), zero cleanup — the exact accumulation the leak registry docblock (lines 227-241) claims to close.

## F2 [MEDIUM] `assertCid` failure path leaks the very container it just created

`scripts/build-exedev-image.ts:909-919`: `docker create` has already run (and succeeded — `run()` at lines 985/1064 dies on non-zero status) before `assertCid` inspects the stdout. If stdout carries anything besides the bare id — the docblock's own named cases: platform-mismatch warning, deprecation notice, credential-helper chatter — the regex at line 911 fails and `die(2)` fires at line 912 *before* `leaked.containers.add(cid)` at line 917. A real container exists (its id is somewhere in the polluted output) but is registered nowhere: not in `leaked`, not reachable by any `finally`. Every subsequent run then trips the preflight at lines 1454-1458 ("remove the containers holding it") — the condition the leak registry exists to prevent, produced by the leak registry's own guard. The die path needs to attempt extraction/removal (e.g. rm any 64-hex token found in the raw output) before exiting.

## F3 [MEDIUM] buildId's systemd-file ordering uses `localeCompare` — a locale/ICU-dependent sort feeding a hash that must be host-independent

`scripts/build-exedev-image.ts:488`: `[...inputs.systemdFiles].sort((a, b) => a.name.localeCompare(b.name))` inside `deriveBuildId`. `localeCompare` with no arguments uses the runtime's default locale and ICU tables; collation of punctuation/case (`@` vs `.` vs `-`, upper vs lower) differs between locales and ICU builds. The hash bytes include the files in sorted order, so two hosts that sort the set differently mint different buildIds for identical bytes — a pin-gate failure that names nothing. Today's two names (`qds-run@.service`, `qds-steering.conf`) happen to agree everywhere; the first added unit whose name differs from a sibling only in case or punctuation (e.g. `qds-run.timer` alongside `qds-run@.service`) makes CI-vs-macOS divergence live. The new test at `tests/scripts/build-exedev-image.test.ts:72` ("function of the SET of inputs, not the order") pins order-independence but runs both sides under one locale, so it can never observe the cross-host divergence. Guard: sort with a code-unit comparator (`a.name < b.name ? -1 : …`), matching the locale-independent `.sort()` already used for `baseDigests` (line 484) and `readdirSync` (line 716).

## F4 [MEDIUM] `tarUnescape` decodes bytes correctly and then destroys non-UTF-8 names in `toString("utf8")` — phantom exit-1 finding on a clean image

`scripts/build-exedev-image.ts:955`: after the byte-accurate octal decode the function ends with `Buffer.from(bytes).toString("utf8")`, which replaces any invalid UTF-8 sequence with U+FFFD. A file in the base image whose name is latin-1/raw bytes (legal on ext4/overlayfs; GNU tar emits it as `\NNN`) round-trips to a *different* string than the real name. Downstream at line 1021 that string is classified and — if it matches `CONFIG_CANDIDATE_OUTSIDE_DEPS` (any `.pem`/`.key`/`credentials` basename) — handed to `docker cp` in `inspectConfigs`, which cannot find the mangled path, so both spelling variants fail and line 880 raises "could not read /… — treating as a finding" → exit 1 on a clean image. This is the same 126-phantom-findings failure shape the docblock (lines 922-929) says this function was written to end, re-entered one encoding layer down. It fails closed, but as a false compliance failure (exit 1) rather than a fatal (exit 2), on content the repo does not control (the vendor base). Guard: carry the decoded bytes (or a `latin1` round-trip string) to `docker cp` instead of forcing UTF-8.

## F5 [LOW] The added pre-drop loop and `mkdtempSync` are unguarded — a bad `--summary`/`--evidence` path or full disk exits 1, the code reserved for compliance failure

`scripts/build-exedev-image.ts:1445`: `fs.rmSync(stale, { force: true })` over `[NOTICE_PATH, opts.summary, opts.evidence]` — `force` suppresses ENOENT only; `--summary` pointing at a *directory* (an easy operator mistake for an output flag) throws `ERR_FS_EISDIR`/`EPERM`, uncaught → bun exits 1. `scripts/build-exedev-image.ts:1468`: `fs.mkdtempSync(path.join(BUILD_DIR, "run-"))` likewise throws uncaught on EACCES/ENOSPC → exit 1. Both are exactly the "fatal before the gates could conclude" condition the diff's own `readInput`/`writeJson` additions (lines 681-696, 1343-1358) exist to route to `die(2)`; these two added call sites skipped the same guard, so a path/disk error is reported with the exit code the contract reserves for a licence failure.

## F6 [MEDIUM] Leaked `run-*` dirs are never garbage-collected and live inside the docker build context — one SIGKILL/SIGHUP leaks 1.6 GB into every future context transfer

`scripts/build-exedev-image.ts:1468-1471`: `runDir` is `mkdtempSync` under `BUILD_DIR` = `oci/.build/exedev`, which is *inside* the build context (`REPO_ROOT`, line 1509) and not excluded by `.dockerignore` (it appears only in a comment, `.dockerignore:3`). Cleanup relies entirely on the exit hook / `finally`, and F1 shows the SIGKILL path is realistic; SIGHUP (dropped ssh session during the ten-minute build — no handler registered at lines 260-268) also terminates with no `exit` event. The old fixed-path code self-healed: the next run's `fs.rmSync(archive)` pre-clean removed the stale 1.6 GB tar before the context snapshot. The new per-run `mkdtempSync` never revisits old `run-*` dirs, so each leak is permanent: every subsequent `docker buildx build` ships the orphaned 1.6 GB archive(s) to the docker-container builder as context, silently multiplying build time and disk until someone hand-cleans. No startup sweep of stale `run-*` siblings exists.

## F7 [MEDIUM] The concurrency rationale is half-true: matrix runs still collide on the tag preflight, NOTICE, and default summary/evidence paths

The added comment at `scripts/build-exedev-image.ts:1461-1467` justifies per-run dirs with "the CI matrix that runs two of them at once", but only `archive`/`metadataFile` were made per-run. Two concurrent invocations (the invited `--platform` matrix, defaults otherwise) still share: (a) `spawnSync("docker", ["rmi", "-f", opts.tag])` at 1450 — run B's preflight force-unresolves the tag run A just applied at 1679, so run A's `--push` rebuild/`manifestDigest` read races a deleted tag; (b) the added pre-drop at 1445 deletes the *other* run's freshly written `opts.summary`/`opts.evidence` (both default to fixed paths, 126-127); (c) `NOTICE_PATH` write at 1653. Failure scenario: amd64 and arm64 matrix legs overlap → leg 1 exits 0 but its `build-evidence.json` (the file `tier1-image-contract.live.test.ts` reads, per the comment at 1439-1444) was deleted or overwritten by leg 2 — the exact "run A reading run B's state" defect the comment claims was closed.

## F8 [LOW] `parseArgs` silently drops positionals and single-dash typos — `-push` builds-without-publishing with exit 0

`scripts/build-exedev-image.ts:1311-1316`: `tokenizeArgs` is called without `rejectStraySingleDash`, and the returned `positionals` are discarded. Per `scripts/lib/cli-args.ts:166-176`, a single-dash token (`-push`, `-keep-tree`) lands in `flagTokens`, and `parseValueFlags` (cli-args.ts:52-88) ignores any token not starting with `--`; a bare `push` lands in the dropped `positionals`. So `bun scripts/build-exedev-image.ts -push` runs the whole build, exits 0, publishes nothing — the "silently DROPPED … unacceptable when the command is destructive" case cli-args.ts:100-103 documents `rejectStraySingleDash` for. The one flag whose silent loss changes what reaches a registry is left on the tolerant grammar.

## F9 [LOW] TAG_RE accepts a digest-only reference that every later consumer refuses — validated at parse, fails after the ten-minute build

`scripts/build-exedev-image.ts:148-149`: the grammar's trailing `(?:@sha256:[0-9a-f]{64})?` admits `--tag ghcr.io/x/y@sha256:<64hex>`. That reference passes the "before ANY action" gate at 1333, but `docker tag <id> ref@sha256:…` at line 1679 is refused outright by docker ("refusing to create … a digest reference"), and `--output type=image,name=ref@digest` (1526) cannot name an image by digest either. The refusal therefore arrives as an opaque `die(2, ["docker tag exited 1"])` after the full QEMU build and every gate — precisely the "fails ten minutes in" timing the surrounding additions (ARG lockstep check, TAG_RE itself) argue must be caught at parse time. The `@sha256` arm should be rejected for `--tag` (it is only meaningful for the *base* refs).

## F10 [LOW] `fromInstructions` is line-based: heredoc bodies and line continuations can mint phantom FROMs that move the buildId and can flip the runtime base

`scripts/build-exedev-image.ts:517-533` matches `^FROM\s+` per physical line with no awareness of `\`-continuations or `RUN <<EOF` heredocs (the `# syntax=docker/dockerfile:1` header in `oci/exedev/Dockerfile:1` enables heredocs). A heredoc line beginning `FROM x` (e.g. generated config text) is parsed as a real FROM: it enters `parseBaseRefs` → `resolveBaseDigest` (die, or worse, resolves a same-named public image and folds a foreign digest into the buildId), and in `resolveRuntimeBaseRef` (559-575) it becomes `last`, silently redirecting AC5's negative control to the wrong image — the docblock's own "fails in the direction that greens an unattributed binary". Today's Dockerfile has neither construct, but DF1.10's engine build stage (which this diff's docblocks repeatedly design for) is the moment multi-line RUNs arrive. No guard or refusal exists for `\`-terminated lines or `<<` markers.

## F11 [LOW] `readInput` reads buildId inputs as lossy UTF-8 — two distinct on-disk byte sequences can hash to one identity

`scripts/build-exedev-image.ts:687-696` (new) returns `fs.readFileSync(file, "utf8")`; any invalid UTF-8 byte in the Dockerfile or a systemd asset becomes U+FFFD before `deriveBuildId` hashes it (475-495 frames by `Buffer.byteLength` of the *string*). Two files differing only in which invalid byte they carry produce identical hashed bytes — "two different substrates claiming the same identity", the collision class the framing docblock (466-469) says the function exists to prevent. Repo-controlled text files make this remote, but the guard is one word: read the bytes (no encoding) and hash the Buffer.
