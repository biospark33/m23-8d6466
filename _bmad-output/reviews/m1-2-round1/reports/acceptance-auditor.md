## Findings

- **[HIGH] Recalled KG content can hard-fail dispatch (exit 2) — no producer-side charset guard, so a poisoned bank breaks every future dispatch instead of degrading to v5.**
  - Violates: story Overview ("a broken KG can only degrade to v5 behavior"), AC2's ladder (no rung exists for "recall succeeded but content is brief-invalid" — it neither primes nor proceeds unprimed, it kills the verb), AC1's negative-control spirit (recall content changing dispatch's exit codes), and the Files-to-Modify list, which explicitly assigns a "charset guard" to `src/hindsight/kg-context.ts` — the implementation has none.
  - Evidence: `src/hindsight/kg-context.ts` `escXml` escapes only `& < >`; nothing in the assembly path filters control characters (verified: the only charset check in the module is `CITABLE_ID` on observation ids). `src/fleet/brief-schema.ts` `KG_CONTEXT_CONTROL_CLASS` refuses C0 (minus \n\t) + DEL, so any recalled observation whose `text` carries `\r` (CRLF text), `\x0b`/`\x0c`, or DEL flows verbatim into `kgContext`, BriefSchema refuses the primed brief, and the dispatch verb answers with the invalid-brief exit (the exact class AC3's negative control names as exit-2). This is reachable in practice: M1.1's `src/hindsight/mulch-importer.ts` retains repo-derived expertise with no control-char sanitization (verified: it splits on `\n` only), and `qds-collective` aggregates every repo. One bad retained observation = every subsequent dispatch for that repo exits 2 until the bank is manually cleaned. The brief-schema comment's own framing ("reaching this refusal means the boundary was bypassed") is false for the charset leg: recalled content is the boundary's legitimate input. Fix is one guard in `buildKgContextXml`/`observationXml` (strip or drop whole observations carrying refused code points), which is also the smaller diff than any schema-side relaxation.

- **[MEDIUM] Side-channel row is keyed on, and labels as `runId`, the brief's `requestId` — and is silently absent for briefs that carry no UUID requestId.**
  - Violates: the Observability Contract and E2E slice, both of which name `_bmad-output/memory/recall/<runId>.json` recording `{runId, ...}` where the story's `runId` is elsewhere defined as the minted `qds-YYYYMMDD-*` id; and the contract's cycle-counting guarantee ("M1.3 counts every M1 cycle from these rows"), which makes env-configured dispatch the only no-write case, not requestId-less dispatch. Not covered by any recorded amendment (R2/R3/R4, path drift, or the three listed deviations).
  - Evidence: `src/hindsight/kg-context.ts` `primeDispatchBrief` reads `briefStr(briefJson, "requestId")`; `writeRecallRow` returns early when undefined (no row AND no `kg-recall` line), and the row's `runId` field carries that UUID. The minted runId does not exist yet at the seam (it is minted later inside `dispatch` — `src/fleet/dispatch.ts` `mintRunId`/`resolveBriefRequestId`; the record's requestId falls back to `newRequestId()` in `src/providers/run-record.ts:1282` when the brief carries none). `BriefSchema` does not require `requestId`, and the seam's own tests omit it deliberately. So the common plain-brief dispatch produces priming with zero observability, and when a row exists its `runId` is a UUID that matches no receipt subject (receipts use the minted runId) except via the separate requestId join. The live test pins the conflation (`expect(row.runId).toBe(round.requestId)`), so it is known-but-unrecorded.

  - Evidence: `src/hindsight/run-retain.ts` `buildRetainPayload` supports `spendMicroUsd`/`bundlePath` (tested), but both callers — `scripts/fleet.ts` `retainRunOutcomeBestEffort` and `src/fleet/run-completion.ts` `postHarvestRetain` — pass only `runId/repoSlug/requestId/exitClassification/harvestedCount?/tags/repoBankId`. The bundle path is known at the call site (the bundle just landed), so at minimum that field is dropped on the floor; live outcome documents carry no cost or bundle provenance.

- **[LOW] The kgContext charset guard misses the Unicode Cc C1 range (U+0080–U+009F) and the U+2028/U+2029 line separators, though the guard's stated purpose is line-boundary-forging defense.**

NEL (U+0085), LS (U+2028), PS (U+2029) are exactly the "forge a line boundary" class the field comment says it refuses. Producer-side impact is identical to the HIGH finding once that guard exists.
