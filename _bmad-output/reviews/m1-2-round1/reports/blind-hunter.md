# Blind Hunter — M1.2 round 1

Reviewed: `_bmad-output/reviews/m1-2-round1/diff.patch` (diff only — no repo, no spec, no referenced files).

- **[HIGH] Unvalidated brief field used as a filename — path traversal at the dispatch seam.** `primeDispatchBrief` runs on the RAW parsed JSON in `scripts/fleet.ts` `ingestBriefJson` (the hunk explicitly primes *before* the verb's schema refusal: "passed through untouched to the verb's own schema refusal"), so `briefStr(briefJson, "requestId")` in `src/hindsight/kg-context.ts` reads an arbitrary attacker/host-controlled string with no charset or length check. `writeRecallRow` then does `writeFileSync(join(base, \`${runId}.json\`))` — a `requestId` of `"../../anything"` escapes `DEFAULT_RECALL_DIR` and overwrites an arbitrary file with attacker-chosen JSON, and an empty/1 KiB id produces filesystem-dependent failures. The diff's own `pipeline-run.ts` comment ("a newline in a hand-forged witness value must not forge instruction lines") shows this repo's threat model already treats brief/witness values as forgeable; the write site has no such guard. The same unvalidated string is also passed as `requestId` into `log()`.

- **[HIGH] Live-round L3 cleanup guard is outside its try/finally — partial L2 failure leaks a real box, key, and probe bank.** In `tests/fleet/e2e/memory-cycle.live.test.ts` L3, the guard `if (ctx === undefined || round.runId === "" || round.vmName === "" || round.repoBankId === "") throw ...` executes BEFORE the leg's `try { ... } finally { cleanup }`. L2's finally is deliberately empty of teardown ("DELIBERATE: no box destroy / no revoke here — L3's finally owns the full cleanup verdict"), and `round.runId` is only armed on the dispatch success path (`emittedRunId` is called after `runFleet` resolves; the timeout catch rethrows without arming). So a dispatch that times out *after* provisioning the box and creating `repoBankId` leaves L3 throwing the hollow-leg error with no cleanup at all: live box (billed box-hours), minted key, and a `banksWeCreated` bank all leak — exactly the failure mode the file's own comments claim L3 recovers. The comment "a bun timeout abort skips this finally only — the box/key leak is still recovered by L3's finally" is false for this path.

- **[MEDIUM] L1's "fallback" fabricates evidence and proves nothing — echo failure is converted into a pass.** In the L1 catch block, the fallback proof does exactly one retain + one recall on a fresh bank and asserts one document — a property of a single retain, not of skip-on-replay. No replay call is ever made, yet the written ledger records `replaysSkipped: 1, replayPolicy: "skip-on-replay"` and the evidence records `replaySkipped: true`. Nothing anywhere in the diff consumes that ledger file (no production code reads `m12-retain-identity-ledger-*`), so the "fallback" exists only inside the test; `failure = undefined` then lets the leg pass on a substrate where the DD-28.26(3) echo actually failed. In a suite whose header declares "no fakes anywhere in this file", invented `replaysSkipped` counts and an unimplemented fallback are evidence-integrity defects.

- **[MEDIUM] Wire-level retain failure is silently converted to success.** `RetainWireSchema` (`src/hindsight/schemas.ts`) accepts `success: z.boolean()` and `items_count: z.number()` without constraining either, and the `.transform()` drops `success` entirely — a `{"success": false, "items_count": 0, "async": false}` body parses cleanly into the legacy success view. `HindsightClient.retain` never checks `success`, so a server-side rejection delivered with HTTP 200 (or a partial-failure body) flows through `retainRunOutcome` as a landed retain: the ok `memory-retain` log line fires and the audit receipt is written for a memory that was never stored. `items_count` is also never checked against the single item sent.

- **[MEDIUM] The recall query silently drops the numeric issue id — task-scoped recall never fires on the field briefs actually carry.** In `src/hindsight/kg-context.ts`, `briefStr(briefJson, "workId") ?? briefStr(briefJson, "issueId")` returns `undefined` for any non-string, and dispatch briefs carry `issueId` as a number (`issueId: 123` in the brief-schema test fixtures; `issueId: 46` in the live L2 brief). The "short deterministic query" therefore degenerates to `${repoSlug}` alone on the primary path: every dispatch for a repo recalls the same top-k regardless of the task, and the "repo **or task**" grounding the file's own header advertises silently doesn't happen. `String(workId)`-style coercion was trivially available; the typeof guard turns it into a silent quality regression instead.

- **[MEDIUM] A non-identical replay replaces the retained outcome and fires the tamper alarm on a legitimate operation.** `documentId = runId` + server-side replace means a re-harvest whose payload differs (first harvest `harvested`/green/count N, re-harvest `none`/unsettled, or a changed count) silently OVERWRITES the good memory — a green outcome can be downgraded to `unsettled` in the bank — while the audit store keeps the first receipt digest and logs the divergent-evidence alarm (`src/hindsight/run-retain.ts` header: "different content under the same documentId trips the store's divergent-evidence alarm by design"). An alarm designed for tampering now fires on ordinary re-harvests, and the memory of record flips without any operator-visible gate. The L3 test asserts `receipts.length === 1` after re-harvest but never asserts non-divergence, so this path is unverified.

- **[MEDIUM] The retain twins diverge in structured failure output and logging stack.** For the identical condition (record without `budget.repoSlug`), `scripts/fleet.ts`'s `retainRunOutcomeBestEffort` logs code `"retain-skipped"` via `log` imported from `src/swarmclaw/log.ts`, while `src/fleet/run-completion.ts`'s `postHarvestRetain` throws and logs code `"retain-failed"` via `log` imported from `src/swarmclaw/mcp/stdio-transport.ts`. Same operation family, same condition, two different codes, two different log modules/sinks (and different redaction: `redactSecrets(...).slice(0, 200)` vs `errText(e)`). Any M1.3-style consumer keying on the operation+code pair gets inconsistent results depending on which twin ran, and the two `log` implementations may not even share a sink.

- **[MEDIUM] "No prose channel" invariant is false as implemented.** `buildRetainPayload` (`src/hindsight/run-retain.ts`) validates `exitClassification` as a union and type-checks only `harvestedCount`/`spendMicroUsd`/`tags`/three id strings — `bundlePath` is never type-checked or bounded, and `repoSlug`/`requestId` are only checked non-empty (no length/charset bound). Any caller-supplied string rides verbatim into the retained memory up to the 4 KiB cap. The negative-control test proves only that *extra* properties can't enter; the module's own header ("the payload has NO prose channel... raw box prose has no field to ride in on") is contradicted by the free-text `bundlePath` field it also serializes.

- **[MEDIUM] kgContext breaks the witness channel's own trust rule: validated once, never re-checked in-box.** The context lines the new `dispatch.ts` spread sits under state the rule explicitly: "the engine re-checks the bounds fail-closed before rendering, because what is trusted here is the channel, not the content" (that's the fixContext discipline). `residentContextLines` (`scripts/pipeline-run.ts`) appends `kgContext` verbatim with no ceiling or charset re-check, on the argument that BriefSchema validated it at dispatch. A hand-forged or stale-witness `run-context.json` therefore delivers unbounded, control-character-bearing text directly into the resident prompt — the one field for which the file's stated fail-closed rendering rule is waived.

- **[MEDIUM] The best-effort retain helper's "cannot move the exit code" guarantee has a hole: the catch handler itself can throw.** `retainRunOutcomeBestEffort` (`scripts/fleet.ts`) wraps everything in try/catch, but the catch body calls `redactSecrets((e as Error)?.message ?? e)` — for a thrown primitive (e.g. `throw 42`), that passes a non-string into `redactSecrets`, and any exception raised inside `skipLine` (throwing log sink, redaction crash) escapes the helper entirely into `runHarvest`, moving the harvest exit code — the exact outcome the hunk's comment promises is impossible. The run-completion twin has the same shape via `errText(e)` inside its catch.

- **[LOW] Runs without a requestId stamp are misclassified as failures, not skips.** The direct `fleet harvest` arm passes `requestId: tdeps.requestId ?? ""`; if the record carries no stamp either, `buildRetainPayload` throws `retain-payload-invalid` ("payload field requestId must be a non-empty string") and the helper emits a `"retain-failed"` error line — an expected, benign condition surfaced in the same class as real retain failures. The twin guards the analogous `repoSlug` case explicitly; `requestId` got no equivalent guard.

- **[LOW] Ladder-(b) side-channel rows can misreport the attempted fan-out.** In `primeDispatchBrief`, `attempted`/`bankMs`/`recallMs` are only assigned after `recallFanOut` returns, so a `listBanks` failure or bank-resolution failure writes a row with `banks: []` even though listBanks was attempted, and the row (as opposed to the log line) carries no per-bank timing at all — M1.3 cannot distinguish "no banks attempted" from "bank resolution failed".

- **[LOW] Side-channel row filename collisions corrupt the cycle count.** `writeRecallRow` keys the file on the brief's `requestId`, which dispatch honours from the client; two concurrent dispatches reusing a requestId (a plain operator error the system otherwise tolerates) silently overwrite each other's row — last writer wins — so one cycle becomes uncountable to M1.3. The dir is also `DEFAULT_RECALL_DIR` relative to cwd, so dispatches run from another working directory scatter rows elsewhere.

- **[LOW] The wire-body schema and the body the client actually sends disagree.** `RetainPayloadSchema` (`src/hindsight/schemas.ts`) requires a body-level `bank_id`, but `HindsightClient.retain` sends `{ items: [...] }` with the bank only in the URL path. Nothing in the shown client path validates the outgoing body against this schema, so the schema documents a wire shape the client never produces — a contract that fails the day anyone actually enforces it.

- **[LOW] Harvest retain resolves a fresh bank id for a since-deleted repo bank and fails opaquely.** Both retain twins call `resolveRepoBankId(resolveBankId(repoSlug), existing)`, whose semantics (as exercised by the L2 seam mirror) return a fresh candidate id when the bank is absent from the live list. Retaining then fires at a nonexistent bank and surfaces as a raw transport/server error (`retain-failed`) instead of a distinct "repo bank missing" skip — the opposite resolution posture from what retain needs (existence, not freshness).

- **[LOW] Memory retain latency is coupled onto the teardown critical path.** The injected `postHarvest` is awaited inside `teardownSteps` before the revoke+destroy steps, and each retain costs a `listBanks` plus a retain at client timeouts — so a slow or hung Hindsight adds tens of seconds (per run; per candidate in an observe sweep) to every teardown while boxes keep billing. Failure-isolated, but the box-hour clock runs during the memory round-trip, and the diff nowhere bounds or accounts for that added dwell.
