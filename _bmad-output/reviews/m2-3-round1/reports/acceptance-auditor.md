## 2. Findings

**F1 — A probe that succeeds (including no-auth 200) does NOT fail the round — CRITICAL — violates AC5 negative control, INV-M3-2, DoD "adversarial".**
In L3's `finally`, battery failures go into a local `problems` array (`tests/fleet/e2e/memory-combined.live.test.ts:827-828` for `allRefused:false`, `:832` for a battery that cannot run) — and `problems` is never passed to `settleRun` (`:849-854`, which receives only destroyFailures / fleetCleanupProblems / keyProblems / bankProblems). Same array silently absorbs L3 evidence-write refusals (`:204`). Contrast L1/L2, which re-throw after `finally` (`:534`, `:656`). Net effect: a gateway regression that answers a no-auth request 200 — the literal 0.8.6 danger this round exists to retire — produces a GREEN round with the defect recorded only inside an evidence JSON; the story's "ANY probe succeeding … fails the round" and "a probe that cannot run is a FAILED round, not a skipped assertion" are not enforced by the round. (Related, lower: the in-process battery's `cleanup` entries with `result:"failed"` are also evidence-only — a probe key left unrevoked on the shared ledger surfaces only if the F17 hash-delta happens to re-list after the battery, which it does not, since `keyLeakProblems` runs before the battery in the same `finally`; the 1 h backstop TTL bounds the blast radius. Fold a cleanup-failure check into the same fix.) Fix: append `problems` (and battery cleanup failures) to the `settleRun` problems list — one line.

**F2 — The divergent-digest alarm is invisible to the round's AC7 walk — MEDIUM — violates AC7 / Technical Notes digest-stability method.**
`src/audit/link-store.ts:489-501`: a divergent re-emit is logged at error and DROPPED — the row count stays 1 either way. L2's dedup assertion (receipts still 1 after re-harvest, `memory-combined.live.test.ts:633-638`) therefore passes identically for a clean duplicate AND for a DIVERGENT drop (re-emit with a different evidence digest). The story explicitly names this bug class ("the store reports `divergent` on re-emits with a different evidence digest"); the round as written cannot detect it. Fix: run the re-harvest with `QDS_LOG_VERBOSE=1` and assert the stderr contains no `audit link divergent` line (the emit outcome is otherwise unobservable).

**F3 — "Server duration alongside" and in-box call latency are recorded nowhere — MEDIUM — violates Observability Contract / AC3's latency clause.**
The contract requires "recall wall-clock host-side, server duration alongside". The round's evidence carries host-side `latencyMs` via the RecallRow (`:497`, row object pushed at `:498`; `kg-context.ts:112`), but `bankMs`/`recallMs` ride the dispatch LOG line only (never captured into evidence), and in-box `kg_recall.call` success events carry no timing (the extension emits `clientMs` on refusals only; the round's own comment at `:617-618` admits it). A leg that ran reports its server-side sub-timing as absent without the "absent, not 0" marker either. Fix: capture the extension's call latency (or record the L1 row's log-line `recallMs`) in the leg JSON, or amend the contract in the story.

**F4 — `auditHopsUntouched` is a hardcoded literal, not a check — LOW — weakens AC7 / INV-M3-4's evidentiary value.**
`memory-combined.live.test.ts:762` writes `auditHopsUntouched: true` without comparing the observed hop set against `src/audit/link-store.ts:52` `AUDIT_HOPS` / `HOP_EVENT_VOCABULARY`. The `leaked` scan only catches rows containing "memgate" or the volatile marker; a hypothetical new memory hop with a different name would pass. One-line fix: assert every `rows[i].hop` ∈ AUDIT_HOPS (import the frozen list).

**F5 — Fixture-at-SHA precondition is documented but unchecked; failure mode is post-spend — MEDIUM — AC1/AC2 robustness.**
The in-box `dispatch_task` loads `spec.roster = config/rosters/memory-live.roster.yaml` resolved against the box's checkout at `QDS_EXEDEV_SHA` (test header `:130-135` calls it "an operator precondition"). The driver verifies the working-tree fixture exists (`:367-370`) and stages a byte-identical copy (`:441-442`) but never checks the pinned commit carries the file (no `git cat-file`/`ls-tree` anywhere in the file). A stale pin fails the round mid-flight, after dispatch spend. Cheap pre-fire fix: `git cat-file -e ${ctx.sha}:config/rosters/memory-live.roster.yaml` before FIRING dispatch.

**F6 — Interrupt-path cleanup has no mechanism — MEDIUM (DoD names it) — AC6 / INV-M3-5.**
DoD: "`finally` cleanup verified on pass, fail, and interrupt paths." Pass and fail are solid (L3 `finally` + `settleRun`), but a process interrupt between L1 and L3 strands the box and the run key: there is no describe-level `afterAll`, no signal handler, and L1's `finally` deliberately cleans nothing (`:516-519`). This matches tier2 sibling precedent, so it may be an accepted posture — but then the DoD line is not demonstrably satisfied by this diff and should be satisfied by the operator runbook explicitly, or a SIGINT handler / afterAll backstop added.

**F8 — The lead role runs `tools: null` (unrestricted) on the credential-holding box — LOW — roster least-privilege binding.**

The binding constraint is satisfied by the credential-carrying worker (fixer, `kg_recall` named), and the lead has no extension so `kg_recall` is not registered for it — but the DD-16 pair sits in one box-wide `KEY_ENV_FILE` readable by any process, and the unrestricted lead can reach it via bash. Key is recall-only + capped, so LOW; naming `tools` on the lead (or `[]`) would close it.

**F9 — `QDS_EXEDEV_ROSTER` is presence-gated but never consumed — LOW — spec-wording deviation.**

The roster actually consumed is the staged byte-identical copy (host gate) plus the committed fixture (in-box) — practically equivalent/stricter thanks to the byte-identity assert, but the spec's "consumed via `QDS_EXEDEV_ROSTER`" is not literally true. **F10 — `requireMemoryEnv` demands `HINDSIGHT_BEARER_TOKEN`; the ladder's own gate accepts `HINDSIGHT_API_KEY` — LOW.**
`memoryEnvConfigured()` (`kg-context.ts:271-274`) accepts BEARER_TOKEN **or** API_KEY; the round's `requireMemoryEnv` (`:126-135`) refuses without BEARER_TOKEN. An API_KEY-only operator gets a fail-closed refusal at LD/L1 where the ladder would have engaged. Harmless (fails closed), but a needless round-killer for a legitimate env shape.
