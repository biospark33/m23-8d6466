# Blind Hunter — M1.2 round 2

Reviewed: `_bmad-output/reviews/m1-2-round2/diff.patch` (8,776 lines, read in full; diff only — no repo, no spec, no referenced files). Round-1 fix list (F1–F22, triage.md embedded in the diff) checked hunk-by-hunk against the final state.

- **[HIGH] The producer charset guard (F3) sanitizes observation content but NOT the `documentId` attribute — a poisoned bank still exit-2s every future dispatch.** In `src/hindsight/kg-context.ts` `observationXml`, `kgContextSanitize` is applied only to `o.content`; the `documentId` attribute is emitted with `escAttr`, which escapes only `& < > "` — control characters (`\r`, `\x0b`, DEL, C1, U+2028/2029) ride through untouched. `src/hindsight/schemas.ts` `RecallResponseSchema` types `document_id: z.string().nullish()` with no charset bound, so any recalled item whose `document_id` carries a refused code point produces a `kgContext` that fails `BriefSchema`'s `kgContextIsWellFormed` refine at dispatch — FleetError(2, invalid-brief), repeatedly, until the bank is manually cleaned. The box-side drop (pipeline-run.ts) cannot help: the host schema refuses before the verb ever runs. This is exactly the round-1 HIGH's failure mode ("a poisoned bank breaks every future dispatch"); the fix covered the content leg and left the attribute leg open. `CITABLE_ID` guards `id` but nothing guards `documentId`.

- **[HIGH] Retain/recall bank resolution diverge in the collision case: the F16 fix makes the retain twins silently write the outcome document into a foreign pre-existing bank.** `scripts/fleet.ts` `retainRunOutcomeBestEffort` and `src/fleet/run-completion.ts` `postHarvestRetain` both do `resolveBankId(repoSlug)` then `existing.has(repoBankId)` — presence of the RAW normalized id. `src/hindsight/kg-context.ts` recall uses `resolveRepoBankId(resolveBankId(repoSlug), existing)`, which (per this diff's own test "provision-time bank id: collision suffix resolves against the LIVE list", kg-context.test.ts) returns the SUFFIXED id (`acme-widget-2`) when the raw form already exists. So when the provisioned bank is `acme-widget-2` (because `acme-widget` existed at provision time), recall reads `acme-widget-2` while the retain's presence check finds `acme-widget` EXISTS — and writes there: a bank the run never provisioned, possibly another repo's. Cross-bank contamination of a shared memory substrate, and the outcome document is invisible to M1.3 probes keyed on the recall bank. The two hunks directly contradict each other: kg-context.ts states "The raw form can diverge from the provisioned id and is never used as the bank id itself (AC1)" while both retain twins use exactly the raw form as the bank id. Round-1's F16 behavior (retain into a nonexistent bank) failed loudly; this fix's behavior fails silently in the wrong place.

- **[MEDIUM] The fast-fail dispatch path never calls `recoverDispatchIds` — ownership arming is asymmetric and can leave a live box unnamed.** In `tests/fleet/e2e/memory-cycle.live.test.ts` L2, `recoverDispatchIds(partial.stdout, partial.stderr)` runs only inside the `runFleet(...).catch` arm, i.e. the timeout path. A dispatch that RESOLVES with a non-zero exit (e.g. setup-gate refusal after provisioning — the case the harness's own docstring says "refusal envelopes + teardown remediation lines name the box") takes the resolve path, where arming relies solely on `lastJsonLine(dispatch.stdout)` + `emittedRunId`. If the refusal's ids live in remediation prose or a non-final JSON line, `round.vmName` stays `""` and L3's finally skips `destroyQuietly` (`if (ctx !== undefined && vmName !== "" && !bodyTeardownOk)`), leaving a billed box alive — a residual of the round-1 HIGH leak class on the one path F4 did not re-plumb. Additionally, if `dispatch.stdout` contains no JSON line at all, `ack` is undefined and `ack.runId` throws a TypeError inside the try — the leg's failure evidence becomes "Cannot read properties of undefined" and the `expect(dispatch.exitCode).toBe(0)` assertion never runs, obscuring the real verdict.

- **[MEDIUM] `retainRunOutcome`'s own log emissions are unguarded — a throwing sink converts a LANDED retain into a "retain-failed" report and drops the receipt.** In `src/hindsight/run-retain.ts`, both the post-retain success `log(...)` and the `log(...)` inside the receipt-refusal catch are bare calls. Round-1 fixes F9/F19 were applied at the twin layer (every `skipLine`/catch wrapped) and in `emitAndReturn`, but not to the seam both twins call. Trigger: memory env configured + a sink that throws (custom `setLogSink` callback, JSONL file sink) + any retain. Consequence: the network retain succeeded, then the throw escapes `retainRunOutcome` into the twin's catch, which emits `retain-failed` — the operator is told the retain failed when it landed, no receipt row is written, and in the teardown path a spurious `teardown.post_harvest` error line fires. The exact scenario F9's comments describe ("a raising log sink must not turn a skipped retain into a crashed path") is still reachable one layer down.

- **[LOW] `src/providers/teardown.ts`'s post-harvest catch feeds a possibly non-string throwable to `redactSecrets`.** `const err = (e ?? {}) as { code?: string; message?: string }; ... redactSecrets(err.message ?? e)` — for a thrown plain object or primitive, `err.message ?? e` is that non-string value, and the twins' F9 hardening (`String(...)` before redact) was not mirrored at this site even though the interface comment declares the hook "untrusted here regardless of what its own body catches". A hostile/odd throwable produces either a garbage log message or an exception from inside the catch, depending on `redactSecrets`'s tolerance.

- **[LOW] `success:true` with `items_count: 0` (or `async: true`) still parses as a landed retain.** `src/hindsight/client.ts`'s F6 arm refuses only an explicit `success === false`; `src/hindsight/schemas.ts` `RetainWireSchema` accepts `items_count: z.number()` (no `.min(1)`) and `async: z.boolean()` unconstrained. A 2xx `{success:true, items_count:0, async:true}` — zero items stored, or queued-not-stored — flows through `retainRunOutcome` as success: the ok `memory-retain` line fires and the audit receipt records a landed document that may not exist. The round-1 finding's residue beyond the explicit-false case.

- **[LOW] The live round leaves the dispatch side-channel row in the repo working tree.** L2 asserts `_bmad-output/memory/recall/<uuid>.json` exists under `REPO_ROOT` (the dispatch subprocess's cwd-relative `DEFAULT_RECALL_DIR`); neither L2's nor L3's finally removes it — cleanup covers the tmp workspace, probe banks, box, and key only. Every live round deposits a new row file into the checked-out tree, polluting the very directory M1.3's cycle counter reads with round-instrumentation cycles.

- **[LOW] `recalledDocumentIds` can advertise documents whose observations the assembly ceiling dropped.** `primeDispatchBrief` computes the row's `recalledDocumentIds` from ALL of `fan.observations`, but `buildKgContextXml` drops whole observations that do not fit (`if (used + cost > KG_CONTEXT_MAX_CHARS) continue`). A near-ceiling block ships a row listing ids the resident never saw, so M1.3's probe-for-recalled-id verification hunts documents that were recalled but never grounded — the row overstates what the cycle delivered.

- **[LOW] `bundlePath` is supported by the payload builder but populated by neither call site — triage F12's condition is unmet and unamended.** Round-1 triage records "F12 [MED] AC4 payload: populate bundlePath if trivially available at call sites"; the final `scripts/fleet.ts` and `src/fleet/run-completion.ts` retain inputs carry only `runId/repoSlug/requestId/exitClassification/harvestedCount/tags/repoBankId`. Amendment R6 defers only the cost µ$ field ("ledger join = A5/DD-20 scope"); the bundle path — known at the harvest site the moment the bundle lands — is dropped with no recorded amendment. Outcome documents carry no bundle provenance.

- **[LOW] `buildRetainPayload` still has unbounded free-text fields after F8.** The F8 fix bounds only `bundlePath` (≤512, no control chars); `repoSlug` and `requestId` remain checked merely non-empty (no length/charset bound), and both serialize verbatim into the retained memory up to the 4 KiB cap. A hostile or corrupted run record can carry ~4 KB of arbitrary text into the shared bank under the "payload has NO prose channel" header — the header's claim is now mostly true but not entirely.

- **[LOW] A retain that loses the F17 wall-cap race keeps running and can contradict its own timeout line.** Both twins fire `retain-timeout` at 10 s and return, but the racing body is deliberately left alive (`body.catch(() => {})`): its late `memory-retain` ok line and audit receipt can land after the harvest completion line has printed (or after the teardown verb moved on to revoke+destroy), so the log stream shows `retain-timeout` followed by a success — two witnesses telling opposite stories — and in a CLI process the late network work races process exit, so the receipt may or may not persist.
