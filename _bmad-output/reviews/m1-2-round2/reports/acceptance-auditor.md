## Findings

- **[HIGH] AC1 make-or-break / E2E slice: the dispatch fan-out can never recall the provisioned repo bank — the read leg resolves with the CREATE-side collision resolver, so in the normal M1.1 state it recalls a nonexistent bank, and the harvest→dispatch memory cycle never closes (the write and read legs target different banks).**
  - Violates: AC1 ("fan-out recall over `{<provision-time repo bank id>, qds-collective}` — the repo bank id pinned to PROVISION-TIME resolution … **never re-derived** … which can diverge from the provisioned id"), the E2E slice ("Given M1.1's banks and one retained observation matching repoSlug … the shipped brief's `kgContext` carries the `<kg_context>` block"), and AC4's pairing (outcome retained to the bank dispatch reads).
  - Evidence: `src/hindsight/kg-context.ts:353` — `const repoBankId = resolveRepoBankId(resolveBankId(repoSlug), existing)`. `resolveRepoBankId` (`src/hindsight/bank-provisioner.ts:184-208`) returns `safeBase` **only when `!existing.has(safeBase)`**, else the first free `-2..-11` suffix — it is a create-side resolver whose output is by construction NOT in the live list. When the repo's bank IS provisioned (the only state M1.1 produces), dispatch resolves `<base>-2`, recalls it (404/empty), and the provisioned bank's observations never prime; only `qds-collective` ever feeds the block. The harvest twins meanwhile retain to the base id (`scripts/fleet.ts:6153`, `src/fleet/run-completion.ts:273` — base-presence check), so the outcome document lands in a bank dispatch never reads. Nothing persists the provision-time id on either leg (the spec's sanctioned alternative, "persisted by M1.1's provision leg", is unimplemented). The unit test enshrines the inversion: `tests/hindsight/kg-context.test.ts:222` asserts that when `acme-widget` EXISTS the fan-out recalls `acme-widget-2` and "the raw resolveBankId form must never be recalled directly" — the exact opposite of AC1's provision-time-id contract. The only dispatch-tier wiring test with a real listBanks uses `{banks: []}` (seam test b), the one state where the resolver happens to return the base id. Consequence for AC7: live L2's SEAM MIRROR creates the resolver-fresh id, then the production seam re-resolves against a list that now contains it → next suffix → `row.banks`/`recalledDocumentIds` assertions (`toContain(repoBankId)`/`toContain(primeDocId)`) cannot pass in ANY live state — the T2 round as authored deterministically fails after real spend (it is unfired, D4, so this is currently latent). The in-code comments state the misunderstanding outright: kg-context.ts:348-350 ("[the resolver] picks the provision-time id against the LIVE bank list") and fleet.ts:6089 / run-completion.ts:218. Not raised by round 1 (the round-1 auditor marked AC1 "verified clean"), and not covered by any FIX/DISMISS/amendment — a new violation in the final state.

- **[MEDIUM] AC4/AC1: a collision-provisioned repo's harvest outcome is retained into ANOTHER repo's bank — the F16 fix inverted the failure mode instead of implementing provision-time resolution.**
  - Violates: AC4 ("retained to the provision-time repo bank id (`resolveRepoBankId` semantics — see AC1)") and AC1's explicit prohibition on raw-`resolveBankId` re-derivation for retain/read targeting.
  - Evidence: `scripts/fleet.ts:6153-6157` and `src/fleet/run-completion.ts:273-277` — `repoBankId = resolveBankId(repoSlug)`, retained iff present in the live list. Presence cannot distinguish "our provisioned base" from "another repo's bank that won the base id": when this repo's bank is `baseId-2` (the collision `resolveRepoBankId` exists for), the check passes and the outcome document (and its receipt `detail.bank`) lands in the other repo's bank. The fleet.ts/run-completion.ts justification ("it returns ids NOT in the live list, so it can never locate the provisioned bank") is true of the resolver's output set but does not follow — the correct fix is persistence of the provisioned id (spec's first option), not the raw normalizer.

- **[MEDIUM] Round-1 FIX F10 only half-landed: the live L1 fallback still has no gated second retain attempt, and still writes fabricated counts.**
  - Violates: binding triage F10 — "actual second retain attempt through the ledger + recall unchanged; no fabricated counts" — and AC7's no-fakes posture for evidence.
  - Evidence: `tests/fleet/e2e/memory-cycle.live.test.ts` fallback arm: one retain → recall → ledger write → ledger read-back (`identityPresent`, :423-426) → a SECOND RECALL (`afterSkip`) → `replaysSkipped: 1` written (:447) and `networkRetainCalls: 0` pushed as a hardcoded evidence literal (:427). No second retain is ever attempted (gated or otherwise), no production code implements or consumes a retain-identity gate (grep: `retain-identity|skip-on-replay` has zero hits under `src/`/`scripts/`), and `networkRetainCalls: 0`/`replaysSkipped: 1` describe events that never occurred — the same evidence-integrity defect round 1 flagged, minus the recall re-assertion that was added. Only reachable when the echo fails (rare; round unfired), hence MEDIUM.

  - Evidence: `buildRetainPayload` guards the field (F8 landed: `src/hindsight/run-retain.ts:125-136`), but grep confirms zero `bundlePath` references in `scripts/fleet.ts` and `src/fleet/run-completion.ts` — both twins build `RetainOutcome` without it.
