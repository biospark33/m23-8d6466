## DF3.7 — findings

| ID | Class | Sev | Finding |
|----|-------|-----|---------|
| DF3.7-W16-1 | C2 | HIGH | **The `gate-refused` discriminator is not observable at the chain boundary.** AC5/DoD: "every gate refusal **throws**, and `reverify()`'s approval-request catch surfaces it — so the discriminator is the thrown error carrying the gate's typed refusal code." Traced end to end, this is false in both halves. (a) The shipped gate refusals (`refuseLiveInfraOnDecidable`, the resume/rebind mismatch refusals, the R5-C no-keyHash refusal, the INV-APPROVE-6 no-seam refusal, `assertBundlePresent`) all throw plain `Error` objects whose codes exist only as parenthetical prose in the message — no structured `code` field exists on any of them. (b) `reverify()` does not surface the throw to its caller: its approval-request catch converts it to `approval: null` plus the single generic flag `approval-request-failed` on a re-sealed report — the identical shape a non-gate failure (`refuseHollowBundle`, an EIO) produces. The chain calling `reverify()` therefore cannot satisfy its own AC5 contract ("`gate-refused` is reserved for the gate's own typed refusal… one that reports `gate-refused` for a non-typed request failure … MUST fail"): the test it mandates is unwritable against the shipped surface. A workable mechanism exists without touching fenced files — `ReverifyDeps.approval` is a shipped seam, so `run-completion.ts` can wrap `recordApprovalPort`, classify the typed throw at the wrapper, and rethrow — but the story never states it, and it needs a sentence reconciling it with "the chain composes them and re-implements neither". As written, the arm's producer ("the throw") has no observer. |
| DF3.7-W16-2 | C2 | MEDIUM | **The `ChainOutcome` union has no arm for reachable failure throws inside the chain it composes.** Two producers: (a) `teardownSandbox` — the chain's own harvest/destroy/revoke step — throws typed step failures by contract, and every shipped holder idiom handles them; (b) `reverify()` can throw from its report leg: the prior-report read and the report append sit outside both of its try blocks, so an EACCES/ENOSPC on the reverify dir escapes the "always returns a typed outcome" contract. Both fire **after** the box is destroyed and `closedAt` is set — exactly the closed-with-no-pause witness-less shape this story exists to end — yet the union (`driven | unsettled | refused | gate-refused | vetoed | handed-off`) covers only reverify's *returns* and the gate's throw, and the exit table assigns nothing. The "every outcome the shipped code can produce has exactly one arm" property fails on the error paths. |
| DF3.7-W16-3 | C3 | MEDIUM | **AC5's pre-flight order strands the crashed-chain `pausing` record AC3 routes to `promoteStrandedPause`.** In the chain's own flow, `closedAt` is set by teardown *before* `requestApproval`, so a crash between the gate's `pausing` register and its promote leaves a record that is **both** `pausing` **and** `closedAt`-set. AC3 says exactly this record "takes AC5's `promoteStrandedPause` path and never polls at all" — but AC5 enumerates the pre-flight as extension-state first, then "the same pre-flight refuses a record whose `closedAt` is already set", and a literal reading of that order refuses the record at `run-already-closed`, permanently stranding the run (the exact hazard AC5's own negative control ("one that **refuses** on `pausing` leaves a run stranded forever") targets). The pausing branch must be stated to precede the `closedAt` refusal; the DoD's pausing test only catches the bug if its fixture record carries the `closedAt`. |
| DF3.7-W16-4 | C1 | MEDIUM | **Wrong credential-chain anchor.** Files-to-Modify: "`keyApi` resolved by the caller from the same credential chain `startResident` uses". `startResident`/its module contains no `KeyApi` at all — by its own docblock "the resident never mints, borrows, or falls back to a second key". The shipped chain that matches the requirement (a revoke-capable run-key `KeyApi`, fail-closed with `provisioning-key-missing`) is `openRouterKeyApi()`, used by dispatch's mint-time resolution and by the reaper/`sandbox-reap` revoke path. The requirement is right; the pointer sends the implementer to a module that deliberately has the opposite property. |

The gate's rule is about its **approval** lock (its teardown seam runs outside `withApprovalLock`); the **run** lock is held across `teardownSandbox` by every shipped holder idiom and by this story's own `deps.runLock` discipline.
