## DF3.7 — Approval-Gate Bridge: Findings

| ID | Class | Severity | Finding |
|---|---|---|---|
| DF3.7-W12-1 | C2 | MEDIUM | **The `gate-refused` / `vetoed` split assigns the approval-request-failure arm to both sides.** AC5's discriminator — "a `reverify()` that returns `approval: null` **on a `green` verdict**" fires `gate-refused` — identifies exactly one producer in the shipped runner: the catch around the port call, because the non-green verdict returns before the gate and the `nothing-to-verify` preflight seals its report `red` (the verdict is derived from an empty check list as `red` with reason `nothing-to-verify`). Yet the same AC5 paragraph enumerates "three arms that never reach the gate or are not gate refusals — the non-`green` verdict early return, the `nothing-to-verify` preflight, **and the approval-request-failure catch**" as `vetoed`, and the Impl DoD repeats the same three-name vetoed list. The catch arm is therefore `gate-refused` by the stated discriminator and `vetoed` by the stated enumeration. The AC5 gloss is also factually wrong for that arm: it cites `ReverifyOutcome`'s docblock ("null on a red/error verdict"), but the catch re-seals a report whose verdict is still `green` — it is the one null-on-green. The two readings change the operator's remediation on an already-closed record (`fleet teardown <runId>` vs. a re-verify diagnosis). The negative controls pin only the non-green and `nothing-to-verify` cases, leaving the catch to whichever reading the dev implements. A dev must pick between the spec's own words. |
| DF3.7-W12-2 | C2 | MEDIUM | **`ChainOutcome`'s `driven` arm mandates `markerOk: boolean`, which has no truthful producer on the `promoteStrandedPause` path.** A successful stranded-pause promotion reaches `awaiting-approval`, so it must be reported `driven` — but that path skips the observe leg entirely and never reads a marker, so `markerOk` is undefined, not false. Filling it `false` is exactly the lie-shape the story's own timing rule condemns (`chain_ms` is "absent, not `0`" because "`0` is a lie shaped exactly like an instantaneous chain"); making it optional deviates from the declared union shape. The story cut `markerWitnessed` for carrying "a field with no producer of `true`" by its own reasoning, yet kept a boolean on `driven` whose second sanctioned path witnesses no marker at all. Bounded: the dev must widen the type, add an arm, or accept the lie. |
| DF3.7-W12-3 | C3 | LOW | **The declared `deps` shape cannot drive the full mandated chain for keyed records.** Files to Modify declares `deps` as `{ driver, store, runsDir, hostRoot, runLock, maxTicks?, windowMs? }`, and the module composes `teardownSandbox` internally. `TeardownDeps` carries `keyApi` optional-but-fail-closed ("required iff the record carries keyHash", refusing `provisioning-key-missing`), `requestId`, and the `costLedger` pricing hook — none of which the declared shape can carry. Every ordinary dispatch mints a key and stamps `keyHash`, so the chain as declared fails closed at the revoke step on the common case; the live e2e would surface it, but the story, which names every other seam painstakingly, does not name this one. One-field widening, no story boundary crossed — hence LOW, not HIGH. |
| DF3.7-W12-4 | C4 | LOW | The exit-table annotation in Files to Modify is narrower than the ACs it summarizes: exit 1 is annotated only as `run-completion-unobserved`, while AC2(a) also maps a filled skip streak's `box-unreachable` to exit 1; exit 5 is annotated with `run-engine-dead`, `approval-already-registered`, and the lock refusal, while AC5 maps `run-already-closed` to exit 5 too. The AC bodies carry the mappings; only the annotation list under-declares them. |
