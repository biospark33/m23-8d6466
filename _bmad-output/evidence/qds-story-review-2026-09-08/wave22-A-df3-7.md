| DF3.7-W22-1 | C3 | **HIGH** | `Files to Modify` → `ChainOutcome` `chain-failed` arm vs the verb exit table and the AC5 DoD item | The union admits `chain-failed` "**at any point in the chain**", naming `teardownSandbox`'s harvest and destroy aborts "**with the record still open**" (true — teardown's own step comments say exactly that: a harvest throw aborts before revoke/destroy, a destroy throw is an unconfirmed destroy with the record open). But the exit table maps only "a **post-close** `chain-failed` throw" to exit 6, and exit 6 is defined as "the chain landed and what failed came after it" — false for a harvest/destroy abort, where the chain did not land and the record is open. The DoD AC5 item likewise says "post-close chain-step throw". A pre-close `chain-failed` therefore has **no declared exit**: not 1 (no transient code), not 5 ("refused before anything was mutated" is false — harvest mutates, destroy was attempted), and mapping it to 6 contradicts exit 6's own definition. The registry is a declared contract (the verbs registry's own comment: an undeclared code "lands in a generated skill's default branch"), so a dev cannot resolve this without either weakening the exit-6 definition or shipping an undeclared code. The union and the exit table state two different mappings for one arm — exactly the primary-lens consistency failure. Fix: either widen exit 6's definition to any `chain-failed` (and drop "post-close" from the DoD item and exit-6 bullet), or give the pre-close abort its own declared exit. |
| DF3.7-W22-2 | C2 | MEDIUM | AC5 → `approval-failed` arm description | The arm is defined as "the gate leg errored — **the record is closed, the box is destroyed**" — in the same paragraph that admits "the hand-run live-box `pausing` case included". In that case the opposite is true: `promoteStrandedPause` skips the teardown leg, the gate's INV-APPROVE-6 no-seam guard fires **because** the record is open and still names a `vmName`, `reverify()`'s approval-request catch flattens the plain-`Error` refusal to `approval: null` + the `approval-request-failed` flag, and the run lands in `approval-failed` with the record still `pausing` and the box alive (verified end to end in the gate's promote tail and the runner's catch). No structural damage — the arm's payload is `{kind, error}` with no state fields — but the stated invariant is false for a named producer, and an implementer or test author will read it as the arm's contract (e.g., asserting `closedAt` set or "box destroyed" in CLI output/tests) and fail on the admitted case. Fix: scope the closed/destroyed clause to the driven path (the stranded-pause re-entry's `approval-failed` carries both remediations against live infra — which the dual remediation text already anticipates). |
