# DF3.6b — code review round 1 (mechanism & security)

**Date:** 2026-09-18 · **Scope:** `git diff dev...HEAD` on `feature/df3-6b-resident-memory-cgroup`
**Focus:** correctness and security of the cgroup mechanism in `src/fleet/resident.ts` and its
engine-side classification in `src/phase-engine/steering.ts`.

6 findings. All resolved in-round.

| # | Finding | Resolution |
|---|---------|------------|
| 1 | **INV-MEM-1 is not structural.** pi is `exec`'d into the leaf as the SAME uid that created it, so the leaf's `memory.max` is a file pi's uid owns. A pi with any command-exec or arbitrary-write primitive could raise its own bound, and the engine would not notice (it reads the accounting only after the call). The story claimed the bound was "un-bypassable from inside the box … structurally". What actually keeps it out of reach is `--no-tools`. | Story's INV-MEM-1 **amended** to state the true guarantee, and `--no-tools` recorded as load-bearing security configuration (comment at the pi spawn argv). The structural part that survives — no sampler, no engine timer, bound unreachable from prompt/env/roster/argv — is stated as what F12 asked for. |
| 2 | **A GLOBAL OOM kill was misclassified as this bound firing.** `memory.events`' `oom_kill` counts processes killed by ANY OOM killer, including the system-wide one. A `dispatch_task` worker driving the box into global OOM, with the kernel picking pi, produced `status:"stopped"`, `exitStatus:"overflow"` and a `watchdog_kill` row whose own `detail` contradicted itself (peak far below bound) — and those rows are D4's tier-2 demotion evidence. | `readLeaf` now keys the verdict on `oom_group_kill` (the group kills `memory.oom.group=1` produces) or `oom` (this cgroup hit ITS OWN limit). `oom_kill` is telemetry only. **SUPERSEDED by round 7:** this disjunction was itself wrong — `oom_group_kill` is not own-limit-only, and `oom_kill` is a verdict input again. The shipped rule is the CONJUNCTION `oom > 0 && (oom_kill > 0 \|\| oom_group_kill > 0) && memory.peak >= bound - 2 MiB` (story ruling 8). Four new tests pin the discrimination, including the global-OOM case that previously read as a kill. |
| 3 | **`removeLeaf` had no EBUSY handling.** Two failures: (a) the OOM path flakes — `oom.group` SIGKILLs the subtree but a task leaves `cgroup.procs` only when REAPED, and pi's descendants are reaped asynchronously by PID 1, so AC1's "the cgroup is removed" check would be intermittently red; (b) the timeout/`stop()` paths leak permanently — the engine's SIGKILL reaches pi ONLY, so any descendant survives in the leaf forever. R3's group-kill doctrine is discharged by the kernel on the OOM path but NOT on engine-signalled ones. | `removeLeaf` writes `cgroup.kill` (v2, 5.14+) before `rmdir` and retries bounded (4 × 25 ms) on EBUSY. |
| 4 | **Exit 97 from pi itself is indistinguishable from a placement refusal** and nothing said so. `sh` `exec`s pi, so the wrapper is gone by the time pi picks an exit code. | Accepted (the direction is fail-closed) and **documented** on `_PLACEMENT_REFUSED_EXIT`, including the consequence for AC1's live Leg A: the synthetic allocator MUST NOT exit 97. |
| 5 | **`\|\| exit 97` only caught OPEN-time failures reliably.** `cgroup.procs` also rejects at WRITE time (EBUSY when the target is not a leaf, EOPNOTSUPP, EINVAL), and whether the guard fires then depends on the shell: busybox `ash` returns 1, `dash` exits 2. A generic non-zero exit is not the `unenforceable` classification — the engine latches "degraded", the exact misclassification AC4 exists to prevent. | The wrapper now **verifies membership**: it reads `cgroup.procs` back and refuses unless its own pid is in it, using POSIX shell built-ins only (no `grep`/`awk` dependency on what the image stages). Test rewritten accordingly, with a positive control and an unconditional-`;` negative control. |
| 6 | Three minor, concrete: (a) the "Bun.spawn THROWS on a missing binary — that throw IS the AC3 unreachable path" comment is false on the bounded path (`sh` exists; a missing `QDS_PI_BIN` becomes exit 127); (b) a `createLeaf` throwing after its `mkdir` leaks the arming probe leaf; (c) the `resident_cgroup` line goes through `warn` (prefixed, tail-truncated) and carried neither `bound` nor `allowed`, against the Observability Contract. | (a) comment corrected with the DF3.6b narrowing; (b) probe cleanup moved into its own `finally`; (c) line gains `bound:"rss"` and `allowed`, and the Observability Contract is **amended** to state that the cgroup half rides the fleet chokepoint keyed on `runId`+`seq` — `requestId`/`phase` are engine-side facts that never cross into fleet, so a line emitted there structurally cannot carry them. |
