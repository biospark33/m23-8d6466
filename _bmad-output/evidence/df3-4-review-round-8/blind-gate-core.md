# Blind review — chunk 1: src/fleet/approval-gate.ts

- **HIGH** `withTeardownClaim` has no deadline at all — `src/fleet/approval-gate.ts:1116` — trigger: the approval lock gives up at 5 s with an operator remedy, but this loop spins `for(;;)` on `Bun.sleep(10ms)` forever while the claim holder is *alive*. A teardown seam that hangs (provider API stall) wedges `pauseRun` and the whole reverify indefinitely; worse, a claim left by a crashed process whose pid the OS recycled onto a live process — including a previous crashed run that reused *this* process's own pid — can never satisfy `isLockHolderDead`, there is no age door, and per the header "there is no operator verb for it": permanent silent hang, not even a timeout error.

- **HIGH** teardown claim reclaim treats an unwritten file as a dead holder — `src/fleet/approval-gate.ts:1118` — trigger: `writeFileSync(claimPath, own, {flag:"wx"})` is open-then-write, not atomic. Holder A's `openSync(wx)` succeeds; A is descheduled before its write lands. Waiter B gets EEXIST, `readFileSync` returns `""`, `lockHolderPid("")` is `undefined` → "unreadable holder ... fair game" → `rmSync` + B's own `wx` create wins. A and B now both believe they hold the claim and run `deps.teardown` concurrently — the exact `pullArtifacts` interleave on fixed shared host paths this fence exists to prevent. The approval lock is immune to this window only because its reclaim demands `age > LOCK_STALE_MS` first; the claim path has no such precondition, so the degradation is not just the "pre-claim status quo" the header waves off, it is reachable on ordinary contention.

- **MEDIUM** throw between lock create and content write strands an unrecoverable lock — `src/fleet/approval-gate.ts:186` — trigger: `openSync(wx)` succeeds, then `writeFileSync(fd, ownContent)` or `fstatSync` throws (ENOSPC, EIO). The non-EEXIST rethrow at `src/fleet/approval-gate.ts:193` propagates *before* the `try { body() } finally { release }` is ever entered, so the release never runs and the lock file stays on disk empty or partial. `lockHolderPid` on empty content is `undefined`, so the staleness door (`pid !== undefined && isLockHolderDead(pid)`) can never reclaim it: every future approval verb for the run dies at the 5 s ceiling until `fleet unlock --force`, and the timeout message misattributes the cause to "holder's pid may have been recycled" when no pid exists.

- **MEDIUM** `submitDecision` never checks the bundle — `src/fleet/approval-gate.ts:1242` — trigger: the module's own invariant (`assertBundlePresent`, `src/fleet/approval-gate.ts:705`) is that "a report naming a run with no bundle is bound to nothing", enforced on pause, rebind *and* resume. The decision write path — the act that authorizes the PR — enforces nothing: bundle deleted on day 2 of a 24 h window, operator runs `fleet approve` on day 3, `approved` is recorded against a report whose bundle is gone, and per the module's own comment "nothing later re-checks".

- **MEDIUM** success-shaped return when the promotion did not happen — `src/fleet/approval-gate.ts:1072` — trigger: the promote re-read finds `state !== "pausing"` (extension absent/hand-swept gives `current === ""`); the function skips the write and still returns `{outcome: "requested"}` at `src/fleet/approval-gate.ts:1080`. The caller (reverify) is told the gate holds when no approval binding exists on disk; the run then burns the full `awaitDecision` window to a `null` non-answer instead of failing fast, and the only trace is `state: "unknown"` on one log line.

- **MEDIUM** `awaitDecision` clamps `pollMs` but not `waitMs` — `src/fleet/approval-gate.ts:1349` — trigger: `opts.waitMs = NaN` makes `deadline` NaN, `Date.now() >= NaN` is permanently false, so the function polls the filesystem forever and never returns `null` (`Infinity` behaves the same). The same function's own comment declares the "CLAMPED, never refused" posture for `pollMs`; `waitMs` — the bound that actually terminates the loop — gets neither clamp nor validation.

- **LOW** dead `requestId` re-stamp on the fresh-pause write — `src/fleet/approval-gate.ts:990` — trigger: the spread writes `requestId: rec.requestId` into the approval extension, but the surrounding comments (and the restamp/rebind/promote paths) establish that `set()` merges field-by-field, so the run-level key is either already retained (making this a no-op) or, if the store validates extension keys, a schema hazard on the mainline first-pause path.
